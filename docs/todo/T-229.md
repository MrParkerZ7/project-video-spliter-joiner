## Concept

Found at T-195's acceptance review (2026-10-05), on synthetic fixtures with the bundled ffmpeg 7.1. It was filed as a
side effect of T-195's first design, which remembered a failed flagged grab per input; that memory did not ship
(T-195 landed waveform-only), so only the pre-existing part below holds today.

How the hover time reaches the duration:

- `PlayerView.xaml.cs` maps the cursor to `fraction = Math.Clamp(x / width, 0, 1)` and
  `time = fraction * DurationSeconds` (and `BulkRowScrubView.xaml.cs` does the same).
- So the right edge of the scrub bar asks for `time == duration`.
- `FfmpegThumbnailService` floors that to the bucket, `floor(duration)`.

Why the grab fails:

- For a 12.000000 s MP4 (testsrc at 30 fps, last frame at 11.967 s), `-ss 12` fails: non-zero exit, no file.
- The same happens on any file whose last video frame comes before `floor(duration)`, for example when the audio
  outlasts the video by more than the fractional second.

What happens **today**: the popup shows no picture at the very right edge. Nothing else is lost, and a failure is not
remembered (the grab has no failure memory).

**What it would break later:** T-226 gates the grab's stream-info skip on the probed start time and may add a per-input
failure memory. A right-edge hover fails both the flagged run and the unflagged retry on a healthy file, so a memory
that records "both runs failed" would turn the skip off for that file until `Clear`. This ticket keeps that edge from
ever reaching the service, or T-226's memory must record only a failure that the unflagged retry fixed.

## Design

Recommended (star): clamp the hover request to the last frame. `ThumbnailPreviewViewModel.UpdateHover` (and
`BulkRowScrubView`'s hover) requests `min(time, duration - one frame)`, or the service clamps the bucket below a known
duration. The right edge then shows the last frame, and no failure is recorded for a healthy file.

Alternative: in T-226's memory, remember an input only when the unflagged retry succeeds after the flagged run failed.
That pattern is the real sign of a mislabelled file. When both runs fail, record nothing.

## Acceptance criteria

- [ ] **Repro first:** a test hovers at `time == duration` on a generated whole-second MP4 and asserts that a picture
      comes back. Today it returns null at the edge. It fails.
- [ ] After the fix the right edge shows a picture (the last frame), and a mid-file hover is unchanged.
- [ ] If T-226 has landed with a failure memory: a right-edge hover on a healthy MP4 leaves the input flagged, and a
      real mislabelled file (MPEG-TS content named `.mp4`) is still remembered after its first failed flagged grab.
- [ ] SPEC-005 is updated: a new invariant for the hover clamp, and T-226's memory rule if it changed.
