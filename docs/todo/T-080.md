## Concept
With T-079's crash log in place, reproduce split→Clear→load-new, read the captured exception, and fix the actual fault so the second load continues instead of closing the app.

## Design / investigation
1. **Reproduce** (`app-run`, real video): load → set a cut → run split to completion → Clear → drag/load a NEW video → observe the crash; read `%LOCALAPPDATA%/VideoSplitJoiner/logs/crash-*.log` (now captured by T-079) for the exception type + stack.
2. **Diagnose against the suspects** (confirm from the log, don't guess):
   - **(a) FFME Open-after-Close lifecycle** — `FfmeMediaPlayer.Unload()` → `_element.Close()`, then `Open()` → `_element.Open(uri)`. If the log shows an FFME/native fault or an exception in `Open`, the fix is lifecycle-side: sequence Close→Open safely (await close/ready), guard re-open, or reset the element. (Native AccessViolation → the fix is here, not the handler.)
   - **(b) Stale background task from video #1** — a keyframe continuation (`ResolvePendingMarkerAsync`) or thumbnail grab resolving AFTER Clear touching torn-down state (`_keyframeIndexCts` null, player unloaded). Repair the staleness guard / null-check so a post-Clear resolve is dropped.
   - **(c) Thumbnail service (G-030)** — a grab or the cache Clear/`SetInput` racing the new load. Guard against use-after-clear.
   - **(d) Operation-completion state** — something from the finished split (ResultSummary/state) mishandled on the next load.
3. **Fix at the true layer** the log identifies; add a regression test that reproduces the fault in VM terms (e.g. Clear-then-Load drops the stale continuation; re-Open after Unload is safe with the fake player).

## Acceptance criteria + Case-Coverage Matrix
- [ ] split → Clear → load a new video → the app LOADS the new video and continues (no self-close). Verified live (app-run) with a real file.
- [ ] The captured crash's exception is identified + the fix targets its true cause (cited from the log).
- [ ] Repeat cycles (split→clear→load ×3) stay stable; also load-new WITHOUT clear (drag over an existing file) stays stable.
- [ ] Regression test added; build 0-warning; suite green.
- Matrix — Required-Success: second load after clear works. Boundary: multiple split→clear→load cycles; load-new without clear; clear while a grab/keyframe-index is mid-flight; different codec on the 2nd file. Required-Fail: none.

## Dependencies
T-079 (the crash log is the diagnostic input).

## Risks
May be a native FFME fault (lifecycle fix, not catchable) — the log + repro tell which. Don't "fix" by only swallowing in the global handler (T-079) — remove the actual fault.

## Out of scope
Broader FFME lifecycle refactor beyond making re-open safe; telemetry.
