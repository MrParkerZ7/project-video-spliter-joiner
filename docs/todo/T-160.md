## Reported
> improve buttom vertical on bulk cut I think areas on button is too tight and overflow

## Concept

The Bulk Cut footer has to carry the run action, the destructive post-run action, and every output
option — and it currently does all of it on **one horizontal line**. Each ticket that added an option
added it to the same row. It now holds eight interactive controls and three conditional notes, and it
reads as cramped even when it technically fits.

The value is legibility at the moment of highest consequence: the footer is where you arm
*Replace originals*, arm *Auto-delete + empty bin*, and press *Run*. Those are the irreversible
gestures in this app, and they are currently the ones packed most tightly.

## Design

**Current structure** (`BulkCutView.xaml:983-993`) — one `Grid` row, three columns:

| col | width | content |
|---|---|---|
| 0 | `Auto` | `DeleteOriginalsButton` (danger, T-146 put it here deliberately, far from Run) |
| 1 | `*` | `FooterOptions` **WrapPanel** — `OutputNote` · Overwrite · Exact cut · `PrecisionNote` · `DestructiveOutputNote` · Auto-delete originals · ⚠ and empty bin · ⚠ Replace originals |
| 2 | `Auto` | `RunScopeSummary` (MaxWidth 340, wraps) + Run/Cancel |

The `WrapPanel` is T-156's fix for *clipping* and it works — nothing disappears any more. But wrapping
inside a column that is also squeezed between two `Auto` columns means the options reflow into two or
three ragged lines whose height pushes the whole footer down, while `RunScopeSummary` wraps in its own
column at the same time. Both are correct in isolation and cramped together.

**Chosen approach — give the options their own row.** Split the single-row footer `Grid` into two rows:

```
row 0   [ options — full width, WrapPanel, free to wrap sanely ]
row 1   [ Delete originals ]            (spacer *)          [ RunScope + Run/Cancel ]
```

Options stop competing with Run for horizontal space, so they wrap at a natural width instead of into a
narrow column; the action row keeps T-146's structural separation (danger at one end, Run at the other,
each in its own `Auto` column) unchanged. Vertical cost is one row that was effectively being consumed
by wrapping anyway.

**Grouping within the options row.** Eight controls in a flat wrap is a list, not a layout. Group them
by consequence, in reading order, with a separator between groups:

1. **Output** — `OutputNote` · Overwrite existing output
2. **Precision** — Exact cut · `PrecisionNote`
3. **Destructive** — ⚠ Replace originals · Auto-delete originals · ⚠ and empty bin · `DestructiveOutputNote`

The destructive group ends the row so the red vocabulary sits together instead of being interleaved with
neutral checkboxes — which is what makes the current row hard to scan.

### Rejected
- **A collapsible "Options" disclosure.** Hides armed destructive state behind a chevron; T-156 I137
  exists precisely so the armed state is visible before Run is pressed. Rejected outright.
- **Move options into a settings dialog.** Same objection, plus these are per-run choices.
- **Just shrink margins / font.** Treats the symptom; eight controls in one line stays eight controls.

## Detail
- Footer `Grid` (`BulkCutView.xaml:983`) gains `RowDefinitions` `Auto` / `Auto`; existing children move
  to row 1 and keep their column assignments.
- `FooterOptions` moves to row 0, `Grid.ColumnSpan="3"`, staying a `WrapPanel`.
- Group separators: a 1px `Rectangle` in `BorderBrush`, or a margin step — whichever the UI Designer
  lens prefers; do not invent a new token.
- Vertical/horizontal layout modes both apply (`OrientedSplitPanel`); the footer is outside the split
  panel, so it is mode-independent — verify anyway at 1280px and at the narrow end.

## Interfaces / contracts
View-only. No view-model, command, binding or settings change. Every existing binding
(`OutputNote`, `PrecisionNote`, `DestructiveOutputNote`, `RunScopeSummary`, `CanDeleteOriginals`,
`AutoDeleteOriginals`, `CanAutoEmptyRecycleBin`, `Overwrite`, `CollisionIsInert`, `ExactCut`) keeps its
current source and semantics.

## Acceptance criteria
- [x] Options occupy their own full-width row; Run and Delete-originals share a second row with T-146's
      opposite-ends separation intact.
- [x] At **1280px** every control is visible and reachable, and the footer does not clip — asserted by a
      layout test **measured against the window**, not against the panel (an overflowing panel reports
      its own oversized width, which is how the first version of the T-156 test passed against the bug).
- [x] The three destructive controls read as one group, after the neutral ones.
- [x] `DestructiveOutputNote` is still visible without scrolling whenever it is non-null (SPEC-011 I137).
- [x] No behaviour change: same commands, same gating, same tooltips. The existing Bulk Cut suite passes
      untouched.
- [x] Verified on screen at 1280px and at the narrowest usable width — a green suite is not evidence a
      layout reads well (CLAUDE.md § Rebuild before reporting a UI fix done).

## Edge cases
- All three notes non-null at once (longest possible options row).
- `CanDeleteOriginals` false → button collapsed → action row has an empty column 0; Run must not drift.
- Very narrow window: options wrap to three lines; footer grows rather than clipping.
- Both destructive options armed → red note + two red checkboxes; must not look like an error state.

## Risks
- **Fourth instance of the clipping class.** T-136 (profile bar), T-141 (header), T-156 (this footer) all
  shipped a horizontal container that silently clipped. Any container introduced here must wrap or
  scroll, never clip — and must be pinned by the window-relative layout test above.
- Adding a row changes footer height, which eats list space in vertical layout mode. Measure before/after.

## Out of scope
The profile bar ([[T-161]]) and the row-level controls. This ticket is the footer only.

## Outcome — 2026-09-05

The footer is two rows. Options own a full-width row above `[Delete originals] … [Run]`, and the three
irreversible controls sit together at the end of the options row behind a separator, with
`DestructiveOutputNote` closing the group instead of sitting between *Exact cut* and *Auto-delete*.
View-only: not one binding, command, gate or tooltip changed.

### Measured, not eyeballed
Screen-scraping the desktop turned out to be the wrong instrument — the first capture was clipped by the
window sitting half off-screen and the second grabbed a different application entirely. Rendering the
real view in-process and printing its geometry answered the question exactly:

```
1280x800  FooterOptions          y=458.2  h=18.0  w=1256.0     (one line, full width)
1280x800  RunBatchButton         y=486.2                        (below the options)
 900x700  FooterOptions          y=439.2  h=36.0  w= 876.0     (wraps to two lines)
 900x700  RunBatchButton         y=485.2                        (still below)
```

At 1280 the options now fit on **one** line because they finally have the full width; squeezed into the
old `*` column they wrapped even there. At 900 they wrap to two and Run still clears them.

### Two tests, one of them deleted again
`TheFooterOptionsSitOnTheirOwnRow_NotOnRunsLine` asserts the structural claim at all five window widths;
putting the options back on Run's line fails it.

The second test I wrote — that Delete-originals stays opposite Run — was **removed before commit**:
`TheDestructiveButtonSitsAtTheOppositeEndFromRun_AndRevealingItDoesNotMoveRun` already existed from
T-146 and is strictly stronger (it also asserts Run does not shift when the button appears, and that
Delete stays left of the midpoint). Mine was a subset wearing a new name. Re-ran the placement mutation
against the pre-existing test to prove nothing was lost: it still dies. A duplicate test is not free —
it reads as coverage while adding none.

### What this ticket accidentally uncovered

the footer — it was [[T-159]]'s own fix from earlier the same day, and it is closed as [[T-165]]. The
suite now runs **954 App + 461 Core = 1415 green in 20s**, discovered == ran == passed.
