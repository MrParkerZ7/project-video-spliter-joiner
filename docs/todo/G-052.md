## Why

User: *"on Split feature also add auto remove original and auto clear bin same as bulk cut feature"*

The need is the one [[T-156]] already established on Bulk Cut and is, if anything, sharper here: a split
**multiplies** disk usage. Cutting a 4 GB recording into six parts leaves 8 GB where 4 GB was, and the
source is exactly the file you no longer want. Today Bulk Cut can reclaim that space and Split cannot —
the same user, the same session, two screens, one of which cleans up after itself.

## What is actually missing

Checked before planning: **Split has none of this — not the auto layer, not the manual one.**
`IOriginalDisposer`, `DeleteOriginals`, `AutoDeleteOriginals` and `AutoEmptyRecycleBin` exist only in
`BulkCutViewModel`, `AppSettings`, `BulkCutView` and `RecycleBinOriginalDisposer`.

So *"same as bulk cut"* cannot be one checkbox. Bulk Cut's auto-delete is deliberately built **on top of**
its manual sweep — T-156's own acceptance reads *"routed through `DeleteOriginals()` unchanged — one
deletion path, so there is only one place for it to go wrong."* Split has no such path to route through.
Building the auto layer alone would mean a second, hidden deletion implementation with no visible
counterpart, which is precisely the shape that ticket refused. Hence the manual sweep first (**T-162**),
then the auto layer on it (**T-163**).

## The part that is genuinely different from Bulk Cut

Bulk Cut deletes **one original per row**, each with its own trimmed output to check. Split deletes
**one original that produced N parts**, so eligibility is a different question:

- Bulk: *is this row's single output on disk and non-empty?*
- Split: *are **all** selected parts on disk and non-empty?* Deleting the source when part 4 of 6 is
  missing loses footage that exists nowhere else. This is the invariant the epic hangs on.

Also unlike Bulk, Split can produce parts **into the source's own folder** (the output dir defaults
there, T-061) and the preview player may hold a handle on the source — the same lock T-145/T-155 dealt
with, on the file being deleted rather than a row's.

## Out of scope
Replace-originals mode on Split (Bulk's `OutputMode` axis, G-041) — a different feature that happens to
touch the same file. Deleting *parts*. Any change to Bulk Cut's behaviour beyond extracting what both
screens will share.

## Outcome — 2026-09-06

All three success criteria met.

- *After a successful split, the Split screen can send the source to the Recycle Bin, and refuses when
  any produced part is missing or the run failed* — [[T-162]]. The all-parts rule is enforced fresh on
  every read and again at deletion time, and eight mutations against its guards all die.
- *A checkbox does it automatically, and a second empties the bin, matching Bulk Cut's behaviour and its
  safety gates exactly* — [[T-163]]. All four of T-156's arming gates carried over, each mutation-checked,
  with the settings keys deliberately separate so arming one screen never arms the other.
- *Split and Bulk Cut share ONE deletion path and one confirmation vocabulary* — partly, and the
  partly is deliberate. They share the Recycle-Bin mechanism (ADR-0022), the `FileFacts` predicates and
  the `DangerButton` style. They do **not** share the eligibility rule, because the questions genuinely
  differ — one row against one output, versus one source against N parts — and **ADR-0024** records why
  a shared abstraction over the two would read worse than either.

The epic's own framing held up: *"same as bulk cut" cannot be one checkbox*, and building the auto layer
on top of a visible manual sweep rather than beside a hidden one is what let T-163 skip its per-run
prompt safely — the safety decisions live in `DeletableSource`, not in the dialog.

**The most valuable thing this epic produced was not the feature.** Writing T-164's ARCHITECTURE
paragraph required opening `MainViewModel`, which is how it emerged that the composition root never
passed Split a disposer: fully built, fully tested, 14 tests green, and **inert in the shipped app**.
Documentation written honestly turned out to be a test the suite could not perform.
