## Concept
Let the user drag to resize the video preview area in the Split screen — bigger to watch/scrub, smaller to see more markers. Remove the fixed 320px cap; the FFME video scales to fit.

## Design
- In `src/App/Views/SplitView.xaml`: restructure the top rows so the **player pane is a user-resizable row** with a `GridSplitter` beneath it, separating it from the content below (timeline + marker list + output + run).
  - Player row: `Height="*"`-ish resizable with a `MinHeight` (e.g. 140) and a reasonable default (e.g. 300); remove `MaxHeight="320"` from the `PlayerView`.
  - Add a `GridSplitter` (Height ~6, `HorizontalAlignment=Stretch`, `ResizeDirection=Rows`, a visible grip) between the player row and the rest.
  - The lower content should stay usable at any player size — keep the marker list in a region that scrolls / star-sizes so it doesn't get clipped when the player is enlarged.
- `PlayerView` internal layout unchanged; `<ffme:MediaElement Stretch="Uniform">` already scales without distortion. The T-024 downscaled-preview is independent (caps decode/render resolution, not display size) — leave it alone.

## Detail
- Pick a layout where the video pane and the lower content share the vertical space with the splitter controlling the split (two star rows separated by the splitter, each with a MinHeight), OR player row Auto+draggable — choose whichever cleanly lets the player grow AND the lower content stay reachable. Keep the Split tab's overall structure otherwise intact.
- Ensure resizing while a video is loaded keeps it rendering (no black-out) — verify live (app-run).
- No ViewModel change — this is pure XAML layout. If any tiny code-behind is needed for the splitter, keep logic-free.

## Interfaces / contracts
- No API/VM change; `SplitViewModel`/`PlayerViewModel` untouched. Pure view layout.

## Acceptance criteria + Case-Coverage Matrix
- [ ] The player pane resizes by dragging the splitter; the video grows/shrinks with it (Uniform, no distortion).
- [ ] The 320px cap is gone; the player can be made noticeably larger.
- [ ] At min and max player sizes, the marker list + timeline + Run controls remain visible/reachable (scroll if needed).
- [ ] Build 0-warning; all existing tests stay green (no VM/logic change → no test change expected).
- Matrix (UI) — Required-Success: drag larger → video bigger; drag smaller → more markers visible. Boundary: player at MinHeight (controls still reachable); player very large (lower content scrolls, not clipped). Required-Fail: n/a (layout-only).

## Dependencies
None.

## Risks
Clipping the lower content when the player enlarges → MinHeights + a scrollable lower region. GridSplitter over the FFME native surface → live-verify rendering persists while resizing.

## Out of scope
Persisting size across sessions, full-screen/pop-out video, resizing the Join screen (G-006 § Out of scope). Docs → folded into the pending T-026 finalization pass.
