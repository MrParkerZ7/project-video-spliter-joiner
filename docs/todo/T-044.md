## Concept
Show which STAGE the operation is on, updated in sync with the real work — so a running split reads "Splitting (segment 2 of 4)" not just a bar.

## Design
- **Stage signal from the engines:** `SplitEngine.SplitAsync` / `JoinEngine.JoinAsync` report stage transitions via a new callback (e.g. `IProgress<OperationStatus>` where `OperationStatus { Stage, Detail, Fraction }`, or a `IProgress<string>` status alongside the existing `IProgress<double>`). Stages:
  - Split: `Preparing` (probe + snap cut points) → `Splitting` (running ffmpeg; when the segment muxer is producing outputs, include "segment N of M" from the cut-plan segment count) → `Finalizing` (temp→move / verify) → `Done`.
  - Join: `Checking compatibility` → `Joining` → `Finalizing` → `Done`.
- **`OperationViewModel`:** add `StatusText` (+ maybe a `Stage` enum) set from the stage callback; updates when the actual stage changes. Reset on start/clear.
- **UI (`SplitView`/`JoinView`):** show the `StatusText` near the progress bar (e.g. above/beside it), visible while running.
- Segment N/M: the split knows the number of output segments from the cut plan; the runner can map ffmpeg's per-output progress (or segment-open log lines) to the current segment index — best-effort; if intra-segment mapping is hard, at least show "Splitting…" with the total segment count.

## Detail
- Drive stages from REAL callbacks (engine emits on transition), not a timer — "synced to each process action" is the requirement.
- Keep the existing `IProgress<double>` fraction working (T-042/G-012); the stage is additional. If building with G-012, unify into one status+progress surface.
- Load can optionally reuse this (probing / indexing…) but the ask is about the split/join process — focus there.

## Interfaces / contracts
- New `OperationStatus`/stage callback on the engines (additive; existing `IProgress<double>` overload preserved or extended with a default). `OperationViewModel.StatusText`/`Stage`. VM fake-testable.

## Acceptance criteria + Case-Coverage Matrix
- [ ] Running a split drives `StatusText` through Preparing → Splitting (segment N/M) → Finalizing → Done, from real engine callbacks (VM test with a fake engine that reports staged status).
- [ ] Join shows its stages similarly.
- [ ] The stage text is visible while running and clears/resets on completion.
- [ ] Existing progress fraction still works; build 0-warning; prior tests green.
- Matrix — Required-Success: split → correct ordered stages + segment count. Boundary: single-segment split; a join refusal (stage stops at Checking + error). Required-Fail: op fails mid-stage → status reflects it + clears to the error.

## Dependencies
None (extends OperationViewModel + engine progress). Best built with G-012/T-042.

## Risks
Segment-index mapping from ffmpeg output is best-effort → fall back to stage + total count. Don't fabricate a stage that didn't happen.
