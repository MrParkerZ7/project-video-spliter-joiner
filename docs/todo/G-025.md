## Why / vision
Progress today is overall-only and lives inside the window. The user wants (1) the **Windows taskbar button** to show progress + ETA like a download does, so they can watch it while the app is in the background, and (2) **per-part progress** during a split, so a 3-part split shows "part 2 of 3" advancing, not just one overall bar.

## Grounding (2026-07-18)
- **No `TaskbarItemInfo`** in the app — new integration. WPF supports it natively: `Window.TaskbarItemInfo` with `ProgressState` (None/Normal/Indeterminate/Error/Paused) + `ProgressValue` (0..1).
- `OperationViewModel` exposes `Progress` (0..1), `IsIndeterminate`, `StatusText`, `EtaText`; runs hand an `IProgress<double>` (overall) + `IProgress<OperationStatus>` (staged text). Split reports overall 0..1 only.
- **Split paths** (`SplitEngine`): full contiguous set → `ExtractAllViaSegmentMuxer` (ONE ffmpeg pass, fast — the core value); strict subset → `ExtractSelectedPerSegment` (one ffmpeg run per selected part — per-part index is already known here). Each part's keyframe-snapped `[start,end)` is known from the cut plan.
- **Taskbar text limit:** the taskbar button renders only a progress FILL — no text. ETA must surface via the window `Title` (shown on taskbar hover / alt-tab), not "on" the button literally.

## Decisions
- **D1 · Taskbar progress** — add `Window.TaskbarItemInfo` in `MainWindow.xaml`; bind `ProgressValue` to `Operation.Progress`, `ProgressState` to a new `OperationViewModel` state (None when idle, Indeterminate while `IsIndeterminate`, Normal while running with a real fraction, Error on failed/cancelled). Small VM property or converter — prefer a VM `TaskbarProgressState` computed property so it's unit-testable.
- **D2 · ETA in the window title** — while running, set the window `Title` to include overall % + ETA (e.g. "Splitting 45% · ~1m 20s — Video Split / Join"); revert to the plain title when idle. This is how the ETA becomes visible from the taskbar. The in-app `EtaText` stays unchanged.
- **D3 · Per-part progress channel** — extend the progress reporting to carry per-part info: current 1-based part index, total parts, and that part's local fraction. Options: enrich `OperationStatus` (add optional `PartIndex`/`PartCount`/`PartProgress`) OR a new `IProgress<PartProgress>`. Prefer enriching `OperationStatus` (already threaded through) or a dedicated typed channel — pick the lower-churn option.
  - **Subset path** (`ExtractSelectedPerSegment`): report part index directly from the loop + per-run fraction. Easy.
  - **Fast muxer path** (`ExtractAllViaSegmentMuxer`): DERIVE the current part from ffmpeg's reported `time=` against the known part boundaries (which part's `[start,end)` contains the current time → part K; local fraction = position within that part). **Do NOT switch this path to per-segment** — keep the single pass; only derive richer reporting from the time it already reports.
- **D4 · Per-part UI** — surface per-part in the "Parts to export" list: each part row shows a live progress bar / "writing…" / "done" state as the split advances (row K active while part K writes), plus optionally a status line "Splitting part K of N". Keep the overall bar + ETA too.

## Risks
- **Muxer-path part derivation** (D3) is the hard part — map ffmpeg `time=` → current part via the plan boundaries; verify off-by-one at part edges and that a fast split still reports sanely. Unit-test the mapping (pure function: time + boundaries → (partIndex, partFraction)).
- Taskbar `ProgressState` on failure/cancel — map to Error; ensure it clears to None when the run ends/resets (no stuck red bar).
- Window-title mutation must not fight the WindowChrome caption title binding — set it on the Window, revert cleanly on idle.
- Don't regress the fast single-pass path or the existing overall progress/ETA/staged-status.

## Out of scope
Taskbar thumbnail buttons (pause/cancel on the taskbar preview); per-part ETA (overall ETA is enough); join per-clip progress could be a follow-up if wanted (this goal's per-part focus is the split).
