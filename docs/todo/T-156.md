## Reported
> I want check box options to auto remove original files after bulk cut success, also check box for auto
> clear bin. because sometime space remaining too low and require to be clear

The reason matters: **the disk fills up mid-session.** Today reclaiming space is two manual steps after
every batch — press Delete originals, then go and empty the Recycle Bin yourself. For someone trimming a
season of episodes that is the difference between a batch completing and one failing on a full disk.

## What is being asked for

| checkbox | effect |
|---|---|
| **Delete originals when the batch succeeds** | run the existing delete-originals sweep automatically, instead of waiting for the button |
| **Empty the Recycle Bin afterwards** | actually free the space, since binning alone does not |

## The design hazard, stated plainly

Those two together are **permanent deletion with no undo**. Everything that makes delete-originals safe
to offer today — it goes to the Recycle Bin, you can restore it, the sweep is per-row isolated, it
re-checks eligibility at deletion time ([[T-150]]) — rests on the file still existing afterwards. Ticking
both removes the entire safety net, silently, on every future batch.

That is not a reason to refuse the request: the user's need is real, and low disk space is exactly when
"it went to the bin" is useless. It is a reason to make the *combination* hard to arrive at by accident
and impossible to be surprised by.

Proposed treatment:

1. **The two are independent checkboxes, and the second is disabled unless the first is on.** Emptying
   the bin is meaningless here otherwise.
2. **Ticking the second one asks once**, in plain words — *"Originals will be deleted permanently and
   cannot be restored. The Recycle Bin is emptied, which also removes files deleted by other apps."*
   Defaulting to No, in the pattern the existing counted confirmation already uses.
3. **The second checkbox is styled as destructive** (the screen's existing danger vocabulary, as the
   Delete-originals button now is), and the footer note says permanent while it is on — so the state is
   visible before Run is pressed, not discovered afterwards.
4. **Both default OFF and persist** in `AppSettings` like the other Bulk Cut preferences.

### Emptying the bin is broader than this app
`SHEmptyRecycleBin` empties the **whole** bin for the drive — including files this app never touched, put
there by the user or by other programs. That has to be said in the confirmation; a user reaching for
"free up space" is not necessarily expecting to lose an unrelated document they binned yesterday. Worth
investigating whether the freed space can be limited to our own files (delete permanently instead of
bin-then-empty, which is simpler AND narrower) — that may be the better shape for the whole feature.

## Design
1. Two `AppSettings` flags, both default false, persisted.
2. After a batch **completes with no failed rows**, if flag 1 is on, run the existing
   `DeleteOriginals()` path — the same eligibility re-checks, the same per-row isolation, the same
   summary. No second code path for deletion.
3. The counted confirmation is **skipped when auto-delete is on** (the checkbox IS the consent, given in
   advance) — but the result summary still reports exactly what was binned and what was refused.
4. If flag 2 is on, empty the bin afterwards — or, if the investigation above favours it, delete
   permanently in the first place and drop flag 2 entirely.
5. Land [[T-155]] first: auto-deleting is only tolerable once it cannot pop a Windows dialog on every
   batch. Automatic *and* interrupting is worse than manual.

## Acceptance criteria
- [x] `AutoDeleteOriginals` + `AutoEmptyRecycleBin`, both default OFF, persisted in `AppSettings`.
- [x] Gated on `BatchState == Completed` and routed through `DeleteOriginals()` unchanged - one
      deletion path, so there is only one place for it to go wrong.
- [x] `ConfirmPermanentDeletion` defaults to **refusing**, so an unwired host cannot arm it; asked
      once, not per batch; and turning auto-delete back off disarms the bin box.
- [x] `DestructiveOutputNote` in danger colour. It says "Recycle Bin" (not "permanent") when only
      auto-delete is on, because binning IS recoverable and overstating it teaches people to ignore it.
- [x] `APartlyFailedBatchNeverAutoDeletes` - see the note below on how that test was vacuous at first.
- [x] Not scoped - `SHEmptyRecycleBin` empties the whole bin - so the confirmation says so explicitly:
      "including files deleted by other programs".
- [x] Three mutations, all dead: the clean-batch guard, the confirmation gate, the disarm-on-untick.

## Out of scope
A disk-space monitor or an automatic low-space warning. Worth its own ticket if the reporter wants it —
"tell me before the batch fails" is a different feature from "clean up after it succeeds".

## Outcome - 2026-09-02

Built behind [[T-155]], as planned: automatic *and* interrupting would have been worse than manual.

### The safety, not the feature, is what the tests are about
Auto-delete plus auto-empty is permanent deletion with no undo, so the interesting cases are all the ones
where it must NOT fire. Four gates, each asserted: a partly-failed batch, an unwired confirmation, the bin
box armed on its own, and auto-delete being switched back off.

That last one is subtler than it looks. Without disarming the bin box, someone could tick both, untick
auto-delete, then re-tick it later - silently re-arming permanent deletion on consent given for a
configuration that no longer existed.

### A vacuous test, caught by mutation
`APartlyFailedBatchNeverAutoDeletes` passed from the start - and **so did the mutation that removed the
clean-batch guard entirely.** The VM in that test was built with no `IOriginalDisposer`, so
`DeleteOriginals()` returned immediately and the sweep was inert either way. It asserted that a file still
existed which nothing was ever going to delete.

It now injects a real disposer and asserts on it. Same lesson this session keeps re-learning: a passing
test proves nothing until something proves the test can fail.

### And a third instance of the clipping-StackPanel bug
Two more checkboxes pushed the footer past the window width, and a horizontal `StackPanel` **clips**:
"Replace originals" and both new options vanished off the right edge at 1280px with nothing to suggest
they existed. That is T-136 (profile bar) and T-141 (header) for the third time, so it is now a test.

**Its first version was also vacuous**, for an instructive reason: an overflowing `StackPanel` reports its
own oversized width as `ActualWidth`, so its children never look out of bounds *relative to it* - the clip
happens at the Grid column boundary. Comparing child-to-panel passed against the very layout it was
written to catch. It now measures against the window, and the mutation dies.

Verified on screen: all five options wrap onto two lines, with "and empty bin" correctly greyed out until
auto-delete is ticked.
