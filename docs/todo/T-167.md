## Found

[[T-164]] discovered that Split's whole delete-original feature was **inert in the shipped app**: every
view-model test passed, every invariant was documented, and `MainViewModel` simply never passed
`SplitViewModel` an `IOriginalDisposer`. The feature worked perfectly in the suite and did nothing when
a user clicked it. It was caught by reading a doc claim against the code, not by a test.

The fix added `TheCompositionRootWiresADisposerIntoSplit` (`SplitDeleteOriginalTests.cs:340`), which
constructs the real `MainViewModel` and asserts the wiring survives. **Bulk Cut has no equivalent** —
`grep` finds exactly one composition-root test in the suite, and it names Split.

Bulk Cut's disposer is wired correctly today. That is the point: so was every unit test on Split's, right
up until the day it shipped doing nothing. The class of bug is "the seam is tested, the plug is not", and
one screen currently has the guard while the other, which has the same seam and the same destructive
consequence, does not.

## Design
Mirror the Split test for Bulk Cut: construct the real `MainViewModel`, reach the `BulkCutViewModel` it
built, and assert a non-null `IOriginalDisposer` of the shipped type. Keep it in the Bulk Cut delete
tests beside the behaviour it protects, not in a separate wiring file — the Split one is placed that way
deliberately, so the guard is read by whoever next touches the feature.

Consider whether the two should share one parameterised test over the screens that own a disposer. Prefer
that only if it stays as loud on failure: this test's whole value is naming which screen shipped inert.

## Acceptance criteria
- [x] Bulk Cut is asserted to receive a disposer — see the note below on why this reads the
      composition root's **source** rather than constructing it.
- [x] Mutation: removing `originalDisposer:` from the `BulkCutViewModel` construction in
      `MainViewModel` failed **exactly one** test — the new guard — while **156** others passed,
      every Bulk Cut view-model test among them. The gap is demonstrated, not asserted.
- [x] The Split guard still passes; its behaviour is unchanged (it now calls a shared
      repo-root helper instead of its own private copy of the same walk).

## Out of scope
Auditing every other constructor argument in the composition root. Worth doing, much larger, and the
disposers earn priority because their failure mode is silent and destructive-adjacent (the user believes
files were cleaned up).

## Outcome — 2026-09-06

Bulk Cut is covered, and so is the third screen nobody has written yet.

### It discovers the screens instead of listing them
The obvious fix was a second copy of `TheCompositionRootWiresADisposerIntoSplit` with "Bulk" substituted
for "Split". That closes today's gap and leaves the same one open for tomorrow: a hand-written guard per
screen is a hand-maintained list of screens to check, and this drive has already fixed three separate
drifts caused by exactly that arrangement — the picker filter, `_GAPS.md`'s header, the ROADMAP's frozen
test count.

`EveryScreenThatCanTakeADisposerIsHandedOneByTheCompositionRoot` instead **reflects** over the App
assembly for view-models whose constructor accepts an `IOriginalDisposer`, and requires the composition
root to pass one to each. Two today; a third is covered the day it compiles.

### The floor, because a reflection query is a good way to test nothing
A `where` clause that quietly stops matching — a renamed interface, a moved namespace — would leave the
loop iterating over an empty list and reporting green. So the discovered set is first asserted to contain
both known screens as a **minimum, never as the list**. Mutating the query to match `System.Uri` instead
of `IOriginalDisposer` kills the test; without the floor it would have passed.

### Two mutations, both dead
- Removing `originalDisposer:` from Bulk Cut's construction: **1 failed, 156 passed**. The one failure
  names the screen and prints the offending call.
- Breaking the reflection query so it matches nothing: killed by the floor.

### Why it reads source rather than constructing the root
Same reason the Split guard does: the parameterless `MainViewModel` builds the FFME player and the ffmpeg
graph. The injectable test constructor exists but bypasses production wiring, so it would prove nothing —
that constructor is the reason the original bug was invisible. Asserting against source is a deliberate,
narrow tool here, used the same way as T-147's installer script and T-153's spec index.
