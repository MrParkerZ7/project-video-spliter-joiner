## Concept

Every frame grab is floored to a 1-second bucket (`FfmpegThumbnailService.cs:111`, `FloorToBucket` at `:217`), and
that bucket drives both the cache key and the `-ss` value (SPEC-005 I3). For a hover that is right, because one
picture per second is plenty. For a **cut-point picture** it is wrong twice over.

- **Cost.** Bulk Cut asks for a Lossless chip at the handle's snapped cut, which is a keyframe
  (`BulkItemViewModel.cs:1135, 1144`). Save asks for the profile picture at `row.IntroEnd.Snapped`
  (`BulkCutViewModel.cs:1985`). The floor moves `-ss` *before* that keyframe, so ffmpeg seeks to the previous
  keyframe and decodes most of a GOP. Measured on 4K H.264 with a keyframe at 8.333333 s:
  - `-ss 8` costs 3.5-4.4 s CPU and 69 MB read;
  - `-ss 8.333333` costs 0.39 s CPU and 8.8 MB, which is **9-11x** less.

  In wall time on 4K: 0.50 s on a keyframe against 0.62 s mid-GOP (2 s GOP), and 0.50 s against 1.74-2.03 s on a
  10 s GOP. Up to three grabs run at once across all rows (SPEC-011 I67) while rows are still scanning.
- **Correctness.** The picture shows a frame up to 1 s *before* the cut. T-174's title promises *"the frame the
  run will cut at"*. T-174 left the bucket explicitly out of scope (`T-174.md:210-212, 447`): it did not endorse
  the floor, it left it for later.
- **A second time base.** A grab seeks with `-ss` before `-i` (`FfmpegThumbnailService.cs:207-214`), which ffmpeg
  counts from the format `start_time`. A cut point's `Snapped` is a keyframe time, an absolute source pts (ffprobe
  `pts_time`). The two agree only when `start_time` is zero. On a `.ts`, `.m2ts` or `.mts` row (accepted by
  `VideoFileFilter.cs:29`, `start_time` about 1.4 s) a grab at `Snapped` lands about 1.4 s after the cut T-219's
  lossless path makes. Core had no `start_time` until T-219 adds `MediaInfo.StartTime`.

## Design

- **A second kind of request.** `IThumbnailService` gains `GetExactThumbnailAsync(inputPath, time, width, ct)`.
  - **`time` is an ffmpeg seek offset**, counted from the format `start_time`, the same base as the bucketed
    request's `-ss` and T-219's `PerSegment` `-ss`. The service passes it through unchanged; it never reads the
    source's `MediaInfo`.
  - It seeks to the **exact** time, formatted with up to 6 decimals by the existing `FormatSeconds`
    (`"0.######"`, I5). It is **never rounded to milliseconds**. A keyframe at 8.333333 s rounded to 8.333 would
    land just before the keyframe, decode the whole previous GOP and show the previous frame.
  - Its cache key and temp file name use microseconds plus the width: `x<µs>_w<width>.jpg`. It can never
    collide with a bucket file `<bucketMs>_w<width>.jpg`, so an exact request and a hover never serve each other.
  - Same LRU, the same per-input folder (so `Clear`/`ClearAll` remove it), the same prior-run on-disk reuse for
    its own name (I12), and the same best-effort never-throw contract. T-195's MP4/MOV flag and retry apply too.
- **Callers that switch to exact:**
  - the Bulk row cut-point chips at the row's **effective cut time** (`GrabTime`, `BulkItemViewModel.cs:1135,
    1144`). Today that is `Requested` whenever Exact is on (`:317-323`, `:405`), which after T-189 is wrong for every
    row whose Exact cut falls back (every HEVC row, and after T-190 every source whose `start_time` is not zero): the
    run cuts at `Snapped` while the chip would show `Requested`. So the effective time is defined by **one predicate
    shared with T-189 and the run**: `Requested` only when Exact is on **and** `SmartCutArgsBuilder.TryResolveEncoders`
    accepts the row's probed `MediaInfo`; `Snapped` otherwise (provisional while snap-pending). T-189 introduces
    that per-row rule; this ticket only makes the chip's grab exact-time at it;
  - Save's automatic profile picture (`BulkCutViewModel.cs:1985`);
  - 📷 *Use current frame* at the player position (`:2047`);
  - the profile re-take on apply (`:2567`).
- **Each caller passes its time in ffmpeg's base.** A new pure Core method, `MediaInfo.ToSeekOffset(TimeSpan
  sourceTime)` = `max(0, sourceTime − StartTime)`, the same conversion T-219's `PerSegment` makes, converts a
  keyframe time:
  - **converted:** the chip when its effective cut time is `Snapped`, and Save's auto-capture at
    `row.IntroEnd.Snapped` (`:1985`). Both read the row's probed `MediaInfo`, which exists before `Snapped` does: a
    row is probed before its keyframe scan starts (`RowState.Loading`, *"Probe done but the background keyframe
    scan has not finished yet"*);
  - **passed unchanged:** the chip at `Requested`, *Use current frame* at `Player.Position` (`:2047`) and the apply
    re-take at `profile.IntroFromStart` (`:2541`, the caller of `:2567`). These are requested or player times, not
    keyframe times: `IntroEnd.Requested` is set from `Player.Position` (`:1752`) and from `IntroFromStart`
    (`CutProfileApplier.cs:62`), and the player reports its position from the start of the file, ffmpeg's base. That
    last point is read from the player, not measured on a TS file here, so the relaunch check below confirms it on
    a synthetic TS row.

  On an MP4 or MOV whose `start_time` is zero nothing changes. On a TS row the chip and the profile picture show the
  first frame of T-219's lossless cut. That is why this ticket is blocked by T-219.

  **Choice logged.** Rejected:
  - limiting the *"shows the cut frame"* claim and the SPEC-005/SPEC-011 wording to sources whose `start_time` is
    zero and logging the TS offset as a later ticket: the conversion is one subtraction on a field T-219 already
    adds, and a chip 1.4 s past the cut on every TS row contradicts this ticket's own title;
  - converting inside `GetExactThumbnailAsync`: the service would need the source's `MediaInfo`, and it would
    shift the player-time callers, which are already in ffmpeg's base;
  - offsetting the whole timeline (ticks, handles, player) by `start_time`: out of scope for G-059 (T-190, T-219).
- **Hover stays bucketed:** Split's `ThumbnailPreviewViewModel` and the Bulk row scrub hover keep 1 s buckets,
  debounce and latest-wins.
- `NullThumbnailService` and every test fake implement the new method. Fakes record which method was called, so
  App tests can prove the chips use the exact one. This is the T-179 lesson: a fake must not hide the behaviour
  under test.

## Detail

- An exact time of 0 or less clamps to 0, as the bucket path does (I4), with file name `x0_w<width>.jpg`.
- Cached pictures at floored seconds from earlier runs are never matched by an exact request. They stay until the
  next `Clear`, which is the same policy T-179 used for width-less files.
- Existing profile pictures are not re-taken by this ticket. New captures and re-takes are exact.

## Interfaces / contracts

- `IThumbnailService.GetExactThumbnailAsync` (new, no default implementation). Its `time` is an ffmpeg seek offset
  from the format `start_time`.
- `MediaInfo.ToSeekOffset(TimeSpan sourceTime)` (new, public, pure: `max(0, sourceTime − StartTime)`), on the
  `StartTime` T-219 adds. T-208's option (b), if the owner picks it, converts its keyframe time the same way.
- **SPEC-005, same commit:**
  - I3, I4 and I5 are scoped to *bucketed* (hover) requests.
  - New invariants (next free ids after T-195):
    - an exact request seeks to the exact time at microsecond precision;
    - its `time` is an ffmpeg seek offset from the format `start_time`, never converted by the service; a caller
      holding a keyframe time (source pts) passes `MediaInfo.ToSeekOffset(t)`;
    - its cache key and file name are `x<µs>_w<width>`;
    - an exact and a bucketed request never share an entry in either direction;
    - two widths of one exact time are two files (as I26).
- **SPEC-004, same commit:** next to T-219's `StartTime` invariant, *"`ToSeekOffset(t)` is `max(0, t − StartTime)`"*.
- **SPEC-011, same commit:** I61 and I158 say the chip grab is an exact-time request at the effective cut time, as
  T-189 defines it (`Requested` only when Exact will really run for the row), converted with `ToSeekOffset` when
  that time is `Snapped`.
- **SPEC-007, same commit:** **I61** (Save's auto-capture, now at `ToSeekOffset(row.IntroEnd.Snapped)`) and **I110**
  (the re-take on apply, at `IntroFromStart`, unconverted) are exact-time grabs; **I106** (the one stored width,
  640) gains *"captures and re-takes are exact-time grabs at that width"*.
- **CLAUDE.md, same commit:** the G-030 thumbnail bullet (*"bucket-cached LRU"*) gains that cut-point and profile
  pictures use the exact-time request with its own `x<µs>_w<width>` key, at a keyframe time minus `StartTime`,
  while hover stays bucketed.
- Recount `_index.md`.

## Acceptance criteria + Case-Coverage Matrix

**Repro first — confirmed FAILING on shipped code before the fix:**
- [ ] On the shipped code, a chip request at a keyframe time of 8.333333 s produces `-ss 8`. After the fix the exact
      request produces `-ss 8.333333`.
- [ ] Integration (`[SkippableFact]`) on a synthetic `testsrc2` fixture at 30000/1001 fps encoded with `-g 75
      -keyint_min 75 -sc_threshold 0`, so keyframes fall every 2.5025 s. The test takes the keyframe at frame 225
      (7.507500 s, read from `GetKeyframesAsync`, not a literal), 15 frames past 7 s; the floored grab (`-ss 7`)
      shows frame 210 (7.007 s). **Every grab and reference is at the pinned width 640** (the profile width):
      - **references go through the grab's own JPEG args** (`FfmpegThumbnailService.BuildArgs`, T-195's flag
        included), with only the frame selection changed: the frame is picked **by index**, `-vf
        select=eq(n\,N),setpts=PTS-STARTPTS,scale=640:-1 -frames:v 1`, never by `-ss`. The `setpts` reset is
        required: the default mjpeg rate control depends on the frame's pts, and without it a correct grab scored
        45.8 dB against its reference (measured on a 30000/1001 `testsrc2` clip); with it the JPEG is byte-identical
        to the grab. The keyframe reference is N = 225, the floored reference N = 210;
      - **precondition:** the keyframe and floored references differ (different md5), so the case can fail on
        shipped code. Measured: with a regular 2 s GOP at 30000/1001 the keyframe sits at 8.008 s, and the `-ss 8`
        and `-ss 8.008` grabs are byte-identical, so a repro on that fixture would pass on shipped code;
      - an exact grab at the keyframe is **md5-identical** to the keyframe reference (PSNR ≥ 50 dB as the fallback,
        recorded in the Build log if used) and **md5-different** from the floored reference. No dB threshold
        decides "differs": at the 64 px chip width frames 1 apart scored 33.8 dB and 11 apart 28.2 dB (measured),
        so a PSNR line there is unsound;
      - on the shipped path the chip is md5-identical to the floored reference (the repro).

## Edge cases

- **Exact mode, mid-GOP cut:** the grab decodes up to a GOP, the same cost as today, but it now shows the exact
  frame.
- **A whole-second keyframe** (common in synthetic fixtures): the cost is about the same as today, and the picture
  is the same frame under a different key.
- **Many rows with apply-to-all:** each row still makes up to two exact grabs, three at a time (I67), each cheaper
  in Lossless.
- **A TS, M2TS or MTS row:** the chip and the profile picture seek to `Snapped − StartTime`, the first frame of the
  lossless cut. In Exact mode such a row falls back once T-190 ships, so its chip is at `Snapped − StartTime` too.

## Dependencies

- **T-195:** the same `BuildArgs` and SPEC-005 numbering.
- **T-189:** the per-row rule that decides the chip's effective cut time (`Requested` only when Exact will really
  run), and SPEC-011 I61/I158 as it leaves them.
- **T-188:** the bench and its `ntsc` fixture.
- **T-219:** `MediaInfo.StartTime`, which `ToSeekOffset` subtracts, and the lossless boundary the TS case compares
  against. A logic edge.

## Risks

- **Users see slightly different chips** (the true cut frame, up to 1 s later), which is the point. The
  `ux-ui-reviewer` lens checks that nothing else on the row relied on the floored frame.
- **Orphaned floored cache files** stay until `Clear`. It is a temp cache, so no sweep is added.

## Out of scope

- Hover bucketing.
- Keyframe-snapped hover pictures (T-208).
- Re-taking existing profile pictures.
- Pausing grabs during a run (T-205).
- Offsetting the timeline the UI shows (ticks, handles, player position) by `start_time` (G-059). If the TS relaunch
  check finds *Use current frame* off by `start_time`, that gets a later ticket.
