## Concept

`docs/DEV.md` sets *"a 0-warning build is the bar"*. An incremental `dotnet build -c Release` meets it, but a
`--no-incremental` rebuild prints **six xUnit1031 warnings** ("Do not use blocking task operations in test method"),
all from `row.InFlightGrabs.Wait(TimeSpan.FromSeconds(30))` inside synchronous tests that T-174 added (`8b6f51b`):

- `tests/App.Tests/BulkRowIntentTests.cs` lines 431, 435, 786, 790
- `tests/App.Tests/BulkItemThumbnailTests.cs` lines 692, 713

Found by T-188's build (2026-10-05): the same six appear on HEAD `bd06844`, before any G-059 code. A clean CI build
shows them, so the bar is quietly broken.

## Design

Per test, the smallest change that keeps its meaning:

- **Not pump-bound** (no `pump.PumpSettled()` / dispatcher work after the wait): make the test `async Task` and
  replace `x.Wait(t).Should().BeTrue()` with `await x.WaitAsync(t)` (a timeout still fails the test, now as a
  `TimeoutException`), keeping every assertion after it.
- **Pump-bound** (the test drives a dispatcher pump synchronously — `BulkItemThumbnailTests` uses
  `ExactScanningRowUnderThePump`): keep the synchronous wait and wrap exactly that statement in
  `#pragma warning disable/restore xUnit1031` with a one-line reason (the pump needs the test thread). Never a
  file-wide or project-wide suppression.

## Edge cases

A test that both awaits and pumps: convert it only if the pump call can still run on the test thread after an
`await` (xUnit runs async tests without a synchronization context); otherwise use the scoped pragma.

## Dependencies

None.

## Risks

Making a pump-driven test async can move continuations off the pump thread and change what it observes — that is why
pump-bound tests keep the synchronous wait.

## Out of scope

Other analyzers or warnings; changing `InFlightGrabs` itself.
