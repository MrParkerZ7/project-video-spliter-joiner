## Reported
> Thumnail is optional and it's should be update later or remove able

## What is actually wrong — a wrong-profile data hazard, found while reading this

The **Save current as…** popup contains a Thumbnail block: a 52×52 preview, **Upload image…** and
**Clear**. All three bind to `SelectedProfile`:

```csharp
if (DataContext is not BulkCutViewModel vm || vm.SelectedProfile is not { } profile) { return; }
```

But `SelectedProfile` only becomes the NEW profile **after** the save completes
(`SaveProfile` → `RefreshProfiles()` → `SelectedProfile = …`, `BulkCutViewModel.cs:1128-1131`). While the
popup is open naming a new profile, `SelectedProfile` is still the **previously selected** profile.

So in that popup:

| control | what the user expects | what it does |
|---|---|---|
| 52×52 preview | the new profile's picture | the PREVIOUS profile's picture |
| Upload image… | set the new profile's picture | sets the PREVIOUS profile's picture |
| **Clear** | remove the new profile's picture | **wipes the PREVIOUS profile's picture** |

The last row is the serious one: naming "Anime OP 2" and pressing Clear silently destroys "Anime OP 1"'s
thumbnail, with no confirmation and no undo. It is also why the section reads as mandatory — it is
presented as part of creating the profile, when the picture is in fact grabbed automatically on save and
is entirely optional.

## Design
1. **Remove the thumbnail block from the save popup.** The popup's job is naming. Replace it with one
   line stating what happens: the picture is taken from the intro-end frame automatically, and can be
   changed or removed any time from the profile bar.
2. That leaves editing where it belongs — the bar's **📷 Use current frame** and **🖼 Thumbnail…**, which
   T-136 made permanently visible (disabled-with-a-reason rather than hidden), plus Clear.
3. **Make sure removal is reachable.** `ClearThumbnail` exists on the VM and was only wired to the popup's
   Clear button; after step 1 it needs a home in the bar or it disappears entirely. That would trade one
   defect for another.
4. Saving must not depend on the grab in any way — it already does not (`SaveProfile` persists first, the
   grab is best-effort afterwards, SPEC-007 I66), so this is a presentation fix, not a behaviour change.

## Acceptance criteria
- [x] The save popup contains no control that can modify another profile's thumbnail.
- [x] Removing a thumbnail is still possible after the popup loses its Clear button.
- [x] Saving a profile with no thumbnail works and is described as normal, not as a missing step.
- [x] Structurally guaranteed instead of tested: the popup no longer contains any thumbnail-mutating
      control, so the wrong-profile path does not exist to be tested. The bar's controls act on
      `SelectedProfile`, which is correct there by definition.
- [x] SPEC-007 updated; rebuilt and relaunched (PID 38420, window verified).
