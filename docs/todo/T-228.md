## Concept

Found while reviewing T-195 (2026-10-05). `FfmpegThumbnailService.GetThumbnailAsync` has an on-disk reuse branch: *"A
prior run may have left the file on disk though it's not tracked (fresh process). Reuse it"*
(`FfmpegThumbnailService.cs:136-142`). It returns any file at the temp path and `Remember`s it, without checking that a
run finished writing it.

Two things can leave such a file:

- a failed run never deletes its output (`if (!produced) return null;`, `:166-169`);
- `FfmpegRunner` kills the process tree on cancellation (`FfmpegRunner.cs:111-114`). Hover latest-wins cancels grabs
  constantly, so a kill during the JPEG write leaves a truncated file.

The next request for that bucket and width returns the truncated JPEG with zero runs and caches it until
`Clear`/`ClearAll`. The App's frozen `BitmapImage` then shows nothing or a partial image.

## Design

Recommended (star): write each grab to a unique temp name (`<bucketMs>_w<width>.<guid>.tmp.jpg`), then move it onto the
final name only after a successful run. The final name then only ever holds a complete picture. On any failure or
cancel, delete the temp in a `finally`.

Alternative: delete the temp path in a `finally` whenever the run did not produce, and require a non-empty file in the
reuse branch.

## Acceptance criteria

- [ ] **Repro first:** a scripted runner writes a partial file and throws `OperationCanceledException`. The next
      `GetThumbnailAsync` for the same bucket must run ffmpeg again, not return the leftover. This fails today.
- [ ] A failed run (exit 1) that leaves a file: the next request runs ffmpeg again.
- [ ] Cache, LRU, width-in-key (I26) and Clear tests pass unchanged; SPEC-005 is updated if an invariant is added.
