## Concept

G-059's tickets must each show a measured before and after, and T-137 bans wall-clock assertions in
tests, so the numbers have to come from somewhere else. The harness that produced the T-187 evidence
works: 677 measured rows, real Core services, the app's own runners. But it was written in a session
scratchpad, with absolute scratchpad paths hardcoded in `Infra.cs:14-22`, and the tickets will be built in
later sessions, after that folder is gone. So a reference copy of its sources (`*.cs`, `Bench.csproj`,
`show.py`) and of the measurement agent's full return (`measure_result.json`) was made at planning, in
**`docs/design/references/T-187-bench/`**, committed with this plan. It is never built. This ticket ports
from that copy.

The history reader also found why the 4K regressions went unseen. `tests/Core.Tests/FourKPerformanceTests.cs`
covers only the copy split and the keyframe scan on a 15 s clip, and nothing measures Exact cut, probes or
thumbnails at 4K on a long, high-bitrate file.

This ticket moves the harness into the repo as a dev tool that compiles with the solution, generates its
own fixtures, and refuses any input outside its own fixture folder.

## Design

- **Project:** `bench/VideoSplitJoiner.Bench/` — a net8.0 console app referencing `src/Core` only, added to
  `VideoSplitJoiner.sln` so a Core API change breaks its build. It is not a test project, so `dotnet test`
  does not run it. `packaging/package.ps1` publishes only `src\App\VideoSplitJoiner.App.csproj`
  (`package.ps1:52`), so nothing ships.
- **Ported from the reference copy** `docs/design/references/T-187-bench/`: `CoreScenarios.cs`,
  `Alternatives.cs`, `Smart2.cs`, the results writer and `show.py`'s filter. **`Mp4Index.cs` is not ported**,
  because T-194 builds the production reader in Core (from the same copy) and the bench then times it through
  `MediaProbe`. The reference copy stays as the evidence record.
- **No direct process spawning.** The prototype's `IoMeter.cs` called `Process.Start` itself so it could
  read each child's `GetProcessIoCounters`. That breaks the CLAUDE.md rule *"All FFmpeg/ffprobe execution
  goes through FfmpegRunner / FfprobeRunner"*. The bench instead puts its own process in a **Windows job
  object** at start-up. Children that `FfmpegRunner`/`FfprobeRunner` start inherit the job, so the job's
  `JOBOBJECT_BASIC_AND_IO_ACCOUNTING_INFORMATION` gives the bytes read and written, the CPU time and the
  number of processes started (`TotalProcesses`) of everything a scenario ran, as a delta around the
  scenario. Scenarios run one at a time, so the delta
  belongs to the scenario. The bench's own file reads (for example the sample-table reader after T-194)
  are counted too, which is what a "bytes read" figure should mean.
- **Fixture generator:** `bench fixtures [--nvenc]` builds the matrix into a folder outside the repo
  (default `%TEMP%\vsj-bench-fixtures`, overridable with `--root`). It runs `FfmpegRunner` with typed
  `FfmpegArgs` from `lavfi` `testsrc2` plus `sine` sources. It uses libx264/libx265 by default, so it works
  on a machine without an NVIDIA GPU; `--nvenc` reproduces the T-187 evidence recipe. Every recipe is
  written in code, and each output is self-checked with ffprobe (codec, size, GOP, B-frames, tag) before
  it counts. The self-check also records each fixture's `format.start_time` in the results file (zero expected,
  since ffmpeg's mp4 muxer writes an edit list); T-190's and T-219's Build logs quote it.
- **Path guard:** every scenario resolves its inputs through one `FixtureRoot.Resolve(path)`, which accepts a
  path only when its full, link-resolved form is inside the fixture root. Anything else exits non-zero
  before any file is opened.
- **Results:** each run appends one JSON line per measurement to `<root>/results/timings.jsonl`: scenario,
  fixture, wall time, CPU time, bytes read and written, machine-load sample, git sha. It also prints a
  markdown table to paste into a Build log.

## Detail

**Fixture matrix.** Only the shapes some now-ticket's Build log names. The first five are the T-187 shapes,
so "before" figures are comparable.

| key | recipe | used by (Build logs) |
|---|---|---|

| `1080` | the same at 1920x1080, ~15 Mbit/s | T-192, T-193, T-195 |
| `hevc` | 4K HEVC Main, hvc1, 60 s, GOP 2 s, AAC | T-194, T-195 |
| `g10` | 4K H.264, 60 s, GOP 10 s | T-191, T-192, T-195, T-196 |
| `4k10m` | `4k` concatenated five times with `-c copy`, 600 s, ~4.5 GB | T-190, T-191, T-192, T-193, T-194, T-219 |
| `ntsc` | 1080 H.264 at 30000/1001 fps, so keyframes fall between whole seconds | T-196 |
| `mkv` | `4k` remuxed to Matroska | T-194, T-195 |

Not in the matrix: the shapes a ticket checks for correctness rather than times. T-189 to T-196 and T-219
generate theirs inside their own tests (an HEVC source with non-default x265 settings, an MPEG-TS source, a MOV
with a leading empty edit, `+faststart`, hev1, Main10, 60 fps, fragmented, a B-frame and a `-bf 0` H.264 pair, a
Main and a 10-bit H.264 source, a rotated MP4, a 30000/1001 clip with a 2.5025 s GOP), where `dotnet test` can see
them. A shape is added here only when a ticket's Build log needs it (T-217 adds `ts` if its trigger
fires).

**Scenarios** (`bench core <fixtures…> <scenarios…>`): `probe`, `kf`, `wf`, `thumb`, `load` (probe, then
keyframes and waveform in parallel, in `SplitViewModel.LoadAsync` order), `split`, `join`, `bulk` (add rows,
then a lossless and an Exact run), `smart` (head variants at named cut positions). `bench selftest` exercises
the guard, the job accounting, the fixture self-checks and the results file (cases under Acceptance).

**Not run by the suite.** `FourKPerformanceTests` stays as it is; T-197 points its header at `bench/`.

## Interfaces / contracts

- No Core API change. If a scenario needs a Core internal, it uses public API, or the ticket adds
  `InternalsVisibleTo Include="VideoSplitJoiner.Bench"` in `VideoSplitJoiner.Core.csproj` (beside the test
  one at line 11) and says so in the Build log.
- **CLAUDE.md, same commit:** the Layout section gains `bench/` ("dev-only performance bench, synthetic
  fixtures only, never packaged"). The Build/test section gains the rule: *performance timings go in a
  ticket's Build log via `bench/`, never into a test assertion (T-137); the bench only ever opens files it
  generated*.
- `bench/README.md`: how to build and run it, the fixture matrix, the guard, and that the bench must only
  ever see its own synthetic fixtures. It also records the T-187 findings with their repro commands:
  the HEVC joint (→ T-189), the H.264 80 ms joint (→ T-190), the output-seek comment (→ T-191), and the two
  lossless-boundary faults found at plan review, the B-frame segment muxer and the non-zero `start_time` in
  `PerSegment` (→ T-219).

## Acceptance criteria + Case-Coverage Matrix

- [ ] `D:\_env_storeage\dotnet\dotnet.exe build VideoSplitJoiner.sln -c Release` builds the bench.
      `dotnet test VideoSplitJoiner.sln` runs no bench code, and the suite count is unchanged.
- [ ] `powershell -File packaging/package.ps1` output contains no bench binary (the published file list is
      unchanged).
- [ ] `bench fixtures` regenerates the whole matrix from nothing **without `--nvenc`**, and every self-check
      passes. A grep of `bench/` finds no `Process.Start` or `ProcessStartInfo`. All spawning goes through
      `FfmpegRunner`/`FfprobeRunner` with typed `FfmpegArgs`.
- [ ] **Guard:** `bench selftest` passes these cases, and none opens a file outside the root:
      - a path inside the root is accepted;
      - a path outside it is refused;
      - a `..` path that escapes the root is refused;
      - a junction or symlink inside the root that points outside is refused.

      For each refused path (outside, `..`, junction) the scenario exits non-zero, and the job's
      `TotalProcesses` delta is **0** and its bytes-read delta is **0**: no ffmpeg or ffprobe was started and no
      file was read.
- [ ] **Job accounting is real:** in `bench selftest`, a scenario that runs `ffprobe -show_packets` on `4k`
      reports bytes read of at least 90% of the file size. A metadata probe reports under 10 MB.
- [ ] **Self-checks and failure paths,** also in `bench selftest`:
      - a deliberately wrong fixture (the `4k` recipe with `-bf 0`) is rejected by its self-check and is not
        recorded as valid;
      - with the ffmpeg location pointed at an empty folder (a selftest-only override), the bench exits non-zero
        with the `packaging/fetch-ffmpeg-shared.ps1` hint and records no fixture as valid;
      - a second run grows `timings.jsonl`, and the earlier lines are byte-identical;
      - `bench core` on an empty fixture root refuses with a message and a non-zero exit.
- [ ] **Baseline reproduced:** `bench core 4k 4k10m kf smart` reproduces the T-187 orders of magnitude:
      - `kf` reads about 100% of the file, 0.7 s on `4k`;
      - the Exact head at 104.5 s on `4k` takes tens of seconds and reads most of the file.

      The full baseline goes in this ticket's Build log as G-059's "before" figures: every scenario, on
      `4k`, `1080`, `hevc`, `g10` and `4k10m`, with the load sample.
- [ ] No test asserts a wall-clock time (T-137). No file is written in the repo outside `bench/`; results
      and fixtures live under the fixture root.
- [ ] Same commit: the CLAUDE.md Layout and Build/test lines, and `bench/README.md`.

| cell | cases |
|---|---|
| Required-Success | the solution builds with the bench · `fixtures` makes the matrix without NVENC · the baseline matches the T-187 magnitudes |
| Required-Fail | an outside path is refused before any open (`TotalProcesses` and bytes-read deltas 0) · a self-check rejects the `-bf 0` fixture |
| Optional-Success | `--nvenc` reproduces the evidence recipe · `--root` moves fixtures and results together |
| Optional-Fail | ffmpeg-shared missing → the fetch hint, a non-zero exit, no fixture counted as valid (selftest) |
| Boundaries | a junction inside the root pointing out · an empty fixture root refused (selftest) · a re-run appends, earlier lines byte-identical (selftest) |

## Edge cases

- A machine without `ffmpeg-shared/` cannot run the bench. It says where to fetch it
  (`packaging/fetch-ffmpeg-shared.ps1`) and exits. The test suite is unaffected.
- The job object may be nested inside a terminal's job, which Windows 8+ allows. If `AssignProcessToJobObject`
  fails, the bench stops with the error. It never falls back to spawning processes itself.
- Generating `4k10m` needs about 5 GB of free space at the fixture root. The generator pre-flights that.

## Dependencies

No ticket. The input is the reference copy in `docs/design/references/T-187-bench/`, committed with this plan
(not the session scratchpad, which will be gone). It is read to port from, never built.

## Risks

- **libx264-made fixtures differ from the NVENC-made evidence** in absolute timings. Only before/after from
  the same run are compared, and every Build log says which recipe it used.
- **Machine load moves numbers about 1.6x** (measured on 2026-10-04). The load sample on each row makes
  that visible.

## Out of scope

- Any Core behaviour change.
- An HDD-class or cold-disk bench (that belongs to T-205).
- Running the bench in CI (ADR 0014: no CI yet).
