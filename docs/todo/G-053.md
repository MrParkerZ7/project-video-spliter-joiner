## Why

User: *"on profile section the profile list should be full width bar of item full width then new line
instead scroll able, for action buttons should be separate lines from profile list also full width, but
need to make sure to be auto new line if overflow too"*

Three clauses, and they are one complaint: **the card is narrower than the space it has, so everything
inside it is fighting.** The card carries `HorizontalAlignment="Left"` and is therefore content-sized —
measured **1535 of an available 1576px** at 1600 wide, and **706 of 736** at 760 wide. Inside that, the
chip list is capped at `MaxWidth="420"` and scrolls, so with any real number of profiles most of them are
off-screen behind a scrollbar; and the action buttons share the *same* `WrapPanel` as the chip list, so
they are whatever the bar leaves them.

## What this reverses, deliberately

[[T-161]] chose scroll-inside-a-cap **on purpose**, and SPEC-007 **I98** records it: *"the bar scrolls
inside a fixed cap (`MaxWidth`) rather than widening with the profile count."* Its second clause names the
very behaviour the user is now asking for — a `WrapPanel` wrapping the actions onto the next line — as the
**failure mode the cap existed to prevent**.

So this is not a bug fix. It is a reversal of a reviewed decision, and the ticket has to say what that
decision was protecting and how the protection survives. It was protecting **the header's height**: this
card lives in the header, where [[T-141]] already fought a row that grew until it pushed the tab
off-screen.

## The measurement that makes this non-obvious

An uncapped wrap does re-create exactly that failure. Measured at 760x620 — the tightest supported size:

| | header growth | result |
|---|---|---|
| today (420px cap, scrolls) | — | Run on screen |
| **uncapped wrap** | **+154px** | **Run pushed 74px off-screen** |
| wrap + two-row cap | +60px | Run on screen (72px of slack available) |

So the cap does not disappear — it **rotates onto the axis the new layout is free on**. The chip list is
bounded by `MaxHeight` at about two rows and scrolls *vertically* past it. "Too many profiles" still
degrades into scrolling; it degrades on the axis where splitting the rows removed the displacement hazard.

## Out of scope

Re-designing the chips themselves, the thumbnail pipeline, or any command binding. `Profiles` /
`SelectedProfile` and every apply/save/delete command are untouched — SPEC-007 I96 holds verbatim.
