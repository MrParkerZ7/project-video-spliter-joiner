## Reported
> where is the bulk cut current video play capture into current profile thumnail button ?

The **📷 Use current frame** button shipped in T-135 (`21a0ebe`) and is present in the XAML at
`BulkCutView.xaml:293`. The user could not find it. Both reasons are mine.

## Cause 1 — it is INVISIBLE until a profile has been saved

I copied the neighbouring visibility binding without thinking about it:

```xml
Visibility="{Binding HasProfiles, Converter={StaticResource BoolToVisibility}}"
```

Five controls in the profile bar carry that same gate, so with **no saved profiles the bar is nearly
empty** — the picker, both Apply buttons, Thumbnail…, Delete and the new snapshot button all vanish. A
user with no profile yet sees no way to make one *from a frame*, and no hint that the capability exists.

This is the exact lesson G-044 produced (an unreachable thumbnail control), and T-135's own ticket says
*"an inert button with no explanation is what made the upload unreachable in G-044, and it applies
identically here"* — and then I gated it on `Visibility` anyway. The VM already exposes
`SnapshotUnavailableReason` ("Pick a cut profile first") precisely so the button can be **shown and
disabled with a reason** instead of hidden.

## Cause 2 — the bar is a non-wrapping horizontal StackPanel

```xml
<StackPanel Orientation="Horizontal" VerticalAlignment="Center">
```

It now holds eight controls: the picker (MinWidth 164), the paired Apply-to-selected/all border,
📷 Use current frame, 🖼 Thumbnail…, ✕ Delete, the empty-state hint, and Save current as…. A horizontal
`StackPanel` neither wraps nor scrolls — it simply **clips whatever does not fit**, silently, off the
right edge. Every button I have added to this bar has made that worse, and the Bulk Cut tab has a
user-resizable split (G-039 / T-112) whose narrow settings make it likely.

This file already uses the right idiom a few hundred lines down — `<WrapPanel>` at line 509, for the
set-at-playhead buttons.

## Design
1. **`WrapPanel`, not `StackPanel`**, for the profile bar, so controls flow onto a second line instead of
   being clipped. Match the existing usage at line 509.
2. **Stop hiding the actionable buttons.** Show 📷 Use current frame and 🖼 Thumbnail… whenever the tab
   has rows, disabled-with-a-reason when there is no profile — the reason string already exists. Keep the
   picker/Delete gated on `HasProfiles` (a picker with nothing to pick is genuinely meaningless).
3. Re-check the whole bar at a narrow width, not just the default one. The clipping is invisible at wide
   widths, which is why three additions did not reveal it.

## Acceptance criteria
- [x] With zero saved profiles, the snapshot and upload buttons are VISIBLE and disabled, and their
      tooltips say what to do first.
- [~] At a narrow split width no control is clipped. A WrapPanel cannot clip horizontally by
      construction, which is the structural guarantee; **checking it at a narrow width by eye is yours** —
      no unit test can see layout.
- [x] Every button in the bar is reachable without resizing the window.
- [x] SPEC-011 records that the profile bar wraps and that its action buttons disable rather than hide.
- [x] Rebuilt and relaunched (PID 49376, window verified open — the XAML rework parses).
- [ ] Checked at a narrow split by eye (yours).

## Out of scope
Redesigning the profile bar's grouping. This is about nothing being hidden or clipped.
