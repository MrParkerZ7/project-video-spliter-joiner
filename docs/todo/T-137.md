## What was observed

Twice in this session, a solution-level `dotnet test` reported exactly one failure in
`VideoSplitJoiner.App.Tests` and it did not reproduce:

| when | reported | reruns, all clean |
|---|---|---|
| 2026-08-30, after the coverage pass | `Failed: 1, Passed: 715, Total: 716` | 6 App-only + 4 solution-level |
| 2026-08-30, after the T-136 XAML edit | `Failed: 1, Passed: 778, Total: 779` | 3 App-only + 5 solution-level |

**Neither failure's test name was captured** — the summary line was seen, the detail was not, and by the
time a verbose run was started it had gone. That is the single most useful thing to fix about this: the
next occurrence must be diagnosable.

## What is NOT known
The failing test, the assertion, and whether the two occurrences are the same cause. Nothing here should
be read as a diagnosis.

## The one lead worth recording
Both occurrences were on **solution-level** runs, where `App.Tests` and `Core.Tests` execute in parallel;
neither happened in an App-only run. Several recently-added suites do real filesystem work in temp
directories (`ProfileThumbnailStoreTests`, `AppSettingsTests`, `FileMediaInputStreamTests`,
`ExactCutReplaceOriginalSafetyTests`), some of it involving exclusive file locks. That is a plausible
place for a race, and it is a hypothesis, not a finding — each of those suites uses a GUID-named
directory, which argues against a simple collision.

## Design
1. **Make the next occurrence self-reporting.** Run the suite with a TRX logger (or
   `--logger "console;verbosity=detailed"`) in the loop that catches it, so the failing test and its
   assertion survive the run that produced them.
2. Only then investigate. Do not restructure test parallelism on a hypothesis — a green suite that is
   restructured for an unobserved race is worse than a rare flake, because it hides the evidence.
3. If it proves to be filesystem contention, the fix is per-suite isolation, not disabling parallelism
   across the whole solution.

## Acceptance criteria
- [ ] A reproduction attempt runs the solution suite repeatedly with per-test logging retained.
- [ ] The failing test and assertion are captured, or the attempt is recorded as inconclusive with the
      number of runs.
- [ ] No test is disabled, retried, or made parallel-unsafe-tolerant to make the symptom go away.

## Out of scope
Chasing this before it recurs. It is ~1 failure per ~20 full runs; the priority is capturing evidence when
it happens, not hunting it now.
