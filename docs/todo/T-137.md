## What was observed

Twice in this session, a solution-level `dotnet test` reported exactly one failure in
`VideoSplitJoiner.App.Tests` and it did not reproduce:

| when | reported | reruns, all clean |
|---|---|---|
| 2026-08-30, after the coverage pass | `Failed: 1, Passed: 715, Total: 716` | 6 App-only + 4 solution-level |
| 2026-08-30, after the T-136 XAML edit | `Failed: 1, Passed: 778, Total: 779` | 3 App-only + 5 solution-level |
| 2026-09-01, after the T-146 style edit | `Failed: 1, Passed: 451, Total: 452` in **Core.Tests** | 2 before, 6 after — all clean |

**Neither failure's test name was captured** — the summary line was seen, the detail was not, and by the
time a verbose run was started it had gone. That is the single most useful thing to fix about this: the
next occurrence must be diagnosable.

## What is NOT known
The failing test, the assertion, and whether the two occurrences are the same cause. Nothing here should
be read as a diagnosis.

## The lead is now WEAKER than it looked

The first two occurrences were on solution-level runs and both reported by `App.Tests`, which suggested a
race between the two assemblies running in parallel. **The third (2026-09-01) was in a `Core.Tests`-only
run** — one assembly, no cross-assembly parallelism. That rules out the tidiest hypothesis and leaves
per-assembly test parallelism, or genuine filesystem contention inside one suite, as what is left.

The name was again not captured: it failed on run 3 of a bare loop, and six subsequent runs WITH logging
were clean. Rate is roughly 1 in 10-20.

Original note, kept for the record: both early occurrences were on **solution-level** runs; Several recently-added suites do real filesystem work in temp
directories (`ProfileThumbnailStoreTests`, `AppSettingsTests`, `FileMediaInputStreamTests`,
`ExactCutReplaceOriginalSafetyTests`), some of it involving exclusive file locks. That is a plausible
place for a race, and it is a hypothesis, not a finding — each of those suites uses a GUID-named
directory, which argues against a simple collision.

## Design
1. **Make the next occurrence self-reporting.** The loop that catches it must ALREADY be running with
   `-v n` (or a TRX logger) — a bare loop that catches it produces only a count, which is what happened
   all three times. Verified 2026-09-01: `for i in 1..6; dotnet test -v n > run$i.log` is the right
   shape; it just needs enough iterations, and 6 was not enough.
2. Only then investigate. Do not restructure test parallelism on a hypothesis — a green suite that is
   restructured for an unobserved race is worse than a rare flake, because it hides the evidence.
3. If it proves to be filesystem contention, the fix is per-suite isolation, not disabling parallelism
   across the whole solution.

## Acceptance criteria
- [x] A reproduction attempt runs the solution suite repeatedly with per-test logging retained. (10 runs, `-v n`, logs kept - 2 failures caught.)
- [x] The failing test and assertion are captured. **Two** tests, one shape: `ThumbnailPreviewViewModelTests.UpdateHover_ResolvesFrameForHoveredTime` and `BulkItemThumbnailTests.RapidIntroMoves_AreDebounced_ToASingleGrab`, both *"Expected ... Requests to contain a single item, but the collection is empty"*.
- [x] No test is disabled, retried, or made parallel-tolerant. The opposite: the waits got **stricter**, and three mutations confirm the tests still fail when the behaviour actually breaks.

## Out of scope
Chasing this before it recurs. It is ~1 failure per ~20 full runs; the priority is capturing evidence when
it happens, not hunting it now.

## Outcome — 2026-09-01: a wall-clock wait, fixed

Caught on the 4th sighting, this time with its name, during the T-147 full-suite run.

### It was far more frequent than this ticket assumed
Measured deliberately — pristine tree, solution-level, idle machine, logs retained: **6 failures in 15
runs**. The "1 in 10-20" estimate came from four incidental sightings; it is closer to **40% of full-suite
runs**, and had been taxing every verification run for a month.

| test | failures in 15 pristine runs |
|---|---|
| `ThumbnailPreviewViewModelTests.UpdateHover_ResolvesFrameForHoveredTime` | 6 |
| `ThumbnailPreviewViewModelTests.SupersededRequest_NeverClobbersNewer` | 2 |
| `BulkItemThumbnailTests.RapidIntroMoves_AreDebounced_ToASingleGrab` | 2 |

All the same shape: *"Expected ... Requests to contain a single item, but the collection is empty."*

### The cause
Not filesystem contention, not cross-assembly parallelism, not a race in the code under test. Both
harnesses waited for the debounced frame grab with a **wall-clock deadline**:

```csharp
var deadline = DateTime.UtcNow.AddMilliseconds(300);   // 500 in BulkItemThumbnailTests
while (DateTime.UtcNow < deadline) { if (Drain() > 0) { Drain(); return; } Thread.Sleep(1); }
Drain();
```

The grab is fire-and-forget by design (`_ = GrabAsync(...)` — a hover or handle move must never block the
UI), so once the debounce gate is released the continuation must be **scheduled by the thread pool** before
it calls the service and posts its result. In a solution-level run the other assembly's 452 tests saturate
the pool, the continuation misses the deadline, and the assertion runs early.

That explains every observation, including the one that had looked contradictory:

| shape | pool load | result |
|---|---|---|
| the single test alone, x14 | idle | 0 failures |
| `App.Tests` alone, x16 | light | 0 failures |
| **solution-level, x15** | **saturated by Core.Tests** | **6 failures** |

The third sighting being reported by `Core.Tests` fits too: it is the *presence* of the other assembly that
matters, not which one reports.

### The fix: wait for the work, not for time to pass
Both view models keep their most recent grab task and expose it `internal` for tests
(`ThumbnailPreviewViewModel.InFlightGrab`, `BulkItemViewModel.InFlightGrabs`, via the existing
`InternalsVisibleTo`). The harnesses await that, then drain. **No production behaviour changed** — the
pipeline is still fire-and-forget; it merely stopped being unobservable. The 30s bound that remains is a
deadlock guard a healthy run never approaches, not the synchronisation mechanism.

Same principle the project already applies to performance tests — never assert on wall-clock — applied
where it was quietly load-bearing for *correctness*.

### Evidence
- **0 failures in 20 solution-level runs** on a verified-clean build, against **6 in 15** pristine on the
  same idle machine. If nothing had changed, 20 clean runs at that rate is roughly a 1-in-4000 coincidence.
- App.Tests also got faster (1s → ~750ms): the waits are no longer padding the run.
- **Three mutations, all dead, all deterministic**: skipping the service call in
  `ThumbnailPreviewViewModel.GrabAsync` (4 tests), skipping its `_postResult.Report` (4 tests), and
  skipping the service call in the row's grabber (1 test). The tests still catch the exact failure they
  were intermittently suffering — stricter now, not weaker.

### A wrong turn worth recording: the measurement lied before the code did
Midway through, this fix appeared to break three unrelated tests 15 runs out of 15
(`BulkSelectAllTests`, `BulkRowIntentTests`, `BulkItemThumbnailTests.ManyRows_ShareOneGate`). It was
written up, reverted, and split into a follow-up ticket on that basis. **All of it was an artefact of a
stale build.**

The mutation harness restored files with `shutil.move`, which **preserves the backup's mtime**. MSBuild
then saw the restored source as older than its compiled output, skipped recompiling, and the next test run
executed the still-mutated binary. One of those mutations was *"the grab never reaches the service"* —
which produces exactly "the collection is empty" and "grabsBefore = 0". The tool was reporting the mutant,
not the fix.

Caught when a layout test (T-138) failed with `MinHeight` = **20** — a value that existed only in a
mutation that had been "restored" minutes earlier. With `os.utime` added to every restore and a
`--no-incremental` rebuild, the whole suite passes and the flake is gone.

### Worth carrying forward
1. **A poll-with-deadline in a test is a race dressed as synchronisation.** It only fails on a busy machine
   — which is to say in CI and full-suite runs, not while you are watching. If the code under test starts
   work that is not awaitable, make the work observable; do not guess how long it takes.
2. **Measure the flake rate before and after, on an idle machine.** "It stopped failing" means nothing
   without a baseline. An early measurement here was also polluted by a stray `VideoSplitJoiner.App`
   process burning CPU in the background.
3. **A mutation harness must invalidate the build when it restores.** Preserving the original timestamp is
   the default for `shutil.move`/`copy2`, and it silently converts every later measurement into a lie.
   Three separate wrong conclusions in this session trace to that one line.
4. **When the evidence says something implausible, suspect the instrument.** "Assigning a Task to a field
   instead of discarding it broke three unrelated tests" was never a credible mechanism, and it was not
   true.
