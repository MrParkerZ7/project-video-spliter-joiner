## What is wrong

`tests/Core.Tests/FfmpegTestBinaries.cs` hardcodes ffmpeg at
`D:\_env_storeage\ffmpeg-7.1.1-essentials_build\bin\ffmpeg.exe`. `SkipIfMissing` writes an xUnit
output line and returns `true`; every caller then does a bare `return;`.

**xUnit records that method as PASSED, not Skipped.** That is why a local run reports 0 skipped while the
guard is live — the guard is invisible in the result count.

On GitHub's `windows-latest` that path does not exist, and `packaging/fetch-ffmpeg-shared.ps1` runs
*after* the `Test (release gate)` step and would not put ffmpeg there anyway. So **43 `[Fact]`/`[Theory]`
methods** across `SplitEngineIntegrationTests`, `JoinEngineIntegrationTests`, `SmartCutEngineIntegrationTests`
and the probe suites report green on CI **without executing anything**.

## The concrete failure it allows
The release gate is the last thing standing between a broken cut and a shipped installer. Every test that
actually exercises ffmpeg — lossless split, join, smart/exact cut, keyframe probing — passes vacuously
there. A regression that corrupts output would go out with a green gate.

## Design
1. Resolve ffmpeg by discovery, not a hardcoded absolute path: `FFMPEG_PATH` env var → `PATH` →
   the packaging download location → the current hardcoded path last.
2. When it genuinely is absent, the tests must **skip visibly** (`[SkippableFact]` / `Assert.Skip`), never
   return as passed. A skipped test is honest; a vacuous pass is not.
3. Make CI **fail** if the integration tests skip on the release-gate job: fetch ffmpeg *before* the test
   step, then assert a minimum executed count so absence is loud rather than silent.

## Acceptance criteria
- [ ] No test method can report Passed without executing its body.
- [ ] Absent ffmpeg produces Skipped, visible in the run summary.
- [ ] The release-gate job fetches ffmpeg before testing and fails if the integration suites skip.
- [ ] A deliberate break in a cut path is caught by the gate (verify by mutation, not by reasoning).

## Out of scope
Rewriting the integration tests themselves. They are fine; nothing runs them.
