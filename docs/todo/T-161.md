## Reported
> on profile bulk cut insted of drop down, let make it as profile bar which scroll able incase too many
> profile but just click select on proifle then selection acction to apply all or something

## Concept

Cut profiles carry **pictures** — T-135 and T-129 both exist so a profile can have a recognisable
thumbnail. A `ComboBox` then hides every one of them behind a closed popup: you see one profile at a
time, and picking the right one means opening a list and reading names. The pictures are doing no work
until after you have already chosen.

A horizontally scrollable bar of profile chips shows the pictures **at rest**. Selecting becomes one
click on the thing you recognise instead of open→scan→click, and "too many profiles" degrades into
scrolling rather than a taller and taller popup.

## Design

**Current** (`BulkCutView.xaml:254-262`): a `WrapPanel` holding a `ComboBox` (`MinWidth=164`,
`ItemsSource={Binding Profiles}`, `SelectedItem={Binding SelectedProfile}`,
`ItemTemplate={StaticResource ProfileItemTemplate}`) followed by the Apply split-control, the two
thumbnail buttons, and Delete.

**Chosen approach — swap the ComboBox for a selection bar; keep every action exactly where it is.**

- A `ScrollViewer` (`HorizontalScrollBarVisibility="Auto"`, `VerticalScrollBarVisibility="Disabled"`)
  wrapping a `ListBox` with a horizontal `ItemsPanel`, `ItemsSource={Binding Profiles}` and
  `SelectedItem={Binding SelectedProfile, Mode=TwoWay}` — **the same two bindings the ComboBox uses**,
  so selection semantics, `HasSelectedProfile`, and every existing command keep working untouched.
- Each item is a chip reusing `ProfileItemTemplate`'s content (thumbnail + name), restyled for the
  at-rest bar: selected state marked by **≥2 differentiators** (accent border + raised surface), never a
  tint alone.
- **Actions stay separate from selection.** The existing `⧉ Apply to selected` / `⧉ Apply to all` split
  control, `📷 Use current frame`, `🖼 Thumbnail…`, `✕ Picture`, and Delete are unchanged and continue to
  act on `SelectedProfile`. The user's *"then selection action to apply all"* is already exactly this
  pair — this ticket makes the selection half visual, it does not redesign the actions.

### The double-click question, decided
A profile chip is a **selection**, not a command. Click selects; the apply buttons apply. Making a click
apply-to-all directly would make an irreversible-ish bulk edit (it rewrites every ticked row's cut
points) reachable by a single misclick on a scrolling strip. **Recommended and taken: click selects
only.** Double-click-to-apply can be added later if the user asks; it is cheap then and unsafe now.

### Rejected
- **WrapPanel of chips (no scroll).** Grows vertically without bound; the profile card is in the header,
  where T-141 already fought a growing row.
- **Keep the ComboBox and add a thumbnail strip beside it.** Two selection surfaces for one selection.
- **Virtualising list.** Profile counts are human-scale (tens); a `VirtualizingStackPanel` is available
  if a real count problem ever appears, and is not worth the complexity now.

## Detail
- Bar sits where the ComboBox sits — first element of the profile card's `WrapPanel`, still gated on
  `HasProfiles`.
- Give it a `MaxWidth` (or `*` within a grid column) so it scrolls instead of pushing the action buttons
  off the row — the profile bar is the T-136 clipping site, so this must be verified, not assumed.
- Chip height must not grow the header row beyond its current height (the 28px thumbnail chip already
  sets it).
- Keyboard: arrow keys move selection within the `ListBox` (free with `ListBox`); the bar must be
  focusable and show a focus visual.
- Empty state: `HasProfiles` false → bar collapsed, exactly as the ComboBox is today.

## Interfaces / contracts
- `BulkCutViewModel.Profiles` and `SelectedProfile` — **unchanged**, both bindings reused verbatim.
- `HasProfiles`, `HasSelectedProfile`, `ApplyProfileToSelectedCommand`, `ApplyProfileToAllCommand`,
  `SnapshotProfileThumbnailCommand`, `DeleteProfileCommand` — all unchanged.
- `ProfileItemTemplate` — reused; may gain a chip-oriented sibling template rather than being mutated,
  if the popup/save flow still needs the original shape.
- No settings, no persistence, no `CutProfile` model change.

## Acceptance criteria
- [x] Profiles render as a horizontal bar of clickable chips showing each profile's picture at rest.
- [x] The bar scrolls horizontally when profiles exceed the available width; the action buttons beside it
      never move off-screen and are never clipped (**window-relative layout test**, per the T-136/T-141/
      T-156/T-160 clipping class).
- [x] Clicking a chip sets `SelectedProfile`; `⧉ Apply to all` then applies that profile to every ticked
      row exactly as it does today (existing profile-apply tests unchanged and still green).
- [x] The selected chip is distinguishable by **≥2** of border / elevation / weight / colour-role — not a
      tint alone.
- [x] A click **never** applies anything by itself.
- [x] Keyboard selection works and the focused chip is visible.
- [~] **Partly verified.** 14 profiles are laid out in the real view by the layout harness (the cap
      and the apply-button placement are asserted there), and the published build was launched and
      all three tabs rendered — but with **zero** saved profiles, so the bar was collapsed. The
      one-profile, no-picture and scrolling-with-many cases are NOT eyeball-verified. Left unticked
      rather than claimed: this repo has been burned by a criterion ticked from a comment (T-146).

## Edge cases
- Zero profiles → bar hidden (unchanged from today).
- One profile → bar shows one chip, no scrollbar.
- Profile with no thumbnail → placeholder, same as the ComboBox path renders today.
- A profile deleted while selected → selection clears; the action buttons re-gate on
  `HasSelectedProfile` (existing behaviour, must survive).
- Very long profile name → chip truncates with ellipsis rather than widening without bound.

## Risks
- **The profile bar is the original clipping site (T-136).** Replacing its widest control with a
  scrolling one is the right shape, but the surrounding `WrapPanel` must still be verified at 1280px.
- Restyling `ListBoxItem` in a themed app risks inheriting the default selection highlight; the chip
  style must set its own selected visual against the app's tokens.

## Out of scope
Reordering profiles, profile folders/tags, multi-select, double-click-to-apply, and any change to what
the apply actions do. Selection surface only.

## Outcome — 2026-09-05

The ComboBox is a `ListBox` with a horizontal `ItemsPanel`, capped at 420px and scrolling inside that
cap. It reuses **both** original bindings (`Profiles`, `SelectedProfile`), so every apply, thumbnail and
delete command is untouched — the surface moved, the model did not. Selected state uses three
differentiators (accent border · muted-accent fill · an accent bar under the label), with the bar
reserved as `Hidden` at rest and a constant border thickness so moving the selection changes no
measurement.

`SPEC-007 I95–I99`. Suite **956 App + 461 Core = 1417 green in 18s**.

### Both of my first tests were vacuous, and the second one instructively so
Neither caught its mutation on the first attempt.

**The layout test** asserted the bar stayed inside the window. It does — with or without the `MaxWidth`
cap, because the surrounding `WrapPanel` simply wraps the apply buttons onto the next line instead of
letting anything overflow. So the assertion was true for reasons unrelated to the thing it was meant to
pin. It now asserts the **cap itself** (`ActualWidth <= 420` with 14 profiles loaded); removing
`MaxWidth` fails it.

**The selection test** asserted that picking a profile changes no row's cut points — and passed against
a mutation that made selection call `ApplyProfileToAll()`. The reason is worth keeping: `SaveProfile`
already leaves its new profile selected, so the test's `vm.SelectedProfile = …` assigned the value that
was **already there**, `SetProperty` short-circuited, and the mutated code never ran. The test exercised
nothing. It now deselects first and asserts that precondition explicitly, so the same vacuity cannot
return silently.

That is the fifth and sixth vacuous test this session. The pattern in both: the assertion was true, and
true for a reason that had nothing to do with the behaviour under test.

### Deliberately not built
Double-click-to-apply. A chip is a selection; `Apply to all` rewrites every ticked row's cut points, and
a scrolling strip makes a stray click cheap. Cheap to add later if asked, unsafe to assume now.
