## Concept

The keyframe cache lives only in the process and has no size limit (ADR 0009 § Consequences and *Forced follow-ons*,
`0009-two-path-keyframe-scan.md:93, 101-112`). After T-193 the probe cache is the same. So:

- every app restart re-pays each file's scan;
- every *Replace originals* re-pays it, because the mtime changes;
- a very long session grows both caches without bound.

The proposal:
- persist the keyframe list under `%LOCALAPPDATA%\VideoSplitJoiner\` keyed by full path + mtime + length, with an LRU
  limit, and fall back to scanning on any miss or error;
- bound both in-memory caches with an LRU.

## Why later

- After T-194, an MP4/MOV first load costs milliseconds, so persistence only helps MKV, TS and fallback files.
- The first load still pays.
- No memory growth has been measured.
- Tests must never write real app data (the T-140 lesson).

## Trigger

- T-199 is not built and MKV/TS restarts are common.
- Memory growth is measured in a long session.
