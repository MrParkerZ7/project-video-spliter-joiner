## Found

While closing [[T-154]]'s Split/Join half, an adversarial review of the drop path asked what a drop does
*during* a run. Every screen guards **Clear** with `!Operation.IsRunning`
(`SplitViewModel.cs:421`, `JoinViewModel.cs:179`, `BulkCutViewModel.cs:990`) — and **no screen guards
Load or Add with anything at all.**

## What actually happens

Split's `LoadAsync` and `RunSplitAsync` share **one** `OperationViewModel` instance. Both route through
`RunWithResultAsync` → `BeginRun`, whose first two statements are:

```csharp
_cts?.Dispose();
_cts = new CancellationTokenSource();
```

There is no in-flight check. So dropping a video onto Split while a split is exporting:

| # | effect | why it matters |
|---|---|---|
| 1 | **disposes the running split's CTS** | the split still holds that token; `FfmpegRunner`/`FfprobeRunner` call `process.WaitForExitAsync(ct)`, which registers on the token and throws `ObjectDisposedException` on a disposed source |
| 2 | **detaches Cancel** | `Cancel()` cancels `_cts`, which is now the *load's* source — the Cancel button no longer stops the split |
| 3 | **resets the run's own UI** | `Progress` → 0, `StatusText` → "Loading…", `Error` and `ResultSummary` cleared, mid-run |

This is reachable by an ordinary gesture — dropping a second file while the first is still exporting — and
it is a far better candidate for *"works sometimes, doesn't work other times"* than any of the three
extension cases T-154 already closed.

## Design

1. **Refuse the load/add while `Operation.IsRunning`, and say so** — reuse the `DropSummary` surface
   T-154 just added on all three screens ("nothing was added — a split is still running"). Refusing in
   silence would re-create the exact defect T-154 exists to fix.
2. Cover **every door**, not just drop: the tab-strip Load / Add files… buttons and the picker path reach
   the same `LoadAsync`/`AddFilesAsync`.
3. Consider making `BeginRun` itself **defensive** — a second `BeginRun` while `IsRunning` is a
   programming error, and today it silently corrupts rather than failing loudly. A guard there protects
   every current and future caller, not just the three the review happened to check.

## Acceptance criteria
- [x] A drop while an operation is running adds/loads nothing and **explains why** on the screen's
      existing note surface.
- [x] The Load / Add files… buttons and the file picker are guarded identically — one rule, every door.
- [x] Cancel still stops the original operation after such a drop is attempted.
- [x] A test that **fails against today's code**: start a run, attempt a drop, assert the original run's
      token is still live and its Cancel still cancels it.
- [x] Mutation: all four guards mutation-checked; each removal fails a test.

## Out of scope
Queueing the dropped file to load *after* the run finishes. Plausible and possibly nicer, but it is a
feature; this ticket is about not corrupting a run in progress.

## Outcome — 2026-09-04

Closed, with one correction to this ticket's own framing.

### It is Split-only, not all three screens
The ticket says "no screen guards Load or Add with anything", which is true but implies the damage is
three-way. It is not. Checked before building: `Operation.RunWithResultAsync` appears **once** in
`JoinViewModel` (line 480, `RunJoinAsync`) and **once** in `BulkCutViewModel` (line 2137, the batch) —
neither screen's add path touches its `Operation` at all. Only Split has two callers on one instance
(`LoadAsync` 550, `RunSplitAsync` 1062), so only Split can tear its own run down. Join and Bulk were
left alone rather than given a guard against a defect they do not have.

### A second instance of the same bug, through the other door
`CanRunSplit` gated on input path, markers, output dir and selected segments — **everything about the
request and nothing about the operation**. So pressing Run twice re-entered `BeginRun` exactly as the
drop did. `CanClear` has carried `!Operation.IsRunning` since T-047; Run never did. Fixed in the same
change (SPEC-010 I50).

### Three guards, one backstop
- **`AddDroppedFilesAsync`** refuses first, so the reason lands in `DropSummary` — the surface [[T-154]]
  just built. Refusing a drop in silence would have re-created the very defect that ticket exists to fix.
- **`LoadAsync`** refuses for the other two doors (tab-strip Load button, picker), reporting via
  `StatusText`.
- **`CanRunSplit`** disables Run.
- **`BeginRun` throws** on re-entry (SPEC-008 I45). A second run on a live operation is a programming
  error; it used to be an invisible one. The three guards above keep a user gesture from ever reaching
  the throw, so it protects future callers rather than shaping present behaviour.

### The test that had to exist before the fix did
`ParkedSplitEngine` holds a split open inside `SplitAsync` and exposes the token the run is observing —
the only way to watch what a concurrent load does to it. Against the unfixed code all four cases fail;
the decisive assertion is that `Cancel` still cancels **the split** afterwards, because the old failure
was precisely that it cancelled the load's replacement source instead.

### Two mutations survived the first pass, and both were worth the second
- **The `LoadAsync` guard survived.** Every existing test reached the drop path, which is refused one
  step earlier in `AddDroppedFilesAsync` and so never enters `LoadAsync` at all — the button and picker
  doors had no coverage whatsoever. `TheLoadButtonAndPickerAreGuardedToo_NotJustTheDrop` now covers them.
- **The `CanRunSplit` guard survived a misaimed probe.** The edit appended `&& true` to the line *above*
  the new clause, so the guard was never actually removed. Re-run against the real clause, it dies.
  Same lesson the 09-03 run recorded: a surviving mutant is as often a bad probe as a weak test.

All four guards are now mutation-checked. Suite 1408 → **1413 green**.

## Correction — 2026-09-05: the Join door, and a deadlock I introduced

Two things the 09-04 outcome above got wrong, found while landing it.

### `CanRunJoin` had the same hole, and the new throw made it dangerous
The outcome says the defect is Split-only. That is right for the *load-during-run* half — Join's and
Bulk's add paths never touch their `Operation`. It is **wrong for the double-Run half**: `CanRunJoin`
gated on item count, compatibility and output path — everything about the request, nothing about the
operation — exactly as `CanRunSplit` did. Bulk's `CanRunBatch` already carried `!Operation.IsRunning`;
Join did not.

That mattered *because* of this ticket's own backstop. Adding the `BeginRun` throw without closing
Join's door would have converted a silent corruption into an **unhandled exception on a double-click** —
strictly worse for the user, and caused by the fix. `CanRunJoin` now carries the clause, covered by
`JoinAlsoRefusesASecondRunWhileOneIsGoing`.

The general lesson: a guard that turns silent misbehaviour into a throw is only safe once **every**
caller that could reach it has been checked. "Only Split can reach it" was a claim about one of the two
doors, applied to both.

### The Join test deadlocked the whole suite
Its first version was a `void` test that blocked on `engine.Entered.Wait(...)`. The view-model's awaits
are `ConfigureAwait(true)`, so their continuations were posted to the very context the test was
blocking — the run never entered the engine, and the App suite hung indefinitely instead of failing.
It passed in isolation and hung under the full run, which is the worst shape for a test bug to have.
Now `async Task` throughout with `WaitAsync` timeouts, and the file carries a comment saying why.

### Test-runner note, not a code problem
On this machine `dotnet test VideoSplitJoiner.sln` currently hangs at the solution level while each
project passes on its own (App **953** green in 7s, Core **461** in 14s, **1414** total). Verified it
reproduces with `--filter FullyQualifiedName!~LoadDuringRunTests`, i.e. **without** any of this ticket's
tests, so it is the parallel solution runner on this box rather than the change. Per-project runs are
the reliable verification path here.
