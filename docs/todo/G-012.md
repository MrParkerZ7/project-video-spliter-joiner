## Why / vision
Two "it seems broken but it's actually just slow / silent" problems: placing a cut appears to do nothing (it's waiting on the background keyframe index), and running a split gives no visible feedback (looks stuck). Both are responsiveness/feedback gaps — the app must always show it's working.

## Gap from current state (diagnosed, not guessed)
- **Set-cut slowness** — `SplitViewModel.AddCutAt` (src/App/ViewModels/SplitViewModel.cs:535): when `IsIndexingKeyframes && Keyframes.Count == 0`, it calls `AddCutAtWhenIndexedAsync` which **awaits `EnsureKeyframesAsync()` before adding the marker at all**. So on a big file the marker doesn't appear until the whole keyframe scan finishes → feels broken. (A side effect of the T-030 non-blocking-load background index.)
- **Split feedback** — `SplitView.xaml:196` has a `ProgressBar` bound to `Operation.Progress`, visible while `Operation.IsRunning`. But for a `-c copy` split the ffmpeg `time=` progress may be sparse/instant (segment muxer) so the bar doesn't visibly move, or on a large file it isn't clearly conveying "working" — the user reads it as "nothing happens."

## Decisions
- **D1 · Optimistic marker** — `AddCutAt` should add the marker IMMEDIATELY at the requested position (snapped = requested, delta 0, a "snapping…" / pending flag), then RESOLVE the real snapped time when the keyframe index arrives (update the marker's Snapped/Delta in place). Never defer the visible add. The eventual split still uses the true keyframe snap.
- **D2 · Visible split/join progress** — verify `IProgress<double>` flows from `RunSplitAsync`/join through the engine to `Operation.Progress`; make the progress bar clearly show + move. Where ffmpeg can't give granular `-c copy` progress, fall back to an **indeterminate** progress bar + a **"Splitting… (segment N/M)"** / "Working…" status so it's unmistakably active. Keep the operation off the UI thread (it already is) and ensure progress marshals to the UI.
- **D3 · Keep the seam** — changes live in `SplitViewModel`/`CutMarkerViewModel` (optimistic snap) + the operation/progress surface + XAML; split/join engine contracts unchanged; VM stays fake-testable.

## Risks
- Optimistic marker then re-snap → the displayed position "jumps" from requested to snapped when the index lands; make that read as a resolve ("snapping…" → final), not a glitch. Dedupe must still work on the final snapped time.
- Indeterminate progress must still end/clear correctly on success/fail/cancel.

## Out of scope
