## Why / vision
The preview player is locked to a small fixed area (`MaxHeight=320`), so you can't make the video bigger to actually watch/scrub it, nor shrink it to see more of the marker list. Users expect to drag the boundary to size the video to taste. Small change, everyday quality-of-life.

## Gap from current state
`SplitView.xaml` hosts `PlayerView` in a fixed row with `MaxHeight="320"`; the video area is not user-resizable. No `GridSplitter`. Need a draggable splitter + a resizable player row (min + default), FFME video scaling to fit.

## Decisions
- **D1 · `GridSplitter`** between the player pane and the content below it in `SplitView`. Player row becomes user-resizable (star-sized with a `MinHeight`), remove the `MaxHeight="320"` cap.
- **D2 · FFME scales to fit** — the `<ffme:MediaElement Stretch="Uniform">` already scales without distortion; the downscaled-preview (T-024) is unaffected (it caps decode/render resolution, independent of the display area).
- **D3 · Lean goal** — one build task; docs fold into the pending finalization docs pass (T-026), not a separate closer.

## Plan
```
T-027 resizable player pane (GridSplitter + relax cap + min/default)  → docs via pending T-026
```

## Risks
- Layout regressions (marker list / timeline / run controls must stay reachable at any player size) → set a MinHeight on the player row + keep the lower content in a scrollable/star region.
- GridSplitter + FFME native surface interaction → verify live via app-run (video keeps rendering while resizing).

## Out of scope
Persisting the chosen size across sessions, pop-out/full-screen video, resizing the Join screen — later if wanted.
