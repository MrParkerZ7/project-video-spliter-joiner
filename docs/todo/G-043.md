## Why

User, after importing a batch: *"bulk cut is not proceed able to cut after import multiple video to cut"*
and *"bulk cut should have select all/dis select all for item list"*.

Both land on the same piece of code: `BulkItemViewModel.IsEnabled` is doing two different jobs at once.

```csharp
private bool _isEnabledByUser = true;
public bool IsEnabled
{
    get => _isEnabledByUser && !IsAutoDisabled;     // user intent AND computed eligibility
    set { if (_isEnabledByUser != value) { _isEnabledByUser = value; OnPropertyChanged(); } }
}
private bool IsAutoDisabled => _loadFailed || (KeyframesReady && (IsNoOpTrim || !IsValidCut));
```

and the row checkbox is bound straight to it, two-way:

```xml
<!-- BulkCutView.xaml:641 -->
IsChecked="{Binding IsEnabled, Mode=TwoWay}"
```

A freshly imported row has intro = 0 and no outro, so `IsNoOpTrim` is true, so `IsAutoDisabled` is true,
so the getter returns **false for every row** even though `_isEnabledByUser` is `true` for every row.
The list comes up looking entirely unticked, and the setter cannot fix it: clicking a box passes
`value = true`, which equals the existing `_isEnabledByUser`, so the guard short-circuits, no
`PropertyChanged` is raised, and the getter still answers false. The user's click cannot move the
property in the direction they want — it can only ever turn a row OFF.

The codebase already knows the two concepts need separating — `IsCheckedByUser` exists internally for
exactly this reason (SPEC-011 I56: `ApplyProfileToAll` deliberately reads the raw intent, not the
computed value). This goal finishes that separation at the UI boundary.

## Out of scope

The auto-exclusion RULES themselves — a load-failed row and a genuine no-op trim should still be excluded
from the batch. This is about making the intent and the exclusion two visible, separable things.
