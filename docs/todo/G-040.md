## Why / vision
Two rough edges the user hit: (1) selecting a Bulk row is "extremely slow, sometimes doesn't work" — because every
selection synchronously opens that video in the shared FFME preview player (heavy decode init, and rapid selection thrashes
the element); (2) the apply-to-all button is hard to find after the recent regroup + the added thumbnail columns.

## Plan
```
T-115  Fix slow row selection — DEBOUNCE + defer the SelectedItem→preview-open (highlight instant, preview settles)   [M] ← proceedable now
T-116  Apply-to-all discoverability — make the per-row ⧉ + profile apply-to-all clearly findable/labelled in both modes [S] ← proceedable now
  └─ T-117  Docs + spec update: SPEC-011 (deferred/debounced preview-open invariant; apply-to-all affordance note)      [S]  (needs T-115 + T-116)
```
T-115 (the urgent perf bug) and T-116 (UX) are independent; T-117 docs after.

## Root causes (grounded 2026-08-23)
- **Selection lag:** `BulkCutViewModel.SelectedItem` setter → `OpenOrUnloadSelected(value)` → `Player.Open(item.Path)`
  (`BulkCutViewModel.cs:559`), **no debounce** — one FFME open per selection; rapid selection queues opens via
  `MediaReopenGuard` and thrashes the element.
- **Apply-to-all:** present but compact — per-row **⧉** (row template col 6, `BulkCutView.xaml:713`, binds
  `ApplyToAllCommand`) + profile **⧉ all** (`:260`, `ApplyProfileToAllCommand`). Discoverability, not a missing button.

## Out of scope
Rearchitecting the preview player; removing select→preview (keep it, just debounced); new apply behaviors; Split/Join.
