## Concept
Make 4K (3840x2160) preview smooth and confirm 4K split stays near-instant. The cut is stream-copy (resolution-independent — no decode), so the real cost is the PREVIEW decode; the secondary cost is the keyframe scan on very large files.

## Design
- **Measure first** (generate a real 4K fixture with ffmpeg — e.g. `testsrc2=size=3840x2160:rate=30:d=15 -c:v libx264 -g 60`). Profile: FFME preview CPU/frame-drops, keyframe-scan time, split time.
- **Preview smoothness (D2):**
  - Enable FFME **hardware-accelerated decoding** where available (D3D11VA/DXVA2) via FFME's renderer/decoder options (e.g. `MediaElement.RendererOptions` / `Media.Options` in `MediaInitializing`/`MediaOpening` — check the FFME beta API for the HW-decoder hook, e.g. `VideoHardwareDecoders` or `EnableHardwareAcceleration`).
  - **Fallback / complement:** cap the preview render cost — decode/scale the preview to roughly the view size (a 4K source rendered into a ~720–1080p preview surface) so the UI thread isn't saturated. FFME can be told a target size / the video is scaled to the control. Never upscale the SOURCE — this only affects the on-screen preview, never the cut.
  - Consider lowering the `PositionChanged`/render cadence if it floods the UI thread.
- **Split/scan (D3):** confirm `SplitEngine` 4K split time ≈ small-file time (copy). If `MediaProbe.GetKeyframesAsync` stalls on a large 4K file, ensure it streams ffprobe output (doesn't buffer all frames) + the cache works. Optimize only if measured slow.

## Detail
- The HW-decode + downscale settings live in the FFME impl (`FfmeMediaPlayer`) / `PlayerView`, applied at open time. Keep behind the `IMediaPlayer` seam (no VM change).
- Record the before/after numbers in the report (fps/drops or a qualitative "smooth vs choppy" from the live app-run + the scan/split timings).
- Graceful: if HW decode init fails on a machine, fall back to SW + downscale automatically (don't crash / don't blank the preview).

## Interfaces / contracts
- No public contract change (`IMediaPlayer` unchanged). Internal FFME options only.

## Acceptance criteria + Case-Coverage Matrix
- [ ] A 4K fixture plays in the preview without obvious choppiness (verified live via app-run; report the setting used).
- [ ] HW decode enabled when available, with an automatic SW+downscale fallback (no crash if HW unavailable).
- [ ] 4K split time is within ~2x of a 1080p split of similar length (copy — should be near-identical); keyframe scan on the 4K fixture completes promptly (report the time).
- [ ] Build 0-warning; existing tests (post T-023) stay green. Any pure logic added (e.g. a downscale-size calc) is unit-tested.
- Matrix — Required-Success: 4K plays smooth + splits fast. Required-Fail: HW-decode unavailable → SW+downscale fallback, still plays. Boundary: very large 4K file keyframe scan doesn't hang; a non-4K file still plays (no regression).

## Dependencies

## Risks
FFME beta HW-decode API/GPU variance → the downscale fallback is the reliable floor. Live-verify via app-run; some tuning may need the user's actual 4K file.

## Out of scope
