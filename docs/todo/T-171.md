## Concept

A remembered checkbox in the Bulk Cut footer, beside *Replace originals*, that empties the row list once a
batch finishes cleanly — without taking the run's report down with it.

## Design

**1. Where it goes.** The `FooterOptions` WrapPanel (`BulkCutView.xaml:1202`), which already holds
*Replace originals* (`:1257`), *Auto-delete originals* (`:1269`) and *and empty bin* (`:1280`). T-160 put
the destructive three together at the end of that row deliberately (SPEC-011 I152/I154: order is the
mechanism inside a `WrapPanel`). **Auto-clear is not destructive** — it discards screen state, not files —
so it should sit with the ordinary options and NOT inside the red group, or the red vocabulary stops
meaning "this touches your files".

**2. When it fires.** Immediately after `RunAutoDeleteIfArmed()`
(`BulkCutViewModel.cs:2195`), never before: auto-delete acts on the rows, so clearing first would silently
disarm it. Gate it exactly as auto-delete is gated (`:932`) — `BatchState == BulkBatchState.Completed`
only. Clearing after a partly-failed batch would drop `LastFailedItems`, which is the only record of which
rows failed.

**3. ❗ The report must survive.** `Clear()` (`:1232`) also does `Operation.Reset()`,
`BatchState = Idle` and `LastFailedItems = Array.Empty<…>()`. Calling it verbatim erases the summary the
batch just produced. Two shapes to weigh:
   - a **row-only clear** — factor the row-dropping half of `Clear()` out and call that, leaving
     `Operation` and its `ResultSummary` alone; or
   - **capture and restore** — snapshot the summary, `Clear()`, put it back.
   The first is cleaner and keeps one meaning per method; the second is smaller but leaves `Clear()`
   meaning two things depending on caller. Prefer the first unless it drags in more than it saves.

**4. ⚠ The `CanClear` timing trap.** `CanClear` is `Items.Count > 0 && !Operation.IsRunning`
(`:975`), and `Clear()` returns silently when it is false. At `:2195` the awaited run has completed, so
`IsRunning` *should* be false — **verify it, do not assume it**. If it is still true the feature is inert
and every unit test that drives the VM directly would still pass. That is the T-162 shape exactly: a
feature that works in tests and does nothing in the app.

**5. Persistence.** A new nullable `bool? BulkAutoClearAfterRun` on `AppSettings`, following
`BulkAutoDeleteOriginals` (`AppSettings.cs:186`, DTO round-trip at `:386` and `:542`): absent → null → OFF.
Off by default — a first run must not make the list vanish before the user knows the option exists.

## Acceptance criteria
- [ ] A clean batch with the box ticked leaves the list empty.
- [ ] **The run's report is still on screen after the auto-clear** — the aggregate summary and the
      Recycle-Bin line survive. Mutation: reuse `Clear()` verbatim → this test fails.
- [ ] A batch that ends `CompletedWithFailures` or `Cancelled` does NOT clear, and `LastFailedItems`
      survives so the failed rows are still listed.
- [ ] Ordering: with auto-delete also armed, the originals are deleted and THEN the list clears.
      Mutation: clear before deleting → the delete finds no rows and the test fails.
- [ ] The setting round-trips and defaults OFF when the key is absent.
- [ ] Whatever the `decision:` settles is asserted, including the case it rules out.
- [ ] A composition-root style check that the hook is actually reached in the shipped path, not only in a
      VM test — see the `CanClear` trap above.

## Risks
- SPEC-011's invariant count moves, so `docs/specs/_index.md` must change in the same commit or three
  guards go red. SPEC-009 gains the persistence invariant.
- The footer gained a row in T-168/T-160 for crowding reasons; one more checkbox is cheap, but re-check
  the 760x620 layout tests rather than assuming (`BulkCutViewLayoutTests`).

## Out of scope
Mirroring onto Split/Join, and any change to what `Clear all` does when pressed by hand.
