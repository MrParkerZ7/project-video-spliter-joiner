## Concept

A remembered checkbox in the Bulk Cut footer, beside *Replace originals*, that empties the row list once a
batch finishes cleanly — without taking the run's report down with it.

## Design

**1. Where it goes.** The `FooterOptions` WrapPanel (`BulkCutView.xaml:1202`), which already holds
*Replace originals* (`:1257`), *Auto-delete originals* (`:1269`) and *and empty bin* (`:1280`). T-160 put
the destructive three together at the end of that row deliberately (SPEC-011 I152/I154: order is the
mechanism inside a `WrapPanel`). **Auto-clear is not destructive** — it discards screen state, not files —
so it should sit with the ordinary options and NOT inside the red group, or the red vocabulary stops
meaning "this touches your files".

**2. When it fires.** Immediately after `RunAutoDeleteIfArmed()`
(`BulkCutViewModel.cs:2195`), never before: auto-delete acts on the rows, so clearing first would silently
disarm it. Gate it exactly as auto-delete is gated (`:932`) — `BatchState == BulkBatchState.Completed`
only. Clearing after a partly-failed batch would drop `LastFailedItems`, which is the only record of which
rows failed.

**3. ❗ The report must survive.** `Clear()` (`:1232`) also does `Operation.Reset()`,
`BatchState = Idle` and `LastFailedItems = Array.Empty<…>()`. Calling it verbatim erases the summary the
batch just produced. Two shapes to weigh:
   - a **row-only clear** — factor the row-dropping half of `Clear()` out and call that, leaving
     `Operation` and its `ResultSummary` alone; or
   - **capture and restore** — snapshot the summary, `Clear()`, put it back.
   The first is cleaner and keeps one meaning per method; the second is smaller but leaves `Clear()`
   meaning two things depending on caller. Prefer the first unless it drags in more than it saves.

**4. ⚠ The `CanClear` timing trap.** `CanClear` is `Items.Count > 0 && !Operation.IsRunning`
(`:975`), and `Clear()` returns silently when it is false. At `:2195` the awaited run has completed, so
`IsRunning` *should* be false — **verify it, do not assume it**. If it is still true the feature is inert
and every unit test that drives the VM directly would still pass. That is the T-162 shape exactly: a
feature that works in tests and does nothing in the app.

**5. Persistence.** A new nullable `bool? BulkAutoClearAfterRun` on `AppSettings`, following
`BulkAutoDeleteOriginals` (`AppSettings.cs:186`, DTO round-trip at `:386` and `:542`): absent → null → OFF.
Off by default — a first run must not make the list vanish before the user knows the option exists.

## Decisions (answered)

### Auto-clear when originals are still left to delete — answered 2026-09-18 (`todo-next-all`, Recommended taken)

**Original fork (archived):**
> Auto-delete is OFF and rows still have deletable originals — what should auto-clear do? (a) clear anyway, the user opted in; (b) skip the clear and say why, so the manual Delete originals button survives; (c) gate the checkbox on AutoDeleteOriginals the way `and empty bin` already is (CanAutoEmptyRecycleBin, BulkCutViewModel.cs:900).

**Chosen: (b) — skip the clear and say why.** After a clean batch (and after auto-delete, when armed), the list is
cleared only if **no row still has an original the user could delete by hand** (`DeletableOriginalCount == 0`).
Otherwise the rows stay, and the batch's own summary gains one line naming how many originals are left, so the
✕ *Delete originals* button — which needs the rows — is still there to press.

Taken under the owner's standing rule (a typed command is consent; a fork with a sound recommendation is decided,
logged and built, not parked), because the grounding leaves one sound answer:

- **G-055's own success criterion 3 decides against (a).** *"Nothing the user could still have done is silently
  taken away: if originals were left to delete by hand, auto-clear does not remove that chance without saying
  so."* Clearing anyway removes exactly that chance, silently.
- **(c) would switch the feature off where it was asked for.** The request was a box *"near by `replace
  originals`"*. Under Replace originals there is never an original left to delete — `DeletableOriginals()` skips a
  row whose output IS its original (`BulkCutViewModel.cs:725`) — so auto-clear is safe there with or without
  auto-delete. Gating it on `AutoDeleteOriginals` would make the user arm a destructive option that does nothing in
  that mode just to get a harmless one, and it ties a non-destructive control to the red group the ticket's § Design
  point 1 keeps it out of.
- **(b) is the only option that is correct in every mode:** Replace originals → always clears; auto-delete on and
  everything binned → clears; auto-delete on but a file refused (*"Still in use: …"*) → keeps the rows and says so,
  which is also when the user most needs them; new-file mode with auto-delete off → keeps the rows and says so.

**Rejected:** (a) *clear anyway* — silent loss of the manual delete, against G-055 criterion 3. (c) *gate on
auto-delete* — disables the feature in Replace-originals mode, where it is both wanted and safe, and couples a
harmless option to a destructive one.

**Refined 2026-09-18, after the build's adversarial review — per row, not whole list.** The review (five lenses, every
finding put to two refuters) showed a whole-list rule both over- and under-reaches: it wiped rows that were never in
the run and rows whose only record of an exact-cut fallback was their warning, yet it also kept every clean row when a
single original was refused. So the rule became: **take out the rows this run finished cleanly; keep every row the user
could still act on** — a row not in the run, a row whose original is still deletable (the recorded (b)), and a row the
run warned about — and say how many were kept and why. This is (b) applied row by row: stricter about what stays, with
the same reason for keeping it.

## Acceptance criteria
- [x] A clean batch with the box ticked leaves the list empty.
- [x] **The run's report is still on screen after the auto-clear** — the aggregate summary and the
      Recycle-Bin line survive. Mutation: reuse `Clear()` verbatim → this test fails.
- [x] A batch that ends `CompletedWithFailures` or `Cancelled` does NOT clear, and `LastFailedItems`
      survives so the failed rows are still listed.
- [x] Ordering: with auto-delete also armed, the originals are deleted and THEN the list clears.
      Mutation: clear before deleting → the delete finds no rows and the test fails.
- [x] The setting round-trips and defaults OFF when the key is absent.
- [x] Whatever the `decision:` settles is asserted, including the case it rules out.
- [x] A composition-root style check that the hook is actually reached in the shipped path, not only in a
      VM test — see the `CanClear` trap above.
