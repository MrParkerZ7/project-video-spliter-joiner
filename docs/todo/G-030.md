## Why / vision
Like YouTube's scrubber: hovering the timing bar should show a mini frame of the video at that point, so the user can find the right split point by sight without seeking the main player.

## Grounding (2026-07-19)
- **No thumbnail/frame-extract code exists** — new. `FfmpegRunner.RunAsync(FfmpegArgs, ...)` runs ffmpeg but reads **stdout as a UTF-8 string** → piping binary image bytes through stdout is out; extract frames to **temp files** and load those. `FfmpegArgs` has `ForFfmpeg()`/`Input`/`Output`/`Raw` — enough to build `-ss T -i in -frames:v 1 -vf scale=W:-1 out.jpg`.
- The main preview is FFME-decoded and separate — thumbnails must use the ffmpeg CLI (own process), NOT FFME, so they don't fight the player.
- `PlayerView.xaml` `ScrubSlider` is the hover surface (46-wide caption aside; the slider spans the width). The existing scrub logic already models coalescing (one in-flight seek, latest target wins, throttle+deadband) — mirror that for thumbnail requests.
- Temp/cleanup convention: disposable files use the `🚫` prefix / `clean` command; logs live under `%LOCALAPPDATA%/VideoSplitJoiner/`.

## Decisions
- **D1 · On-demand frame grab to a temp file** — a Core `IThumbnailService` extracts one frame at a time `T` via ffmpeg: `-ss <T> -i <input> -frames:v 1 -vf scale=<W>:-1 -y <temp.jpg>` with **fast seek** (`-ss` before `-i`, keyframe-accurate — fine, matches the keyframe-snap philosophy). Width capped ~160px. Returns the temp path (or null on failure — best-effort, never throws). (Sprite-sheet/storyboard pre-gen = future optimization, not v1.)
- **D2 · Debounce + coalesce + cache (the crux)** — hovering must not flood ffmpeg. (a) **Debounce** the hover (~60ms settle) before requesting. (b) **Coalesce**: at most ONE extraction in flight; the latest hovered time wins, intermediate requests dropped (mirror the scrub `_pendingScrubTarget` pattern). (c) **Cache** by time-bucket (round T to ~1s or nearest keyframe) → repeat hovers reuse the file; cap the cache (LRU/size). (d) **Cancel** stale requests.
- **D3 · App hover UI** — on `ScrubSlider` `MouseMove`, compute hovered time = `mouseX / trackWidth * duration`; show a WPF `Popup` above the bar at the cursor X with the `Image` + a `mm:ss` time label; hide on `MouseLeave`. A WPF-free VM (extend `PlayerViewModel` or a new `ThumbnailPreviewViewModel`) exposes `HoverTime`, `HoverThumbnailSource`/path, `IsThumbnailVisible`, `HoverOffsetX`. Load the temp jpg into a **frozen** `BitmapImage` (cross-thread safe).
- **D4 · Cleanup** — temp thumbnails in a dedicated cache dir (e.g. `%LOCALAPPDATA%/VideoSplitJoiner/thumb-cache/<file-key>/`), cleared on new load / Clear / `Unload()` and swept by `session-end`/`clean`. Never leak the temp dir.
- **D5 · Best-effort** — a failed/slow grab shows nothing (or a subtle placeholder), never blocks the UI thread or crashes. Extraction is async + cancellable off the UI thread.

## Risks
- **Performance** — the whole point of D2; without debounce/coalesce/cache, hovering spawns dozens of ffmpeg procs. Verify a hover-sweep issues few processes and the UI stays smooth.
- **Binary output** — the runner reads stdout as text, so use temp files (D1), don't pipe image bytes.
- **Cross-thread ImageSource** — build + `Freeze()` the BitmapImage off-thread before binding.
- **Cleanup leaks** — ensure the temp cache dir is cleared on load/clear/unload + session-end.
- Don't fight the FFME preview (separate ffmpeg CLI) or regress the scrub/seek behavior (G-028).

## Out of scope
