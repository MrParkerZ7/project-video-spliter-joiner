## Why / vision

The user asked: *"bulk cut before we could apply profile cut able, doesn't it require to be snapping first?"*

Today it does, but not because anything needs it. Drop 20 episodes, apply a profile while 17 are still
scanning keyframes, and the app says `Applied to 3 row(s).` The other 17 are silently untouched, the Apply
buttons were enabled the whole time, and the user has to notice, wait, and apply again.

All three copy paths write **requested** times computed from the row's `Duration`. Only the run needs the
**snapped** time, and it already waits for the scan on its own. The skip came in with the first
`ApplyToAll` (T-096) and was never decided.

**What done buys:**
- Apply a profile as soon as the files have loaded, without waiting for every keyframe scan to finish.
- See which rows are still waiting for their scan.
- Never re-apply to them.

Rows still loading at the click are skipped and counted (§ Out of scope). Designed and sealed as [[D-005]].

## Decisions (2026-09-13, after the review panel)

The five-lens review surfaced three forks D-005 had not seen. The user answered each:

1. **Thumbnails under Exact cut → show the real cut frame.** The chip grabs at the time the run will cut:
   - Lossless waits for the snap;
   - Exact grabs at the requested time right away;
   - a precision flip re-grabs.

   This also fixes today's chip, which under Exact shows the nearest keyframe instead of the cut. *Rejected:*
   "wait in both modes" (a placeholder for Exact users during every scan, and still the wrong frame afterwards);
   "gate Lossless only" (Exact keeps the wrong frame after the scan). → [[T-174]]
2. **The older Exact-cut bug → its own ticket in this epic.** Rows added after the toggle, and outro handles added
   later, ignore Exact. It predates D-005, so it does not ride inside T-173. *Rejected:* keep it folded into
   T-173; a separate goal. → [[T-176]]
3. **Rows certain to be invalid but still scanning → count them, and say when they turn red.** The wording is
   `K invalid (red when their scan finishes)`. *Rejected:* mark the row now (more UI change inside T-173); fold
   them into "waiting" (the line would under-report a certain failure). → [[T-173]]

## Risks

- **Visible behaviour change.** An apply now changes rows that are still scanning, and many rows can read
  `→ snapping…` at once. Intended — and the apply line now says so.
- **Borderline rows turn red after the snap.** Before its scan lands, a row is called invalid only when its
  outro handle is at or before its intro. Everything else is reported as waiting for its scan, and may turn red
  once the scan lands: the snap moves a handle, or a long GOP lifts `MinKeptSpan`. So a late surprise always runs
  waiting → red, never invalid → ready. The row chip shows it; the apply line is a snapshot of the click and is
  not re-issued (D-005 OQ3).
- **Rows dropped under Exact change verdict** ([[T-176]]). A coarse-GOP row that was excluded as "nothing to
  trim" becomes eligible and runs, which is what Exact already does for rows that were in the list.
- **A latent trap is pinned, not fixed.** A future `CancelScan` on a row that stays in the list would leave its
  handles pending on a `KeyframesReady` row. Unreachable today — only Remove `:1218` and Clear `:1246` call it.
  T-173 records it as I157 and enforces it with a source-assert test.

## Out of scope

- Letting the run cut without keyframes — the snapped cut is the product; `-c copy` needs keyframes.
- Scanning the selected row first, or any scan prioritisation.
- Disabling the Apply buttons during scans — they stay enabled; that is the point.
- Split-tab markers (SPEC-010 owns their pending path).
- Persisting the precision choice.
- **Accepted limitation — set-at-playhead fan-out from an unprobed selected row** (as in [[T-173]] § Out of
  scope). `CanSetCutAtPlayhead` needs only a selection and a ready player (`BulkCutViewModel.cs:985`), and a
  row is selectable before its probe returns (`Items.Add` `:1151` runs before `PopulateAsync` `:1168`). With
  apply-to-all-rows on, the gesture writes the selected row, but `ApplyToAll` returns null for a source with
  no `Duration` (`:1490`). No checked row is reached, even one whose duration is known, and no apply line is
  written, so the previous one stays up (`ApplyToAllReport` is assigned only at `:1536`).
- **Accepted limitation — ⧉ apply-to-all from an unprobed source** (as in [[T-173]] § Out of scope). The
  command is enabled whenever there are two or more rows (`:262`), so ⧉ on an unprobed row is a silent no-op
  for the same reason: null at `:1490`, no apply line written.
- **The profile auto-thumbnail on save** (`SaveProfileWithAutoThumbnailAsync`, `BulkCutViewModel.cs:1602-1604`)
  still grabs at `IntroEnd.Snapped`. For a snap-pending handle that equals `Requested`, the time the profile
  stores (`CutProfileApplier.cs:94`). For a ready row under Exact it is the keyframe frame — an older mismatch,
  left unchanged here ([[T-174]] § Out of scope).
