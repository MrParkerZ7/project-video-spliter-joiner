## Why / vision
Reported: split one video → Clear → drag a new video → **the app just closes itself** (no dialog, no log). A silent process exit = an unhandled exception the app never catches. It's both a specific bug in the load-after-clear path AND a missing safety net (the app should never die silently).

## Grounding (2026-07-19 — root-cause direction found)
- **No global crash handler exists** — grep found NO `DispatcherUnhandledException`, `AppDomain.CurrentDomain.UnhandledException`, or `TaskScheduler.UnobservedTaskException` in `src/App`. So an unhandled exception on the UI dispatcher, a background task, or FFME silently kills the process. This is why there's no dialog/log AND why a possibly-recoverable error is fatal.
- **The trigger path:** `SplitViewModel.Clear()` (`:1038`) cancels+disposes `_keyframeIndexCts`, sets it null, and calls `Player.Unload()` → `FfmeMediaPlayer.Unload()` → `_element.Close()`. A new drag → `LoadAsync` → `Player.Open(path)` → `_element.Open(new Uri(...))`. **FFME Open-after-Close** is a known native-crash spot; and background continuations from video #1 (keyframe `ResolvePendingMarkerAsync`, thumbnail grabs) can fault AFTER teardown if a staleness guard is missing → unobserved background exception → silent death.
- The thumbnail service (G-030, new) also participates: Clear → `Thumbnail.Clear`, new load → `SetInput`; a grab resolving against torn-down state is a suspect.

## Decisions
- **D1 · Add a global crash safety net FIRST (also the diagnostic).** In `App.xaml.cs` wire: `DispatcherUnhandledException` (log full exception via the existing `ErrorLogWriter` to `%LOCALAPPDATA%/VideoSplitJoiner/logs/`, show a friendly copyable message, set `e.Handled = true` so a recoverable UI error doesn't kill the app); `AppDomain.CurrentDomain.UnhandledException` (log — last-ditch, can't recover); `TaskScheduler.UnobservedTaskException` (log + `SetObserved()` so a faulted background task never tears down the process). This both **captures the crash** for T-080 and **stops silent death** permanently.
- **D2 · Reproduce + fix the true root cause.** With D1's log, reproduce split→Clear→load-new, read the captured exception + stack, and fix at the true layer. Likely candidates (confirm, don't guess): (a) FFME `Open` after `Close` lifecycle (may need to reset/guard the element or sequence Close→Open safely); (b) a stale keyframe/thumbnail background task from video #1 faulting post-Clear (add/repair a staleness guard); (c) the thumbnail service touching disposed state. Fix the one the log points to.
- **D3 · Don't mask with the catch-all.** The global handler is a safety net, not the fix — D2 must remove the actual fault. Keep `e.Handled` only for genuinely-recoverable UI exceptions; a corrupted-state/native crash still logs + exits.

## Plan

## Risks
- Native (AccessViolation/corrupted-state) crashes aren't caught by managed handlers by default — if the log shows a native FFME fault, the fix is lifecycle-side (D2a), and the handler may need `[HandleProcessCorruptedStateExceptions]`/`legacyCorruptedStateExceptionsPolicy` only to LOG it.
- Reproduction needs a real app-run with a real video (headless can't). D1's log makes it diagnosable even from the user's machine.
- Don't let the global handler swallow real bugs (D3) — it logs everything; only recoverable UI errors are `Handled`.

## Out of scope
A crash-reporting/telemetry service; retry-load UX beyond not-crashing. This makes the app survive + fixes the specific load-after-clear fault.
