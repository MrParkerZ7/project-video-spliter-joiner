## Why / vision
G-017 themed the app dark+gold, but the OS title bar is still the default light chrome — a jarring bright strip above a dark app. A custom themed title bar completes the redesign.

## Gap from current state
`MainWindow.xaml` uses the standard WPF window chrome (native title bar, light in a light OS theme). No `WindowChrome`, no custom caption.

## Decisions
- **D1 · Custom title bar via `WindowChrome`** (WPF) — keep the window resizable/system behavior but replace the caption with a themed one: `WindowChrome` with a ~34–36px `CaptionHeight`, `ResizeBorderThickness` for edge resize, `GlassFrameThickness=0`. A top row (token `SurfaceBrush`/`BgBrush`) with the app title (gold accent) on the left + custom min/max-restore/close buttons on the right (`WindowChrome.IsHitTestVisibleInChrome=True` so they click; the rest of the bar drags).
- **D2 · Themed caption buttons** — styled to the tokens (dark, gold hover; close = red/`DangerBrush` hover), wired to `SystemCommands` (Minimize/Maximize/Restore/Close) or `WindowState`. The max button toggles its glyph (□/❐) with state.
- **D3 · Correct window behavior** — handle the classic WindowChrome gotchas: maximize must NOT cover the taskbar (WM_GETMINMAXINFO / work-area clamp, or the modern `WindowChrome` + `SingleBorderWindow` combo that handles it), a small maximized-state content margin, working resize on all edges, and Aero snap. Verify the app still opens, drags, resizes, maximizes/restores, closes.

## Risks
- WindowChrome maximize-covers-taskbar + resize-grip edge cases are the classic pitfalls → handle WM_GETMINMAXINFO / clamp to work area; test maximize/restore. If custom chrome proves too edge-casey, the safe fallback is a **dark native title bar** via DWM immersive-dark-mode (`DwmSetWindowAttribute` attr 20) — note it as the fallback, but aim for the custom themed bar.
- Per-monitor DPI + multi-monitor maximize.

## Out of scope
Custom window animations, a mica/acrylic backdrop, a fully frameless design — later.
