## Found

While [[T-172]] bounded the backup size of a 640px picture, the base64 budget came out short by several thousand
bytes. The cause is `ProfileBackup.Options` (`src/App/Settings/ProfileBackup.cs:35-39`): it sets only
`WriteIndented` and `DefaultIgnoreCondition`, so the default encoder escapes HTML-sensitive characters, and `+` is
one of them. Every `+` in an inline picture's base64 becomes `\u002B` — 6 bytes instead of 1. Measured on one
640px picture: 31,418 bytes of backup; T-172's test now counts the escapes into its budget.

## Why it is only a decision

The file is valid JSON, it reads back byte-exact (SPEC-007 I91), and at 640px an 11-profile backup is ~0.23–1.1MB
either way. Changing the encoder changes the bytes of every future backup, and it would also write non-ASCII
profile names as raw UTF-8 — arguably better for a user reading the file, but a visible format change. Worth
deciding on purpose rather than folding into an unrelated ticket.

## Acceptance criteria (if (b) is chosen)
- [ ] `ProfileBackup` writes with a relaxed encoder; a backup contains no `\u002B`.
- [ ] A backup written by the previous version (escaped) still plans and restores byte-exact — a test with a
      checked-in escaped sample.
- [ ] The T-172 size test's budget drops the escape allowance, and SPEC-007 I81 notes the encoding.
