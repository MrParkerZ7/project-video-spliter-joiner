## Concept

The card is where a profile is recognised before it is chosen (SPEC-007 I95/I101). It squeezes every
picture into 320 DIPs, so a 640px picture shows at half its size on this machine's 100% display, and it
answers *"where does this profile cut?"* with one small muted line. Show the picture at its own size, and
state the cut points in words.

**Priority high** (the two earlier rounds on this card were medium): this is the third request, and the
readout is visible on every card the day it ships.

## Design

### 1. The picture box follows the picture's width, between a minimum and a cap

`W = clamp(PixelWidth / scale, Min, Max)` DIPs, `H = W × 9/16`, with `Image Stretch="Uniform"` inside
(unchanged, so nothing is ever cropped).

- **`Min`** = the existing resource `ProfilePreviewCardWidth` (**320**), kept under its name and now
  meaning *minimum*. A narrower picture still fills a 320 box and still shows the low-resolution note
  (I109, unchanged).
- **`Max`** = new resource `ProfilePreviewCardMaxWidth` (**640**), pinned by a test to
  `BulkCutViewModel.ProfileThumbnailWidth`, so a stored capture shows pixel-exact at 100% and the two
  cannot drift.
- **`PixelWidth`** comes from the loaded bitmap (the same `Source` the note already reads), never from
  its DPI-derived `Width` (I109).
- **`scale`** is the horizontal display scale of the card's visual. The app has no `app.manifest` and is
  not per-monitor DPI aware, so this is the system scale, fixed for the life of the process. The card
  therefore never renders at one size and then jumps. If the scale cannot be read, use `1.0`.
- **The 16:9 box** is kept at every width (decision on G-058). Every capture is a frame of a 16:9 video,
  and all 13 profiles' pictures are 16:9. A fixed shape stops a non-16:9 upload from producing a tall
  strip of a card, and such a picture still shows whole (a 640x480 picture draws at 480x360, centred in a
  640x360 box).
- The **text column** is `W` wide, so the name and readout wrap at the box width. With no picture the box
  collapses and the column is `Min` wide.
- The **box's `Visibility`** binds to `CardImage.Source` by `ElementName` (null → collapsed), as the note
  already does. It no longer binds to `ThumbnailPath`, so a path whose file is missing or fails to decode
  collapses the box instead of showing an empty frame.
- The `ToolTip` style's **`MaxWidth`** goes from 360 to **650** (640 + 2×4 padding + 2×1 border), so a
  640 box is never clipped by the tooltip chrome.

### 2. The cut readout: two labelled lines at body size

| profile | Intro value | Outro value |
|---|---|---|
| intro 32 s, no outro | `cuts at 00:32.0` | `none — keeps to the end` |
| intro 32 s, outro 90 s | `cuts at 00:32.0` | `cuts 01:30.0 before the end` |
| intro 32 s, outro **0** | `cuts at 00:32.0` | `none — keeps to the end` |
| intro 0, outro 90 s | `none — keeps from the start` | `cuts 01:30.0 before the end` |
| intro 0, no outro | `none — keeps from the start` | `none — keeps to the end` |
| intro 1 h 2 m 3.4 s | `cuts at 01:02:03.4` | … |

- **An outro of 0 reads "none".** `CutProfile` allows it (`CutProfile.cs:54-60`), and applying it puts
  the outro at the file's end, which trims nothing (`CutProfileApplier.cs:64-74`). This matches how an
  intro of 0 is read.
- **Times** come from `CutMarkerViewModel.FormatClock`, exactly as the row's cut fields show them:
  `mm:ss.f`, or `hh:mm:ss.f` from one hour.
- **Styling.** Every run of the readout uses `FontSizeBody` (13). The app's own font is already mono
  (`AppFontFamily`), so the font does not change. Labels (`Intro`, `Outro`) and the words (`cuts at`,
  `before the end`, `none — …`) use `TextSecondaryBrush` at normal weight. A time uses `AccentTextBrush`
  and `SemiBold` — two differentiators, colour role and weight, never a tint alone — so for this user's
  intro-only profiles the one real cut stands out. Nothing in the readout uses `TextMutedBrush` or
  `FontSizeSmall` any more. The **low-resolution note keeps its small, muted style**; the rule covers the
  readout only.
- *"before the end"* is the point of the outro line: an outro is measured from the end of each file, and
  the old *"outro 01:30.0"* did not say so.
- **The card shows the profile's own values.** On each video the applied cut then snaps to a keyframe,
  and the row shows *requested → snapped*. The guide says so (T-182), so a 2-second difference on a row is
  not read as the profile being wrong.

## Interfaces / contracts

- **Pure sizing function** (unit-testable without rendering), e.g.
  `ProfilePreviewBox.Width(int? pixelWidth, double scale, double min, double max) → double`, returning
  `min` for a null picture. Height is `Width × 9/16`.
- **`ProfilePreviewBoxSizeConverter : IMultiValueConverter`** in `src/App/Views`, with inputs
  `CardImage.Source` (ElementName), the card element itself (for the display scale), and `Min`/`Max`
  (`Binding Source={StaticResource …}`), and `ConverterParameter` = `width` or `height`. The box's
  `Width`/`Height` and the text column's `Width` bind to it.
- **Display-scale seam:** an `internal static Func<Visual?, double> DisplayScale` on the converter.
  - The default is `VisualTreeHelper.GetDpi(v).DpiScaleX`. It falls back to `1.0` on null, on an
    exception, and on a NaN or non-positive value. The pure `ProfilePreviewBox.Width` applies the same
    rule, and that rule is unit-tested.
  - **Every render test sets the seam** (1.0 or 2.0) **inside the `StaViewHarness.OnSta` body** and
    restores it in a `finally`. All card-rendering tests live in one class, so a 2.0 can never leak into
    another test class's render and no result depends on the DPI of the machine running the suite.
- **Readout formatting:** a pure helper, `ProfileCutReadout.Intro(TimeSpan)` / `.Outro(TimeSpan?)` →
  (prefix, time-or-null, suffix). It is unit-tested for every row of the table above. It is bound through
  **`ProfileCutReadoutConverter : IValueConverter`**, with `ConverterParameter` = `intro-prefix |
  intro-time | intro-suffix | outro-prefix | outro-time | outro-suffix`, on the readout's `Run`s. The Core
  `CutProfile` record gets **no** display properties.
- **Resources:** `ProfilePreviewCardWidth` (320, minimum — the name stays, because T-181 pins its
  threshold to it) and `ProfilePreviewCardMaxWidth` (640).
- **Pins:** `Max == ProfileThumbnailWidth`, and `Min == 320` on its own.
  **Replaced on purpose:** the T-172 pin `ProfileThumbnailWidth == 2 × Min`. Its reason ("sharp up to
  200% in a 320 card") no longer describes a card that grows to the picture. `Max == ProfileThumbnailWidth`
  is the relationship that now matters. Update the comments at `BulkCutView.xaml:17-20` and
  `BulkCutViewModel.cs:139-148` to match.

## Edge cases

- A name that wraps to three lines at 320.
- A picture between 320 and 639px (the user's five 320px pictures) shows at its own size, sharp and with
  no note. This is deliberate; T-181 does not refresh them, and *Use current frame* re-takes them at 640
  if the user wants them larger.

## Dependencies

- **Blocked by:** none. T-179 (cache) changes what captures return; this changes only how the card draws.
- **Blocks T-181:** T-181 rewrites the low-resolution note inside the template this task restructures,
  and pins its threshold to the `ProfilePreviewCardWidth` resource this task keeps.
- **Shared spec text:** SPEC-007 I106 is edited here (the rationale) and again by T-181.

## Risks

- **Harness blind spots.** The hover tests never open the real `Popup`
  (`ProfileHoverPreviewTests.cs:362-371`), so "one picture pixel per screen pixel" is proven by the pure
  function plus a measured card, not by the live popup. After the build, check it once in the running app
  (`app-run`): hover a profile whose picture is 640px wide and confirm the card is 640 DIPs wide and not
  clipped.
- **What changes on the user's library on day one.** No stored picture is wider than 320px, so only the
  readout visibly changes until pictures are re-taken (T-179 and T-181). The ship note says so.

## Out of scope

The picture refresh (T-181); the outro frame; keyboard access to the card (I105); a "picture missing"
hint (a missing file now looks like no picture); any change to the chip, the selection or the apply
commands.
