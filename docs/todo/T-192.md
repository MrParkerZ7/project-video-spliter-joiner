## Concept

After T-191 an Exact head costs the same at any cut position, but that cost is still the encode. The head is
encoded with libx264 at its defaults (`SmartCutArgsBuilder.cs:122-137` adds no `-preset` or `-crf`), which
means `medium`/crf 23. A grep of `src/` finds no preset, crf or thread setting anywhere. Near the start of a
file, where most intros are, the input seek alone gains nothing: 18.25 s against 18.98 s for a 225-frame
head at 12.5 s on the 10 s GOP fixture. So for the common case, encoder speed is the whole remaining cost.

Measured on the 4K fixture at 104.5 s, all with the input seek, in one run:

| variant | head time | PSNR vs source | head size | profile |
|---|---|---|---|---|
| libx264 default (medium, crf 23) | 4.94 s | 41.9 dB | 8.5 MB | High |
| **libx264 `-preset veryfast`** | **2.16 s** | 40.7 dB | 6.3 MB | High |
| libx264 `-preset ultrafast` | 1.47 s | 44.5 dB | 16.6 MB | Constrained Baseline |
| h264_nvenc p4 cq19 | 1.52 s | 45.7 dB | 17.2 MB | — |

On the 10-min file at 540.5 s: veryfast 1.99-2.21 s against 4.65 s.

The head is at most one GOP, so its size does not matter. Its speed and its quality do.

## Design

- **For libx264 only**, `HeadReencode` adds `-preset veryfast -crf <X264HeadCrf>` right after
  `-c:v libx264`. Both are named constants in `SmartCutArgsBuilder`, so the choice is reversible in one place.
- **`X264HeadCrf` is chosen on the bench** so that, on the `4k`, `1080` and `g10` fixtures, the veryfast head
  scores no more than 0.5 dB PSNR below today's default head against the same source frames. veryfast at
  crf 23 is 1.2 dB below, so the constant will be lower than 23. The chosen value and the per-fixture PSNR
  go in the Build log.
- **Profile rule:** the head's H.264 profile is never lower than the source's (Baseline < Main < High <
  High 10 < High 4:2:2 < High 4:4:4). The concat output takes its `avcC` from the head, the first file, so
  the declared profile must cover the copied part. veryfast keeps CABAC, B-frames and 8x8 transforms, so it
  stays High. **ultrafast is rejected** for exactly this reason: it declares Constrained Baseline while the
  copied part is High.
- **Every other encoder is unchanged**: libvpx-vp9, libvpx, libsvtav1, mpeg4, mpeg2video. libx265 is no longer
  mapped after T-189.
- **The batch weight's encode cost follows the preset.** T-191 sets the public constant
  `SmartCutEngine.EncodeCostFactor` (`k`, copy-equivalent seconds per re-encoded second) from its own bench run,
  which encodes heads at the default `medium` preset. veryfast more than halves the head's time (4.94 s → 2.16 s at
  104.5 s on `4k`, above), so T-191's `k` would weigh every head about twice too heavily, and the batch bar, the
  taskbar progress and *"~Ns left"* would again be mis-weighted during heads. So this ticket **re-measures `k` at
  veryfast**, with the same bench scenario T-191 used and in the same run as its before/after numbers, and updates
  the constant. Nothing else changes: T-191's one cost function is the only reader of the constant, and both the
  engine's slice weight `w` and `RowWeight` come from it.

## Detail

- The quality comparison is relative and computed in the test itself. Two heads are built from the same
  source and start, one with today's args and one with the new ones, and each is compared with the source
  frames `[start, HeadEnd)` through ffmpeg's `psnr` filter (run by `FfmpegRunner`, stats written to a temp
  file). No absolute dB figure is hard-coded, and no time is measured.
- libx264 is deterministic for fixed settings on one machine, so the comparison is stable from run to run.

## Edge cases

- **10-bit or 4:2:2 H.264 sources:** the existing `-pix_fmt` token makes libx264 pick High 10 or High 4:2:2.
  The profile rule holds.
- **A very short head** (a few frames): same settings. The cost is tiny either way.

## Dependencies

- **T-191:** the input-seek head these settings apply to, the same file and spec block, and the
  `EncodeCostFactor` this ticket re-measures.

## Risks

- **The head's bytes change** for every H.264 Exact output. The joint, frame-identity and quality tests guard
  the frames.
- **Real camera content** (60 fps, noisy, CABAC-heavy) may need a different crf for the same PSNR gap than
  synthetic `testsrc2`. The floor is enforced on synthetic fixtures only; that limit is stated in the Build log.

## Out of scope

- Hardware encoders (T-203).
- HEVC (T-189, T-201).
- Tuning other encoders.
