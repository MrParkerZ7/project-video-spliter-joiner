## Why

User, after G-041 shipped: *"what is wrong? you didn't fix `Set intro-end here`."*

Two separate things were wrong, and only one of them was fixed:

1. **A process failure (mine).** G-041's fixes were committed and pushed but the app binary was never
   rebuilt — the running instance was built at `23:39`, the fixes landed at `00:48`/`01:00`. The user was
   clicking a build that could not contain the fix. Rebuilt + relaunched 2026-08-28 01:10.
2. **The real gap (this epic).** G-041 made keyframe snapping *visible and honest*; it did not make the cut
   *land where the user points*. That was the correct first step — a silent wrong number is worse than a
   visible one — but the user's actual request is unmet: they point at 5s and want the intro gone at 5s.

## Why it currently cannot land at 5s

Every cut is a stream copy (`-c copy`), and a copied segment **must start on a keyframe** — that is exactly
what makes the operation lossless and near-instant. So the reachable cut points are the keyframes, and on a
~4s grid the nearest one to both 5s and 6s is 4s. No snap *policy* fixes this:

```
nearest (today)   5s -> 4s   6s -> 4s     leaves 1-2s of intro behind
ceil / forward    5s -> 8s   6s -> 8s     removes 3s of real content
exact             5s -> 5s   6s -> 6s     needs the first GOP re-encoded
```

Only the third row answers the request. This is the well-understood "smart cut" technique: re-encode the
short head fragment from the requested time to the next keyframe, stream-copy everything after it, and
concatenate the two. The cost is bounded and small — roughly one GOP (~1-2s of video) is re-encoded; the
other 99%+ of the file is still copied untouched.

## Approach

Keep **lossless stream-copy as the default** — it is the app's identity and the right choice for most bulk
trimming. Add exact cutting as an explicit opt-in whose cost is stated where the user chooses it, so nobody
pays for re-encoding without knowing.

## Out of scope

Changing the default cut mode; re-encoding whole files; changing the Core snap contract or the ties-to-earlier
rule (both stay correct for the lossless path); the Join screen.
