## Why / vision

User report: *"on bulk cut when I select on intro to cut at 5 sec from current video play but on actual list
it's still cut on sec 4 even I move to 6 sec"* — plus: *"I also want new option output by override original
file, is there possible?"*

## Root cause (RCA — two independent lenses, high confidence, 2026-08-28)

The number is **not** miscalculated. Cuts snap to the nearest keyframe (that is what makes the copy lossless),
and `MediaProbe.SnapToNearestKeyframe` breaks exact ties toward the **earlier** keyframe (`MediaProbe.cs:355`).
On a ~4s keyframe grid `{0, 4, 8}`:

```
set 5s → |5-4|=1 vs |5-8|=3        → 4s
set 6s → |6-4|=2 vs |6-8|=2 → TIE  → earlier wins → 4s     ← "still 4 even at 6"
```

Both observations, exactly, with no defect required. (Lens B: this is also the discriminator that RULES OUT a
2s grid — on a 2s grid 6s would land on 6s. A 60s test tells the user which case they have: still 4s ⇒ a
truncated keyframe list, i.e. a genuine clamp bug; ~60s ⇒ an ordinary coarse GOP.)

**What IS defective is everything around it:**

1. **Zero feedback (the actual bug).** Every visible surface of the row derives from `Snapped` only — the IN
   field (`BulkCutView.xaml:711`), the `keep` duration, the scrub handle, the thumbnail. `Requested` lives
   ONLY in a hover tooltip (`IntroEnd.Display`). When the second gesture snaps to the same keyframe,
   `SetProperty` suppresses the change notification and **not one pixel moves** — a correct snap is
   pixel-for-pixel identical to an ignored click. The Split screen binds `Display` and shows the delta
   (`SplitView.xaml:305`); Bulk does not — and `docs/USER_GUIDE.md:258-260` already *claims* it does.
2. **Value corruption.** The IN TextBox is editable with `LostFocus="OnCutTimeLostFocus"`, and `CommitCutTime`
   runs on EVERY focus loss even when nothing was typed (`BulkCutView.xaml.cs:164-194`), parsing the displayed
   **snapped, 0.1s-truncated** text back into `Requested` — silently destroying the user's real 5s/6s request,
   zeroing the delta (the only surviving evidence of the snap), and feeding the truncated value to the engine.
3. **Warning hole.** The coarse-GOP note is gated on a strict `gop > 4s` (`BulkItemViewModel.cs:76,:422`), so a
   file with a mean GOP of exactly 4.0s — the grid that best fits this report — gets **no warning at all**.
   The planner already computes the exact sentence the user needed (`SplitPlan.cs:158-162`) but
   `KeptSegmentSelector.ResolveKeptIndex` throws `plan.Warnings` away, and Bulk only surfaces warnings
   *after* the run via the ledger.

## Feature: overwrite-original (feasible, yes-with-caveats)

ffmpeg cannot read and write one path in a single pass — but the engine **already** writes to a
`.vsj-split-<guid>` temp dir and only moves into place after the process exits (`SplitEngine.cs:151-153,173`),
which is exactly the mechanism this needs. Design: a **new orthogonal axis** `OutputMode { NewFile,
ReplaceOriginal }` on `BulkTrimOptions` — deliberately NOT a fourth `CollisionPolicy` value, because collision
policy answers *"what if the destination is taken?"* while this answers *"which destination?"*, and folding it
in would falsify `CollisionPolicy`'s own invariant ("the source file is NEVER a write target under any
policy") and SPEC-002 I22. As a separate axis, that invariant survives, rescoped to `NewFile`, and the
relaxation is one named branch no existing caller can reach.

## Out of scope

Frame-exact cutting (would require re-encoding — contradicts the app's lossless promise); changing the
Core snap contract / tie rule; the Split screen; any change to the `_trimmed` + AutoSuffix default.
