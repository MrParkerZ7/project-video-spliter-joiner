## Concept

Make the profiles card full width; wrap the chips instead of scrolling them; put the actions on their own
full-width wrapping row below. Bound the chip list's HEIGHT so the header cannot grow without limit.

## Design

**1. The card — one attribute.** `BulkCutView.xaml:244` `HorizontalAlignment="Left"` is the only reason
the card is narrow. Its parent Grid row is already commented *"profiles bar, full width"* (`:205`), so the
attribute contradicts the row's own stated intent. Remove it.

**2. The chip list — wrap, do not scroll.** `BulkCutView.xaml:278` `ProfileBar`:
- drop `MaxWidth="420"`
- `ItemsPanel` `StackPanel Orientation="Horizontal"` → `WrapPanel`
- `ScrollViewer.HorizontalScrollBarVisibility` `Auto` → **`Disabled`**
- `ScrollViewer.VerticalScrollBarVisibility` `Disabled` → `Auto`
- add `MaxHeight` ≈ two chip rows

> ❗ **The `Disabled` is load-bearing, not tidying.** A `WrapPanel` inside a `ScrollViewer` whose horizontal
> scrolling is `Auto` *or* `Hidden` is measured at **infinite width** and therefore never wraps. Only
> `Disabled` makes it wrap. Get this wrong and the change silently does nothing while looking correct in
> the diff — the same shape as the T-136 clip.

**3. Chip margin.** `ProfileChipItem` (`:36`) is `Margin="0,0,6,0"` — no bottom margin, so wrapped rows
touch. Needs a bottom gutter.

**4. Chip label bound.** `ProfileItemTemplate` (`:77`) is a horizontal `StackPanel`, which measures at
infinite width. With horizontal scrolling now `Disabled`, a long profile name is a **silent clip** rather
than a scroll. The label needs a width bound (it already has `TextTrimming`, which does nothing unbounded).

**5. The actions — their own row.** Lift every action out of the shared `WrapPanel` into a second,
full-width `WrapPanel` (`ProfileActions`) below the chip list. This is [[T-160]]'s footer cure applied one
region north.
- **✕ Delete profile goes LAST in flow order.** Inside a `WrapPanel`, adjacency is decided by flow order —
  `HorizontalAlignment` is inert and a Grid column is unavailable. Ordinal position is the only expressible
  form of the rule that a destructive control must not sit beside the one people press repeatedly.
- **Save goes first**: it is the only ungated control, so its position must not move when `HasProfiles` flips.
- The row itself carries **no** `Visibility` gate — gating stays per-control (SPEC-011 I110).

## Acceptance criteria
- [ ] The card's width equals its header row's width. Asserted with a SHORT profile list — a full one fills
      the row by itself, so a `Left`-aligned card would pass.
- [ ] With 14 profiles the chips occupy **≥2 distinct Y bands** and every chip is inside the bar's bounds.
- [ ] Every action-row control begins **below** where the chip list ends, at all five window sizes.
- [ ] The actions wrap rather than clip — none extends past the window at 760x620.
- [ ] With 40 profiles the chip list is capped **and** `ScrollableHeight > 0` — a cap that clips instead of
      scrolling must fail.
- [ ] **Run stays on screen** at every size with 40 profiles loaded. This is the regression T-161 feared.
- [ ] A 300-character profile name does not widen the card, at all five sizes.
- [ ] Mutations, each killing a named test: restore `MaxWidth="420"` · revert the `ItemsPanel` to a
      horizontal `StackPanel` · set `HorizontalScrollBarVisibility` back to `Auto` (the wrap silently stops)
      · move the actions back into the chip `WrapPanel` · drop the `MaxHeight`.

## Tests to delete, not adjust
- `BulkCutViewLayoutTests.cs:341` `TheProfileBarScrolls_AndNeverPushesTheApplyActionsOffScreen` — its cap
  assertion pins the exact promise being removed; its other two sub-assertions become **vacuous by
  construction** (a stretched bar inside a stretched card cannot end past the window; actions on their own
  row cannot be displaced). The file's own comment at `:372-377` records that this precise on-screen check
  already survived a mutation once.
- `BulkCutViewLayoutTests.cs:44-45` `ProfileBarMaxWidth = 420` and its doc-comment — false documentation
  the moment the cap goes.
- ⚠ **Latent vacuity to not reintroduce:** `:397` selects buttons via `b.Content as string` containing
  `"Apply to"`, with no count guard. `SaveProfileButton` already uses a `StackPanel` content — the day
  either Apply segment gains an icon, the filter matches zero buttons and the test passes green checking
  nothing. The replacement walks descendants of `ProfileActions` and asserts a minimum count.
- `:49` `TheContentAreaSurvivesAGrowingProfileBar…` still passes but is **misnamed**: it uses no
  `DataContext` and grows the header synthetically, so it tests a growing *header*, not a growing profile
  bar. Rename it.
