## Concept

Make the profiles card full width; wrap the chips instead of scrolling them; put the actions on their own
full-width wrapping row below. Bound the chip list's HEIGHT so the header cannot grow without limit.

## Design

**1. The card — one attribute.** `BulkCutView.xaml:244` `HorizontalAlignment="Left"` is the only reason
the card is narrow. Its parent Grid row is already commented *"profiles bar, full width"* (`:205`), so the
attribute contradicts the row's own stated intent. Remove it.

**2. The chip list — wrap, do not scroll.** `BulkCutView.xaml:278` `ProfileBar`:
- drop `MaxWidth="420"`
- `ItemsPanel` `StackPanel Orientation="Horizontal"` → `WrapPanel`
- `ScrollViewer.HorizontalScrollBarVisibility` `Auto` → **`Disabled`**
- `ScrollViewer.VerticalScrollBarVisibility` `Disabled` → `Auto`
- add `MaxHeight` ≈ two chip rows

> ❗ **The `Disabled` is load-bearing, not tidying.** A `WrapPanel` inside a `ScrollViewer` whose horizontal
> scrolling is `Auto` *or* `Hidden` is measured at **infinite width** and therefore never wraps. Only
> `Disabled` makes it wrap. Get this wrong and the change silently does nothing while looking correct in
> the diff — the same shape as the T-136 clip.

**3. Chip margin.** `ProfileChipItem` (`:36`) is `Margin="0,0,6,0"` — no bottom margin, so wrapped rows
touch. Needs a bottom gutter.

**4. Chip label bound.** `ProfileItemTemplate` (`:77`) is a horizontal `StackPanel`, which measures at
infinite width. With horizontal scrolling now `Disabled`, a long profile name is a **silent clip** rather
than a scroll. The label needs a width bound (it already has `TextTrimming`, which does nothing unbounded).

**5. The actions — their own row.** Lift every action out of the shared `WrapPanel` into a second,
full-width `WrapPanel` (`ProfileActions`) below the chip list. This is [[T-160]]'s footer cure applied one
region north.
- **✕ Delete profile goes LAST in flow order.** Inside a `WrapPanel`, adjacency is decided by flow order —
  `HorizontalAlignment` is inert and a Grid column is unavailable. Ordinal position is the only expressible
  form of the rule that a destructive control must not sit beside the one people press repeatedly.
- **Save goes first**: it is the only ungated control, so its position must not move when `HasProfiles` flips.
- The row itself carries **no** `Visibility` gate — gating stays per-control (SPEC-011 I110).

## Outcome — 2026-09-07

Built, and the reversal did not re-create what T-161 was protecting against.

### The measurement was the whole ticket
T-161's `MaxWidth` was not fussiness — it kept the header from growing. Removing it without replacement
grows the header **154px** at 760x620 and pushes **Run 74px off-screen**, against 72px of slack. So the
cap rotated onto the free axis: the chip list is capped at two rows (`ProfileBarMaxHeight`, a named
resource the test reads back rather than a hand-copied number) and scrolls vertically past it.
`RunStaysOnScreen_EvenWith40Profiles` is the guard, and dropping the cap kills it.

### Six mutations, six dead — but two only after the tests were fixed
Two of them **survived first**, and both survivals were the test's fault rather than the code's:

- **Restoring `MaxWidth="420"` killed nothing.** The full-width test measured the *card*, and the wrap
  test measured chips *relative to the bar* — with 14 profiles a 420px bar still wraps and still keeps
  every chip in bounds, so both passed. The card being wide is worth nothing if the list inside it is
  not; the test now asserts **the bar fills the card**, and the mutation dies.
- **Removing the chip label's `MaxWidth` killed nothing.** The assertion was *"the chip does not extend
  past the bar"* — unfalsifiable, because a `WrapPanel` measures children against the available width.
  Rewritten to assert what the bound actually buys: a 300-character name does not swallow the row, so a
  chip-width ceiling **plus** at least one neighbour still sharing the line.

Both are recorded in the specs (SPEC-007 I98, SPEC-011 I155) because the failure mode — an assertion
satisfied by construction — is the one this suite keeps re-learning.

### A third trap, caught by a count guard
The actions test first filtered controls by `IsVisible`. This harness measures and arranges **without a
window**, so there is no `PresentationSource` and `IsVisible` is false for every element: the sweep found
**zero** controls. It only surfaced because the test demands at least 8 before sweeping — the guard the
deleted T-161 test lacked. Filtering is now on `Visibility`.

### Deleted, not adjusted
`TheProfileBarScrolls_AndNeverPushesTheApplyActionsOffScreen` and the `ProfileBarMaxWidth = 420` const:
the first pinned the exact promise being removed and its other two assertions were vacuous by
construction. `TheContentAreaSurvivesAGrowingProfileBar…` was renamed to `…AGrowingHeader…` — it builds
the view with no `DataContext` and grows the header synthetically, so it never tested a profile bar.

### What shipped
- Card: `HorizontalAlignment="Left"` gone — it contradicted its own row comment.
- Chip list: `MaxWidth` gone · `ItemsPanel` → `WrapPanel` · horizontal scrolling **`Disabled`** (the
  load-bearing one: `Auto`/`Hidden` measures at infinite width and never wraps) · vertical `Auto` ·
  `MaxHeight` capped · 6px wrap gutter on the chip.
- Actions: their own full-width `ProfileActions` `WrapPanel`, Save first, ✕ Delete last.
