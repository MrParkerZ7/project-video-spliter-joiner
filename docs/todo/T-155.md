## Reported
> currently delete original files is work, but everytime windows will popup unable to remove file able, but
> remove original files still work. there's possible to auto clear files to unblock using file by app first
> then proceed to delete original file ?

So: the feature works, but a Windows dialog interrupts **every** run. A destructive action that already
needs a confirmation should not then need a second dismissal from the OS.

## The popup has a specific, findable cause

`RecycleBinOriginalDisposer.DisposeOriginalBackup` calls:

```csharp
FileSystem.DeleteFile(backupPath, UIOption.OnlyErrorDialogs, RecycleOption.SendToRecycleBin);
```

`UIOption` has exactly two values — `AllDialogs` and `OnlyErrorDialogs`. **There is no "no dialogs".**
`OnlyErrorDialogs` is already the quieter one, and it still shows a shell error dialog whenever the file
cannot be binned — which is what the reporter sees. The API cannot be made silent by configuration.

That also explains *"but remove original files still work"*: the shell dialog offers a retry, or the file
is released a moment later, so the deletion completes after the interruption. The outcome is right; the
experience is not.

## Two separate things to fix, in this order

### 1. Find out what is still holding the file
T-145 released the app's own **preview** handle before the sweep (`SelectedItem = null; Player.Unload()`)
and that fixed the previewed row being refused outright. A dialog on *every* run means something is
**still** holding a handle — and that is the reporter's actual question ("auto clear files to unblock
using file by app first"). Candidates, none yet ruled out:

- a frame-grab or keyframe-probe subprocess (`ffmpeg`/`ffprobe`) that has not fully exited
- a row thumbnail still reading from the source
- the OS thumbnail cache or an antivirus scanner — **outside our control, which is exactly why part 2
  matters even if part 1 finds nothing**

Diagnose it before changing anything: on a refusal, log which process holds the handle (Restart Manager
`RmGetList`, or `handle.exe` during investigation) rather than guessing. This project has repeatedly paid
for hypothesis-first fixes.

### 2. Stop using an API that can put UI on screen at all
Replace the VB `FileSystem.DeleteFile` call with the Win32 shell operation
(`IFileOperation`, or `SHFileOperation` with `FOF_NOCONFIRMATION | FOF_NOERRORUI | FOF_SILENT`), which
bins to the Recycle Bin **without any dialog** and returns a result code instead.

This is the durable half: the app already tracks refusals and reports "Sent N, refused M" — it does not
need Windows to tell the user, and a failure it can report is strictly better than a modal it cannot
control. Retry briefly on a sharing violation before giving up, since the common case is a handle about
to close.

## Acceptance criteria
- [x] The dialog-capable API is gone. `SHFileOperation` with
      `FOF_ALLOWUNDO | FOF_SILENT | FOF_NOCONFIRMATION | FOF_NOERRORUI` cannot show UI — it returns a
      code. (A test cannot see a dialog; what is pinned is that no API capable of one is called.)
- [x] A locked file comes back `false`, the sweep adds it to `refusedPaths`, and the summary names it —
      now **with whoever is holding it**: "Still in use: ep1.mp4 (held by ffmpeg.exe)".
- [x] `FileLockOwner` asks the Windows **Restart Manager** and reports process names. Asserted against
      a real lock: the test holds a file and the lookup names `testhost`. Nothing is assumed — and if
      the holder turns out to be an antivirus scanner or the shell thumbnail cache, the user is told
      that rather than the app retrying forever against something it cannot release.
- [x] 3 attempts, 120ms apart, structurally bounded — asserted by
      `TheRetryIsBounded_AndDoesNotHangOnAPermanentlyHeldFile`. Trading a dialog for a frozen app
      would not be an improvement.
- [x] Two mutations, both dead: dropping `FOF_ALLOWUNDO` (which would silently turn this into
      **permanent deletion** while every "did it vanish" assertion still passed) fails 1; trusting the
      return code instead of verifying the file is gone fails 2.
- [ ] Confirmed by the reporter on a real batch — this is a UI-interruption bug, so the check is
      "no dialog appeared", which only they can see.

## Out of scope
Permanent deletion instead of the Recycle Bin. Recoverability is what makes this feature safe to offer;
[[T-156]] covers emptying the bin as a separate, explicit choice.

## Progress — 2026-09-02

### The cause was in the API, not in a mystery
`UIOption` has exactly two values and neither is silent. No amount of handle-releasing would have stopped
the dialog, because the dialog is what that API *does* when a file is locked. Replaced with
`SHFileOperation` + `FOF_SILENT | FOF_NOERRORUI | FOF_NOCONFIRMATION`, which returns a result code. The
screen already said "Sent N to the Recycle Bin. Still in use: …" in its own words — it never needed
Windows to speak for it.

### The reporter's question, answered properly
*"is there possible to auto clear files to unblock using file by app first?"* — the honest answer is that
we first have to know **what** is holding it, and this project has paid three times over for answering
that kind of question with a hypothesis. `FileLockOwner` asks the Restart Manager and puts the process
name in the summary. If it is ours, that is a bug with an address; if it is an antivirus scanner or the
shell's thumbnail cache, no self-release would ever have worked and now the user can see why.

### A bug I introduced and caught
The first version marked `SHFILEOPSTRUCT` with `Pack = 1`. On x64 that removes the 4 bytes of padding
after `wFunc`, so shell32 reads `pFrom` from the wrong offset and dereferences garbage — an
`AccessViolationException` that **killed the test host mid-run**. The run still printed
`Passed! … 5 of 5`, because the host died after five cases and the summary described only what had
finished. A green line from a crashed run is a genuinely dangerous artefact: it is the same
"the instrument lied" class as the stale-build trap in T-137, and worth the same suspicion.

### Still open
The acceptance criterion that matters is the reporter's: **no dialog appears on a real batch.** That is a
UI-interruption bug, so only they can confirm it. `dist/publish` needs republishing before they test —
see [[T-154]] for how testing the wrong build already cost a round-trip here.
