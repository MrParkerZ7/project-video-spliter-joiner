## Concept

The option checkboxes at the bottom of Bulk Cut, beside the Run button, do not all remember their last state. Three
persist — *Auto-clear list* (`BulkAutoClearAfterRun`), *Auto-delete originals* (`BulkAutoDeleteOriginals`) and
*and empty bin* (`BulkAutoEmptyRecycleBin`) — and three reset to off on every launch: **Overwrite existing output**,
**Exact cut** and **Replace originals**. They are plain fields on the view-model (`_overwrite`, `_exactCut`,
`_replaceOriginal`); the user's `settings.json` holds none of them.

"check-box on button" most likely means "on the bottom" (the footer, which is where T-183's checkbox is too). The
literal reading — the *Apply to all ticked videos* box under the *Set … here* buttons — is ruled out on evidence: it
already persists as `BulkApplyCutToAllRows`, and the user's `settings.json` holds it (`bulkApplyCutToAllRows: true`).

## Design

- Three new nullable settings on `IAppSettings` / `AppSettings` / its DTO, the same shape as the existing ones:
  `BulkOverwrite`, `BulkExactCut`, `BulkReplaceOriginals` (`bool?`; absent in an older file → null → **off**, today's
  default; each setter saves only on a change).
- **One source the run reads.** The three fields stay — `RunBatchAsync` and `AddFiles` read them — and are **seeded
  from settings in the constructor**, directly, not through the property setters, so building the view-model writes
  nothing back. The setters write through to settings on every change and keep their side effects (`CollisionIsInert`
  / `OutputNote` for Replace, `PrecisionNote` and each row's `SetExactCut` for Exact cut). A row added later inherits
  the persisted Exact cut, as it inherits the current one today.
- **Replace originals persists too.** It is destructive, but remembering it removes no safeguard: every batch still
  asks `ConfirmReplaceOriginals` (T-123) before it replaces anything, replaced originals still go to the Recycle Bin,
  and `OutputNote` reads `Output → REPLACES each original file …` from the first frame. *Auto-delete originals*, at
  least as destructive, has persisted since T-156.
- **Overwrite persists, and says so in red while it is on.** Unlike Replace it has no confirmation and no Recycle
  Bin: it writes over an existing `_trimmed` output in place (`CollisionPolicy.Overwrite`). Remembered silently it
  would re-arm that for a batch next week. So while Overwrite is on **and Replace is off** (Replace makes the
  collision policy inert), `DestructiveOutputNote` — the red, SemiBold note that closes the irreversible group
  (SPEC-011 I137/I146) — includes `Existing _trimmed files will be overwritten in place — not recoverable`, joined
  with ` · ` to any auto-delete sentence. The Overwrite setter raises `DestructiveOutputNote` (it raises nothing
  today), and so does the Replace setter.

## Acceptance criteria

- [ ] **Repro first:** toggling each of the three on, then building a new view-model over the same settings object,
      finds it still on. (Fails today for all three.)
- [ ] **The run uses them:** a view-model built over settings with each key true runs a batch whose
      `FakeBulkTrimEngine.ReceivedOptions` has `Output == OutputMode.ReplaceOriginal`,
      `Precision == CutPrecision.Exact`; with Replace false and Overwrite true, `Collision == CollisionPolicy.Overwrite`.
- [ ] Each round-trips through a real `AppSettings` file (`AppSettingsTests` style): written as its own key, read
      back, and an absent key reads as off (an older settings file keeps today's defaults). Turning one off persists
      `false`.
- [ ] Building the view-model with each new key set to true performs **zero** settings writes.
- [ ] Replace restored ON: `CollisionIsInert` is true, `OutputNote` is the REPLACES line before any run, and a
      refusing `ConfirmReplaceOriginals` still blocks the run.
- [ ] Exact cut restored ON: `PrecisionNote` says so at startup and a newly added row cuts exactly.
- [ ] Overwrite ON (restored or ticked), Replace OFF: `DestructiveOutputNote` contains `Existing _trimmed files will be
      overwritten in place — not recoverable`; ticking and unticking Overwrite raises `PropertyChanged` for it and
      flips the clause; ticking Replace hides the clause; with Auto-delete also on, both sentences show, joined.
- [ ] The note is red and SemiBold in the view (the existing `DestructiveOutputNote` TextBlock — asserted by brush and
      weight), and the footer layout tests (SPEC-011 I139/I145) pass at the narrowest window with Overwrite and
      Auto-delete + empty bin all on (the longest note).
- [ ] Every `IAppSettings` test fake gains the three members, and each delegating fake
      (`LastTabRestoreTests.WriteCountingSettings`) routes each key to its **own** member.
- [ ] The existing tests for the already-persisted options pass unmodified.
- [ ] **Same commit:** SPEC-009 (the new keys in its key lists; I27 — the destructive preferences that are `bool?`
      with absent = OFF — gains `BulkReplaceOriginals` and `BulkOverwrite`, its count fixed; an I29-style invariant
      for `BulkExactCut`, not destructive, absent = off); SPEC-011 I83/I84 qualified (Overwrite's red clause), I89
      reworded ("absent = Lossless; persisted as `BulkExactCut`"), and the persistence of all three stated;
      `docs/adr/0015-bulk-trim-reuses-split-single-segment.md` Status gains "Amended by T-186 — (d): the Overwrite
      toggle is remembered; the default is still AutoSuffix"; the `Overwrite` doc comment ("Per-run overwrite toggle"
      → remembered); `docs/USER_GUIDE.md` (the Output, Exact cut and Replace sections say the choice is remembered);
      `docs/GLOSSARY.md` (precision is no longer a "per-batch" choice); `CHANGELOG.md`. `_index.md` recounted if an
      invariant is added.
