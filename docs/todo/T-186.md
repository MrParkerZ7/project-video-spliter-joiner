## Concept

The option checkboxes at the bottom of Bulk Cut, beside the Run button, do not all remember their last state. Three
persist — *Auto-clear list* (`BulkAutoClearAfterRun`), *Auto-delete originals* (`BulkAutoDeleteOriginals`) and
*and empty bin* (`BulkAutoEmptyRecycleBin`) — and three reset to off on every launch: **Overwrite existing output**,
**Exact cut** and **Replace originals**. They are plain fields on the view-model (`_overwrite`, `_exactCut`,
`_replaceOriginal`); the user's `settings.json` holds none of them.

"check-box on button" most likely means "on the bottom" (the footer, which is where T-183's checkbox is too). The
literal reading — the *Apply to all ticked videos* box under the *Set … here* buttons — is ruled out on evidence: it
already persists as `BulkApplyCutToAllRows`, and the user's `settings.json` holds it (`bulkApplyCutToAllRows: true`).

## Design

- Three new nullable settings on `IAppSettings` / `AppSettings` / its DTO, the same shape as the existing ones:
  `BulkOverwrite`, `BulkExactCut`, `BulkReplaceOriginals` (`bool?`; absent in an older file → null → **off**, today's
  default; each setter saves only on a change).
- **One source the run reads.** The three fields stay — `RunBatchAsync` and `AddFiles` read them — and are **seeded
  from settings in the constructor**, directly, not through the property setters, so building the view-model writes
  nothing back. The setters write through to settings on every change and keep their side effects (`CollisionIsInert`
  / `OutputNote` for Replace, `PrecisionNote` and each row's `SetExactCut` for Exact cut). A row added later inherits
  the persisted Exact cut, as it inherits the current one today.
- **Replace originals persists too.** It is destructive, but remembering it removes no safeguard: every batch still
  asks `ConfirmReplaceOriginals` (T-123) before it replaces anything, replaced originals still go to the Recycle Bin,
  and `OutputNote` reads `Output → REPLACES each original file …` from the first frame. *Auto-delete originals*, at
  least as destructive, has persisted since T-156.
- **Overwrite persists, and says so in red while it is on.** Unlike Replace it has no confirmation and no Recycle
  Bin: it writes over an existing `_trimmed` output in place (`CollisionPolicy.Overwrite`). Remembered silently it
  would re-arm that for a batch next week. So while Overwrite is on **and Replace is off** (Replace makes the
  collision policy inert), ~~`DestructiveOutputNote` … includes `Existing _trimmed files will be overwritten in place —
  not recoverable`, joined with ` · ` to any auto-delete sentence~~ **built as a separate red, SemiBold
  `OverwriteOutputNote` closing the irreversible group after `DestructiveOutputNote`, reading `Overwrite existing
  output is on — existing _trimmed files are replaced in place, not recoverable`** (⚠ contract change — see the build
  log). The Overwrite and Replace setters raise it.

      `FakeBulkTrimEngine.ReceivedOptions` has `Output == OutputMode.ReplaceOriginal`,
