## Concept
The report shows a Japanese path rendered as mojibake (`ç«‹xè¯xxé`) — proof the ffmpeg process output is captured with the wrong (console codepage) encoding, and possibly that unicode paths aren't passed cleanly. Fix encoding end-to-end so unicode files work and errors are readable.

## Design
- In `FfmpegRunner`/`FfprobeRunner` (`src/Core/Ffmpeg`): set `ProcessStartInfo.StandardOutputEncoding = StandardErrorEncoding = System.Text.Encoding.UTF8` (ffmpeg emits UTF-8). Ensure redirected reads decode as UTF-8, so the captured stderr tail + full log show unicode paths correctly.
- Verify the PATH going IN: args use `ArgumentList` (T-002) which passes each token to the OS as UTF-16 — confirm a Japanese input + output path reaches ffmpeg intact (ffmpeg on Windows opens UTF-8/wide paths; validate with a real fixture). If needed, ensure no lossy string round-trip in `FfmpegArgs`/path handling.
- Probe (`ffprobe` JSON) already UTF-8 via `-print_format json` — confirm `MediaInfo`/keyframes work for a unicode-named file.

## Detail
- Add a test fixture at a non-ASCII path (e.g. a temp dir containing a `立` or `テスト` folder) and run probe + split against it.
- Confirm the captured stderr/`UserFacingError.RawTail` renders the unicode path correctly (no mojibake) — this is the check that the fix worked.

## Acceptance criteria + Case-Coverage Matrix
- [ ] A file at a Japanese/unicode path probes, loads, splits, and joins correctly (no mojibake, no path-not-found).
- [ ] Captured ffmpeg stderr / error RawTail shows the unicode path correctly (UTF-8), not garbled.
- [ ] Existing ASCII-path behavior unchanged; tests green.
- Matrix — Required-Success: unicode path → all ops work + readable errors. Boundary: mixed ASCII+unicode; spaces + unicode; very long unicode path. Required-Fail: truly missing file → correct "not found" (not a mojibake path).
