## Concept
A ticked box must mean "the user wants this row", and Run must count it. Today one property means both
"the user wants it" and "the app judges it usable", so after a multi-file import every box reads unticked
and clicking cannot re-tick it.

## Reported
> bulk cut is not proceed able to cut after import multiple video to cut

## Leading hypothesis — derived from reading the code, NOT yet reproduced against a running build

1. Import N videos. Each row: intro 0, no outro -> `IsNoOpTrim` true -> `IsAutoDisabled` true.
2. `IsEnabled` getter returns false for every row -> the whole list renders unticked.
3. `CanRunBatch` needs `Items.Any(i => i.IsEnabled && i.IsValidCut)` -> false -> **Run disabled**.
4. Clicking a checkbox sets `value = true`, but `_isEnabledByUser` is already `true`, so the setter's
   `!=` guard short-circuits: no field change, no `PropertyChanged`. The row cannot be turned on.
5. Because no `PropertyChanged` is raised, WPF does not push the getter back to the target either, so the
   box can be left **visually ticked while `IsEnabled` is false** — a checkbox that lies about the state,
   which matches "I ticked them and Run still won't go".

There is a second, independent blocker on the same command worth verifying while here: `CanRunBatch` also
requires `Items.Where(i => i.IsEnabled).All(i => i.KeyframesReady)`, and `AddFilesAsync` awaits
`PopulateAsync` **sequentially** per file — so on a large import the last rows stay Loading (not
auto-disabled, by design) for a long time and hold Run disabled with no indication of what is being
waited on.

## Design
1. **Separate the two concepts at the boundary.** Bind the checkbox to a genuine two-way intent property
   (promote the existing internal `IsCheckedByUser`), and keep the computed eligibility as its own
   read-only property. Intent is what the user toggles; eligibility is what the engine filters on.
2. **Make the setter honest.** Raise `PropertyChanged` for the derived/computed property whenever intent
   or eligibility changes, so the box can never sit in a state the VM disagrees with.
3. **Say why a row is out.** A row excluded because it is load-failed or a no-op trim should read as
   excluded-with-a-reason, distinct from a row the user unticked. "Nothing to trim yet" is not an error.
4. **Surface what Run is waiting for.** When Run is disabled purely because rows are still indexing, say
   so ("scanning 3 of 12...") rather than presenting a dead button. Consider whether the sequential
   `PopulateAsync` loop should overlap under the existing bounded `_scanGate` (max 3).

## Acceptance criteria
- [ ] Reproduced against a **rebuilt, running** app before any fix is written, and the repro recorded here.
      (G-042/T-126 rule: a green suite is not evidence the user can see a change.)
- [ ] After importing N videos, ticking a row leaves it ticked and increments "Run bulk cut (N)".
- [ ] No state exists where the checkbox renders ticked but the row is excluded from the batch.
- [ ] A row auto-excluded (load-failed / no-op) is visually distinct from a user-unticked row, with the
      reason legible.
- [ ] Run being disabled while scans are in flight is explained in the UI, not silent.
- [ ] SPEC-011 updated for the intent/eligibility split; `serves-spec` tests cover: tick-after-import,
      the setter no-op trap, and the lying-checkbox state.
- [ ] Rebuilt + relaunched, and the original gesture verified by hand.

## Out of scope
Changing which rows are auto-excluded. Redesigning the item list.
