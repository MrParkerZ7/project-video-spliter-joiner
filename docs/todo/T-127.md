## Concept
A ticked box must mean "the user wants this row", and Run must count it. Today one property means both
"the user wants it" and "the app judges it usable", so after a multi-file import every box reads unticked
and clicking cannot re-tick it.

## Reported
> bulk cut is not proceed able to cut after import multiple video to cut

## Repro — CONFIRMED at the ViewModel level 2026-08-29

A diagnostic walked the reported journey against the real ViewModels. What it found:

```
1. import 3 videos       -> all rows IsEnabled=False, IsNoOpTrim=True, "Run bulk cut (0)"
2. row0.IsEnabled = true -> getter STILL False, PropertyChanged fired 0x      <-- THE BUG
3. set intro=5s on row0  -> row0 enables, "Run bulk cut (1)"                  <-- happy path WORKS
4. ApplyToAll            -> applied=2, "Run bulk cut (3)"                     <-- works
5. untick row1, give it a real cut -> still excluded; ApplyToAll skips it
```

**Correction to this ticket's original claim.** It said Run was dead after a multi-file import. That was
too strong: setting a cut on any row *does* enable the batch, and apply-to-all *does* fan it out. The
happy path was never broken. What is broken is narrower and still real:

- **The click is a dead gesture (step 2).** Ticking a checkbox on a not-yet-eligible row writes `true`
  over an already-`true` field, the `!=` guard short-circuits, and no `PropertyChanged` is raised. Because
  nothing pushes the getter back to the target, the box can sit **rendering ticked while the row is
  excluded** — a checkbox that lies.
- **Clicking twice poisons the row (step 5).** The second click writes `false`, which *does* take. That
  row then stays excluded even after a real cut is set, and `ApplyToAll` skips it entirely (it filters on
  `IsCheckedByUser`). A user who fiddles with the boxes — the natural response to a click that appears to
  do nothing — silently drops videos from their own batch.

The second, independent observation from the original hypothesis still stands and is worth a look:
`AddFilesAsync` awaits `PopulateAsync` **sequentially**, and `CanRunBatch` waits on every enabled row
being keyframes-ready, so a large import holds Run disabled with nothing on screen saying why.

## Design
1. **Separate the two concepts at the boundary.** Bind the checkbox to a genuine two-way intent property
   (promote the existing internal `IsCheckedByUser`), and keep the computed eligibility as its own
   read-only property. Intent is what the user toggles; eligibility is what the engine filters on.
2. **Make the setter honest.** Raise `PropertyChanged` for the derived/computed property whenever intent
   or eligibility changes, so the box can never sit in a state the VM disagrees with.
3. **Say why a row is out.** A row excluded because it is load-failed or a no-op trim should read as
   excluded-with-a-reason, distinct from a row the user unticked. "Nothing to trim yet" is not an error.
4. **Surface what Run is waiting for.** When Run is disabled purely because rows are still indexing, say
   so ("scanning 3 of 12...") rather than presenting a dead button. Consider whether the sequential
   `PopulateAsync` loop should overlap under the existing bounded `_scanGate` (max 3).

## Resolution — 2026-09-02 (via [[T-152]])

This ticket sat `done` with five unticked hand-verification boxes, released in v1.1.0. It had the widest
blast radius of the nine: *"No state exists where the checkbox renders ticked but the row is excluded"* —
a user acting on a wrong tick loses work silently.

**That criterion turned out to be obsolete rather than unmet**, which is the more interesting outcome.
T-127's own fix deliberately separated intent from eligibility: the checkbox binds `IsCheckedByUser`, Run
counts `IsEnabled && IsValidCut`. A ticked-but-not-yet-cuttable row is now a *legitimate* state — it is
what lets you tick a row before setting its cut. Conflating the two is precisely what made one click do
nothing and a second silently drop the video.

So the criterion was restated to the guarantee that actually matters, and asserted:

> a ticked row Run will not cut must either carry an `ExclusionReason` or be visibly still scanning —
> it is never dropped in silence.

`ATickedRowThatRunWillNotCut_AlwaysSaysWhy_OrIsVisiblyStillScanning` walks a deliberately mixed batch and
checks the property over every row, with a precondition assertion so it cannot pass by having nothing to
inspect.

**Why a test rather than a click.** "No state exists where…" is a claim about a state space; a human
clicking checks one path through it. The VM-level check is the stronger instrument here, not a cheaper
substitute for the real one.
