## Why / vision
Many videos — especially same-series episodes — carry a long intro (and often an end-credits outro). Trimming those off
shrinks files and is pure housekeeping, but doing it one-at-a-time in the Split tab is tedious. **Bulk Cut** is a third
tab: load many videos, mark each one's intro-end (+ optional outro-start) on a per-row scrub bar (or set one and apply to
all), and trim them all in one failure-isolated run — keeping the middle of each, stream-copy, originals kept.

Sealed design: **[D-004](./D-004.md)** → [`docs/design/D-004/README.md`](../design/D-004/README.md) +
[`core-flow.md`](../design/D-004/core-flow.md). Core insight: **a bulk trim IS a Split that keeps ONE middle segment** —
the engine is reused wholesale; the only genuinely new work is the list + two cut points per row + a Core batch runner.

## Decisions (from D-004 seal + planner critic)
- **Batch orchestration lives in Core (`BulkTrimEngine`, T-095)**, not the VM — UI-free + unit-testable with a fake
  `ISplitEngine`; T-096's `RunBatchAsync` **delegates** to it (resolves the planner's T-095/T-096 duplication finding).
- **Reuse, don't rebuild** — `SplitEngine` single-segment path, `CutMarkerViewModel` (×2/row), `OperationViewModel`
  (per-row + aggregate), Join's list scaffold, `IThumbnailService`. One new token: `DropScrimBrush`.
- **Apply-to-all outro = time-from-END**; **collision default = AutoSuffix** (+ per-run Overwrite); **sequential** batch.
- **Bounded keyframe-scan concurrency** (T-096) — N distinct files must not fire N concurrent ffprobe scans.
