## What is wrong

`BulkCutViewModel.DeleteOriginals` re-checks each row inside the sweep loop:

```csharp
if (!FileThere(row.Path) || !IsNonEmptyFile(row.OutputPath)) { continue; }
```

That guard is what stops the app binning an original whose trimmed output vanished or went zero-byte
**between the confirmation dialog and the sweep** — i.e. binning the only surviving copy. It is written
down as SPEC-011 I118.

**Deleting the guard leaves all 1303 tests green.** `DeleteOriginalsTests` covers only the *pre-sweep*
offer (`IfTheOutputHasVanishedSinceTheRun_TheOriginalIsNotOffered` asserts `CanDeleteOriginals`, not the
loop). Nothing exercises the window between confirming and sweeping.

## The concrete failure it allows
A user confirms the delete; the trimmed output is removed or truncated in that window (an antivirus
quarantine, a sync client, a second app, a full disk finishing a flush); the sweep bins the original
anyway. The only copy of their video goes to the Recycle Bin — and the summary reports it as a success.

## Design
Drive the VM through a real sweep where the output disappears (or becomes zero-byte) **after**
`CanDeleteOriginals` reads true and the confirmation returns yes. Assert the original survives and the
row is reported as skipped rather than binned. The existing `IOriginalDisposer` fake is the seam.

## Acceptance criteria
- [x] Verified by mutation, three ways: whole guard removed → 2 fail; `FileThere` half only → 2 fail;
      `IsNonEmptyFile` half only → 1 fail. Every half of the guard is now load-bearing.
- [x] Both covered, plus a third the ticket did not anticipate: the ORIGINAL vanishing in the same
      window (no data at risk, but it was being counted as binned).
- [x] The summary reports what was actually binned (`Sent 1`), not what was offered.

## Out of scope
Locking the output for the duration of the sweep. The re-check is the cheaper, honest guard.

## Outcome — 2026-09-02

The claim was verified before it was fixed: deleting the in-loop re-check left **all 851 App tests
green**. The guard protecting the only surviving copy of someone's video was held in place by nothing.

Three tests now close the window, all driving the real sweep and using the confirmation hook as the
injection point — whatever it does happens *after* the decision and *before* the sweep, which is exactly
the interleaving at issue:

| what vanishes mid-window | consequence without the guard |
|---|---|
| the trimmed output is deleted | the original — the only copy left — is binned, and reported as success |
| the trimmed output is truncated to 0 bytes | same, and an existence-only check would sail past it |
| the **original** is deleted | no data lost, but the row is counted as binned, overstating the summary |

The third was not in the ticket. It surfaced from mutation testing: dropping the `FileThere(row.Path)`
half of the guard originally killed nothing, which meant that half was unprotected even though the other
was. It is now covered, and all three mutants die.

Each test also asserts the row never reached the disposer at all — not merely that the file survived —
so a future change that calls the disposer and relies on it to refuse cannot pass quietly.

Suite 1312 → **1315 green**.
