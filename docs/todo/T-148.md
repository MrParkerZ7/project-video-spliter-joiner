## What is wrong

Three suites install a pumpable `SynchronizationContext` and never clear it:

| suite | sites |
|---|---|
| `ThumbnailPreviewViewModelTests` | `Build()` |
| `BulkItemThumbnailTests` | two |
| `BulkCutViewModelDebouncedPreviewTests` | one |

Every other context-installing suite in the project already saves and restores
(`BulkCutViewModelTests`, `OperationViewModelTests`, `SplitViewModel*`, `StagedStatusWiringTests`), so this
is an inconsistency rather than a house style.

`SynchronizationContext` is per-thread and xUnit reuses pooled threads, so a leaked pump is inherited by
whatever class runs next on that thread. A class that installs none of its own would then have its
`ConfigureAwait(true)` continuations posted into a queue nobody drains, and the work would silently never
happen.

Found by inspection while fixing [[T-137]]. It was **not** the cause of that flake, which was a wall-clock
wait and is fixed.

## Status of the evidence — read this before acting

An attempt to fix this during T-137 appeared to break three tests
(`BulkSelectAllTests.BulkSelection_IsPureVmState_NoKeyframeReScan_NoThumbnailGrab`,
`BulkRowIntentTests.TogglingIntent_TriggersNoKeyframeScan_AndNoFrameGrab`,
`BulkItemThumbnailTests.ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree`).

**That evidence was contaminated** and should not be trusted: the mutation harness in use at the time
restored files with `shutil.move`, preserving their mtime, so MSBuild skipped the rebuild and the test runs
executed a still-mutated binary. One of the live mutations was "the grab never reaches the service", which
produces exactly the failures that were observed. See T-137's outcome for the full account.

So the open question is simply **unanswered**, not answered badly: nobody yet knows whether clearing the
context on teardown breaks anything. Re-test it on a verified-clean build before concluding.

Two shapes to consider when it is tried again:

1. **Restore the previously-current context.** Suspect on its face: that value can itself be another
   suite's leaked pump, so the restore would re-install the leak rather than end it.
2. **Clear to `null`.** A pooled thread's natural state, and every suite that needs a context installs its
   own. The more likely correct answer.

## Design
1. Clear to `null` on teardown in the three suites above; make that the single convention.
2. Rebuild with `--no-incremental` (or verify timestamps) before measuring anything.
3. Measure the solution-level flake rate before and after, >= 15 runs each, on an idle machine — check for
   stray `VideoSplitJoiner.App` / `testhost` processes first; one burning CPU invalidated a measurement
   during T-137.
4. If anything does break, fix the dependent test rather than the convention: a test that reads the result
   of fire-and-forget work needs a settle point, and `BulkItemViewModel.InFlightGrabs` (added by T-137) is
   the seam for it.

## Acceptance criteria
- [ ] Every suite that installs a `SynchronizationContext` clears it on teardown.
- [ ] Full suite green on a verified-clean build.
- [ ] Solution-level flake rate measured before and after, >= 15 runs each, and not worse.
- [ ] No test disabled, retried, serialised, or made tolerant to achieve it.

## Out of scope
Changing test parallelism. Changing production async behaviour — the fire-and-forget pipelines are correct;
only their observability was ever the problem, and T-137 addressed that.
