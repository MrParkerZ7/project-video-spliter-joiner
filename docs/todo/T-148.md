## Why this exists

[[T-137]] diagnosed a ~40%-per-run flake (6 failures in 15 solution-level runs, idle machine) and built a
working fix. The fix had to be **reverted**, because it makes `App.Tests` faster and three other tests
then fail 15/15. This ticket clears the way so T-137 can ship.

## Problem 1 — three tests are propped up by unrelated suites being slow

| test | what it assumes |
|---|---|
| `BulkSelectAllTests.BulkSelection_IsPureVmState_NoKeyframeReScan_NoThumbnailGrab` | `thumbs.GetThumbnailCallCount > 0` immediately after `AddRowsAsync` |
| `BulkRowIntentTests.TogglingIntent_TriggersNoKeyframeScan_AndNoFrameGrab` | `thumbs.Requests` is populated immediately after adding rows |
| `BulkItemThumbnailTests.ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree` | 3 grabs reach the shared gate within 500ms |

Each reads the result of a **fire-and-forget** grab without waiting for it. That assumption currently
holds only because two unrelated suites burn 300-500ms per call site in wall-clock waits, which slows the
whole assembly enough for the continuations to land. Remove that waste (T-137's fix) and all three fail
every run. They are latently broken today.

Note the trap: adding `await Task.WhenAll(rows.Select(r => r.InFlightGrabs))` is **not sufficient** — it
was tried. The grab is only *requested* once the row's keyframe scan resolves, so an in-flight task that
does not exist yet completes instantly and the counter is still zero. The settle has to cover the scan
first, then the grab.

## Problem 2 — three suites leak a SynchronizationContext

`ThumbnailPreviewViewModelTests`, `BulkItemThumbnailTests` and `BulkCutViewModelDebouncedPreviewTests`
install a pumpable `SynchronizationContext` and never clear it. Every other context-installing suite in
the project (`BulkCutViewModelTests`, `OperationViewModelTests`, `SplitViewModel*`,
`StagedStatusWiringTests`) saves and restores, so this is an inconsistency rather than a house style.

`SynchronizationContext` is per-thread and xUnit reuses pooled threads, so a leaked pump is inherited by
whatever class runs next there. A class that installs none of its own has its `ConfigureAwait(true)`
continuations posted into a queue nobody drains, and the work silently never happens.

Both obvious fixes were tried and both made things worse:

1. **Restore the previously-current context.** That value can itself be another suite's leaked pump, so the
   restore re-installs the leak on the way out. Turned an intermittent failure into a permanent one.
2. **Clear to `null`.** Correct in isolation, but it breaks the same three tests from Problem 1, for the
   same reason — with no ambient context their continuations go to the pool and the timing assumption
   fails.

So Problem 1 must be fixed first; Problem 2 becomes safe once it is.

## Design
1. **Give the three tests real settle points**, covering scan *then* grab. `BulkItemViewModel` needs an
   awaitable seam for the keyframe scan the way T-137's branch added one for the grab
   (`InFlightGrabs`); `ManyRows_ShareOneGate` needs a signal for "N grabs are parked at the gate" rather
   than a 500ms spin.
2. **Then** make every context-installing suite clear to `null` on teardown, and make that the single
   convention.
3. **Then** re-apply T-137's fix and close it.
4. Verify each step with a before/after flake-rate measurement over >= 15 solution-level runs on an idle
   machine — not a single green run. (Check for stray `VideoSplitJoiner.App` / `testhost` processes first;
   one burning CPU in the background invalidated a measurement during T-137.)

## Acceptance criteria
- [ ] The three tests assert on settled work and pass with `App.Tests` running at full speed (T-137's fix applied).
- [ ] They also pass with no ambient `SynchronizationContext`.
- [ ] Every suite that installs a context clears it on teardown.
- [ ] Flake rate measured before and after, >= 15 solution-level runs each, and strictly better.
- [ ] No test disabled, retried, serialised, or made tolerant to achieve it.
- [ ] T-137 unblocked, its fix re-applied, and both closed.

## Out of scope
Changing test parallelism. Changing production async behaviour — the fire-and-forget pipelines are correct;
only their observability was ever the problem.
