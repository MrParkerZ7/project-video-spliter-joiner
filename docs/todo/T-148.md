## What is wrong

Three suites install a pumpable `SynchronizationContext` and never clear it:

| suite | sites |
|---|---|
| `ThumbnailPreviewViewModelTests` | `Build()` |
| `BulkItemThumbnailTests` | two |
| `BulkCutViewModelDebouncedPreviewTests` | one |

Every other context-installing suite in the project already saves and restores
(`BulkCutViewModelTests`, `OperationViewModelTests`, `SplitViewModel*`, `StagedStatusWiringTests`), so this
is an inconsistency rather than a house style.

`SynchronizationContext` is per-thread and xUnit reuses pooled threads, so a leaked pump is inherited by
whatever class runs next on that thread. A class that installs none of its own would then have its
`ConfigureAwait(true)` continuations posted into a queue nobody drains, and the work would silently never
happen.

Found by inspection while fixing [[T-137]]. It was **not** the cause of that flake, which was a wall-clock
wait and is fixed.

## Status of the evidence — read this before acting

An attempt to fix this during T-137 appeared to break three tests
(`BulkSelectAllTests.BulkSelection_IsPureVmState_NoKeyframeReScan_NoThumbnailGrab`,
`BulkRowIntentTests.TogglingIntent_TriggersNoKeyframeScan_AndNoFrameGrab`,
`BulkItemThumbnailTests.ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree`).

**That evidence was contaminated** and should not be trusted: the mutation harness in use at the time
restored files with `shutil.move`, preserving their mtime, so MSBuild skipped the rebuild and the test runs
executed a still-mutated binary. One of the live mutations was "the grab never reaches the service", which
produces exactly the failures that were observed. See T-137's outcome for the full account.

So the open question is simply **unanswered**, not answered badly: nobody yet knows whether clearing the
context on teardown breaks anything. Re-test it on a verified-clean build before concluding.

Two shapes to consider when it is tried again:

1. **Restore the previously-current context.** Suspect on its face: that value can itself be another
   suite's leaked pump, so the restore would re-install the leak rather than end it.
2. **Clear to `null`.** A pooled thread's natural state, and every suite that needs a context installs its
   own. The more likely correct answer.

## Design
1. Clear to `null` on teardown in the three suites above; make that the single convention.
2. Rebuild with `--no-incremental` (or verify timestamps) before measuring anything.
3. Measure the solution-level flake rate before and after, >= 15 runs each, on an idle machine — check for
   stray `VideoSplitJoiner.App` / `testhost` processes first; one burning CPU invalidated a measurement
   during T-137.
4. If anything does break, fix the dependent test rather than the convention: a test that reads the result
   of fire-and-forget work needs a settle point, and `BulkItemViewModel.InFlightGrabs` (added by T-137) is
   the seam for it.

## Acceptance criteria
- [x] Every suite that installs a `SynchronizationContext` clears it on teardown. *(The three named suites
  now clear to `null`; the other six uninstall their own pump by restoring the value they captured, which
  was measured to be xUnit's per-test context and never a foreign pump — see Outcome.)*
- [x] Full suite green on a verified-clean build.
- [x] Solution-level flake rate measured before and after, >= 15 runs each, and not worse.
- [x] No test disabled, retried, serialised, or made tolerant to achieve it.

## Out of scope
Changing test parallelism. Changing production async behaviour — the fire-and-forget pipelines are correct;
only their observability was ever the problem, and T-137 addressed that.

## Outcome — 2026-09-02: the convention is now uniform, and the leak was latent

Shape **2 (clear to `null`)** was taken, at 25 install sites across the three suites. Nothing broke.

### The contaminated evidence is formally refuted
All three tests the previous attempt blamed pass on a verified-clean build: 20/20 solution-level runs, plus
10 consecutive targeted runs of exactly those three. Clearing the context breaks nothing.

| test | result |
|---|---|
| `BulkSelectAllTests.BulkSelection_IsPureVmState_NoKeyframeReScan_NoThumbnailGrab` | pass, 30/30 |
| `BulkRowIntentTests.TogglingIntent_TriggersNoKeyframeScan_AndNoFrameGrab` | pass, 30/30 |
| `BulkItemThumbnailTests.ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree` | pass, 30/30 |

### Flake rate — measured, unchanged

| | runs | failing runs | tests per run |
|---|---|---|---|
| before | 20 | **0** | 1302 (850 + 452) |
| after | 20 | **0** | 1302 (850 + 452) |

Solution-level `dotnet test`, `--no-build` against a `--no-incremental` build, idle machine (no stray
`VideoSplitJoiner.App` / `testhost`), logs retained. The test binary's md5 was recorded before and after
each block: unchanged across all 20 runs of a block, and different between blocks — so no run executed a
stale binary. **The baseline was already clean, so the only claim this supports is "not worse".** This
change fixes no observed failure; T-137 had already removed the wall-clock wait that produced them.

### The leak was real by construction but never actually bit
Instrumented with an assembly-level `BeforeAfterTestAttribute`, whose `Before` runs *before* xUnit installs
its own context and therefore sees the raw ambient context of the pooled thread:

- **0 leaked contexts observed at test entry**, across 5 solution runs (~4250 App-test starts) before the
  fix — and 0 after.

The reason is that xUnit 2.8.1 already cleans up incidentally: `TestInvoker` wraps every test method in its
own `AsyncTestSyncContext` and restores the pre-test ambient context in a `finally`. A suite's installed
pump therefore does not survive its own test even without a teardown. What this ticket removes is the
*dependence* on that undocumented behaviour, not an active fault.

### Where the clear has to live (measured, and not obvious)
A class-level `IDisposable.Dispose()` on the test class — the shape the Design implied — would have been
**inert**. xUnit's restore runs BEFORE the test class is disposed, so a class-level teardown only ever
observes the already-restored context. Probed directly: a test that installs a marker context in its body
sees `null` by the time `Dispose()` runs, on the same thread.

So the clear lives in the scope that *installed* the context: `PumpContext` implements `IDisposable`
(clearing to `null`) and each test binds it with `using var pumpScope = pump;`. Instrumenting that
teardown across a full `App.Tests` run:

| suite | sites | pump still current at teardown |
|---|---|---|
| `ThumbnailPreviewViewModelTests` | 13 | 13 |
| `BulkCutViewModelDebouncedPreviewTests` | 4 | 4 |
| `BulkItemThumbnailTests` | 8 | 1 |

**18 of 25 clears are load-bearing.** In the other 7 (the `BuildReadyRowAsync` tests) xUnit's
`AsyncTestSyncContext` is current at end-of-body — on the *same* thread that installed the pump, so the
pump had already been displaced by xUnit's own machinery and there was nothing left to uninstall. Those
seven clears are no-ops that null out xUnit's wrapper a moment before xUnit restores the entry ambient
itself; harmless, and the suite is green, but they are not evidence of a pump being removed.

### Shape 1's suspicion is retired
The worry that restoring the previously-current context re-installs another suite's leak does not hold: in
the six conforming suites the captured `prior` is xUnit's own per-test `AsyncTestSyncContext` (confirmed by
both probes), never a foreign pump. Those suites were left as they are — converting them would strip
xUnit's context mid-body for no gain.

### What changed
`tests/App.Tests/{ThumbnailPreviewViewModelTests,BulkItemThumbnailTests,BulkCutViewModelDebouncedPreviewTests}.cs`
— teardown only. No assertion, timeout, trait, attribute or parallelism setting was touched; no test was
disabled, retried, serialised, or made tolerant.
