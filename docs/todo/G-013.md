## Why / vision
A single progress bar isn't enough reassurance on a long split — the user wants to see WHICH step it's on (synced to the actual actions) and roughly HOW LONG until it's done. This turns "is it stuck?" into "it's splitting segment 3 of 4, ~40s left."

## Gap from current state
- `OperationViewModel` exposes `Progress` (0..1) + `IsRunning` only. There's no per-stage status synced to the real work, and no ETA. (G-012/T-042 plans a basic "Splitting…" status + indeterminate mode — this goal formalizes named stages + adds ETA.)
- The engines (`SplitEngine`/`JoinEngine`) report a `IProgress<double>` fraction but not named stage transitions; the runner parses ffmpeg `time=` for the fraction.

## Decisions
- **D1 · Stage model synced to real actions** — the engines report stage transitions (not just a fraction): e.g. split = `Preparing` (probe/snap) → `Splitting` (per-segment, with "segment N of M" when the segment muxer is producing outputs) → `Finalizing` (temp→move) → `Done`. `OperationViewModel` exposes a `StatusText`/`Stage` that the UI shows; it updates when the actual stage changes, driven by real callbacks — never a fixed timed script.
- **D2 · ETA from real elapsed-vs-progress** — while running, track elapsed (a `Stopwatch`) + the current progress fraction → remaining ≈ elapsed × (1−frac)/frac; smooth it (moving average) so it doesn't jitter. Show "~Xs / ~N min left"; when progress isn't granular (indeterminate), show the stage + "estimating…" instead of a fake number. Clear on success/fail/cancel.
- **D3 · Extend the existing surface** — build on `OperationViewModel` + the `IProgress` path (ideally the same work as G-012/T-042); split/join engines gain a stage/segment signal; VM stays fake-testable. **Build with G-012** to avoid two passes over the same progress code.

## Risks
- Stage granularity depends on what ffmpeg/the engine can actually report — segment-count is knowable (from the cut plan); intra-segment % may be coarse for `-c copy`. Report honestly (stage always; % + ETA when available).
- ETA jitter on fast/nonlinear progress → smoothing + a "~" prefix; never show a precise-looking wrong number.
- `Stopwatch`/time is fine in the app (unlike the workflow-script constraint).

## Out of scope
Byte-accurate per-file %, historical/learned time estimates, ETA for the background keyframe index — later.
