## Concept

An existing bug, found by T-189's adversarial review (2026-10-05). `SmartCutPlanner.Plan` returns `PureCopy` whenever
the **start** is on a keyframe (or at 0) and ignores the **end**. The engine then runs the lossless cut, which snaps a
mid-GOP outro to a keyframe, with no warning. Meanwhile the Bulk Cut row (where `ExactCutApplies` is true) shows and
judges the Requested outro, so the row and the result disagree.

Measured (synthetic, `g=50` at 25 fps): intro 4.0 s / outro 7.1 s → a 4.18 s output; an **outro-only** cut (intro 0,
outro 7.1 s) → 8.10 s, the same as Lossless, with only an unrelated "Cut at 0s is outside the file bounds" note.
Trimming only the end is a common Exact use. SPEC-011 I158/I164 and ADR 0018 already name this as a known exception
(written by T-189).

## Design

Recommended (★): **keep the requested end with no re-encode.** After T-190 the Exact joint is one concat pass over
`[head, source with inpoint/outpoint]`. A `PureCopy` plan with an end becomes that same concat with no head:
`[source inpoint=Start (a keyframe), outpoint=End]`, so the end lands on the requested frame (subject to T-220's
B-frame end overrun, which this ticket does not change). A plan with no end (outro "none") stays the lossless cut.
Alternative, not chosen: make the row predicate per cut and show the outro at Snapped with a warning (honest, but
loses the exact end the user asked for).

## Detail

- `PureCopy` with `End` set → the single concat leg (no head encode); without `End` → today's lossless path.
- The row needs no change: it already shows the Requested outro, which now matches the result.

## Interfaces / contracts

- SPEC-001 I40 (PureCopy) gains the end rule; SPEC-011 I158/I164's known-exception sentence and ADR 0018's matching
  note are removed in the same commit.

## Acceptance criteria + Case-Coverage Matrix

- [ ] **Repro first:** an integration test runs an Exact row with intro 0 (and one with intro on a keyframe) and outro
      7.1 s on a `g=50`, 25 fps synthetic source and asserts the output ends at 7.1 s (within one frame plus T-220's
      documented B-frame allowance); it FAILS on the code as it stands when this ticket starts (output 8.10 s).
- [ ] After the fix it passes; the output decodes with 0 errors and its first frame is the source's frame at Start.
- [ ] Outro "none" with the intro on a keyframe: unchanged (lossless, no concat).
- [ ] The row's shown outro, the batch duration and the result agree.
- [ ] SPEC-001 / SPEC-011 / ADR 0018 updated in the same commit; full suite green, 0 skipped.
