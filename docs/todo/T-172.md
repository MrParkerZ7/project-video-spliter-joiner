## Concept

Give the hover card pictures worth showing — stop discarding resolution on the way in, and stop
manufacturing it on the way out.

## Design

**1. Stop capping so hard on the way in.** `TryAttachThumbnail` shrinks every upload to
`ProfileThumbnailWidth = 320` (`BulkCutViewModel.cs:127`, `:1877`) and captures grab at exactly that width
through ffmpeg's `scale=320:-1`. 320 was chosen when the card was the only consumer and the card is 320
wide, so it is a cap with no headroom: any future card, any high-DPI display, any zoom re-creates this
ticket. **Settled: 640** — see § Decisions. Uploads are shrunk to at most 640 (never enlarged);
captures are scaled to exactly 640.

✓ **Measured: raising the capture width is free.** A single-frame grab took ~119 ms at 320, 640, 960
and 1920 alike — decode and seek dominate, scaling does not register. Width costs bytes, not time.

**2. Fill, and say when the picture is soft.** The card is
`StackPanel Width="320"` → `Border Height="180"` → `Image Stretch="Uniform"`
(`BulkCutView.xaml`, the `ProfilePreviewCard` template). `Uniform` scales **up** as readily as down, so a
64x36 picture is drawn at 320x180 — a 5x enlargement. **Decided: keep filling** (the request was
"fill picture"), and when the bitmap's `PixelWidth` is below the card's box width, show a short note —
"low resolution — re-take with 📷 Use current frame for a sharp preview". The enlargement becomes a
disclosed limitation instead of a silent blur. I107 is rescoped to storage accordingly.

**3. Two widths that must stay related — no longer equal.** The card's box stays 320 DIP; the stored
width becomes 640. They were equal by accident before and are now deliberately 1:2 (sharp to 200%
scaling). The low-res note's threshold must read the **card's** box width, not a third hand-typed number.
Make the box width a named resource, as T-168 did for `ProfileBarMaxHeight`, and pin both relationships
in tests: threshold == box width, stored width == 2x box width.

**4. The eleven existing pictures.** They cannot be re-grabbed — `CutProfile` records no source video.
Settled: they keep filling the card, soft, and carry the low-res note until re-taken by hand. Do NOT
add a migration that upscales them on disk: that is I107's exact prohibition, and it would destroy the
evidence that they are small.

## Acceptance criteria
- [ ] A picture narrower than the card's box still **fills** it AND the card shows the low-resolution note
      naming *Use current frame*. Mutation: drop the note's visibility binding → fails; set the threshold
      to 0 → a 64px picture shows no note → fails.
- [ ] A picture at or above the box width fills it exactly, with no crop and no bars, and shows **no**
      low-res note. (Guards the vacuous version: a note that is always visible passes the test above.)
- [ ] A newly captured picture is stored **640** px wide, and an upload wider than 640 is shrunk to 640
      (narrower uploads untouched) — asserted by reading each stored file's real pixel width, not the constant.
- [ ] Tests pin the relationships so they cannot drift: low-res threshold == card box width, and stored
      width == 2x card box width.
- [ ] Backup/restore still round-trips a picture at the new size (SPEC-007 I81/I91), and the test names
      the resulting backup file size so a regression in bulk is visible.
- [ ] The chip is unchanged — still 28x28, still `UniformToFill`.

## Risks
- **Backup size.** `ProfileBackup` inlines pictures as base64 (I81). At 640 an 11-profile backup measures
  ≈0.23–1.1MB (was ≈0.10–0.26MB at 320). Bounded — this is why the answer was a cap, not "keep everything".
- SPEC-007 I106 changes 320 → 640, and **I107 is rescoped**: storage never enlarges; the card may fill a
  smaller picture but must disclose it. If a new invariant is added for the low-res note, the count moves,
  so `docs/specs/_index.md` changes in the same commit or three guards go red.

## Out of scope
Re-picturing the existing eleven, and the 1-byte file [[T-170]] left in the store — a separate cleanup.

## Decisions (answered)

### Two forks — answered 2026-09-13 via `todo-options`

**Original fork (archived):**
> Two forks. (1) STORED WIDTH — keep the upload's original resolution uncapped, or raise the cap (640?
> 960?)? Uncapped is simplest and sharpest, but ProfileBackup inlines every picture as base64 (SPEC-007
> I81), so a backup file grows with it; the whole store is 10KB today. (2) SMALL PICTURES IN THE CARD —
> never upscale past native, upscale to fill as today, or allow a bounded stretch such as 2x. Option 1
> obeys I107; option 2 is what ships now.

#### Fork 2 — a picture smaller than the card: **fill it, and flag it as low resolution**

Chosen, and it reverses this ticket's own plan, which said *"the honest one to keep is I107's"*. The
grounding is what moved it:

- **All 11 pictures in the real store are 16:9 at 64 or 96px** — there is no 320-wide picture to compare
  against, so "never enlarge" would have shown every existing profile at a fifth to a third of the card.
- **They cannot be regenerated.** `CutProfile` is `(Name, IntroFromStart, OutroFromEnd, ThumbnailPath)`;
  nothing records the source video, so nothing can re-grab the frame.
- The request was explicitly to **fill** the picture.

So the card keeps filling, and a picture narrower than the card's box says so and names the gesture that
fixes it (📷 *Use current frame*). What keeps this honest is the disclosure, not the refusal: an
enlargement the user is told about is a known limitation; a silent one looks like a rendering bug.
**SPEC-007 I107 is rescoped** — storage never enlarges; the card may fill a smaller picture, but must
disclose it.

**Rejected:**
- *Never enlarge (card fits the picture)* — sharp, but a 64px picture at 64x36 is a fifth of the card, and
  not the "fill" asked for. (For this library it would have been one attribute, `StretchDirection="DownOnly"`
  — all 10 readable files are 96 DPI, so WPF's natural size equals pixel size. An upload with other DPI
  metadata would be sized by DPI, not pixels, so a robust version binds to `PixelWidth` instead.)
- *Enlarge up to 2x* — still visibly soft, and fills neither.
- *Fill as today, no flag* — the silent 5x blur that prompted the ticket.

#### Fork 1 — stored width for NEW pictures: **640**

Measured, not estimated:

| check | result |
|---|---|
| system display scale | **100%** (`AppliedDPI` 96) — the 320-DIP card is exactly 320 physical px. Per-monitor scale on the two secondary screens was **not** read. |
| capture time by width | **~119 ms at 320, 640, 960 and 1920 alike** — best of 5, the app's arg shape (`-ss` before `-i`, one frame, `scale=W:-1`), synthetic 60s 1080p H.264. Decode and seek dominate; scaling is free. |
| bytes per capture (H.264 decode path) | 320: 6.8KB · 640: 15.5KB · 960: 25.5KB · 1920: 74KB |
| backup of 11 profiles (base64, x4/3) | 320: ≈0.10–0.26MB · **640: ≈0.23–1.1MB** · 960: ≈0.37–2.3MB · 1920: ≈1.1–10MB (low end smooth footage, high end a noise worst case) |

640 is exactly sharp in the 320-DIP card up to 200% scaling, costs nothing extra to capture, and roughly
doubles backup size rather than multiplying it tenfold.

**Rejected:**
- *Keep 320* — already pixel-exact on this machine's primary display, but soft on any screen scaled to 150%
  or more; the secondary screens' scale was not measured.
- *Keep the original, uncapped* — a 1080p capture stores at 1920px, putting an 11-profile backup at up to
  ≈10MB. It also breaks a stated design premise: `ProfileBackup.cs:23` justifies inline base64 with
  *"Images are ~96px, so base64 inside the JSON costs little"*.
- *960* — sharp to 300%, for a scale factor nobody has measured here, at up to ≈2.3MB per backup.

#### ⚠ What neither answer does

**None of this sharpens the eleven pictures already saved.** Only re-taking each one does. The low-res flag
is what makes that visible per profile instead of leaving the user to guess which cards are soft and why.

Also noted for the builder: `ProfileBackup.cs:23`'s "images are ~96px" comment was already wrong at 320 and
will be further off at 640 — correct it in the same change.
