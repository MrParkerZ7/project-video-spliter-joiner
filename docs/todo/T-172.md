## Concept

Give the hover card pictures worth showing — stop discarding resolution on the way in, and stop
manufacturing it on the way out.

## Design

**1. Stop capping so hard on the way in.** `TryAttachThumbnail` shrinks every upload to
`ProfileThumbnailWidth = 320` (`BulkCutViewModel.cs:127`, `:1877`) and captures grab at exactly that width
through ffmpeg's `scale=320:-1`. 320 was chosen when the card was the only consumer and the card is 320
wide, so it is a cap with no headroom: any future card, any high-DPI display, any zoom re-creates this
ticket. What the new width should be is the `decision:` — as is whether an upload is capped at all.

⚠ **Raising the capture width is not free the way raising the upload cap is.** Captures come from
`IThumbnailService` and a wider grab costs ffmpeg time on every profile save. Measure before choosing.

**2. Stop inflating on the way out.** The card is
`StackPanel Width="320"` → `Border Height="180"` → `Image Stretch="Uniform"`
(`BulkCutView.xaml`, the `ProfilePreviewCard` template). `Uniform` scales **up** as readily as down, so a
64x36 picture is drawn at 320x180 — a 5x enlargement. Bounding the render at the bitmap's own
`PixelWidth`/`PixelHeight` makes the card honour I107 instead of contradicting it.

**3. Two hardcoded 320s that must agree.** The card's `Width="320"` is a XAML literal; the store's
`ProfileThumbnailWidth = 320` is a C# const. Nothing ties them together, and this project has been bitten
by exactly this shape more than once. T-168 made `ProfileBarMaxHeight` a named resource so a test could
read it; do the same here, or assert the two agree.

**4. The eleven existing pictures.** They cannot be re-grabbed — `CutProfile` records no source video.
Whatever the display fork settles decides what they look like until they are re-taken by hand. Do NOT
add a migration that upscales them on disk: that is I107's exact prohibition, and it would destroy the
evidence that they are small.

## Acceptance criteria
- [ ] A picture whose stored width is below the card's box is **not** enlarged beyond its own pixel
      dimensions (whatever the decision settles). Mutation: restore the unbounded `Uniform` → the test fails.
- [ ] A picture at or above the box width still fills it exactly, with no crop and no bars.
- [ ] A newly captured or uploaded picture is stored at the width the decision settles, asserted by
      reading the stored file's real pixel width — not by trusting the constant.
- [ ] The card's box width and the stored-width constant are pinned to each other by a test, so they
      cannot drift apart silently.
- [ ] Backup/restore still round-trips a picture at the new size (SPEC-007 I81/I91), and the test names
      the resulting backup file size so a regression in bulk is visible.
- [ ] The chip is unchanged — still 28x28, still `UniformToFill`.

## Risks
- **Backup bloat.** `ProfileBackup` inlines pictures as base64 (I81). Uncapped originals could turn a
  10KB store into a multi-megabyte backup file. This is the main argument for a cap over "keep everything".
- SPEC-007 I106/I107 are reworded, and I107's rule is extended to rendering. Invariant counts move, so
  `docs/specs/_index.md` changes in the same commit or three guards go red.

## Out of scope
Re-picturing the existing eleven, and the 1-byte file [[T-170]] left in the store — a separate cleanup.
