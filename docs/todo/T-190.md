## Concept

Found by the T-187 measurement. In an H.264 Exact result the copied part lands **about 80 ms late**, and
about 80 ms of audio overlaps at the joint.

- The tail is made by `SmartCutArgsBuilder.TailCopy`, which delegates to `SplitArgsBuilder.PerSegment`
  (`SmartCutArgsBuilder.cs:162`): `-ss HeadEnd` before `-i`, `-c copy`, `-avoid_negative_ts make_zero`
  (`SplitArgsBuilder.cs:96-99`). With B-frames that gives the tail a video `start_time` of 0.080 s against
  audio at 0.000.
- The concat demuxer places the tail at the head's duration and keeps that internal offset. So in the final
  the first tail frame sits at 1.6 s instead of 1.5 s, and the tail's audio starts 80 ms before its video,
  overlapping the head's audio. Both were verified with frame md5s and ffprobe. The 1.6 s is an absolute reading:
  about 21 ms of it is the shift every concat-to-mp4 final gets from the head's AAC priming packet (§ Design, *joint
  time base*), so the tail itself is about 80 ms late.
- A full `-v error` decode of a shipped H.264 Exact final prints `[null @ …] non monotonically increasing dts to
  muxer` lines (verified: 1 on `t187bulk/final.mp4`, 4 on `t187-fixtures/work/smart2-final-current-4k-104.5.mp4`).
  The inpoint concat below printed 0 (`final2.mp4`).
- The same three-run shape also writes the kept bytes **twice**: once into `tail.mp4`, then again in the
  concat (`SmartCutEngine.cs:141-165`). On a 2-min 4K row the tail copy alone costs 0.41-0.65 s. On a
  multi-GB kept range on a slow disk it doubles the row's I/O.

The Bulk Cut reader measured the alternative: one concat over `[head, SOURCE with inpoint <keyframe>]`.
The output was the same size (61,407,365 vs 61,407,385 B), decoded with **zero** errors where the current
output has one boundary DTS warning, and lasted 10.02 s against 10.09 s for a 10 s keep.

**A second timing fault on the way: the time base.** Keyframe times (ffprobe packet `pts_time`) and the concat
demuxer's `inpoint`/`outpoint` are **absolute source timestamps**. ffmpeg's `-ss` (before or after `-i`) is an
**offset from the format `start_time`**. Core reads no `start_time` anywhere (a grep of `src/Core` is empty).
On a source whose `start_time` is not zero (MPEG-TS starts near 1.4 s by default; AVCHD `.mts` likewise), the
head and the kept part overlap by `start_time`, today and with the design below alike. The lossless path has the
same fault (measured at plan review, below), and T-219 fixes it there.

## Design

- **Two runs instead of three for a `HeadReencode`.** The head encode stays as it is in this ticket. The tail
  run and its temp file go. The concat reads the source itself from the boundary keyframe:

  ```
  file '<tempDir>\head.mp4'
  duration <HeadEnd − Start>
  file '<source>'
  inpoint <HeadEnd>
  outpoint <End>          ← only when the kept range has an end
  ```

  `HeadEnd` is by construction a keyframe (SPEC-001 I41), so the demuxer's seek to `inpoint` lands exactly
  on it and no frame before it is copied.
- **The time-base contract.** Exact assumes source pts and ffmpeg's `-ss` offsets coincide, which holds only
  when the format `start_time` is zero. So:
  - the gate reads `MediaInfo.StartTime` (ffprobe `format.start_time`, zero when absent or unparsable), which
    T-219 adds and maps in `MediaProbe.ProbeAsync`;
  - the Exact gate returns false when `|StartTime| > 1 ms`, with the reason *"frame-exact cutting is not
    supported yet for .ts, .m2ts and .mts files or other files whose timestamps do not start at zero"* (no parentheses
    inside the row warning, T-189's copy rule). The check sits in
    `SmartCutArgsBuilder.TryResolveEncoders`, the one gate the engine falls back on (`SmartCutEngine.cs:98-101`)
    **and** the one the Bulk row calls before Run (T-189), so the row and the run never disagree;
  - the engine returns `FellBack = true` with zero runs; `BulkTrimEngine` writes the lossless cut and its row
    warning, as for HEVC.

  **Choice logged.** Rejected: offsetting every time by `start_time` (the head `-ss Start − StartTime`, `inpoint`
  left absolute). It would make Exact correct on such files, but the same offset is unaccounted for across the
  whole timeline (keyframe ticks, `SplitPlanner`, the player position), no screen test covers that time base
  (T-219's TS tests cover the copy path's arguments, not an Exact head), and it is new capability rather than
  this fix.

  **The lossless path does not tolerate the offset either** (an earlier draft claimed it did). Measured at plan
  review on a synthetic TS (`start_time` 1.445 s, 2 s GOP, keyframes at 1.4667, 3.4667 and 5.4667 s):
  `PerSegment`'s `-ss 5.466667 -to 4` starts at source frame 180 (the 7.4667 s keyframe) instead of 120, with 106
  frames; `-ss 4.021334` (`start_time` subtracted) lands on frame 120, and so does the same content remuxed to
  MP4. The stop rule below is applied now: the copy-path fix is **T-219**, and this ticket is blocked by it, so the
  lossless cut a TS row falls back to is a correct keyframe-snapped cut by the time this ships.
- **The joint time base (for every timing check below).** The head's AAC priming packet has pts −0.021333, and the
  concat-to-mp4 shifts every stream to make it non-negative, so the final's video does not start at 0. Simulated on
  a synthetic libx264 B-frame mp4 (30 fps, 2 s GOP, `Start` 3.3, `HeadEnd` 4) with the shipped head args and the
  [head `duration 0.7`, source `inpoint 4`] list: the final's video starts at 0.021029, and the joint frame (index
  21) sits at 0.721029 absolute and 0.700 relative to the final's first video frame. Half a frame at 30 fps is
  16.7 ms, so an absolute reading would fail even after a correct fix. *"Presented at `HeadEnd − Start`"* therefore
  always means **relative to the final's first video frame**: frame N's pts minus the final video stream's
  `start_time`, in the repro, in the after-fix cases and in the SPEC-001 joint-timing invariant.
- **The list is built inside SmartCut**, by a new `SmartCutArgsBuilder.RenderJointList(headPath, headDuration,
  sourcePath, headEnd, end)`. It formats seconds with `SplitPlanner.ToFfmpegSeconds` and quotes paths with
  `JoinArgsBuilder.QuoteConcatPath` (internal, `JoinArgsBuilder.cs:73`). Join's own `RenderConcatList` and
  every Join test stay untouched (SPEC-003 I20-I25). The command is the unchanged
  `JoinArgsBuilder.ConcatCopy` (`-f concat -safe 0 -i list -map 0 -c copy`), so it still satisfies
  `SatisfiesCopyInvariant`.
- **The head's `duration` directive** fixes where the source leg starts. It is exactly `HeadEnd − Start`,
  whatever the head's AAC priming or padding makes its container duration. If the audio criterion below
  still sees an overlap, the head entry also gets `outpoint <HeadEnd − Start>`. The tests decide, and the
  Build log records which directives were needed.
- **`TailCopy` is deleted.** Its callers are the engine (`SmartCutEngine.cs:143`) and one test,
  `SmartCutTests.cs:140-148` `TailCopy_IsStillAPureStreamCopy_NoEncoderLeaksIn`, which is replaced (a recorded
  contract change, under Interfaces). SPEC-001 I44's *"byte-identical to what the lossless path would have
  produced"* becomes *"the kept part is the source's own packets, read by the concat demuxer from the boundary
  keyframe"*.
- **Fallback candidate, only if the design above fails the repro tests:** keep three runs, but write the tail
  so its video starts at 0 (an Exact-only tail builder: `-copyts`, or no `make_zero`, and the concat
  `inpoint`). Record in the Build log which candidate passed, and why. **Stop rule (applied at planning):** the
  standalone lossless output is shifted on two shapes, a B-frame source in the segment muxer and a source whose
  `start_time` is not zero in `PerSegment`, and T-219 fixes both. If the diagnosis here finds a further shape (for
  example a standalone `PerSegment` output A/V-shifted against the source), that is another bug in the sacred copy
  path: open a separate fix ticket; never patch it silently here. **A third shape is already found (plan review
  round 4): the end overrun.** The concat demuxer's `outpoint` is a decoding timestamp (ffmpeg docs), so on a
  B-frame source a cut with an end keeps the reorder depth past `End`: on the fixture of § Design *joint time base*
  with `End` 9.5, 188 frames against 186 and 6.2667 s of video against 6.2 s, with a clean decode. The shipped
  `PerSegment` `-to` does the same (92 frames against 90 for [3, 6) on the `MediaFixtures` recipe). It is **T-220**
  (later). This ticket's duration, A−V and frame checks allow it for a cut with an end, and never patch it.

## Detail

- **Interim progress:** `progress?.Report(0.5)` after the head and `1.0` after the concat (the old 0.8 step
  goes with the tail run). T-191 replaces these with real progress.
- **`FullReencode`** (no keyframe between start and end) is unchanged: one run, the head is the output.
- **`PureCopy`** is unchanged: fall back, zero runs.
- **Temp dir:** still `.vsj-smartcut-<guid>`, swept in `finally`. It now holds the head, the list and the
  final temp, and no tail.
- **Replace originals:** unchanged. The engine is handed the sibling `.vsj-exact` temp
  (`BulkTrimEngine.cs:260-262`), and the source is only read.
- **Files touched outside SmartCut:** none in Core. `MediaInfo.StartTime` and its probe mapping come from T-219,
  which is why this ticket is built after it (T-193's probe cache comes through T-219). In the App, only
  `PrecisionNote` (below).

## Edge cases

- **A source with an open GOP** (a non-IDR keyframe whose leading pictures refer back across it). For H.264
  in MP4, `stss` normally lists IDRs only. If a leading-picture case appears, the joint check catches it, and
  the row should fall back rather than write it. No such fixture can be made with the bundled encoders. This
  is noted in Risks.
- **An `End` inside the last GOP** keeps today's planner behaviour. `outpoint` works at packet level, on
  decoding timestamps. The output's video duration is asserted within the end-overrun allowance above (T-220).
- **Non-MP4 outputs (.mkv/.mov)** use the same list. The integration tests cover mp4. The other containers
  are covered by the args tests only. An MKV whose `start_time` is not zero falls back like TS.

- **T-219:** `MediaInfo.StartTime` and its probe mapping, and the lossless fix that makes the fallback this

## Risks

- **The evidence for `inpoint` is from a reader's run**: duration, size and decode errors, not the frame-md5
  and audio checks this ticket requires. If it fails them, the fallback candidate is specified above.
- **VP9/VP8/AV1/MPEG-4/MPEG-2 Exact rows take the new two-run path too.** Their joints were never verified
  before or after (T-202). The change does not make them less verified, but it does change their bytes.
- **The concat demuxer's `inpoint` can hand over a few audio packets before the in point.** They get
  timestamps just before the file's start. The audio criterion is there to catch an overlap, and the head
  `outpoint` is the remedy named in the Design.
- **Exact on TS/MTS becomes a stated fallback.** Those rows used to write an overlapping file; now they get the
  keyframe-snapped lossless cut with a reason, before and after the run. That cut is correct only with T-219's
  copy-path fix, which is why this ticket is blocked by it.
- **Some MP4/MOV files may start above zero too** (a B-frame delay with no edit list). They fall back with the same
  reason, and the row says so before Run. Real camera files cannot be sampled here, so how often that happens is
  unknown; the Build log records the `start_time` of every synthetic fixture the bench makes (all zero expected,
  since ffmpeg's mp4 muxer writes an edit list).
