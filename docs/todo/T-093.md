## Concept
Running a split sits in **"Preparing…"** for a long time (looks frozen) and the ETA shows **"estimating…"** seemingly
forever. Fix the redundant/blocking work in the Preparing stage and make the progress/ETA honest.

## Grounding (2026-08-13 — root cause found)
- `SplitEngine.SplitAsync` reports `"Preparing"` (`:74`) then, **before the ffmpeg pass**, calls `ProbeAsync` (`:77`)
  AND `GetKeyframesAsync` (`:85`). On a big/4K file the keyframe scan dominates the wait; the whole "Preparing" stage
  blocks on it with **no progress shown** → looks frozen.
- **`MediaProbe.GetKeyframesAsync` has NO in-flight dedup** (`MediaProbe.cs:141-185`): it checks `_keyframeCache` at
  the START and only writes it at the END. So two concurrent calls for the same file **both scan**. The app already
  runs a **background keyframe index at load** (`SplitViewModel.cs:589 _probe.GetKeyframesAsync(path, cts)`), sharing
  the SAME `MediaProbe` instance (`MainViewModel.cs:61`). **If the user clicks Run before that load-scan finishes**
  (or the cache is cold), the split starts a SECOND full scan instead of awaiting the first → doubled wait. ← the certain bug.
- ETA (`EtaEstimator`): stays `null` → "estimating…" while `fraction ≤ MinFraction`. A fast single-pass `-c copy`
  reports `time=` sparsely, so the fraction can stay low most of the run → "estimating…" for most/all of the op.

## Fix (confirm the dominant cause by measuring a real large-file split first)
1. **In-flight dedup on `GetKeyframesAsync` (certain win).** Add a `ConcurrentDictionary<string, Task<IReadOnlyList<TimeSpan>>>`
   of IN-FLIGHT scans keyed like the cache: a second caller for the same key **awaits the running scan** instead of
   starting its own. So the split reuses the load-time scan (or awaits it) — never double-scans. Keep the completed-result
   cache as-is.
2. **Reuse load-time work / don't re-probe.** The split's `ProbeAsync` + keyframe scan should reuse what the load already
   computed. Options: pass the load-time keyframes (and probe result) INTO the `SplitRequest` from `SplitViewModel`
   (which already holds `Keyframes` + the probe), OR rely on the shared cache + the new in-flight dedup so both are cache/await hits.
   Prefer whichever is cleanest; the goal is **zero redundant scan/probe** in Preparing when the UI already has them.
3. **Make "Preparing" look active, not frozen.** While the keyframe scan/probe runs in Preparing, surface it as
   **indeterminate / a sub-status** (e.g. "Preparing — scanning keyframes…") so the user sees motion. `OperationViewModel`
   already flips `IsIndeterminate` when there's no fraction — ensure the Preparing stage shows the indeterminate pulse.
4. **ETA fallback instead of "estimating…" forever.** When the fraction stays below the estimate threshold but the op is
   clearly running, fall back to a **duration-based estimate** (total file/segment duration vs elapsed copy rate) or seed
   the EMA from the FIRST real `time=` sample (lower `MinFraction`, or a wall-time-based seed) so the ETA converges within
   a few seconds. For a genuinely instant op, show nothing rather than a stuck "estimating…".

## Acceptance criteria + Case-Coverage Matrix
- [ ] Clicking Run right after loading a large file does NOT trigger a second keyframe scan — the split reuses/awaits the load-time scan (verify via `MediaProbe` scan-count / a runner-call-count test with the in-flight dedup).
- [ ] "Preparing" completes promptly when the keyframes are already available/in-flight; when a scan must run it shows an active (indeterminate) status, not a frozen "Preparing…".
- [ ] The ETA converges to a real estimate within a few seconds of the ffmpeg pass starting (or a sensible duration-based fallback), instead of "estimating…" for the whole run.
- [ ] Split output unchanged; the `-c copy` / keyframe-snap invariants intact.
- [ ] Build 0-warning; suite green + tests: in-flight dedup (2 concurrent GetKeyframesAsync for one path → ONE scan), ETA fallback converges.
- Matrix — Success: fast Preparing + converging ETA. Boundary: run-before-load-scan-done (dedup/await, not double-scan); huge 4K file (active Preparing status); very short/instant split (no stuck estimating); cancel during Preparing (scan cancels). Required-Fail: none. (Live timing = app-run/user-verified on a real large file.)

## Dependencies
None. Touches `MediaProbe` (in-flight dedup), `SplitEngine`/`SplitViewModel` (reuse), `OperationViewModel`/`EtaEstimator` (status + ETA).

## Risks
Measure first — confirm whether the dominant cost is the double-scan (dedup fixes it), a genuinely slow single scan
(active-status + reuse), or the ETA (fallback). In-flight dedup must be cancellation-safe (a cancelled caller must not
cancel the shared scan for others) and cache only successful results. Don't change split output or the copy invariants.

## Out of scope
Speeding up the ffmpeg copy itself; a progress bar for the keyframe scan (indeterminate is enough); re-architecting the probe.
