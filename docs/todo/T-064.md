## Concept
The user can add a cut marker only once after the T-059 two-column relayout. Reproduce it in the running app, identify which cause (S1–S4 in G-022) is real, and fix the actual layer — without weakening the correct "one marker per keyframe" dedup.

## Design / investigation steps
1. **Reproduce** — `app-run` with a real video; load it, add a cut (via the "Add" button, "Set cut point at playhead", AND a timeline click), then try to add a second at a **different** position. Note which path(s) fail and whether the source position advances.
2. **Diagnose against G-022 suspects:**
   - **S1** — does the "Add" button's `NewMarkerPosition` re-seed from the playhead between clicks? Pre-T-059, did it auto-track? Check the field's binding + any seed in the moved layout.
   - **S2** — does `Player.Position` still update live in the two-column layout (player moved to the left column)? If it's frozen, `SetCutAtPlayheadCommand` always re-adds the same time.
   - **S3** — is `Track.ActualWidth` valid (non-zero, current) at click time in the new left column? Log/inspect via `OnTrackSizeChanged`. A zero/stale width collapses X→time to a constant.
   - **S4** — reproduce on the pre-T-059 build (`git stash`/checkout `5c8f611^`) to confirm whether it's a true regression or pre-existing.
3. **Fix at the true layer:**
   - S1 → restore the playhead-seed / correct the field binding so each add uses a fresh position.
   - S2 → restore the live `Player.Position` propagation to the timeline/field.
   - S3 → ensure the Track has a real width before mapping (guard `ActualWidth <= 0`, or re-measure).
   - If genuinely pre-existing (S4): still make repeated adds intuitive — e.g. the "Add" affordance should add at the **current playhead** (a live, moving position) rather than a static field, so consecutive adds at the moving playhead just work.
4. Add/adjust a unit test that would have caught the specific cause (e.g. two adds at distinct positions both land; position source advances).
