## Concept

The shared keyframe scan runs on `CancellationToken.None` (`MediaProbe.cs:203, 217`). Clear, a new load, a removed
Bulk row or a cancelled Preparing cancels only that caller's await (`WaitAsync(ct)`, `:177`), so the ffprobe keeps
reading the abandoned file to its end. The 100% read is measured; the reading never stops. Bulk Cut also frees its
scan-gate slot when the await is cancelled, so more than the 3 whole-file readers of SPEC-011 I3 can run at once.

Fix, as designed during G-059 planning:
- reference-count the awaiters of each in-flight key;
- run the shared scan on its own `CancellationTokenSource`;
- cancel it when the **last** awaiter cancels, so `FfprobeRunner` kills the process tree (SPEC-017 I29/I30) and
  nothing is cached;
- a caller that arrives after that cancellation starts a fresh scan, never a dying one;
- the Bulk gate holds its slot until the shared scan has actually ended.

SPEC-004 I19 is reworded: cancelled when no awaiter remains. T-093's guarantee is kept, so one caller's cancel never
tears the scan down while another still waits (`MediaProbeInFlightDedupTests` unmodified).

**Built after T-194.** It reworks cancellation of the one shared scan (`RunSharedScanAsync`,
`MediaProbe.cs:187-231`), which T-194 turns into the index, anchor and packet chain, so the new
`CancellationTokenSource` must also cancel T-194's anchor windows. Its MKV/TS trigger can fire when the drain starts
(G-059 § Risks, the owner question), while T-194 is still rewriting that method.

## Why later

- The disk contention a stale scan causes is **inferred, not measured**: the HDDs were off-limits.
- After T-194, an MP4/MOV scan finishes in milliseconds, so this matters only for MKV, TS, fragmented MP4 and files
  the index declines.
- It is a lock-sensitive change to T-093's cancel-safety.

## Trigger

- The user's 4K turns out to be MKV/TS.
- T-205's slow-disk bench measures contention from an abandoned scan.
- T-199 lands and MKV/TS scans still read whole files.

## Acceptance sketch

- A blocking fake runner: a single awaiter cancels → the runner's token is cancelled and nothing is cached.
- Two awaiters, one cancels → the scan continues for the other.
- An awaiter attaching after cancellation → a fresh scan.
- A race test → no hung awaiter, no cancelled result cached.
- Bulk peak concurrent scans ≤ 3.
