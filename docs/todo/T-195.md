## Concept

Every ffmpeg run on a 4K H.264 file starts by decoding its first frames to fill in stream information
(`find_stream_info`). For a frame grab or a waveform that work is pure overhead. The MP4/MOV container already
states everything those runs need, and the probe cannot skip it only because it reports `pix_fmt` and the format
duration, which these runs do not use.

| run | today | with `-nofind_stream_info` | output |
|---|---|---|---|
| 4K H.264 grab on a keyframe | 0.496 s | 0.252 s | identical (PSNR 99) |
| 4K H.264 grab 1 s into a GOP | 0.624 s | 0.377 s | identical |
| 4K, 10 s GOP, grab on a keyframe | 0.480 s | 0.216 s | identical |
| 4K, 10 s GOP, grab 9 s into the GOP | 1.76 s | 1.56 s | identical |
| 1080 grab on a keyframe | 0.167 s | 0.103 s | identical |
| 4K HEVC grab | — | no change | identical |
| waveform, 4K MP4 | 0.358 s | 0.115 s | PCM byte-identical |
| waveform, 10 s GOP 4K | 0.337 s | 0.077 s | PCM byte-identical |

The grab args come from `FfmpegThumbnailService.BuildArgs` (`FfmpegThumbnailService.cs:207-209`) and the waveform
args from `FfmpegWaveformService.cs:229-233`. A 10-position hover sweep on 4K takes 5.45 s today, against 1.86 s at
1080p. Every Bulk row draws two cut-point chips through the same service, three at a time (SPEC-011 I67).

The class doc at `FfmpegThumbnailService.cs:12` says the seek is *"keyframe-accurate"*. It is frame-accurate:
ffmpeg decodes from the previous keyframe to the exact time. This ticket corrects it.

## Design

- **For inputs whose extension is `.mp4`, `.m4v` or `.mov`** (case-insensitive), both builders put
  `-nofind_stream_info` immediately before `-i`:
  - thumbnail: `-ss <t> -nofind_stream_info -i <input> -frames:v 1 -vf scale=W:-1 -y <temp>`;
  - waveform: `-nofind_stream_info -i <input> -vn -ac 1 -ar <rate> -f s16le -y <temp>`.

  Every other extension keeps exactly today's tokens.
- **One retry without the flag.** If a flagged run exits non-zero, or exits 0 with no output file (or an empty
  one), the service runs once more without the flag and returns that result. A file that is not really MP4 inside
  (TS content named `.mp4`) therefore still gets its picture. Best-effort stays best-effort: never a new `null`,
  never a throw. A **cancelled** flagged run (the runner throws `OperationCanceledException`) is not retried; it
  returns `null` as today, so latest-wins holds.
- **A failure is remembered per input.** Failures are never cached, so on a file whose flagged run fails, every
  hover grab would pay a failed run plus the retry, slower than today. So when a flagged grab fails and its retry
  runs, the thumbnail service records that input path, and from then on uses today's unflagged args for it, until
  `Clear(input)` or `ClearAll()`. A cancelled run records nothing.

  **Choice logged.** Rejected: accepting the double run as rare. It costs one small set per service, and without
  it the one file shape this ticket can slow down (TS content named `.mp4`) gets slower on every hover. The
  waveform keeps the plain rule (no memory): it runs once per load, so it pays the double run at most once.
- **Nothing else changes:** cache keys, buckets, the width in the key (SPEC-005 I26), the LRU, debounce and
  latest-wins cancellation, and the waveform's temp-file PCM path.
- **Not applied to the probe** (measured lossy: `pix_fmt` and the format duration go missing, and `CompatChecker`
  and SmartCut use `pix_fmt`) **or to any `-c copy` run** (the sacred path; T-210).

## Detail

- The extension gate is a pure helper with tests (`IsIsoBmffExtension`). An extension check is enough here
  because the retry makes a mislabelled file safe. A signature read would add file I/O to every grab.
- **Rotation:** the display matrix comes from the container header, not from `find_stream_info`, so autorotation
  still applies. A rotated fixture tests this.
- A no-audio MP4 asked for a waveform fails the flagged run and the retry, and returns `null` as today. The extra
  run is cheap and that case is rare.

**After the fix:**
- [ ] **Tokens (unit):** an `.mp4`, `.M4V` or `.mov` input gets `-nofind_stream_info` immediately before `-i` in

      (`SplitArgsBuilder.PerSegment`, `JoinArgsBuilder.ConcatCopy`, SmartCut's concat) contain no

- [ ] **Retry (fake runner):**
      - a flagged run that exits non-zero is followed by exactly one run without the flag, and its result is
        returned;
      - the same when the flagged run exits 0 but writes no file;
      - the flagged run and the retry both fail → exactly **two** runs, `null` returned, nothing cached, no throw
        (this also covers the no-audio waveform);
      - a cancelled flagged run (the runner throws `OperationCanceledException`) is **not** retried: one run, `null`

- [ ] **Failure memory (fake runner):** after a flagged grab on an input fails and is retried, the next grab on that

- [ ] MKV and TS inputs still yield a picture and peaks.
- [ ] Cache, bucket, width-in-key, LRU, Clear and best-effort tests (SPEC-005, SPEC-006) pass unmodified apart

## Edge cases

- **TS content named `.mp4`:** the flagged run may fail, and the retry returns today's result; later grabs on that
  input go straight to today's args (the failure memory), so hover is never slower than today. A flagged run that
  succeeds with a wrong picture is not expected, because the codec parameters of such a stream come in-band. The
  equivalence tests cover the real MP4 case only.
- **A huge `moov` (a long recording):** the flag does not change header reading.
