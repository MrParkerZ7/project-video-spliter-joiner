# D-005 — Apply a cut before the snap

**Board index for the design.** Full spec: [`../design/D-005/README.md`](../design/D-005/README.md) ·
sequence: [`../design/D-005/apply-before-snap-sequence.drawio`](../design/D-005/apply-before-snap-sequence.drawio)

## Snapshot
- **Question:** "before we can apply a profile cut, doesn't it require snapping first?" — today yes, by inheritance
  from T-096, not by decision. The three copy paths read only `Duration` and requested times; only the run needs the
  snap, and it already waits.
- **Rule (R1):** one predicate `BulkItemViewModel.CanTakeCut => Duration is not null`, read by
  `CutProfileApplier.cs:45`, `BulkCutViewModel.cs:1490` (source) and `:1503` (targets).
- **Pending display (R2):** already right. Handles are born `snapPending: true` (`:174`, `:262`), and `Resnap` never
  clears the flag. Pinned by a test, not rebuilt.
- **Run safety (R3):** `IsValidCut` and `CanRunBatch` still require `KeyframesReady` — unchanged, newly tested.
- **Report (R4):** classify scanning rows by their *requested* geometry. Without that, every scanning row would be
  reported "now invalid". New wording: `· 3 will snap when their scan finishes` and `· 1 not loaded yet, skipped`.
- **Frames (R5):** no thumbnail grab while a handle is pending; the scan's completion grabs once.

## Clarified decisions (round 1)
1. A row takes a cut **once it is probed**.
2. **All three paths, one rule.**
