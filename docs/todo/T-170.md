## Found

While grounding [[T-169]]'s decision against the **real** store rather than against the code's claims,
one of the 11 files in `%LOCALAPPDATA%/VideoSplitJoiner/profile-thumbs` turned out to be junk:

```
P_148de9c5a7a44d19.jpg   1 byte   content: the single ASCII character 'x'
```

Not a truncated JPEG — one byte, no header, no marker. Every other file in the store is a valid 549-1939
byte JPEG.

## Why it matters more than one bad picture

SPEC-007 **I73** promises exactly that this cannot happen:

> copy-then-swap: a failed `Save` leaves the prior thumbnail byte-identical.

**I45** describes the same mechanism (copy-then-swap displacement, including the cross-extension sweep).
A 1-byte file is neither the new picture nor the previous one, so whatever produced it either bypassed
the swap or swapped in a source that was already garbage.

The two candidate paths, and they need distinguishing before anything is fixed:

1. **The upload path never validates its input.** `UploadThumbnail` (`BulkCutViewModel.cs:1760`) hands the
   chosen file to `TryAttachThumbnail`, and `Save` copies **bytes verbatim** (I42) — so choosing any file
   at all, including a 1-byte text file, stores it and reports success. I35 already says `ThumbnailPath`
   performs no format validation, so this may be working exactly as specified and specified wrongly.
2. **A capture wrote a stub.** `GetThumbnailAsync` returning a path to a not-yet-flushed or failed grab
   would produce something short, though 1 byte of `x` does not look like a partial ffmpeg JPEG.

Path 1 is far likelier and is reproducible in seconds; check it first. Do not fix on the hypothesis —
this project has paid repeatedly for that.

## Why now
[[T-169]] puts these pictures on screen at ~5x their current size in a hover preview. A profile whose
picture is a 1-byte file currently shows the placeholder and nobody notices; once there is a large
preview, "why is this one blank" becomes a visible defect with no explanation attached.

## Acceptance criteria
- [x] Reproduced. The UPLOAD path: `UploadThumbnail` -> `TryAttachThumbnail` -> `Store.Save`, which
      copies bytes verbatim with nothing between the picker and the disk. Demonstrated by test, not
      deduced — `Upload_AFileThatIsNotAnImage_...` fails against the old code.
- [x] Refused in words: *"That file is not an image, so the profile thumbnail was not changed."* with a
      hint naming the accepted formats and the *All files* trap. Nothing reaches the store.
- [x] Asserted byte-identical, not merely present.
- [x] Four mutations, all dead: guard removed · `IsImage` always true · RIFF matched on 4 bytes so a
      WAVE passes as WEBP · the `File.Exists` guard dropped (which regresses the missing-file message).
- [x] Already handled, verified rather than changed: `PathToBitmapConverter` catches the decode failure
      and returns null, so the chip shows the placeholder and the profile stays usable. No new code —
      the existing null-safe path already gives I87's guarantee here.

## Out of scope
Re-encoding uploads to a normalized width — that is [[T-169]]'s decision and lands there. This ticket is
only about refusing input that is not an image at all.

## Outcome — 2026-09-07

Reproduced first, then fixed. The upload path was the culprit, as suspected — but the ticket said
demonstrate rather than deduce, so `Upload_AFileThatIsNotAnImage_IsRefusedInWords_AndNothingIsStored`
fails against the old code and passes against the new.

### The design decision worth recording
`BulkCutViewModel` is deliberately WPF-free, so it cannot reach for `BitmapDecoder`. The obvious
alternative — an injected decoder seam defaulting to null — is how T-162's delete feature shipped
**inert**: absent unless the composition root wires it. A **leading-byte signature test** needs no
wiring, cannot be forgotten, and is pure enough to unit-test directly. `ImageSignature.IsImage` covers
exactly the formats the picker's filter offers, so the two cannot drift apart unnoticed.

### Where the check sits, and why not one layer down
On the **upload** path only, not inside `TryAttachThumbnail`. That is the trust boundary: an upload is a
file the user picked through a dialog with an *All files* escape hatch, while the auto and snapshot
frames are written by ffmpeg at this app's own request. Validating those would be checking our own
output — and would have broken every capture test for no gain.

It is also guarded on `File.Exists`, so a **missing** pick keeps its own better message. "That file is
not an image" is true of a deleted file and unhelpful; the store's `FileNotFound` -> `ImageUnreadable`
path already says "may have been moved, renamed or deleted".

### A fiction the suite was carrying
`MakeImage` wrote the text `img-bytes` into a `.jpg`, so the entire upload suite was proving the app
accepts things that are not images — the very defect this ticket exists to fix. It now writes the real
magic bytes followed by the same content, so every assertion that distinguishes one picture from another
by its bytes still works, and the tests exercise the real acceptance path. Nine tests failed on the way
through; all nine were that fiction, not the fix.

### Bounded on purpose
This refuses files that are **not images**. It does not certify an image is undamaged — a truncated JPEG
with an intact header passes and falls back to the placeholder at decode time. The invariant says so.
