## Concept
Running a split must obviously LOOK like it's working — a moving progress bar and/or a "Splitting…" busy state + status — so the user never thinks it's broken. Same for join.

## Design
- **Verify the progress path:** `SplitViewModel.RunSplitAsync` → `SplitEngine.SplitAsync(req, IProgress<double>, ct)` → `FfmpegRunner` progress parser (`time=` vs total duration) → `Operation.Progress`. Confirm the `IProgress` is actually passed + marshaled to the UI (Progress<T> / dispatcher). `SplitView.xaml:196` already binds a `ProgressBar` to `Operation.Progress` visible while `Operation.IsRunning`.
- **Fix / strengthen the feedback:**
  - If ffmpeg reports granular `time=` progress for the split → make sure the bar moves (fix the parser/marshal if it stays at 0).
  - The **segment-muxer `-c copy` split can be too fast/sparse for a smooth %** → add an **indeterminate** mode (`ProgressBar IsIndeterminate=True` when no granular progress is available) + a **status line** ("Splitting…", or "Splitting segment N of M" if the engine can report segment count) so activity is always visible even when % isn't meaningful.
  - Ensure a clear start (bar/status appears immediately on Run) and clean end (clears on success/fail/cancel).
- Apply the same to **join** (`RunJoinAsync`/`JoinEngine`).
- Keep the op off the UI thread (already async) so the bar animates.

## Detail
- `OperationViewModel` may need an `IsIndeterminate`/`StatusText` (or reuse existing status) to drive the bar mode + label.
- Don't fake progress — if it's genuinely indeterminate, show indeterminate + "working…", not a fake crawling %.
- A small "Splitting… please wait" label near the bar removes all doubt.

## Interfaces / contracts
- `OperationViewModel` may gain `IsIndeterminate`/`StatusText`; `SplitView`/`JoinView` bind the bar mode + status. Engine contracts unchanged (they already take `IProgress<double>`).

## Acceptance criteria + Case-Coverage Matrix
- [ ] On Run, a visible progress indicator appears immediately and stays until the op ends (bar + "Splitting…" status).
- [ ] When ffmpeg gives granular progress, the bar reflects it (moves 0→100); when it doesn't, the bar is indeterminate + a status shows activity (no stuck-at-0 silence).
- [ ] Progress/indeterminate clears on success, failure, and cancel.
- [ ] Join shows the same feedback.
- [ ] Build 0-warning; prior tests green; VM-level tests for the progress/indeterminate/status state transitions (fake engine reporting progress vs none).
- Matrix — Required-Success: split with progress → bar moves + clears. Boundary: instant split (brief but visible busy state); long split (bar/indeterminate persists); cancel → clears. Required-Fail: split fails → indicator clears + error shows.

## Dependencies
None (strengthens the existing OperationViewModel/progress path).

## Risks
Indeterminate that never clears → tie clear to the op-complete transitions (already how Error/Progress reset). Don't regress the real % when it IS available.

## Out of scope
Byte-accurate per-segment %; docs (T-043).
