## Concept

Found by the G-059 plan review (round 2) while it checked T-190's claim that the lossless path tolerates a
non-zero `start_time`. That claim is false, and a second fault turned up in the full-file split. Both are bugs in
the `-c copy` path itself, so T-190's stop rule applies: they get their own fix ticket and are never patched
inside the Exact work.

- **(a) The segment muxer splits one GOP late on a B-frame source.** `SplitArgsBuilder.SegmentMuxer`
  (`SplitArgsBuilder.cs:33-56`) passes the snapped keyframe pts unchanged as `-segment_times`
  (`SplitPlanner.ToSegmentTimes`). Measured with the bundled ffmpeg n7.1.5 on the `MediaFixtures` recipe
  (`testsrc` 10 s, 30 fps, libx264 with its default B-frames, `-g 30 -keyint_min 30 -sc_threshold 0`, AAC): cuts
  at 3 s and 6 s give parts of **120/90/90** frames instead of **90/90/120**. Each boundary lands on the next
  keyframe. The same source encoded with `-bf 0`, or the same command with `-segment_time_delta 0.016`, gives
  90/90/120.
- **(b) A per-segment cut on a source whose `start_time` is not zero starts one GOP late.**
  `SplitArgsBuilder.PerSegment` (`:69-100`) emits `-ss <keyframe pts>` before `-i`. Keyframe times are
  absolute source pts, but ffmpeg's `-ss` is an offset from the format `start_time`. Measured on a synthetic TS
  (`start_time` 1.445 s — 1.445333 by the subtraction below — 2 s GOP, keyframes at 1.4667, 3.4667 and 5.4667 s): `-ss 5.466667 -to 4` starts at source
  frame **180** (the 7.4667 s keyframe) instead of 120 and has 106 frames. `-ss 4.021334` (the `start_time`
  subtracted) lands on frame 120, and so does the same content remuxed to MP4 (`start_time` 0) with the
  unchanged command.
- **Who is hit.** (a): every full-selection split (`SplitEngine.cs:194, 288`) of a source with B-frames, the usual
  output of x264 and of OBS. (b): every Split subset part (`SplitEngine.cs:361`) and every Bulk Cut lossless row
  (it reaches `PerSegment` through `KeptMiddleRequestBuilder` and `SplitEngine`) on `.ts`, `.m2ts` and `.mts`
  sources, which `VideoFileFilter.cs:29` accepts. In both cases the file is valid and plays; its boundary is a
  GOP away from the one the plan showed.
- **Why the tests miss it.** `SplitEngineIntegrationTests.cs:58-110` asserts the sum of the part durations and the
  plan-derived `ActualStart`, never each part's frame count or first frame.
- **A third shape, not fixed here: the end overrun** (found at plan review round 4). Under stream copy `-to` acts on
  decoding timestamps, so on a B-frame source a `PerSegment` part that has an end keeps the next keyframe and the
  frame coded after it. Measured with the bundled ffmpeg: on the `MediaFixtures` recipe, shipped [3, 6) gives 92
  frames against 90 with `-bf 0` (its first 90 md5-identical to source frames 90-179); on the synthetic TS above,
  the fixed `-ss 4.021334 -to 2` gives 62 frames against 60, its first frame md5-identical to source frame 120. A
  part that runs to the end of the file has no `-to` and is exact. This ticket leaves `-to` unchanged, so by
  T-190's stop rule the overrun is its own fix ticket, **T-220** (later), and this ticket's frame-count checks cover
  only segment-muxer parts and parts that run to the end; the first-frame check covers every part.
- **T-190 depends on this.** T-190 sends Exact rows on such sources to the lossless cut, and T-189's row text says
  *"cut snapped to the nearest keyframe"*. That is true only once this ticket ships.
- **T-196 depends on this too.** Its cut-point and profile pictures seek with the same `-ss` time base and convert
  a keyframe time with the `MediaInfo.StartTime` this ticket adds, so on a TS row the chip is the first frame of
  this ticket's lossless cut.

## Design

- **No encoder token, no new path.** Both fixes change only cut-time arguments of the existing `-c copy`
  commands. `SatisfiesCopyInvariant` and `AssertCopyInvariant` hold for every built command, and SPEC-001's copy
  invariant is unchanged.
- **The time base (needed for (b)).** `MediaInfo` gains `StartTime` (ffprobe `format.start_time`; zero when absent
  or unparsable), an optional positional parameter defaulting to zero so every existing construction and test fake
  compiles. `MediaProbe.ProbeAsync` maps it. T-190's Exact gate reads the same field. That is why this ticket is
  built after T-193: the same method gains its cache there (a file edge, not a logic one).
- **(b) `PerSegment` converts source pts to ffmpeg's offset.** It gains a required `TimeSpan sourceStartTime`
  parameter and emits `-ss max(0, start − sourceStartTime)`. `-to` stays a duration (`end − start`) and is
  unchanged. `SplitEngine.ExtractSelectedPerSegment` passes `ok.Info.StartTime` from the probe it already makes in
  Preparing (`SplitEngine.cs:121`). `SmartCutArgsBuilder.TailCopy` passes `TimeSpan.Zero` with a comment: Exact
  still assumes a zero `start_time`, T-190 makes such sources fall back, and T-190 deletes `TailCopy`.
- **(a) The segment muxer gets a tolerance below one frame.** `SegmentMuxer` gains a `TimeSpan segmentTimeDelta`
  parameter and emits `-segment_time_delta <d>` (no token when `d` is zero), with `d` half the source's frame
  duration, computed in `SplitEngine.ExtractAllViaSegmentMuxer` from the probed video stream's frame rate. That is
  ffmpeg's documented recipe for this option, and the measured 0.016 s at 30 fps sits inside it. A delta below one
  frame can never move a boundary onto an earlier keyframe, because keyframes are at least one frame apart. A source
  with no usable frame rate keeps `d = 0`, today's behaviour, and the Build log says so.
- **The frame rate is a contract change, not a lookup.** `StreamInfo` (`Core/Media/StreamInfo.cs`) maps no frame
  rate today (verified: its nine fields are index, codec, type, width, height, pixel format, sample rate, channels
  and time base, and a grep of `src/Core` for `frame_rate` or `FrameRate` finds nothing), and the ffprobe DTO
  `FfprobeStream` (`FfprobeJson.cs`) does not read one either, although `-show_streams` prints both. So:
  - `StreamInfo` gains two optional trailing parameters, `double? AvgFrameRate = null` and `double? RFrameRate =
    null` (frames per second), so the 15 `new StreamInfo(` sites in `src` and `tests` compile unchanged, and a
    computed `FrameRate => AvgFrameRate ?? RFrameRate`;
  - `FfprobeStream` gains `avg_frame_rate` and `r_frame_rate`, and `MediaProbe.MapStream` (`MediaProbe.cs:381`)
    parses each rational (`"30000/1001"` → 29.97003); absent, unparsable, `"0/0"` or a zero part gives null;
  - `CompatChecker` is unchanged: it compares named fields (`CompatChecker.cs:62, 108`), so a frame rate never
    becomes a Join mismatch;
  - it gets a SPEC-004 invariant (Interfaces).
- **The segment muxer on a TS source.** ffmpeg shifts output timestamps to start at zero by default, so
  `-segment_times` given as absolute pts are expected to be off by `start_time` too. That is not measured. The TS
  full-split test below decides: if it shows the shift, `SplitEngine` subtracts `StartTime` from each segment time
  as `PerSegment` does, and the Build log records it. **The per-part progress boundaries follow the same list.**
  `ExtractAllViaSegmentMuxer` passes `plan.InteriorSnappedCuts` both as `-segment_times` and as the `boundaries`
  of `PartMapping.PartAt` (`SplitEngine.cs:293-296`, the G-025/T-069 per-part channel), and the runner's `time=`
  counts output time from 0. So if the segment times are converted, one converted list is built once and feeds
  both, or the per-part rows flip about 1.4 s off on TS.
- **Choice logged.** Rejected:
  - re-encoding or `-bf 0` remuxing: it breaks the sacred `-c copy` rule;
  - snapping cuts to keyframe **dts** instead of pts: it changes `SplitPlanner` and every screen that shows a cut,
    for a fault that a muxer option fixes in one place;
  - offsetting the whole timeline (keyframe ticks, the planner, the player) by `start_time`: the conversion
    belongs at the boundary where ffmpeg's time base starts. The planner keeps source pts, as T-190's Exact gate
    assumes.

## Detail

- **Where the probe comes from.** `SplitEngine` already holds `ok.Info` in Preparing. Bulk lossless rows go through
  the same `SplitEngine`, so no new probe is added (and after T-193 it is a cache hit).
- **Frame rate.** `SplitEngine` reads the first video stream's `FrameRate` (`avg_frame_rate`, then `r_frame_rate`,
  as mapped above). `d = 1 / (2 × FrameRate)`, formatted by `ToFfmpegSeconds` (`0.016683` at 30000/1001). A null
  `FrameRate` gives `d = 0` and no token.
- **`-ss` clamp.** A `start − sourceStartTime` below zero (a cut at the first keyframe of a TS whose first keyframe
  pts equals its `start_time`) clamps to 0, which is the file's start.
- **Progress:** the runner's `time=` counts output time, and the part fractions derive from it as today (T-069).
  If the segment times are converted for TS, the `PartAt` boundaries are the same converted list (Design).

## Edge cases

- **A VFR source.** Half the average frame duration stays below the smallest real frame gap only if the rate does
  not vary by 2x or more. The test matrix is constant frame rate, and a VFR fixture is not added here.
- **An MP4 that starts slightly above zero** (a B-frame delay with no edit list) gets the same conversion. The
  bench records `start_time` for every fixture.
- **Non-MP4 outputs** (`.mkv`, `.mov`, `.ts`) use the same args. The integration tests cover `.mp4` and `.ts`
  outputs.

## Dependencies

- **T-193:** the same method (`MediaProbe.ProbeAsync`) gains its cache there. A file edge.
- **T-188:** the bench numbers for the Build log.

## Risks

- **This changes the sacred copy path's arguments.** The copy invariant, the frame-count and first-frame tests,
  and the unchanged controls guard it. The bench shows the copy speed is unchanged.
- **The half-frame delta is ffmpeg's recipe, not a root-cause proof.** If a fixture still lands late with it, the
  Build log records the mismatch, and the ticket tries the documented alternative of passing each boundary as its
  keyframe time minus half a frame before closing.
- **Outputs from earlier versions** are valid files with a shifted boundary. T-197 tells users what to do.

## Out of scope

- Exact cut on such sources (T-190 falls back).
- Offsetting the timeline the UI shows (keyframe ticks, player position).
- MKV/TS keyframe speed (T-199).
- The end overrun of a per-segment part that has an end on a B-frame source (`-to` acts on decoding timestamps):
  a third copy-path shape, its own fix ticket **T-220** (later), per T-190's stop rule.
