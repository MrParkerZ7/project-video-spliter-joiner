## Reported
> one problem on delete original files is un delete able by files is in using by it's own

## Cause — and the codebase already knew about it

The preview player holds an open handle on the selected row's file. `DeleteOriginals` (T-144) asks the
disposer to bin every eligible original **without releasing that handle first**, so the previewed row's
file is refused. It lands in the `refused` tally, which is why it failed quietly rather than crashing —
but the user asked to delete N files and got N-1.

The exact fix already exists a few hundred lines away, written for the same reason under
replace-originals (`BulkCutViewModel.cs:1739`):

```csharp
// T-122: under ReplaceOriginal a Stop is NOT enough - Stop only halts playback, while Unload is
// what closes the media element and RELEASES the file handle. A still-open handle on the selected
// row would make replacing that very file fail, so unload it outright in this mode.
if (_replaceOriginal) { Player.Unload(); } else { Player.Stop(); }
```

T-144 needed the same reasoning and did not get it. That is my omission, not a new discovery: the comment
above states the rule in plain language and I did not apply it.

## Other handles worth checking while in here
- **`FileMediaInputStream`** (T-132) holds a `FileStream` for Uri-less paths; it is disposed on `Unload`,
  so the same fix covers it — but assert that, do not assume it.
- **The thumbnail service** grabs cut-point frames from the source. It writes to a temp cache rather than
  holding the source open, but it is worth confirming rather than reasoning about.
- **The waveform service**, same question.

## Design
1. `Player.Unload()` before the delete sweep — not `Stop()`. The comment above spells out why.
2. Clear the selection too, or the next interaction re-opens the file that was just binned.
3. **Re-verify after unloading**: the eligibility set is computed before the sweep, so recompute or
   re-check each row at the moment of deletion rather than trusting a list built while the handle was
   still open.
4. A file that is *still* refused after unloading is a genuine external lock (another program, a virus
   scanner) and must stay in the `refused` tally — the count must never claim more than it did.
5. Say which files were refused, not just how many. "1 could not be removed" leaves the user hunting.

## Acceptance criteria
- [ ] The previewed row's original is binned along with the rest — asserted with a player that reports an
      open handle, so the test fails if the unload is dropped.
- [ ] Unload, not Stop — asserted specifically, since Stop looks like it should work and does not.
- [ ] A row locked by something *external* still lands in `refused`, and the summary names it.
- [ ] Eligibility is re-checked at deletion time, after the unload.
- [ ] The preview does not silently re-open a file that was just binned.
- [ ] SPEC-011 updated; rebuilt, relaunched, verified by hand on a real batch.
