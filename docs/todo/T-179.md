## Concept

Profile pictures are meant to be stored at 640px (SPEC-007 I106, since T-172). In practice a capture can
come back at **64px**.

- Every frame grab in the app goes through one shared `FfmpegThumbnailService`
  (`MainViewModel.cs:80`).
- That service caches by *(input file, 1-second bucket)* and **ignores the requested width**. It also
  reuses a matching file left on disk by an earlier run.
- The row's cut-point chip grabs the intro frame at 64px (`BulkItemViewModel.ThumbnailWidth`), and the
  scrub preview grabs at 160px.
- So *Save* (an automatic capture at the intro cut) and *📷 Use current frame* (often pressed right after
  *Set intro-end here*) can ask for a second the chip has already cached, and get the chip's 64px file
  back.

This is the likely source of several of the user's six 64px pictures; T-169 counted some pictures as
uploads, so not necessarily all of them. It also explains why T-172's 640 stored nothing wider. The same
fix stops the scrub preview being handed a 64px frame at a second a chip had cached.

## Design

- **Cache key:** `BuildCacheKey(inputPath, bucket, width)` → `"<input>|<bucketMs>|w<width>"`.
- **Temp file:** `ResolveTempPath(inputPath, bucket, width)` → `<cacheRoot>/<hash>/<bucketMs>_w<width>.jpg`.
  The on-disk reuse branch (I12) now reuses only a file of the **same** width, because the width is in the
  name.
- `IThumbnailService` does not change; every caller already passes its width.
- `Clear(inputPath)` and `ClearAll()` are unchanged. They delete the whole per-input folder or the root,
  so files of every width go with it.
- **Old width-less files** (`<bucketMs>.jpg`) from earlier runs are never matched again, and stay until
  `Clear`/`ClearAll`. Consequence: on the first run after the update, each row chip runs ffmpeg once more.
  It is a cache folder, so no separate sweep is made.
- **LRU bound (I9):** the cap stays at 128 entries. One second's frames at three widths are three
  entries, which is correct, because they are three files.
- **Docs in code:** update the class doc comment (`FfmpegThumbnailService.cs:16-19, 26`), which still says
  *"keyed by (inputPath, bucket)"* and `<bucket>.jpg`.

## Detail

- The key uses the **requested** width. With `scale=W:-1` the output has that width, so no probe of the
  output is needed.
- A failed grab at one width is still not cached (I15), and it leaves a cached file at another width
  untouched.

## Edge cases

The same second at the same width from two callers (a chip and the scrub preview) is still one file,
which is the point of the cache. Per-width entries fill the 128-entry cap sooner; that is acceptable,
since each file is a few KB.

## Dependencies

None.

## Risks

- **Green only against fakes.** T-172 passed a "real pixel width" test against a cache-less fake while
  production returned 64px. The fake runner proves the key; only the real-ffmpeg exit probe proves the
  picture.
- **The prior-run reuse (I12) is kept on purpose.** Removing it would re-run ffmpeg for every chip after
  each restart.

## Out of scope

- Deleting old width-less cache files.
- Changing any caller's width.
- The hover card (T-180): this task alone changes nothing visible on the card, because the card stays
  capped at 320 until T-180.
- Refreshing existing pictures (T-181).
