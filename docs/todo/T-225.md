## Concept

Found while measuring T-193 (2026-10-05). The bench times the ffmpeg `-c copy` stage of a split or join as part of each scenario, and G-059 criterion 6 says the copy passes keep their speed. On this machine the copy stage of the same code drifted 2-3x across three back-to-back `bench core` sessions on the default fixture root (`%TEMP%\vsj-bench-fixtures`, drive C: at 93% full; each session writes about 50 GB of parts, joins and bulk outputs):

| session | Core | 4k10m split 3 parts, ffmpeg stage | 4k10m JoinAsync, ffmpeg concat |
|---|---|---|---|
| 20261005-152715-19de (1st) | f4b73f0e (old code) | 1.77-1.98 s | 2.94-3.61 s |
| 20261005-153313-52ce (2nd) | d6fac415 (T-193; changes no ffmpeg args) | 3.60-3.83 s | 5.79-7.27 s |
| 20261005-153958-7be1 (3rd) | f4b73f0e (old code again) | 5.21-6.88 s | 5.45-8.79 s |

The old code run third was the slowest, so the order of the sessions (disk write-cache or SSD state), not the code, moves the copy stage. A plain before-then-after pair would wrongly show T-193 doubling the copy time. T-219 must show criterion 6 holds while it changes where the copy cuts, so it needs a measurement method that is not this noisy.

## Design

Recommended (★): **interleave and say so.** Add a `--interleave <other-bench-dir>` (or document a procedure in `bench/README.md`) that alternates before and after builds scenario by scenario (A B A B), so each pair shares the same disk state. The Build-log guidance then quotes the median of each build's runs from the interleaved session, plus the bytes-written column. Also note in the README that a copy-stage comparison should use a fixture root (`--root`) on a drive with free-space headroom, and that the C: (TEMP) root on this box is near full.

Alternative: report copy throughput (written MB / ffmpeg-stage seconds) beside wall time and ask for 3+ alternating sessions. Simpler, but slower to run and does not remove the order effect.

## Acceptance criteria

- [ ] Repro first: two back-to-back sessions of the same build on the current root show the copy-stage spread above (record the numbers).
- [ ] The chosen method (interleave option or documented A/B/A/B procedure) gives copy-stage medians for two identical builds within 15% of each other on `4k` and `4k10m`.
- [ ] `bench/README.md` says how a G-059 Build log compares copy-stage times, and warns about a near-full fixture drive.
- [ ] No test asserts wall-clock time (T-137); the bench still opens only files it generated.

- Moving the default fixture root.
- Probe-stage numbers: process counts and stage splits are deterministic and already compare cleanly (T-193).
