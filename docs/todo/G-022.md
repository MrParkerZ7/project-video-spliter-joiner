## Why / vision
After the G-019 two-column relayout (T-059), the user reports they can **click "add" for a cut position only once** — subsequent adds don't register. A relayout should be pure re-parent/restyle with zero behavior change, so any action that no longer works is a migration regression. Beyond the one reported symptom, the user wants **assurance that every feature action still works as it did before the tab migration** — a full parity sweep, not just the one fix.

## Grounding already done (2026-07-18 — don't re-tread)
- **No command binding was dropped by T-059.** Diffed `SplitView.xaml` old (`5c8f611^`) vs new: all 8 command bindings identical (`AddMarkerCommand`, `SetCutAtPlayheadCommand`, `RunSplitCommand`, `ClearCommand`, `CancelCommand`, `OpenFolderCommand`, `SelectAllSegmentsCommand`, `SelectNoSegmentsCommand`).
- **Timeline click-to-add is intact.** `TimelineView.xaml` still has `Canvas x:Name="Track"` with `MouseLeftButtonUp="OnTrackClicked"`; the handler maps `e.GetPosition(Track).X / Track.ActualWidth` — **Track-relative**, so robust to the layout move (the Canvas fills its Border regardless of column).
- **Add commands' CanExecute don't latch off:** `AddMarkerCommand`/`AddCutAtCommand` guard on `CanAddMarker => HasFile`; `SetCutAtPlayheadCommand` on `CanSetCutAtPlayhead => HasFile && Player.IsReady`. None flips false after one add.
- **`AddCutAt` dedupes on snapped position** (`AddSnappedMarker`) / requested position while indexing (`AddPendingMarker` → `Markers.Any(m => m.Requested == position)`). So a second add at the **same source position** is intentionally dropped — if the source position (the `NewMarkerPosition` field, the playhead, or the timeline click point) doesn't advance between clicks, the user sees "only 1."

## Suspects (for T-064 to confirm by reproducing in-app — can't repro headless)
- **S1 · Source position not advancing** — e.g. the "Add" button adds at `NewMarkerPosition` (a text field); if it isn't re-seeded from the moving playhead after the relayout, clicking Add again re-submits the same value → dedup → "only 1." Check whether pre-T-059 the field auto-tracked the playhead and the relayout broke that binding/seed.
- **S2 · Playhead not updating in the new layout** — if `Player.Position` stopped propagating (a binding to the moved player), `SetCutAtPlayheadCommand` always adds the same time → dedup. Verify the player/timeline position still updates live in the two-column layout.
- **S3 · Timeline Track zero/!stale width** — if in the new left column the Track's `ActualWidth` is 0 or stale at click time (e.g. it's inside a pane that lays out late), the X→time mapping collapses to a constant. `OnTrackSizeChanged` should keep it fresh — confirm.
- **S4 · Genuinely pre-existing** — the dedup behavior may predate T-059 and the user only now noticed. Confirm against the pre-T-059 build; if pre-existing, still improve it (see T-064 fix direction) since the user expects repeated adds to "just work."

## Decisions
- **D1 · Reproduce first, then fix at the true layer** — run the app (`app-run`) with a real file, reproduce "add once," identify which of S1–S4 it is, fix the actual cause. Do NOT loosen dedup blindly (dedup on the same snapped keyframe is correct — two cuts can't share a keyframe).
- **D2 · Parity sweep is part of the goal, not optional** — T-065 walks every action; the user explicitly asked to verify all features, not just the reported one.
