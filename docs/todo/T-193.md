## Concept

`MediaProbe.ProbeAsync` (`MediaProbe.cs:78-147`) has no cache. The keyframe scan has one (`:162-166`), but the
metadata probe runs ffprobe on every call. On 4K H.264 each call costs **0.27 s** (0.266-0.302 warm), almost all
of it `find_stream_info` decoding the first frames. 1080p costs 0.10 s, and 4K HEVC 0.035 s. Every screen calls it
again at every stage, through the one shared instance (`MainViewModel.cs:72`):

- **Join:** the chip probe on add (`JoinViewModel.cs:620`), then the compatibility probe of every clip
  (`JoinEngine.cs:86`, via `RefreshCompatAsync`), on every add, remove and reorder. At Run, the compatibility
  pre-flight again (`JoinEngine.cs:136 → 86`) and `SumDurationsAsync` (`:143 → 246`).
  - Measured: adding 3 4K clips costs 1.69 s for 6 probes.
  - A 3-clip 4K Join run takes 3.83 s (2.82-4.48 s), of which **1.38-2.22 s is 6 serial probes** before a byte is
    copied.
- **Split:** a re-probe in Preparing (`SplitEngine.cs:121`) after the load already probed the file
  (`SplitViewModel.cs:897`): 0.27-0.35 s of a 1.08 s split.
- **Bulk Cut:** the row probe on add (`BulkCutViewModel.cs:1407`), then `KeptMiddleRequestBuilder.cs:39` at run.
  An Exact row also probes in `SmartCutEngine.cs:78`. The comment at `KeptMiddleRequestBuilder.cs:36-38` says
  *"both cached/deduped by MediaProbe, so the engine's later re-probe of the same file is free"*. For the probe
  that is not true.

## Design

- `ProbeAsync` keeps a `ConcurrentDictionary<string, ProbeResult.ProbeSucceeded>` keyed by the existing
  `BuildCacheKey(path)` (`MediaProbe.cs:416-423`: full path | LastWriteTimeUtc ticks | length). This is the same
  key and the same staleness rule as the keyframe cache (SPEC-004 I16/I17).
- The lookup comes **after** the existing empty-path and missing-file guards (`:80-88`), so those still return
  `Failure` without touching the runner or the file's metadata.
- **Only success is cached.** A `ProbeFailed` (non-zero exit, bad JSON, no streams) is never stored, and neither
  is a cancellation (the `OperationCanceledException` propagates as today). A retry runs ffprobe again.
- **No in-flight dedup.** No concurrent duplicate probe was measured: Join's chip and compatibility probes run one
  after another, and Bulk probes rows one at a time. Two simultaneous calls would each run ffprobe and store
  equal results, which is harmless.
- **Engines and view models are untouched.** Their repeat calls become cache hits, including Join's
  `SumDurationsAsync`, so the SPEC-003 stage order and its "progress degrades to unknown on a probe hiccup"
  (I29-I31) hold unchanged.
- **`MediaInfo` is an immutable record** (`MediaInfo.cs:11-15`, `IReadOnlyList` streams), so sharing the cached
  instance is safe.
- The `KeptMiddleRequestBuilder.cs:36-38` comment is now true; tighten its wording if needed.

## Detail

- **The honest re-check stays honest.** A clip edited between add and Run gets a new key (mtime or length) and is
  probed again at Run. An incompatible change is still refused with named mismatches ("Compatibility is
  refused, not fixed").
- **Memory:** one small record per distinct file version in the session, the same exposure as the keyframe
  cache. Bounding both is T-200.

## Interfaces / contracts

- `IMediaProbe` is unchanged. Test fakes that implement it directly are unaffected.
- **SPEC-004, same commit.** New invariants (next free ids, I33-I36 at planning):
  - **I33** — a successful probe is cached by `BuildCacheKey`; a repeat call on the unchanged file runs no ffprobe.
  - **I34** — a change of mtime or length gives a new key and a fresh probe.
  - **I35** — failures and cancellations are never cached.
  - **I36** — the empty-path and missing-file guards (I1/I2) run before any cache lookup.

## Edge cases

- **A file rewritten in place with the same mtime and length** would be served stale. The keyframe cache already
  accepts this exposure (SPEC-004 I16/I17), and Join's run-time re-check is exactly as honest as that key.
- **A network path whose mtime resolution is coarse:** same rule as the keyframe cache.

## Dependencies

- **T-188:** the bench numbers.

## Risks

- **Low.** It is one dictionary with the key and success-only rule the keyframe cache has used since T-093. The
  only behaviour change is the absence of repeated ffprobe processes.

## Out of scope

- In-flight dedup and `-skip_frame nokey` on the probe (T-211).
- Join's compatibility-refresh race and UI-thread probe start (T-215, T-214).
- Deleting `SumDurationsAsync`: unnecessary once it is a cache hit.
