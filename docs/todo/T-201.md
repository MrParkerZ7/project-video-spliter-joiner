## Concept

T-189 makes HEVC Exact rows fall back to the lossless cut, because their joint was corrupt:

- the concat output keeps the libx265 head's hev1 extradata;
- the copied part decodes against the wrong parameter sets: 250-316 decoder errors, tail PSNR 11-15 dB;
- evidence: `t187-fixtures/work/smart2-final-current-hevc-10.5.mp4`.

The repair would write the source leg so its first IRAP carries the source's VPS/SPS/PPS in-band
(`-bsf:v hevc_mp4toannexb` on that leg, the output tagged hev1), with timestamps placed so the leg lands exactly
(copyts plus a concat `inpoint`). A concat pass cannot apply a bitstream filter to one input only, so HEVC would
likely need three runs where H.264 needs two.

HEVC goes back into `SmartCutArgsBuilder.VideoEncoders` only when T-189's `SmartCutJointIntegrity` and T-190's
joint-timing test pass on HEVC hvc1, hev1 and Main10 fixtures. The head would use libx265 at a fast preset: measured
at an intro of 44.5 s with the input seek, ultrafast takes 2.39-3.17 s against 6.77 s for the default.

## Why later

- There is no proven recipe. The concat demuxer converts parameter sets in-band for H.264 only, and heads made by
  hevc_nvenc still decoded with 12-14 errors.
- **There is a second failure cause, so parameter sets alone will not repair it** (verified in the G-059 plan
  review): an open-GOP source made by libx265 (its default), cut at a CRA keyframe, decodes with *"Could not find
  ref with POC"* errors, because the CRA's RASL leading pictures refer back across the cut. A repair must also drop or
  re-encode those leading pictures, or cut only at IDR/BLA points.
- This is research, not a measured fix.

## Trigger

- The owner wants frame-exact cutting on phone (HEVC) footage.
- A recipe passes the joint check on the bench.
