## Why

User (T-187), verbatim:

> Need improve perfomance for 4K video, because when try to split 4K video it's super slowly. please check all join/spilt/bulk cut

Before planning, the real Core services were timed. A bench (a C# console app driving `MediaProbe`,
`SplitEngine`, `JoinEngine`, `BulkTrimEngine`, `SmartCutEngine` and the thumbnail and waveform services
through the app's own `FfmpegRunner`/`FfprobeRunner`, in the order the view models call them) ran on
**synthetic fixtures only**. No user video was opened, listed or probed. Bytes read per process came
from `GetProcessIoCounters`. Five readers checked every code claim at file:line.

Fixtures: `4k` = 3840x2160 H.264 High, 60.5 Mbit/s, 120 s, 2 s GOP with B-frames, AAC, moov at the end,
907 MB · `1080` = the same recipe at 1080p, 229 MB · `hevc` = 4K HEVC hvc1, 60 s, 381 MB · `g10` = 4K
H.264 with a 10 s GOP, 455 MB · `4k10m` = `4k` concatenated five times, 600 s, 4.5 GB. Machine:
i5-14500 (20 threads), RTX 4070, NVMe. Night runs were quiet. The 2026-10-04 runs had other sessions
using 6-15 of 20 cores (about 1.6x slower on CPU-bound work), so only same-run comparisons are quoted
as gains.

the operation needs: a whole-file read before a cut can be made, an Exact head that decodes from the
start of the file, and probes and grabs that repeat work. Two correctness bugs in Exact were found by the
measurement, and two in the lossless boundary by the plan review; all four are fixed here too, each in its own
fix ticket. A third lossless-boundary shape, a part with an end running two frames past it, is logged as its own
later fix ticket (T-220).

## What the user sees, and when

- **After T-194:** a 4K MP4/MOV loaded in Split shows its keyframe ticks and resolves cuts almost at once.

## Risks

- **The sample-table reader is new parsing code, and real phone and camera files cannot be sampled**
  (hard rule). A wrong but plausible list would snap a lossless cut onto a non-keyframe. Mitigations
  (T-194): a narrow supported subset that declines everything else, TimeSpan-exact parity tests on a
  synthetic matrix shaped like phone files, a runtime ffprobe check of the first and last GOP that sends
  any mismatch to the packet scan, and the frame-scan fallback kept.
- **HEVC loses frame-exact cutting** until the later repair (T-201). The output becomes the honest
  lossless cut with a stated reason, shown on the row before the run, in place of a corrupt file.
- **Exact assumes a zero `start_time`.** Keyframe times and the concat `inpoint` are absolute source pts, but
  ffmpeg's `-ss` is an offset from the format `start_time`, and Core never read it. T-219 records it in
  `MediaInfo` and converts the lossless path's `-ss` with it; T-196 converts its cut pictures' `-ss` the same way;
  T-190 makes a source whose `start_time` is not zero
  (TS about 1.4 s, AVCHD `.mts`) fall back from Exact with a reason. Those rows lose Exact, which was writing overlapping files. Offsetting every time instead is rejected for
  now: the same offset is unaccounted for across the timeline, and nothing tests that time base. An MP4 that starts
  slightly above zero (a B-frame delay with no edit list) falls back too; how common that is cannot be sampled here,
  and the row says so before Run.
- **The H.264 joint fix rests on measured but partial evidence**: same size, zero boundary errors, a
  10.02 s duration against 10.09 s for a 10 s keep. T-190's frame-md5 and audio tests decide, and the
  ticket names a fallback candidate.
- **A fast preset changes the head's bytes.** The quality floor and the profile rule (T-192) guard it.
- **The lossless boundary fix changes the sacred copy path's arguments** (T-219): a `-segment_time_delta` of half a
  frame, and `-ss` minus `start_time`. No encoder token is added, the copy invariant is asserted on every command,
  each part's first frame is checked against the source (and the frame count of segment-muxer parts and parts that
  run to the end), and the bench shows the copy's speed is unchanged. The half-frame delta is ffmpeg's documented recipe, not a proven root cause; T-219 names a second
  candidate.
- **Unknown user setup — asked once, blocking nothing.** The user's container, codec, length and drive are
  unknown. If their 4K is MKV or TS, T-194 does not help, and T-199 and T-198 become the top items. So **when the

## Decisions (taken at planning)

- **Keyframes from the container index, not a windowed lookup.** Only the sample table returns the whole
  list. The planner's average GOP, the coarse-GOP warning, `AddCutAt`, Bulk's `KeyframesReady` gate and
  SmartCut all consume the whole list, and the index keeps them unchanged. A windowed `-read_intervals`
  lookup would rewrite three screens and still read about 125 MB per cut. `-discard nokey` gives wrong
  pts on B-frame MP4 (61 packets against 60, measured) and is ignored by MKV.
- **HEVC falls back now; the repair is later.** Repairing the joint (in-band parameter sets) has no
  proven recipe yet (hevc_nvenc heads still gave 12-14 errors). Falling back restores SPEC-001 I46 ("never
  a silently corrupt concat") with the fallback path that already exists.
- **One predicate decides "Exact will really run".** `SmartCutArgsBuilder.TryResolveEncoders` on the row's probed
  `MediaInfo` decides the engine's fallback, the row's snap readout and eligibility before Run (T-189), the chip's
  cut time (T-196) and the batch weight (T-191); T-190's start-time rule joins the same gate. Rejected: leaving the
  row's honesty to a later ticket, which would have shown a cut the run does not make on every HEVC row.
- **The lossless boundary faults get their own fix ticket (T-219), built before T-190.** They are real bugs in
  the sacred copy path, so they are in scope as drain-discovered fixes. Rejected: patching them inside T-190 (its
  stop rule forbids touching the copy path there); logging them as later tickets (T-190's TS fallback would then
  promise a keyframe-snapped cut the copy path does not make); wording T-190's reason around them (it would leave a
  known wrong boundary in every TS lossless cut).
- **The end overrun of a lossless part with an end is its own later fix ticket (T-220), not part of T-219.** It is a
  third copy-path shape, so T-190's stop rule applies. Every part still starts on its keyframe, the two extra frames
  lie past a cut that is already a keyframe, the behaviour predates G-059, and no fix recipe has been measured (the
  concat `outpoint` T-190 uses behaves the same way). T-219 and T-190 scope their frame-count and duration checks
  around it and name T-220. Rejected: fixing it inside T-219 with no measured recipe; leaving it unnamed, which kept
  frame-count checks in T-219, T-190 and criterion 6 that could not pass.
- **Cut pictures convert to ffmpeg's time base now (T-196, after T-219).** The exact request's time is an ffmpeg
  offset; the chip and Save's auto-capture pass their keyframe time minus `StartTime`, while *Use current frame*
  and the apply re-take, which hold player or requested times, pass theirs unchanged (T-196's TS relaunch check
  confirms the player's base). Rejected: limiting criterion 5 to sources whose `start_time` is zero and logging the
  TS picture offset as a later ticket, because the fix is one subtraction on a field T-219 already adds, and a chip
  1.4 s past the cut on every TS row would contradict the criterion; converting inside the thumbnail service, which
  would need the source's `MediaInfo` and would shift the player-time callers.
- **The H.264 joint becomes one concat pass over [head, source with `inpoint`].** This option is the one
  with measured evidence. It removes code (the tail temp and its run) and writes the kept bytes once.
- **The fast preset is its own ticket (T-192)**, after the equivalence-preserving input seek (T-191), so a
  quality trade never rides along with a pure speed-up. Only libx264 changes, and its profile is never
  lower than the source's. `ultrafast` is rejected: it declares Constrained Baseline while the copied tail
  is High.
- **Probe cache without in-flight dedup; engines untouched.** The cache alone removes every measured
  repeat, including Join's `SumDurationsAsync`, which becomes a cache hit. No concurrent duplicate probe was
  measured.
- **Abandoned-scan cancellation is later (T-198).** Its mechanism is verified in code (`MediaProbe.cs:203,

  milliseconds.

## Review

Three competing designs were judged by a panel (Solution Architect · Tech Lead · Product Owner). The
designs were impact-first, invariant-first and minimal, and each was scored on impact on the note,
invariant safety, testability and effort realism. Impact-first won on impact. The plan keeps its scope,
its success criteria and its in-repo bench. It takes from invariant-first the HEVC fallback, the runtime
ffprobe anchor on the index, the order with correctness first, and the profile rule for the preset. It
takes from minimal the single-pass H.264 joint built inside SmartCut, a probe cache without dedup, and
deferring abandoned-scan cancellation. Every implementation ticket ends `spec: reviewed`.
