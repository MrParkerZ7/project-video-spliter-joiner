## Concept
Placing a cut (Set-cut-at-playhead, manual add, timeline-click) must drop the marker INSTANTLY — even while the background keyframe index is still running — instead of waiting for the whole scan. The snapped position resolves as soon as the index is ready.

## Design
- **`SplitViewModel.AddCutAt`**: stop deferring the visible add. When `IsIndexingKeyframes && Keyframes.Count == 0`:
  - Add the `CutMarkerViewModel` NOW at the requested position with an **un-resolved snap** (Snapped = requested, Delta = 0, an `IsSnapPending`/"snapping…" flag). Dedupe on the requested time for now.
  - Kick off an async continuation (reuse `EnsureKeyframesAsync()`) that, when keyframes arrive, **re-snaps that marker in place** (updates Snapped/Delta, clears the pending flag) and re-dedupes on the final snapped time (if the resolved snap collides with an existing marker, drop the duplicate).
- **`CutMarkerViewModel`**: add an `IsSnapPending` bool + a method/path to (re)compute its snap once keyframes are available; the display shows "snapping…" while pending, then the normal `MM:SS.f → MM:SS.f (±N.Ns)`.
- When keyframes ARE ready (the common case after indexing completes), behavior is unchanged (synchronous snap + add).

## Detail
- Cancellation/stale-load: if the file changes while a marker's snap is pending (a newer load), drop the pending resolve (existing `_keyframeIndexTask`/HasFile guards).
- The split itself always uses the true snapped keyframe times (already the case) — this ticket only changes WHEN the marker appears + how its display resolves.
- Keep `AddCutAt` the single entry point; `SetCutAtPlayhead`/manual-add/timeline-click all benefit.

## Interfaces / contracts
- `SplitViewModel`/`CutMarkerViewModel` internal; no engine/`IMediaPlayer` change. VM stays fake-testable (fake probe with a gated `GetKeyframesAsync`).

## Acceptance criteria + Case-Coverage Matrix
- [ ] With a fake probe whose keyframe scan is gated (still running): `SetCutAtPlayhead`/`AddCutAt` adds a marker IMMEDIATELY (Markers.Count increments before the scan completes), flagged snap-pending.
- [ ] When the gated scan completes → the marker's Snapped/Delta resolve to the nearest keyframe + the pending flag clears.
- [ ] When keyframes are already ready → marker added synchronously with the correct snap (unchanged).
- [ ] Dedupe holds: two cuts that resolve to the same keyframe end as one marker.
- [ ] Build 0-warning; prior tests green.
- Matrix — Required-Success: cut during indexing → instant marker, later snapped. Boundary: file changes mid-pending (drop); cut at 0/end; two pending cuts snapping to same keyframe → deduped. Required-Fail: index fails → identity snap kept (no crash).

## Risks
