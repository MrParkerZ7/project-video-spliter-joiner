## Reported
> please also improve button delete all style

## What is wrong with it now
It ships as a plain default `Button` with `Padding="10,5"`, sitting immediately left of the accent-styled
**Run bulk cut**. So the most destructive control on the screen is the *least* visually distinct one, and
it sits right beside the button people press after every batch. That is a misclick waiting to happen.

The tab already has the vocabulary this needed, and I did not use it:

| exists | used for |
|---|---|
| `ProfileDangerButton` | the profile ✕ — muted at rest, danger-coloured on hover |
| `DangerBrush` (`Tokens.xaml`) | the destructive palette |
| `AccentButton` / `HeroButton` | affirmative actions |

## Design
1. **Danger-styled**, consistent with `ProfileDangerButton`: muted at rest so it does not shout, clearly
   red on hover/press so intent is confirmed before the click lands.
2. **Separate it from Run.** A gap, a divider, or the opposite end of the footer — anything so the
   destructive control is not adjacent to the most-pressed one.
3. **Keep the count-and-size label** (`Delete originals (12 · 4.3 GB)`). It is the reason to press it and
   doubles as a last check on what is about to happen.
4. Consider a leading ✕ or bin glyph, matching how the profile ✕ reads.
5. It stays **hidden until it can act** (T-144) — do not turn it into a permanently-greyed control.

## Acceptance criteria
- [x] Reads as destructive at a glance without being loud at rest — muted at rest, danger on hover.
- [x] Not adjacent to Run bulk cut — far LEFT of the footer, opposite end from the button people press
      repeatedly. **This was ticked FALSELY on 2026-09-01 and is only now true** — see the correction below.
- [x] Uses the existing danger vocabulary (`ProfileDangerButton`) rather than a new one-off style.
- [x] Still shows the count and the reclaimed size (`DeleteOriginalsLabel`) — that is the whole reason to press it.
- [x] Checked at five window widths (1600/1280/1024/900/760) by laying the real view out and measuring
      pixel positions — stronger than eyeballing it, and it cannot silently regress. Not yet seen by a
      human on a finished batch; the original wording said "on screen … in both layout axes" — the footer is where
      clipping has bitten before (T-141).

## Out of scope
Changing what the button does, or when it is offered.

## Outcome — 2026-09-01

Shipped in `430f049`, recorded as SPEC-011 I119.

**One criterion is deliberately left unticked.** The button is gated on a completed batch, so seeing it at
a wide and a narrow window in both layout axes needs a real run over real videos — not something a
screenshot of the idle screen can stand in for. The styling and placement are in and asserted structurally;
the visual check at both widths is outstanding and should be done the next time a batch is run for real.

Reuses `ProfileDangerButton` — the style the profile Delete already uses — rather than inventing a second
destructive look: muted at rest, danger on hover. A button that is red all the time stops meaning anything.

Placed at the far **left** of the footer, the opposite end from *Run bulk cut*. The point is not decoration:
this is the only irreversible control on the screen and it should not sit under the cursor of someone
pressing Run repeatedly. It still names the file count and the space reclaimed, which is the reason anyone
presses it at all.

## Correction — 2026-09-02: the criterion was ticked, and it was false

A board-drain review measured the shipped footer and found the destructive button **on Run's pixels**.
It was right, and the tick above was mine, taken from the XAML comment rather than from the markup.

**What actually shipped.** The button was appended **after** `Run bulk cut`, inside Run's horizontal
`StackPanel`, carrying `HorizontalAlignment="Left"` — which a `StackPanel` ignores along its stacking
axis. The comment beside it read *"pushed to the far LEFT of the footer row, away from Run"*. The layout
did the opposite. Measured at 1000px: Run at x=682.5 (w=123.9), Delete at x=806.4 — **0.0px gap** — and
revealing Delete shifted Run **193.6px left**, so the irreversible button materialised on the exact pixels
Run had occupied. A batch finishes, the layout moves under the cursor of someone who has been pressing
Run, and the thing now under it sends their originals to the Recycle Bin. That is the precise hazard this
ticket was opened to remove, shipped inside the fix for it.

**The fix.** The footer grid gains a dedicated leftmost `Auto` column that the button owns alone; the
options move to the `*` column and Run's stack to the trailing `Auto` column. Separation is now
structural rather than advisory, and because Run sits in a right-hand `Auto` column, revealing Delete
**does not move Run at all**.

**Now pinned by a test**, since a comment is what caused this: `BulkCutViewLayoutTests.
TheDestructiveButtonSitsAtTheOppositeEndFromRun_AndRevealingItDoesNotMoveRun` lays the real view out at
five widths and asserts (a) Run does not move when Delete appears, (b) Delete never overlaps the pixels
Run occupied beforehand, (c) Delete starts left of the midpoint. Mutation-checked: putting the button
back in Run's column kills it.

**Why it happened.** I ticked an acceptance criterion from prose describing the code instead of from the
code. Every other criterion here was verified; this one was read. The generalisable rule — *a claim about
layout is checked by laying it out* — is the same one T-138 arrived at from the opposite direction.
