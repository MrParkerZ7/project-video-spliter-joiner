## Why / vision
Loading a file today means clicking "Load…" / "Add files…" and picking through a dialog. Drag-and-drop is the expected desktop gesture: drag a video (or several) straight from Explorer onto the app. Plus reordering join clips by dragging is more direct than Up/Down. Small feature, big everyday-feel improvement.

## Gap from current state
- The Split screen (T-007) *speced* drop-to-load but only wired the `OpenFileDialog` — no `AllowDrop`/`Drop` handlers exist. The Join screen (T-008) has add-via-dialog + Up/Down reorder, no drag.
- Missing: `AllowDrop` + DragOver/Drop wiring on both views, a shared video-file filter, drop-target visual feedback, and internal drag-reorder for the Join list.

## Decisions
- **D1 · Standard WPF drag-drop** — `AllowDrop=true` + `DragOver`/`Drop` handlers in code-behind (drag events are UI-level), routing dropped paths to the EXISTING VM commands (`LoadCommand` / `AddFilesCommand`). No new load/add logic (reuse).
- **D2 · Testable filter** — the "which dropped paths are acceptable video files" logic is a PURE helper (unit-tested); only the event wiring is code-behind (headless-unverifiable, like the rest of the UI → verified via `app-run`).
- **D3 · Reorder-drag auto-included** (under `--auto-approve`) as part of "drag-and-drop support"; isolated in T-017 so it's separable if unwanted.

## Plan
```
T-016 external file drag-drop (Split load + Join add + shared filter + drop affordance)
T-017 drag-to-reorder the Join list        (independent; serialized on the shared tree)
   └─► T-018 perfect-docs (terminal)
```

## Risks
- Drag-drop event wiring can't be verified headless → the pure filter is tested; live drop verified via `app-run`.
- Reorder-drag fiddliness in WPF ListBox → keep MVP (drag a row to a new index); the Up/Down buttons stay as the reliable fallback.

## Out of scope
Dropping onto the timeline to set a cut, drag between tabs, drag-out/export, folder drops (recursion) — later.
