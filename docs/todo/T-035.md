## Concept
Splitting a real mpegts/.ts file (Japanese path) failed with `exit -28`. Reproduce, confirm the actual cause (exit -28 = AVERROR(ENOSPC) — can't write output), then fix. Investigate-first: don't guess between disk-full / bad-path / mpegts-timestamps.

## Investigate (read-only first)
1. Reproduce: build a `.ts`/mpegts fixture (`ffmpeg -i <src> -c copy out.ts`, or `-f mpegts`) — ideally at a NON-ASCII path (a `立` / Japanese dir) to mirror the report — and run the split engine on it.
2. Determine the real cause of exit -28: (a) is the OUTPUT drive actually full? (b) does the non-ASCII OUTPUT path fail to create (write error → ENOSPC-like)? — pairs with T-036's encoding fix; (c) is it mpegts timestamp/segment handling? Capture the FULL stderr (needs T-036's UTF-8 fix to read the path).
3. Record findings in `## Findings`.

## Fix (per the confirmed cause)
- If bad-path/encoding: fixed by T-036 (UTF-8 + correct path to ffmpeg) — verify the split then succeeds.
- If mpegts timestamps: add mpegts-safe copy flags to the split command for `.ts`/mpegts inputs (candidates: `-fflags +genpts`, `-avoid_negative_ts make_zero`, `-copyts`, `-muxpreload 0 -muxdelay 0`) — verify the output segments are PLAYABLE (re-probe), not just exit 0.
- If genuinely disk-full: map exit -28 / `ENOSPC` → a clear `UserFacingError` (DiskFull: "not enough space to write the output") in `FfmpegErrorMapper` (today it surfaces the mpegts warning tail, not the real cause) + a pre-flight free-space check on the output dir with a friendly message.
- Preserve the `-c copy` no-re-encode invariant throughout.
