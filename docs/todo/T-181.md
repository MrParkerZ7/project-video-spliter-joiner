## Concept

8 of the user's 13 profiles have 64–96px pictures. No card can show them at a full size, because the
pixels do not exist. T-172 recorded them as *"cannot be re-grabbed — `CutProfile` records no source
video"*. That is true at rest, but **applying a profile supplies one**: the video it was just applied to,
from the same series. The frame at the profile's own intro cut in that video is the same kind of picture
the automatic default has always been (SPEC-007 I61), and after T-179 it really is 640px. So when a
profile whose picture is too small is applied, re-take the picture from that video, and keep the old one.

## Design

**Trigger.** `ApplyProfileToSelected()` / `ApplyProfileToAll()` apply exactly as today; they stay
synchronous, and their return values, `ApplyToAllReport` and the apply note (SPEC-011 I26) do not change.
After applying, they start one background refresh **only if** the applied profile has a picture that is
either:
- a readable file narrower than `LowResolutionPictureWidth` (**320**), or
- a file that is missing — there is nothing left to protect, and the card already shows no picture.

`LowResolutionPictureWidth` is a new named constant in `BulkCutViewModel`, pinned by a test to the
`ProfilePreviewCardWidth` resource. That resource is the same minimum box width below which the card
shows the low-resolution note, so "the card flags it" and "applying re-takes it" are one condition.

**Never refreshed:**
- a picture 320px or wider (every capture since T-169, any sharp upload);
- a file that exists but cannot be read — never replace a picture we could not measure;
- a profile with **no** picture — removing one is deliberate (I78);
- on any gesture other than apply (save, select, hover and backup restore never refresh).

**Source row.** For apply-to-selected, the selected row. For apply-to-all, the selected row if it was a
target, otherwise the first target in list order. The chosen row must have a probed `Duration` greater
than the profile's `IntroFromStart`; if it does not, take the next target in list order that does. If
none qualifies, there is no refresh. Whether the *cut* is valid does not matter for a *picture*.

**Time.** The profile's own `IntroFromStart` on that row's file — the requested time, **not** the row's
snapped cut. It is the profile's own value, the same for every target, and it needs no keyframe scan, so
it works while a row is still scanning (T-173). The automatic default (I61) grabs the snapped intro-end;
the two differ by less than one GOP, which does not matter for a recognition picture. Stated in the spec.

**Grab** `_thumbnails.GetThumbnailAsync(path, IntroFromStart, ProfileThumbnailWidth, ct)`. It returns a
true 640px frame only because of **T-179**, hence the edge.

**Re-check just before attaching** (on the UI thread, after the grab lands). A path check is not enough
here. The store names each file after the profile (`<SafeFileName(name)><ext>`,
`ProfileThumbnailStore.cs:115-119`), so a new small upload with the same extension keeps the same path.
The view-model therefore keeps a **picture generation** per profile name (case-insensitive). It is bumped
by every change to a profile's picture or to the profile's existence:
- `TryAttachThumbnail` (every source — auto, upload, snapshot and this refresh);
- `ClearThumbnail`;
- `DeleteSelectedProfile`;
- `SaveProfile` (a re-save);
- backup restore.

The refresh captures the generation at apply time and discards the frame silently unless:
- the profile still exists (by name, case-insensitive);
- its generation is unchanged;
- its picture still qualifies (narrower than 320px, or missing).

This covers *Use current frame*, **any** upload — including another 64px one — *✕ Picture*, a re-save, a
delete, and a delete-then-re-create made while the grab was in flight.

How the generation behaves:
- **It only ever increases.** Every bump takes the next value of one view-model-wide counter and stamps
  it on the name. A delete bumps the name and never removes its entry, so a re-created profile can never
  land back on the value captured earlier.
- **Every `SaveProfile` bumps**, the first save included.
- **A backup restore bumps every name in the restored set.**
- The refresh's own attach bumps too. This is harmless, because the re-check runs before it.
- **A discarded refresh frees its in-flight slot**, so a later apply can retry.

**Keep the old picture.** Before storing, the refresh **copies** (never moves) the current file, when it
exists, into `profile-thumbs/replaced/<SafeFileName(name)>-<yyyyMMdd-HHmmss><ext>` through a new store
method. Then:
- **If that copy fails, the refresh stops** and the old picture stays where it is.
- **If the copy succeeds and the store's `Save` then fails,** the old picture is still at its original
  path and still attached, and the redundant copy in `replaced/` is deleted (best effort).

So a picture is never lost to this path. The store's own sweeps enumerate only the root folder
(`ProfileThumbnailStore.cs:182, 301`), so they never touch `replaced/`.

**Attach without moving the selection.** Today `TryAttachThumbnail` always ends with
`SelectedProfile = FindBarProfile(existing.Name)` (`BulkCutViewModel.cs:2127-2129`). That would drag the
selection back to the applied profile. The refresh uses a selection-preserving variant: it captures the
selected profile's **name** before attaching and afterwards restores `FindBarProfile(thatName)`, or null
if nothing was selected. The existing callers keep today's behaviour. `RefreshProfiles()` clears and
refills the bar, and the ListBox binds `SelectedItem` two-way, so this is also asserted with the real
view binding.

**One at a time.** At most one refresh in flight per profile name (case-insensitive). An apply of the
same profile while one is in flight starts nothing new.

**What the user sees.**
- **On success:** a new view-model string, `ProfilePictureRefreshNote`, shown in the apply-note area
  under `ApplyReportSummary` (and not part of it):
  - old picture kept aside:
    *`Picture for "<profile>" re-taken at full size from <file name> — the old one is in profile-thumbs\replaced.`*
  - old picture file missing (nothing to keep aside):
    *`Picture for "<profile>" re-taken at full size from <file name> — its old picture file was missing.`*
- **It is cleared in the `ApplyToAllReport` setter.** Every writer of the report therefore clears it:
  both profile applies, the row-level *Apply to all* (`BulkCutViewModel.cs:1751`), the set-at-playhead
  fan-out, list clear and batch start. A refresh records the report instance it belongs to. If that
  report has been replaced or reset by the time the grab lands, the picture is still attached, but the
  note is **dropped**, so it never appears under another action's summary.
- **On failure or discard:** nothing. This is silent, like the automatic default (I66/I72), and
  `Operation.Error` is never set.

**The card's note** (I109) changes its words, because re-taking is now automatic:
*"low resolution — applying this profile to a video re-takes it at full size, or use 📷 Use current frame"*.
It shows under exactly the same condition as today.

## Decisions (taken at planning under the `--auto-approve` default; recorded, not blocking)

**Automatic on apply, keeping the replaced file** was chosen over these alternatives:
- *A "re-take at intro cut" button* — safe, but it is the manual gesture T-172 already offered
  (*Use current frame*) in a slightly shorter form. It would add a tenth control to the profile action
  row, and the user has now asked three times for the card simply to show a full picture.
- *Leave the pictures as T-172 settled* — its premise (no source video) does not hold at apply time.
- *Refresh on every apply* — would overwrite pictures the user deliberately took. The 320 gate keeps
  every picture the card can already show sharply.
- *Replace and delete, as the store does for every other source* — rejected; see the cost below.

**The cost, stated in full:**
- The first apply of each of the 8 low-resolution profiles replaces its picture.
- Some of those may be **uploads** the user chose. T-169 counted 6 uploads among 11 pictures; the file
  dates suggest several 64px ones were really captures that hit the 64px chip cache (G-058 § Why).
- Until a follow-up records each picture's source, the user **cannot keep** a picture narrower than
  320px: re-uploading it (uploads only ever shrink, I107) gets it replaced again on the next apply.
- A **mis-apply** (the wrong chip, then the right one) replaces the wrong profile's picture with a frame
  from a different show.
- **Mitigations:** the old file is kept in `replaced/` rather than deleted; the success line names the
  profile and the source file, so the change is visible; *Use current frame* re-takes it.
- If the user wants uploads exempt, the follow-up is to record `ThumbnailSource` on the profile and skip
  uploads. It is not filed now (YAGNI) — revisit when the user reports a replaced upload.

## Detail

- **Pixel-width reader:** `ImageNormalizer.TryReadPixelWidth(string path) → int?` in `src/App/Io`, next
  to the WPF imaging the view-model already calls (`BulkCutViewModel.cs:2092`). The view-model stays
  WPF-free (`ImageSignature.cs:14-18`).
  - It reads the header only: `BitmapDecoder.Create` with `BitmapCreateOptions.DelayCreation` and
    `BitmapCacheOption.None`, then `Frames[0].PixelWidth`, and the stream is closed.
  - It returns null on any failure. The caller tells *missing* (`File.Exists` false → refresh) from
    *unreadable* (exists, null → no refresh).
- **Grab thread:** the grab runs off the UI thread; the re-check, keep-aside and attach run on it, as in
  `SnapshotProfileThumbnailAsync`.
- **Stale comment:** correct the comment at `BulkCutViewModel.cs:146-148` ("a profile records no source
  video", so nothing could be migrated) in this commit.
- **SPEC-007 I106** gains the sentence T-179 hands over: its *"captures are exactly 640"* held only on a
  cold cache second until T-179 keyed the cache on width (link SPEC-005).

## Interfaces / contracts

- `BulkCutViewModel.LowResolutionPictureWidth` (320), pinned == `ProfilePreviewCardWidth`.
- `internal Task PendingPictureRefresh` — a `WhenAll` over every in-flight refresh. It completes when none
  is pending, and is `Task.CompletedTask` when none started. **Every test awaits it before asserting**,
  including the negative ones, so "no grab" can never pass just because the background work had not run
  yet.
- The per-profile picture generation (see § Design) — internal, readable by tests.
- `ProfilePictureRefreshNote` (string, null when none) — shown in the apply-note area; cleared where
  `ApplyToAllReport` is reset.
- `TryAttachThumbnail` gains a selection-preserving mode (a parameter or a sibling method). The existing
  callers are unchanged.
- `ProfileThumbnailStore` gains a keep-aside method, e.g. `KeepAside(string profileName, string path) →
  string`. It **copies** the file to `replaced/<SafeFileName(name)>-<stamp><ext>`, returns that path, and
  throws on failure. A matching best-effort delete removes the copy when `Save` fails afterwards.
- `ImageNormalizer.TryReadPixelWidth(string) → int?`.
- `IThumbnailService.GetThumbnailAsync` is unchanged; it is width-correct after T-179.

## Acceptance criteria + Case-Coverage Matrix

**Harness.** All tests await `PendingPictureRefresh`.
- Build the view-model with `BuildWith(… thumbnailDelay: NeverSettles)` (`BulkCutProfileThumbnailTests.cs:79-90`),
  so the rows' own 64px chip grabs never reach the fake and cannot pollute `Requests` or the call counts.
- The 64px precondition is a real 64px PNG put in place through `UploadThumbnail`; the store keeps small
  uploads as they are.
- The fake thumbnail factory writes a real PNG at the requested width.
- The keyframe grid comes from `SetUniform(path, duration, 2)` (`BulkTestFakes.cs:56`).
- The view-level selection test drains its continuations with a `PumpContext` (as in
  `BulkItemThumbnailTests.cs:29`) inside the `OnSta` body, after the `Gate` is released.

- [ ] **Apply-to-selected, 64px picture.** The profile's `IntroFromStart` is **11 s** on the standard
      2-second keyframe grid, so it snaps to 10 or 12. The grab is called once with **(the row's path,
      11 s, 640)**, and `Requests[0].Time != row.IntroEnd.Snapped`. Afterwards:
      - the stored file's **real pixel width is 640**;
      - `ThumbnailPath` points at it;
      - the old 64px file sits in `replaced/`, **byte-identical**;
      - `ProfilePictureRefreshNote` equals the exact sentence, naming the profile and the file.
- [ ] **Apply-to-all source row:** the selected row when it is a target, otherwise the first target in
      list order. A target with no `Duration`, or with `Duration` ≤ `IntroFromStart`, is skipped for the
      next one.
- [ ] **No grab at all** (call count 0, file byte-identical, no note) for:
      - a 320px or a 640px picture;
      - a profile with no picture;
      - an existing file that cannot be read.
- [ ] **Missing picture file** → refreshed, nothing kept aside, and the note is the exact *"its old
      picture file was missing"* sentence.
- [ ] **Grab returns null or throws** → the old picture is byte-identical, `Operation.Error` is null, the
      state is idle, there is no note, the apply note text is unchanged, and `replaced/` is empty.
- [ ] **Keep-aside fails** (fixture: a FILE named `replaced` in a usable store root) → no refresh, and the
      old picture is untouched.
- [ ] **Save fails after a successful keep-aside** (fixture: a directory occupying the store's staging
      path `<safe>.incoming<ext>`, `ProfileThumbnailStore.cs:127`). `<ext>` is the **grabbed** file's
      extension (`.png` from the fake), not the old picture's; otherwise the fixture is never hit. Confirm
      that the store's `TryDeleteFile(staging)` swallows the directory:
      - `ThumbnailPath` is unchanged;
      - the old file is still at its original path and byte-identical;
      - the stray copy in `replaced/` is gone;
      - there is no note, and `Operation.Error` is null.
- [ ] **In flight (`FakeThumbnailService.Gate`):** each of these changes before the grab lands discards
      the refresh — nothing is attached and no note appears:
      - *Use current frame* on the same profile;
      - an upload of **another 64px PNG** with the same extension (same path — caught by the generation);
      - an upload of a 640px picture;
      - *✕ Picture*;
      - a re-save;
      - delete;
      - delete then re-create with the same name.
- [ ] **Note lifetime:**
      - the note is shown → the next apply of a profile with a picture of 320px or wider → the note is
        null;
      - the note is shown → list clear → the note is null;
      - a refresh that lands after its report was replaced attaches the picture but sets no note.
- [ ] **Selection moved to another profile before the grab lands:** afterwards
      `SelectedProfile.Name` is the other profile's name, `Profiles` contains that `SelectedProfile`, and
      the applied profile's `ThumbnailPath` is updated. This is asserted in the view-model **and** with
      the real `ListBox` binding in a view test.
- [ ] **Two applies of the same profile while one is in flight** → one grab (`WhenCallCountReaches`).
      Profiles are already unique regardless of case, so the case-insensitive key is exercised by
      re-saving the in-flight profile under a different case (same `ThumbnailPath`) and applying again:
      still one grab. This is intended: the re-save bumps the generation, so the first refresh is
      discarded when it lands, and the second apply started nothing because the slot was still occupied.
      An apply **after** the discard retries.
- [ ] **Never on other gestures:** selecting a 64px profile, saving one, and restoring a backup full of
      64px pictures each cause zero refresh grabs.
- [ ] **The apply's own effect is identical** with and without a refresh: the same cut points, the same
      report counts, and a byte-identical `ApplyReportSummary` (SPEC-011 I26 untouched).
- [ ] **Row still scanning** (`BulkFakeProbe.ScanGate`) → the grab still runs at the requested time.
- [ ] **The note's words** name both the automatic re-take and *Use current frame*; its visibility
      condition is unchanged.
- [ ] **SPEC-007, in the same commit:**
      - **I61:** its "`ProfileThumbnailWidth` = 320" is stale — it is 640;
      - **I74:** four sources, not three — add the apply refresh;
      - **I106:** "every gesture targets one width" now covers four gestures, plus T-179's cold-cache
        sentence;
      - **I109:** the note's words, and drop its "cannot be re-grabbed" sentence;
      - **new numbered, atomic invariants** for the refresh: trigger/gate, source row, time, the
        generation re-check before attach, keep-aside (copy, never move), silence on failure, the note
        and its lifetime, the by-name attach that preserves the selection, and one in flight per name;
      - `updated:` and `## Links` refreshed, and `docs/specs/_index.md` recounted from disk.

## Edge cases

- **Intro 0** (an outro-only profile) grabs the first frame, just as the automatic default would.
- **A source video narrower than 640px** is enlarged to exactly 640 by `scale=640:-1` (I106). The
  refreshed picture is then soft but shows no note — a known edge, stated in I106 already.
- `RefreshProfiles()` re-projects the bar, which may reset its vertical scroll. The snapshot path already
  does the same; out of scope here.

## Dependencies

- **T-179:** the grab must return the requested width. Without it the refresh stores a 64px frame and
  fires on every apply.
- **T-180:** the same card template (the note lives inside the part T-180 restructures), and the
  `ProfilePreviewCardWidth` resource that T-180 keeps as the minimum.

## Risks

- **Replacing chosen pictures without a click.** See § Decisions: the file is kept, the change is named,
  and *Use current frame* repairs it.
- **Background-task tests.** `PendingPictureRefresh` is mandatory; a bare `_ =` fire-and-forget would make
  every assertion racy.
- **Backup size** grows as pictures move from 64px to 640px. T-172 measured about 31KB per profile at
  640, with a bound asserted at 120,000 bytes.

## Out of scope

Recording a picture's source to exempt uploads (see § Decisions); refreshing on save, select or restore;
the five 320px pictures; a failure line for a refresh that did not happen.
