## Found

While verifying [[T-160]]. `dotnet test` on the App project reported `Failed: 0` and then **never
returned** — the host sat idle until killed. VSTest's own diagnostic said it plainly:

```
Passed!  - Failed: 0, Passed: 955, Total: 955, Duration: 7 s
Data collector 'Blame' message: The specified inactivity time of 2.5 minutes has elapsed.
```

Worse than the hang: **the counts moved between runs** — 948, then 947, then 955 — because a killed host
reports only what it had finished reporting. That is [[T-155]]'s trap verbatim (*"a green line from a
crashed process is not a pass"*), and I quoted a couple of those moving numbers as "green" before
noticing they could not all be right.

## The wrong diagnosis, recorded because it cost the most time

This ticket originally concluded: *"reproduces with `--filter FullyQualifiedName!~LoadDuringRunTests`
and with the T-160 layout tests filtered out, so it is **not** caused by either of the two test files
added this session."*

Both exclusions were true. The conclusion was still wrong — because a **third** file changed this
session, and I never thought to exclude it. "I ruled out the things I remembered changing" is not the
same as "I ruled out my changes", and the gap between those two sentences was most of an hour.

## The actual cause — mine

Diffing discovery against a `trx` named the missing tests instead of leaving them a count, and **all
seven were in `BulkItemThumbnailTests`** — the one class [[T-159]] had edited hours earlier.

That class installs a `PumpContext`, whose `Post` only **enqueues**; a continuation runs when the test
calls `Drain()`. T-159's fix replaced a blocking `SpinUntil` with `await Task.WhenAny(signal, delay)`.
Under that context the `await` parks a continuation in a queue nobody drains — so the test hangs
forever, the other seven in its class never run, their results are never reported, and the host cannot
exit. Every symptom, from one edit.

The irony is exact: T-159 set out to stop a test being flaky and instead stopped its whole class running
at all, while the suite still printed green.

## The fix

Keep the part of T-159 that was right, drop the part that was wrong. The **signal** stays — the fake sets
it inside the same lock that updates its counters, so there is no sampling window and no race. It is now
observed by **spinning on `signal.IsCompleted`** rather than awaiting it, because a spin needs no pump.
The timeout stays a deadlock guard rather than a timing assumption. `SpinUntil` is restored, with a
comment saying why an `await` must never replace it here.

## Acceptance criteria
- [x] The hang dump / trx names the stuck class rather than a theory being formed about it.
- [x] `dotnet test` on App.Tests returns on its own — **9s**, no `--blame-hang` needed.
- [x] `dotnet test VideoSplitJoiner.sln` completes end to end — **20s**, was an indefinite hang.
- [x] **Discovered == ran == passed: 954.** The moving counts are gone, which is the real fix; the hang
      was only the visible half.
- [x] Cured at its source, not papered over with a global `--blame-hang-timeout` in a `.runsettings`.

## Lesson worth keeping

When a count is inconsistent between runs, **stop reading the count and enumerate the names.** Comparing
`--list-tests` against a `trx` took two minutes and produced the answer immediately; the preceding
half-hour of bisecting by exclusion produced a confident wrong conclusion. Same family as T-137's stale
build and T-155's green line from a crashed host: the instrument was lying, and the cure was to ask it a
question it could not fudge.
