## Concept
Make `StagedStatusWiringTests.RunSplit_StatusTextTransitionsThroughStages` deterministic — but only after determining whether the intermittent failure is a test-sync race or a real race in the product's status-reporting pipeline.

## Design
- **Reproduce** — run the single test 20–50× in isolation (`dotnet test --filter FullyQualifiedName~StagedStatusWiringTests.RunSplit_StatusTextTransitionsThroughStages`). Measured 4/5 failing on 2026-07-18, so a tight loop reproduces fast.
- **Classify** — read `OperationViewModel` + the staged-status wiring (`IProgress<OperationStatus>`, T-044 `50cbfc1`) and the fake staged engine in the test. Decide:
  - **(a) test-only race** — the fake reports stages on a different thread / the `IProgress` callback isn't flushed before the assertion; the product is fine.
  - **(b) product race** — `OperationViewModel` can drop/reorder/miss a `StatusText` stage under real timing (a user-visible glitch).
- **Fix at the right layer:**
  - (a) → make the test deterministic: synchronous `IProgress`/immediate `Progress<T>` capture, await the run pipeline, or inject a controllable scheduler so every reported stage is observed in order. Don't loosen the assertion.
  - (b) → fix the marshalling in `OperationViewModel` (ensure stage updates are ordered + not lost), keep a regression test that would have caught it.

## Acceptance criteria
- [ ] Root cause identified and classified (a) or (b), with the evidence (a failing interleaving) recorded.
- [ ] Fix applied at the correct layer (test-sync fix for (a); product fix + regression for (b)).
- [ ] Test passes **20/20** consecutive isolated runs.
- [ ] Full suite green; build 0-warning.

## Dependencies
None. Independent of the G-019/G-020 UI work.

## Risks
Papering over a product race by relaxing the assertion — forbidden. If it's (b), fix the code.

## Out of scope
Status-pipeline redesign; unrelated test hardening.
