## Concept
Selecting a row in the Bulk list is "extremely slow, sometimes doesn't work." Root cause: every selection **synchronously
opens** the video in the shared FFME preview player, so clicking/arrowing through rows fires a heavy FFME open per row and
thrashes the element. Fix: make the **selection instant** (highlight only) and open the preview **deferred + debounced** —
only the SETTLED selection previews.

## Grounding (2026-08-23 — root cause found)
- `BulkCutViewModel.SelectedItem` setter (`:193`) → `OpenOrUnloadSelected(value)` → `Player.Open(item.Path)` (`:559`) on
  EVERY selection, **no debounce**. FFME `Open` inits a decoder (expensive); rapid selection queues opens through
  `MediaReopenGuard` (T-080) and thrashes the element → lag / "doesn't work."
- The other per-select work (`RaisePlayheadCommandStates`/`RaiseProfileCommandStates`/`HasSelection`) is cheap (post-T-111);
  the FFME open is the cost.
- The cut-point thumbnail grabs (T-108) are already debounced + bounded — NOT the selection-lag cause.
- Precedent: the cut-point thumbnail grabber + `ThumbnailPreviewViewModel` already use a debounce (cancel-prior, latest-wins).

## Fix
1. **Debounce the preview-open** — the `SelectedItem` setter updates the selection + `HasSelection` + command states
   IMMEDIATELY (instant highlight), but the `Player.Open` is scheduled behind a short debounce (~200–300ms; a debounce
   delay-func like the thumbnail grabber uses, so tests can inject an immediate/gated delay). A newer selection **cancels**
   the pending open (latest-wins) so arrowing through 10 rows opens only the row you land on — not all 10.
2. **Keep it non-blocking + guarded** — the open stays off the UI thread (FFME `Open` is already async via `Run` +
   `MediaReopenGuard`); the debounce prevents even QUEUING transient opens, so the element never thrashes. Null selection
   (clear) still unloads (debounced-cancel any pending open first).
3. **Preserve behavior** — the settled selection still opens + previews; the stop-on-run / unload-on-clear / inactive-tab
   / stale-row-removed guards (T-100) all still hold; the outer `MediaReopenGuard` stays as the last-line safety.
4. WPF-free VM — the debounce uses `Task`/`CancellationToken`/a delay func (no PresentationFramework), like T-108's grabber.

## Acceptance criteria + Case-Coverage Matrix
- [ ] Selecting a row updates the highlight + `HasSelection` + command CanExecute IMMEDIATELY (no wait on FFME open).
- [ ] The preview `Player.Open` is debounced (~200–300ms) + latest-wins: arrowing/clicking through N rows opens ONLY the settled row (verify via a fake `IMediaPlayer` recording Open calls — N rapid selections → 1 Open of the last).
- [ ] Rapid selection does not thrash / lag; the settled selection still previews; null/clear still unloads (pending open cancelled first).
- [ ] No regression: stop-on-run, unload-on-clear, inactive-tab, stale-row-removed (T-100) still hold; WPF-free VM.
- [ ] Build 0-warning; suite green (879) + tests: instant-highlight (selection props set before any open), debounce-coalesces-rapid-selects (1 Open), cancel-pending-on-clear. `serves-spec: SPEC-011` + SPEC-013.
- Matrix — Success: single select → previews after the debounce; rapid arrow through rows → smooth, one open at the end. Boundary: select then immediately clear (no stray open), select then start batch (stop-on-run wins), select a row whose scan is still indexing (still opens the settled one), 1-row list. Required-Fail: none. (Feel = app-run — the key verification is the perceived responsiveness.)

## Dependencies
None. Touches `BulkCutViewModel` (the SelectedItem setter / `OpenOrUnloadSelected` — add the debounce) + reuses the
T-108/`ThumbnailPreviewViewModel` debounce pattern. No Core.

## Risks
Keep the debounce short enough that the preview feels responsive on a deliberate single click (~200–300ms is imperceptible)
but long enough to coalesce a fast scroll. Don't break the null/clear unload path (cancel the pending open before unload).
Don't remove the `MediaReopenGuard` (it's the safety net); the debounce is an ADDITIONAL upstream throttle.

## Out of scope
Speeding up FFME's own decode init; removing select→preview; the apply-to-all discoverability (T-116).
