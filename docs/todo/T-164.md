## Concept

Document the surfaces G-052 added to the Split screen, so the epic is not "done" while the docs still
describe a Split that cannot reclaim anything. Terminal node of the epic — runs only after
[[T-162]] and [[T-163]] land.

## Acceptance criteria
- [x] **USER_GUIDE** — the Split screen gains the delete-original gesture and the two automatic options,
      in the same voice the Bulk Cut section uses, including the plain statement that emptying the bin is
      whole-bin and permanent.
- [x] **CHANGELOG** `[Unreleased]` — user-facing outcomes, not commit subjects.
- [x] **SPEC-010** — invariants for the eligibility rule (all parts present), the deletion-time re-check,
      the Recycle-Bin-not-permanent guarantee, and each of the four arming gates; `docs/specs/_index.md`
      recounted **mechanically** and the freshness guard green.
- [x] **ARCHITECTURE** — Split's use of `IOriginalDisposer` / `ShellRecycleBin`, and whatever shared
      extraction T-162 chose (or its recorded decision not to extract).
- [x] **ADR** only if T-162/T-163 made a decision with a rejected alternative worth recording — e.g. the
      shared-vs-duplicated deletion path. No ADR if neither did; do not manufacture one.
- [x] Any claim written is checked against the code, not the ticket. T-154 shipped a spec invariant
      (I122) asserting behaviour the DragOver gate made unreachable, and it survived a whole ticket.

## Out of scope
Re-documenting Bulk Cut's existing delete-originals, except where a shared extraction changed it.

## Outcome — 2026-09-06

Docs brought current for everything G-052 shipped.

- **USER_GUIDE** — a new *"Reclaiming space after a split"* section under Split, in the same voice the
  Bulk Cut one uses: the by-hand button, the all-parts rule stated as the reason it is safe, both
  automatic options, and the plain sentence that emptying the bin is whole-bin and removes files other
  programs deleted.
- **CHANGELOG** — user-facing outcomes for the manual gesture and the automatic pair.
- **SPEC-010** — I52-I60 (T-162) and I61-I67 (T-163). `_index.md` recounted **mechanically** each time;
  the freshness guard is green at **751**.
- **ARCHITECTURE** — Split's use of the disposer, the composition-root wiring for *both* screens, the
  shared `FileFacts` predicates, and a pointer to ADR-0024. Also corrected a **stale claim** while in
  there: the section still described the disposer as running over
  `Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile`, which T-155 replaced with `SHFileOperation`
  three days earlier. Exactly the drift this ticket exists to catch.
- **ADR-0024** — written, because T-162/T-163 did make a decision with a rejected alternative: the
  eligibility rule is **deliberately not shared** between the two screens, while the predicates beneath
  it are. That is the one T-164 named as the example, and a future reader will otherwise "fix" it.

### The check that earned its place
The criterion *"any claim written is checked against the code, not the ticket"* caught the real thing
here — not in the docs, but in the product. Writing the ARCHITECTURE paragraph about `MainViewModel`
wiring the disposer meant opening `MainViewModel`, which is how it emerged that **it never passed one to
Split at all.** The feature was fully built, fully tested, 14 tests green — and completely inert in the
shipped app, because every test injects its own disposer.

Fixed, and now guarded: `TheCompositionRootWiresADisposerIntoSplit` reads `MainViewModel.cs` and fails if
the argument goes missing again. Removing it kills the test.

That is the same family as T-154's I122 (a spec asserting behaviour the DragOver gate made unreachable):
documentation written honestly is a test of the code, and it found something a green suite could not.
