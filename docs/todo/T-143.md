## Reported
> the app should remember last use feature tab & horizontal/vertical alignment

## Half of this already works — checked, not assumed

**The layout axis is already persisted.** `IAppSettings.LayoutMode` (D-001 / T-081) is written on every
toggle and restored on startup:

```csharp
_isVertical = settings.LayoutMode == LayoutMode.Vertical;   // MainViewModel.cs:93 — restore on startup
_settings.LayoutMode = value ? LayoutMode.Vertical : LayoutMode.Horizontal;   // :275 — persist on toggle
```

It is in the settings file today as `"layoutMode": "Vertical"`. If it has felt like it forgets, that is
worth knowing separately — **T-140** is a live bug where running the test suite overwrites the real
settings file, which would wipe it. That may be the whole of the "it forgets" experience.

**The tab is NOT persisted.** `MainViewModel.SelectedTabIndex` (`MainViewModel.cs:161`) is plain
in-memory state; there is no key for it in the settings DTO (`lastInputDir`, `lastOutputDir`,
`layoutMode`, the four split ratios, `bulkApplyCutToAllRows`, `cutProfiles` — no tab). Every launch
starts on Split.

## Design
1. Add `LastTabIndex` (or a named enum — `Split` / `Join` / `BulkCut`, which survives tab reordering far
   better than an int) to `IAppSettings` + the DTO, following the `bulkApplyCutToAllRows` pattern:
   nullable, absent-in-older-files → default, its own `[JsonPropertyName]`.
2. Persist it in the `SelectedTabIndex` setter; restore it in the `MainViewModel` constructor beside the
   existing `LayoutMode` restore, so the two live together.
3. **Restore defensively.** A stored value that no longer maps to a tab (a tab removed, the file
   hand-edited, a future build with fewer tabs) must fall back to Split rather than throw or leave the
   window blank.
4. Restoring the tab must not do the tab's *work* — landing on Bulk Cut should not trigger a probe, a
   scan, or a preview open. Assert that.

## Watch out for
Adding a field to the settings DTO has bitten once already: inserting one between a
`[JsonPropertyName]` attribute and its property silently re-bound the attribute and renamed a persisted
key, which would have orphaned every existing user's saved value (caught by `AppSettingsTests` during
T-133). Put the new attribute and property together and check the round-trip test still passes.

## Acceptance criteria
- [x] Closing on Join or Bulk Cut reopens on that tab.
- [x] The layout axis still restores (it already does — assert it so this change cannot regress it).
- [x] An unknown/corrupt stored tab falls back to Split without throwing.
- [x] An older settings file with no tab key loads and defaults to Split.
- [x] Restoring a tab performs no probe / scan / preview-open — asserted, not assumed.
- [x] The existing persisted keys still round-trip (the attribute-binding hazard above).

## Out of scope
Remembering the loaded files or cut points. This is window state, not session state.
