## Why

User: *"for now on bulk cut profile tootip show full img of thumnail also show which intro/outro cut at"*

This is the third request about the same card. G-054 asked for it *"bigger"*, and G-056 asked for the
picture at its *"original image size … fill picture"*. Before planning, I measured what the user sees
instead of trusting what the code says. The picture files' contents were not opened; only their header
pixel widths and dates were read.

| fact | source |
|---|---|
| The card draws the **whole** picture (`Stretch="Uniform"`, nothing cropped) inside a fixed **320x180** box. | `BulkCutView.xaml`, `ProfilePreviewCard` (SPEC-007 I109) |
| Of the 13 saved profiles, **6 use 64px pictures, 2 use 96px pictures and 5 use 320px pictures. None uses a 640px picture.** The store also holds 4 files no profile points at. | header widths in `%LOCALAPPDATA%/VideoSplitJoiner/profile-thumbs`, matched against `settings.json` paths (no names printed) |
| **Root cause of the 64px pictures:** the shared `FfmpegThumbnailService` caches by *(file, 1-second bucket)* and **ignores width**. It also reuses a matching file left on disk by an earlier run. Each row's cut-point chip grabs its intro frame at **64px** through the same instance, and the scrub preview grabs at 160px. So a "640" capture at a second the chip already grabbed returns the chip's 64px file. | `FfmpegThumbnailService.cs:111-126, 231-241`; `BulkItemViewModel.cs:88, 181-184, 321-333`; `BulkCutViewModel.cs:1222-1229` |
| The file dates fit this. On 2026-09-15 two **64px** pictures were saved a few minutes before five **320px** ones, while the capture width was 320. *Set intro-end here* followed by *Use current frame* grabs the very second the row chip has just cached. | file modification times |
| T-172 raised the stored width to 640, and its acceptance test "read the real pixel width". It passed against `FakeThumbnailService`, which has no cache (`BulkTestFakes.cs:231-251`), so the defect was invisible to it. No picture has been saved since T-172 shipped (2026-09-16 20:24). | T-172 build log; file dates |
| All 13 profiles are **intro-only**. Every card reads *"intro 00:32.0 · outro to end"* (the time varies), in small muted text. *"outro to end"* does not say that no outro is cut. | `settings.json` (values only) |

So *"show full img"* is two problems, and neither is a cropping bug. The card caps every picture at
320 DIPs. The pictures themselves are mostly 64–96px, and the capture path meant to make them bigger
silently hands back cached 64px frames. *"show which intro/outro cut at"* is a readout that exists but
does not read as an answer.

## Plan (critical path)

```
T-179 cache keyed by width ─────────────┐
T-180 card at full size + cut readout ──┴─► T-181 refresh a small picture on apply ─► T-182 docs (terminal)
```

- **T-179 → T-181 is a real edge.** The refresh grabs through the same cache. Without T-179 it would
  store a 64px frame, report success, and then fire again on every apply.
- **T-180 → T-181 is a real edge.** Both edit the same `ProfilePreviewCard` template: T-180 restructures
  it, and T-181 rewrites the low-resolution note inside it. T-181's threshold constant is also pinned to
  the minimum-width resource that T-180 keeps.
- **T-179 and T-180 are independent** (Core cache vs. XAML card) and can be built in either order. The
  one spec paragraph they would both have touched, SPEC-007 I106, is left to T-180 (its rationale) and
  T-181 (T-179's cold-cache sentence), and those two are ordered.

## What the user sees, and when

- **After T-179:** every *new* Save or *Use current frame* stores a true 640px picture. The scrub preview
  also stops showing a 64px frame at a second a row chip had cached. The first run after the update
  re-grabs each row chip once, because the old cache files are no longer matched.
- **After T-180:** the readout changes on every card at once. Card size changes only for pictures wider
  than 320px. Today none is, so the five 320px cards and the eight smaller ones look the same size as
  now until pictures are re-taken. That is expected, not a failure.
- **After T-181:** the first time each of the 8 low-resolution profiles is applied to a video, its card
  becomes a full 640-DIP picture. The five 320px pictures are never replaced, so they stay at 320. If the
  user wants them larger, *Use current frame* re-takes them at 640.

## Risks

- **T-181 replaces pictures without a click — most of today's library.** 8 of the 13 profiles are below
  the 320px gate, so the first apply of each replaces its picture. Some of those may be uploads the user
  chose: T-169 counted 6 uploads among 11 pictures, though the dates above suggest several 64px ones were
  captures that hit the chip cache. **The old file is kept in `profile-thumbs/replaced/` (copied there before the swap), not deleted.**
  The success line names the profile and the source video, so a replacement after a mis-apply is
  visible and can be undone by hand. T-181 § Decisions records why this is still the default.
- **A 640-DIP card has four times the area of today's.** That is what *"full img"* asks for. The card
  opens above the chip bar, WPF keeps a tooltip on screen, and the 650-DIP card is narrower than the
  window's 960 minimum width (`MainWindow.xaml:9`).

## Decisions (taken at planning)

- **Reading of "show which intro/outro cut at":** the cut *times* — the intro cut, and the outro cut
  measured from the end. The other reading, *which cut point the picture was taken at*, cannot be
  answered for existing pictures, because no picture's source is recorded.
- **16:9 box, not a box shaped to each picture:** every capture is a frame of a 16:9 video (all 13
  profiles' pictures are 16:9). A fixed shape keeps a non-16:9 upload from producing a tall strip of a
  card, and such a picture still shows whole.

## Out of scope

- The outro frame. A profile's picture is a single frame, so showing the outro-cut frame would need a
  second stored picture per profile.
- A timeline drawing of the cut points. A profile has no duration, so a bar would be a schematic, not a
  measurement.
- Keyboard access to the card. It is a non-focusable tooltip (I105), as it has been since T-169.
- The 4 orphan files in the store, and pictures of profiles that are never applied again (they keep the
  disclosed low-resolution card).
