# todo-task PLANNED: G-058 — the hover card shows the whole picture at full size, and says where the profile cuts

User: *"for now on bulk cut profile tootip show full img of thumnail also show which intro/outro cut at"*
(the third request about this card, after G-054 and G-056).

**Measured first:**
- 6 of the 13 profiles use 64px pictures, 2 use 96px and 5 use 320px. None uses a 640px picture.
- All 13 profiles are intro-only.
- The card squeezes every picture into 320 DIPs.

**Root cause found by the review panel:** `FfmpegThumbnailService` caches by (file, second) and ignores
width, so a "640" capture at a second the 64px row chip already grabbed returns the chip's file. T-172's
640 passed only against a cache-less fake.

**The plan:**
- **T-179** (S, fix): key the cache and file name on width; repro on shipped code plus a real-ffmpeg exit
  probe.
- **T-180** (M): the card sizes to the picture (320–640 DIPs, 16:9 box) and gets a two-line cut readout
  at body size, where an outro of 0 reads "none".
- **T-181** (L, blocked by T-179 and T-180): applying a profile whose picture is narrower than 320px
  re-takes it at 640 from the profile's own intro time. The old file is kept in `replaced/`, a picture
  generation guards changes made mid-flight, and the selection is preserved.
- **T-182** (docs, terminal).

**Review:** 5-lens panel, 3 rounds (`wf_cd1b2efc-35f`, `wf_1e2576b4-5df`, `wf_fa2cfff5-88b`); every
implementation ticket is `spec: reviewed`.

**Decision recorded on T-181:** replace automatically on apply, keeping the old file. The alternatives
and the cost (uploads may be among the 8 replaced) are stated on the ticket.
