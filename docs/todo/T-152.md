## What is wrong

T-127, T-132, T-133, T-134, T-135, T-136, T-139, T-144 and T-146 are all `status: done` with **exactly
one** acceptance criterion left `[ ]` — and in every case it is the on-screen / by-hand check.

This is not bookkeeping lag. **T-146's single unticked box hid a shipped, user-facing defect**: the
destructive "Delete originals" button was laid out on the pixels `Run bulk cut` had just occupied, found
only when a review measured the footer instead of reading the comment beside it. The class demonstrably
ships defects, not just paperwork debt.

The widest blast radius is **T-127**, released in v1.1.0 with *"No state exists where the checkbox renders
ticked but the row is excluded from the batch"* unverified — a user acting on a wrong tick loses work
silently.

## The concrete failure it allows
Every one of these is a claim about what a user SEES that nothing checks. The T-146 case shows what that
costs: a criterion can sit ticked-adjacent for days while the opposite is true on screen.

## Design
The lesson from T-138 and T-146 is that most of these do **not** need a human — they need the view laid
out and measured. `BulkCutViewLayoutTests` already does this at five window sizes with the app's real
theme dictionaries.

1. Triage the nine: which are genuinely mechanical (position, size, visibility, enabled-state, which
   control binds to which property) and which truly need eyes (colour judgement, "does this read as
   destructive").
2. Convert the mechanical ones into layout/visual-state tests. Start with **T-127** — highest blast
   radius, and checkbox-vs-eligibility is pure VM state, so it needs no view at all.
3. For the rest, either verify them and tick, or restate the criterion as something checkable.

## Acceptance criteria

## Out of scope
A general screenshot-diff harness. Measuring the layout is cheaper and less brittle.

## Outcome — 2026-09-02

Nine `done` tickets each carried one unticked box, and the class had already cost something real: T-146's
single unticked criterion hid a shipped defect — the destructive button laid out on Run's pixels.

### How the nine actually broke down

| resolution | tickets |
|---|---|
| **converted to a mechanical check** | T-127 (2 new tests), T-136 (layout measured at 5 widths) |
| **already covered; tick now cites the evidence** | T-133, T-134 (`RunScopeSummaryTests`), T-135 (`SnapshotProfileThumbnailTests`), T-139 (SPEC-007 I77) |
| **criterion restated — it was obsolete, not unmet** | T-127's "no ticked-but-excluded state exists" |
| **left honestly open** | T-132 (needs a real SMB share with a space in its name), T-144 (wants eyes on a genuine finished batch) |

### The finding worth keeping
**Most of these were not unverified — they were unattributed.** Four had perfectly good tests already; the
box stayed unticked because nobody connected it to them. That is a different disease from T-146's, where
the box was ticked from a comment while the code did the opposite. Both are cured the same way: a tick
must name its evidence.

And one criterion was simply **wrong to still be asking**. T-127's "no state exists where the checkbox
renders ticked but the row is excluded" described the pre-fix world; the fix deliberately created that
state, because separating intent from eligibility is what stopped clicks being swallowed. A criterion
written before a design decision can outlive it, and ticking it would have been as false as leaving it.

### Left open on purpose
T-132 and T-144 are marked `[~]`, not `[ ]` — *known, deliberate, needs hardware or a real batch* rather
than work someone should pick up. Ticking either from adjacent evidence is exactly what produced the T-146
defect.
