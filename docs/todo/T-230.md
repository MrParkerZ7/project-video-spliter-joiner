## Concept

`docs/DEV.md` says a 0-warning build is the bar, but only `src/Core/VideoSplitJoiner.Core.csproj` and `bench/VideoSplitJoiner.Bench/VideoSplitJoiner.Bench.csproj` set `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`. `src/App`, `tests/App.Tests` and `tests/Core.Tests` do not, and `.github/workflows/release.yml` has no warnings-as-errors step. The bar has slipped twice in test code:

- to 5 warnings (CHANGELOG [Unreleased] > Internal: "The build is back to zero warnings (it had drifted to 5)");
- to 6 xUnit1031 warnings (T-221). These were invisible to the usual incremental build, which skips up-to-date projects and does not repeat their warnings. T-221 checked this: with one pragma removed, incremental build 1 showed 1 warning and incremental build 2 showed 0.

A warning in a non-Core project is never a failure today, so nothing stops a third slip.

## Design

- Recommended: set `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` for every project in `Directory.Build.props`, removing the two per-project copies, or add it to the App, App.Tests and Core.Tests csproj files.
- Check that WPF's generated `*_wpftmp` project and the XAML compile still build clean, and that no NuGet or SDK warning (for example NU1603) turns into an error on a clean restore.
- Alternative: a CI or local gate that runs `dotnet build -c Release --no-incremental -warnaserror`. This is weaker, because it only runs where it is invoked.
- **The bundled-ffmpeg warning must stay a warning.** `src/App/VideoSplitJoiner.App.csproj` (target `CopyBundledFfmpeg`, line 76) raises an MSBuild `<Warning>` when the git-ignored `ffmpeg-shared/` folder is absent, and its comment says it warns and skips "so CI / clean checkouts still build". Under warnings-as-errors that `<Warning>` becomes an error, so a fresh clone that has not run `packaging/fetch-ffmpeg-shared.ps1` would stop building. Give it a `Code` and exempt it (`WarningsNotAsErrors`), or the gate and the clean-clone criterion below contradict each other. T-221's review hit this warning in a copy of the tree that lacked `ffmpeg-shared/`.

## Acceptance criteria

- [ ] `dotnet build VideoSplitJoiner.sln -c Release --no-incremental` is green with 0 warnings.
- [ ] Adding a blocking `.Wait()` directly in a test method (xUnit1031) makes the build fail, not warn. Checked once, then reverted.
- [ ] A clean clone with a fresh restore builds green, including with `ffmpeg-shared/` absent (the bundled-ffmpeg warning does not fail it).
- [ ] `packaging/package.ps1` behaviour is unchanged. Verify by reading the script or with a dry publish build, not by running the packager against real settings.

## Case coverage

| case | expected |
|---|---|
| Required-Success: full rebuild of the current tree | 0 warnings, build green |
| Required-Fail: a new analyzer warning in a test project | build fails with that warning as an error |
| Boundary: WPF temp project / XAML-generated code | still builds |
| Boundary: `ffmpeg-shared/` absent | the bundled-ffmpeg warning stays a warning, build green |

## Out of scope

Enabling new analyzers or raising AnalysisLevel; fixing warnings that do not exist today.
