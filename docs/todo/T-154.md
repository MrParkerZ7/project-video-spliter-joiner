## Reported
> I can't drag and drop file any more did you have automate test for this ? why it's work sometime doesn't
> work some time ?

## Answering the first question directly: **no, there is no test**

Grepped the whole test tree for `FileDrop` / `DragDrop` / `OnDrop` / `AllowDrop`: the only hits are
compiled `.dll` artifacts under `bin/`. **Not one test covers drag-and-drop, on any of the three screens** —
even though `BulkCutView.HandleDroppedFiles` carries the comment *"Drop routing extracted for
testability"*. The seam was built for a test that was never written. That is the honest answer, and it is
why this went unnoticed.

## Why it works sometimes and not others

Not randomness — **it depends on the file, and the app never tells you which case you are in.** Three
paths silently discard a drop, all verified by reading the shipped code:

| # | what you dropped | what happens | what you see |
|---|---|---|---|
| 1 | a video whose extension is not on an 11-item allowlist | `HasAnyVideo` returns false → `e.Effects = None` | a "no entry" cursor, then nothing |
| 2 | a file already in the list | `AddFilesAsync` dedupes on normalised path and `continue`s | nothing at all |
| 3 | a mix of videos and other files | the non-videos are filtered out by `AcceptVideoFiles` | the rest arrive; no word about the dropped ones |

**The allowlist** (`VideoFileFilter.VideoExtensions`) is `.mp4 .mkv .mov .avi .m4v .webm .ts .mpg .mpeg
.wmv .flv`. Absent, among others: **`.m2ts` and `.mts`** (AVCHD — every consumer camcorder and most
Blu-ray rips), **`.3gp`/`.3g2`** (phone video), `.ogv`, `.vob`, `.asf`, `.divx`, `.f4v`, `.mxf`, `.m2v`.
Drag an `.m2ts` and the app refuses it without a word — which from the outside is indistinguishable from
"drag and drop is broken today".

Case 2 is the sharpest: re-dropping a file you already added looks *exactly* like a dead drop target.

## Ruled out, with evidence
- **Elevation (UIPI).** A drag from a non-elevated Explorer into an elevated app is silently blocked by
  Windows, and would perfectly explain "worked before, not now". Checked the running process: **not
  elevated**. Not this.
- **Broken wiring.** `RootGrid` still carries `AllowDrop="True"`, `PreviewDragOver`, `DragLeave`, `Drop`;
  `DropHighlight` is `IsHitTestVisible="False"` so it cannot intercept; `AddFilesCommand` has no
  `CanExecute` gate, so it cannot no-op. All three screens (Split, Join, Bulk Cut) are wired the same.
- **A recent regression.** Nothing in the last 8 commits touching these files changed drop behaviour.

## What is NOT yet established
**Which screen, and which file.** The three paths above are long-standing, not new — so if the report is
genuinely *"it used to work with this exact file and now does not"*, none of them is the cause and the
diagnosis is not finished. Per the repro-first rule, this ticket does **not** claim to close the report
until that file is reproduced failing. What is fixed below stands on its own regardless.

## Design
1. **Never refuse in silence.** Every discarded path gets a reason on the screen's existing surface
   (`Operation.ResultSummary` / `Operation.Error`) — "3 files were not added: 2 are not video files, 1 is
   already in the list". Silence is the actual defect; the allowlist is only the most common trigger.
2. **Broaden the allowlist** to the containers ffmpeg handles routinely, `.m2ts`/`.mts`/`.3gp` first.
3. **Test the seam that was built to be tested** — `HandleDroppedFiles`, `AcceptVideoFiles`,
   `AddFilesAsync` dedup — plus the same for Split and Join.
4. Consider accepting anything and letting the probe reject it: an extension allowlist is a guess about a
   container, and ffmpeg already knows the truth. Out of scope here; noted.

## Acceptance criteria
- [x] **On Bulk Cut.** `DropSummary` — "3 files were not added: 2 are not video files, 1 is already in
      the list" — bound into the header note row, collapsed when nothing was refused.
- [x] **On Split and Join** — done 2026-09-04. `DropSummary` on both view-models, fed the **raw** dropped

## Progress — 2026-09-02

### Fixed, with the repro established first
Three silent-discard paths, all verified against shipped code before anything was changed, then closed:

- **Unrecognised container** — the allowlist went 11 → 25. `.m2ts`/`.mts` (AVCHD: camcorders, Blu-ray

`BulkCutViewModel.DropSummary` now accounts for all three in one line, and is **null when nothing was

matters.

## Update — 2026-09-02: the reporter answered, and it is NOT what I fixed

Asked which screen and which file type. Answer: **all three screens, `.mp4`/`.mkv`.**

That eliminates every one of my three hypotheses. `.mp4` and `.mkv` were on the allowlist from the
beginning; dedup and mixed-drop cannot explain a first drop failing on all three screens. **The work
committed above is real and tested, but it is not this bug.** Saying so plainly matters more than the
fix looking complete.

### What that answer rules out
All three screens wire drop **independently and identically** — `AllowDrop`, `PreviewDragOver`,
`DragLeave`, `Drop` on each root grid, each with its own handler. For all three to fail on a file type
they all accept, the cause is almost certainly **not in per-screen code**. Combined with the earlier
checks (not elevated, no window-level overlay, no `CanExecute` gate, `DropHighlight` not hit-testable,
nothing in recent commits), very little of this codebase is left to blame.

What remains, roughly in order:
1. **Windows/shell drag state.** A stuck drag from a previous operation blocks drops into *every*
   application until it clears. Classic, common, matches "worked before, not any more" and "sometimes".
2. **An integrity-level mismatch between the drag SOURCE and this app.** Elevation was checked on our
   side; if files are dragged from an elevated file manager into this non-elevated app, Windows blocks it
   silently and in exactly this shape.
3. Something about how the app is launched that differs from the reporter's normal shortcut.

### Making the next report answerable instead of another round of guesses
`DropDiagnostics` writes one line per drag-over and drop to
`%LOCALAPPDATA%/VideoSplitJoiner/logs/dragdrop.log`, wired into **all three** screens. It splits the two
cases that were impossible to tell apart from the outside:

| after attempting a drag | means |
|---|---|
| **the file does not exist / is empty** | Windows never delivered the drag to us. **Not our bug** — no amount of reading this codebase would have found it |
| **a line appears**, e.g. `over BulkCut files=1 kinds=[.mp4] accepted=False` | we DID see it and refused; the line says what we decided |

Extensions only, never full paths — the file is meant to be pasted into a bug report.

Tested rather than assumed: `TheDragDropTraceActuallyWrites_AndRecordsTheDecision` asserts it reaches
disk, records the decision, and does **not** leak the folder structure; `TheTraceSurvivesGarbageInput`
asserts a diagnostic can never be the reason a drop fails. A probe that silently writes nothing would be
worse than none, because absence would read as evidence.

## Update — 2026-09-04: the Split and Join half, and what mirroring the fix exposed

The remaining buildable criterion is closed. Split and Join now account for a drop the same way Bulk Cut
does — but mirroring the shipped screen turned out to be the wrong instinct twice over, and both
corrections are the interesting part of this change.

### One vocabulary, three different refusals
"Same silence" is not the same sentence. Each screen refuses something the others do not:

| screen | its own case |
|---|---|
| **Split** | opens **one file at a time** — drop five videos, four are ignored with no error and no note |
| **Join** | permits the same clip twice **by design**, so "already in the list" would contradict its own rule — what it must report is the filter collapsing two copies inside *one* drop |
| **Bulk Cut** | keeps one row per source, so a re-drop genuinely is a refusal |

So the shared piece is a clause vocabulary and the pluralisation (`DropRefusal`), not one fixed sentence.
Three hand-copied `DescribeRefusals` would have been three things to keep in step forever, and this repo
has already paid for that pattern once — the spec-index counts drifted in both directions until T-153
recounted them mechanically.

### Copying the screen as-shipped would have reproduced a bug three times
`DropSummary` was written on drop and cleared by **nothing but a later drop**. Clear all left "3 files
were not added" sitting over an empty list, contradicting it. Now nulled in all three `Clear()` methods —
including Bulk Cut's, where it shipped (SPEC-011 I140).

Two smaller corrections came with it: a dropped **folder** is now called a folder rather than "not a video
file" (Explorer delivers folders as ordinary FileDrop paths; the old arithmetic — non-blank count minus
accepted count — swept folders and within-drop duplicates into the same bucket), and the `dragdrop.log`
`accepted` flag now reports the **real decision** instead of a hard-coded `true`. That last one mattered:
the log's entire purpose is telling *"we never saw the drag"* apart from *"we saw it and refused it"*, and
it was recording every drop as accepted even when the filter took nothing — a lie in the one artifact the
reporter is asked to paste into a bug report.

### A claim in the shipped spec that the code cannot deliver
**`OnDragOver` gates on `VideoFileFilter.HasAnyVideo`.** A drag holding *no* recognised video gets
`DragDropEffects.None`, so Windows shows a no-entry cursor and **the drop event is never delivered** — no
handler runs, and no note can ever be shown for that case.

SPEC-011's I122 listed "an unrecognised extension" as a path `DropSummary` explains. It is not one: the
unrecognised-extension case is only reportable as part of a *mixed* drop. The 21 shipped tests did not
catch the overstatement because they call `AddDroppedFilesAsync` directly, which bypasses the very gate
the real gesture goes through.

Left **as-is and documented** rather than fixed (SPEC-010 I48 / SPEC-012 I37 / SPEC-011 I143, and I122
corrected in place). Accepting the drop so it can be refused in words would mean showing a copy cursor for
files we intend to reject on all three screens — promising acceptance and then withdrawing it is worse
feedback than the no-entry cursor, which is immediate and unambiguous. Reopening that is a UX decision,
not a bug fix.

### The tests, and a fifth vacuous one caught before it landed
17 new tests in `SplitAndJoinDropFeedbackTests`. Eight mutations run against them, **all eight now dead**:
removing the `DropSummary = null` from each of the three `Clear()` methods, removing the folder branch
from `Classify`, zeroing Split's skipped-videos clause, zeroing Join's dropped-twice clause, making Join
borrow "already in the list", and moving Split's note assignment past the `await`.

That last one is the lesson. Its first version used the shared `BulkFakeProbe`, whose `ProbeAsync` returns
`Task.FromResult` — so `AddDroppedFilesAsync` ran to completion synchronously and the assertion passed
whether the note was assigned before or after the await. **The mutation survived it.** It now injects a
`BlockingProbe` that genuinely suspends the load and asserts the note is already on screen while the probe
is still blocked. Same lesson this project keeps re-learning: a passing test proves nothing until
something proves it can fail.

Worth recording separately: the first mutation run **misreported** that result. Restoring each file with
`shutil.move` carried the original mtime back, so MSBuild judged the freshly-built (mutated) `App.dll`
up-to-date and skipped the rebuild — the "verification" run afterwards tested the mutant. That is T-137's
stale-build trap in a new costume; the harness now touches every file it restores.
