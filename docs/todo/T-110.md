## Concept
On the Split tab, clicking a skip button (−1s / −5s / +1s …) makes the preview **play for ~1s after each jog** instead of
freezing on the target frame. The user wants a jog to **stop dead on the exact frame** — the still they see is where
"Add cut at playhead" will cut. Fix: make a jog a FREEZE gesture (pause-first + seek), matching how single-frame stepping
already behaves.

## Grounding (2026-08-22 — root cause found)
- **Jog does NOT pause before seeking.** `PlayerViewModel.SkipBy(delta)` (`:552`) → `Scrub(target)` → `IMediaPlayer.Seek`
  → `FfmeMediaPlayer.Seek` (`:292`) which calls `_element.Seek(clamped)` with **no Pause**. FFME's `MediaElement.Seek`
  on a non-paused element renders/advances a short burst (~1s) as it decodes to the target and settles → the "plays ~1s"
  symptom. (If the player was actively playing, it also just keeps playing from the new spot.)
- **`StepFrame` already does the right thing** — `FfmeMediaPlayer.StepFrame` (`:333`) pauses first
  (`if (_isPlaying) Run(() => _element.Pause())`, `:345`) then does the single-frame seek, so stepping lands frozen. The
  jog path lacks this pause-first.
- **The cut IS at the playhead.** `SplitViewModel.SetCutAtPlayhead` adds the cut at `Player.Position` (then
  keyframe-snapped when the marker resolves — SPEC-010). So a frozen frame at `Player.Position` already equals the cut's
  requested point; the cut snaps to the nearest keyframe as it does today (SPEC-001 keyframe-snap invariant).
- Seek is SHARED with the scrub bar / timeline click (`Scrub`/`SeekTo`) — so scope the freeze to the JOG intent, don't
  force-pause a deliberate click-to-play-from-here.

## Fix
1. **Make a jog freeze the player.** After a jog (`SkipBy`) the element must sit **paused on the target frame** with no
   playback burst. Two clean options — pick the tighter one:
   - **(a) Freeze at the FFME seek** — add an explicit `Pause()` before the `_element.Seek()` in the jog/freeze path
     (mirroring `StepFrame`'s pause-first), so the seek renders one still, not a burst. Introduce a "freeze seek" that
     pauses-then-seeks, used by `SkipBy`/`JumpToEnd`.
   - **(b) Freeze at the VM** — `SkipBy` sets `IsPlaying = false` + calls `_player.Pause()` before `Scrub`, and the seek
     leaves the element paused.
   Prefer whichever guarantees FFME renders exactly the target frame and stops (likely (a) — the burst is an FFME
   seek-render behavior, so pausing the element around the seek is the deterministic cure). `StepForward/Back` already freeze — keep them.
2. **Same for the arrow/step + JumpToEnd** jog family — every "position the playhead" gesture freezes.
3. **Confirm the frozen frame = the cut frame.** The still shown after a jog is `Player.Position`, which is exactly what
   `SetCutAtPlayhead` uses. Keep the jog landing at the exact ±Ns offset (do NOT keyframe-snap the jog itself — that would
   surprise "−1s"); the cut snaps as today. (Optional, only if trivial: a tiny "cut snaps to nearest keyframe" hint — the
   marker's `Display` already shows requested→snapped, so no new UI is really needed.)
4. **Don't regress deliberate playback** — Play still plays; clicking the scrub bar while playing may keep playing (that's
   a play-from-here gesture, not a jog); only the jog/step family force the freeze.

## Acceptance criteria + Case-Coverage Matrix
- [ ] Clicking any skip button (−1s/−5s/±any) leaves the preview **paused on the exact target frame** — no ~1s play burst, whether the player was paused or playing before.
- [ ] The frozen frame equals `Player.Position` (what "Add cut at playhead" cuts at); jog still lands at the exact ±Ns offset (not keyframe-snapped).
- [ ] Step-frame + JumpToEnd also freeze; Play/Pause + Stop unaffected; scrub-drag live preview + click-to-seek not regressed.
- [ ] WPF-free VM stays clean; the pause-first lives in the seek/jog path (VM or FfmeMediaPlayer), consistent with `StepFrame`.
- [ ] Build 0-warning; suite green (819) + a VM/player test asserting a jog issues a Pause (or leaves IsPlaying false) and seeks to the target — using the fake `IMediaPlayer` (extend PlayerViewModelTests; the fake records Pause/Seek order). `serves-spec: SPEC-013` (extend the preview-player spec's jog/freeze invariant).
- Matrix — Success: jog while paused → frozen on frame; jog while playing → pauses + frozen. Boundary: jog at the ends (clamped, frozen), rapid multi-jog (each freezes, latest frame shown — reuse the in-flight-seek latest-wins), step-frame still frozen, JumpToEnd frozen. Required-Fail: Play must still play (a jog-freeze must not disable playback). (Exact feel = app-run/user-verified.)

## Dependencies
None. Touches `PlayerViewModel.SkipBy`/jog + `FfmeMediaPlayer.Seek`/freeze path (mirror `StepFrame`). SPEC-013 gets a new jog-freeze invariant (update in the same PR or note for T-109-style doc-sync).

## Risks
Seek is shared with the scrub/timeline — scope the forced-pause to the JOG/STEP family, not every `Seek` (a click-to-play-from-here shouldn't be frozen). Verify the FFME seek-while-paused genuinely renders the target still and stops (headless can't confirm the visual — app-run verifies). Don't break the existing scrub pop-back / seek-hold (SeekTolerance, latest-wins) machinery (SPEC-013) — add the pause, don't rewrite the seek-hold.

## Out of scope
Keyframe-snapping the jog itself; changing what frame the cut lands on (still snapped as today); scrub-bar click behavior while playing; any Bulk-tab player change (this is the Split preview).
