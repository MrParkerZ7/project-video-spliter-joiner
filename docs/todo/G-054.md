## Why

User: *"which hand over on profile item it should pipup show something like tooltip but bigger fro quick
review profile thumnail in a bigger view"*

[[T-161]] moved profiles out of a dropdown and into a bar of chips **specifically so the pictures would be
visible before you chose** — SPEC-007 **I95** says a closed dropdown *"hid every one of them until after
the user had already chosen by name, which is the one moment the picture cannot help."*

That fixed *when* you see the picture. It did not fix *how much* picture you see: the chip renders it at
**28×28** (`BulkCutView.xaml:80`). At 28px two frames from the same show are indistinguishable, so the
promise I95 makes is only half-delivered. The user is asking for the other half.

## The constraint that shapes this

**Captured thumbnails are stored 96px wide** — `ProfileThumbnailWidth = 96`
(`BulkCutViewModel.cs:108`), used by both the auto path (`:1584`) and the snapshot path (`:1646`).

So "a bigger view" has a hard ceiling. Displaying a 96px-wide image at 300px is upscaled blur, which is a
worse answer than the small sharp chip. For scale, the app's **existing** hover thumbnail — the scrub-bar
popup this would mirror — captures at **160** (`ThumbnailPreviewViewModel.cs:33`) and displays in a
160×90 box. A profile preview built today would be **narrower than a hover preview this app already ships**.

That is the whole decision, and it is the user's: live with ~96px, or raise the capture width and accept
that existing profiles keep the picture they were saved with.

## Out of scope

Re-capturing existing profiles' thumbnails in bulk, and any change to the three capture *gestures*
(auto / upload / snapshot). This is about how large the stored picture is shown.
