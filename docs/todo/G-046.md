## Why

User, in one breath:

> set intro/outro-end here button suppose to set to all, or just have an option to set all
>
> and why run bulk cut is execute cut only one file? bulk is mean single or what? why it's execute only file?

**These are one defect seen from both ends**, and the second half is the consequence of the first.

`SetIntroAtPlayhead` writes exactly one row:

```csharp
_selectedItem!.IntroEnd.Requested = Player.Position;
```

and `RunBatchAsync` cuts only rows that have something to cut:

```csharp
var rows = Items.Where(i => i.IsEnabled && i.IsValidCut).ToList();
```

A freshly imported row has intro 0 and no outro, so it is a no-op trim, so it is auto-excluded. The user
therefore: imports N videos → previews one → presses "Set intro-end here" → presses Run → **one file is
cut**. Nothing in that sequence is wrong per the code, and every step is wrong per the user's expectation
of a tool called Bulk Cut.

**Apply-to-all already exists** — `ApplyToAllCommand`, the ⧉ button — but it lives *inside the row
template*, as a per-row gesture whose meaning ("copy THIS row's cut points onto every other row") has to
be inferred. T-116 already had to make it more discoverable once (`e5a2d3b`, "make apply-to-all
discoverable in both layout modes"); this report is evidence that pass did not go far enough. The problem
is not that the capability is missing — it is that the obvious gesture does not have it, and the gesture
that has it is not obvious.

## The shape of the fix

The user offered both options themselves: *"suppose to set to all, or just have an option to set all"*.
Making set-at-playhead unconditionally apply to all would break the legitimate case where rows need
different cuts, so this goal takes the second: an explicit, visible choice sitting next to the buttons
that already exist, defaulting to the bulk behaviour the tab's name implies.

## Out of scope
Per-row cut detection (auto intro/outro). Changing what Run does with rows that genuinely have no cut.
