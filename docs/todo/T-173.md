## Concept

A profile apply, a row's ⧉ apply-to-all and the set-at-playhead fan-out all skip every row whose keyframe scan
has not finished — silently, while the Apply buttons stay enabled. Drop 20 files, apply a profile while 17
still scan, and the app says `Applied to 3 row(s).` The 17 are untouched, nothing says why, and the user must
notice, wait and apply again. None of the three paths reads keyframes: they write **requested** times from the
row's `Duration`. Only the run needs the **snapped** time, and it already waits for the scan on its own.

This task lets a row take a cut as soon as its duration is known, and makes the apply line say which rows are
waiting for their scan and which were skipped because they have not loaded. Designed and sealed in [[D-005]]
(§ R1–R4); refined by the G-057 review panel and the user's answers of 2026-09-13 ([[G-057]] § Decisions).

## Design

**1. One eligibility predicate, stated once.** The rule is spelled three times today:

| Path | Guard today |
|---|---|
| `CutProfileApplier.ApplyProfile` — targets | `CutProfileApplier.cs:45` `target is null \|\| !target.KeyframesReady \|\| target.Duration is not { } duration → continue` |
| `BulkCutViewModel.ApplyToAll` — source | `BulkCutViewModel.cs:1490` `source is null \|\| !source.KeyframesReady \|\| source.Duration is not { } → return null` |
| `BulkCutViewModel.ApplyToAll` — targets | `BulkCutViewModel.cs:1503` `… \|\| !target.IsCheckedByUser \|\| !target.KeyframesReady \|\| target.Duration is not { } → continue` |

Replace `KeyframesReady` with one row predicate, keeping the `Duration` pattern variables the loops already use:

```csharp
// BulkItemViewModel
/// <summary>A row can take a cut once its duration is known; the snap may follow later (D-005).</summary>
public bool CanTakeCut => Duration is not null;
```

The set-at-playhead gestures (`SetIntroAtPlayhead` `:1369`, `SetOutroAtPlayhead` `:1386`) reach other rows only
through `FanOutToCheckedRows` → `ApplyToAll` (`:1413`), so they inherit the rule with no guard of their own.
`Duration` is assigned only on `ProbeSucceeded` (`PopulateAsync`, `:1194-1197`), so a load-failed row never has
one.

**2. The "→ snapping…" display needs no code — pin it.** Bulk handles are born pending: `IntroEnd`
(`BulkItemViewModel.cs:174`) and every `AddOutro` handle (`:262`) are constructed `snapPending: true`. The
`Requested` setter's `Resnap()` never touches `IsSnapPending`. Only `ResolveSnap()` clears it
(`CutMarkerViewModel.cs:179`), and on a Bulk row that runs from `ScanBodyAsync` (failure `:711-712`, success
`:728-729`) and from `AddOutro` only `if (KeyframesReady)` (`:263-265`). The feature now depends on that, so a
test pins it. Under Exact cut the note is hidden instead (§ Detail → Exact cut). Two older precision-inheritance
gaps — a row added after the toggle, and an outro handle added later — are fixed separately in [[T-176]].

**3. Classify the outcome — the trap.** Both loops classify after writing: `if (!target.IsValidCut)
invalidated.Add(target)`. `IsValidCut` returns false whenever `!KeyframesReady` (`:389-395`). Dropping only the
guard would therefore report **every scanning row** as `now invalid (see the red rows)` — a false alarm on the
exact rows the user just fixed. Classify with one shared helper on the existing `public static class
CutProfileApplier` (`:21`), called from both loops:

```csharp
internal static void Classify(BulkItemViewModel target, List<BulkItemViewModel> invalidated,
    ref int invalidStillScanning, List<BulkItemViewModel> pendingSnap)
{
    if (target.KeyframesReady)               { if (!target.IsValidCut) invalidated.Add(target); }    // as today
    else if (target.IsCutHopelessBeforeSnap) { invalidated.Add(target); invalidStillScanning++; }    // no snap or precision can rescue it; not red yet
    else                                     { pendingSnap.Add(target); }                            // the scan decides
}
```

A scanning row is called invalid only when no snap can make it valid, in either precision. That holds only when
both ends are handles and the requested outro already sits at or before the intro:

```csharp
// BulkItemViewModel
/// <summary>
/// No keyframe snap and no precision can make the requested cut valid: both ends are handles and the requested
/// outro sits at or before the intro. A no-outro row is never hopeless — its upper bound, Duration, does not
/// snap (D-005, refined by T-173).
/// </summary>
internal bool IsCutHopelessBeforeSnap =>
    OutroStart is { } outro && outro.Requested <= IntroEnd.Requested;
```

**Why only a two-handle empty span is certain.** While scanning, `MinKeptSpan` is the 1 s floor: it is
`max(1 s, AverageGop(Keyframes))` (`:379-386`), and `AverageGop` returns zero below two keyframes
(`MediaProbe.cs:366-371`). The scan can move the verdict **either way**. A larger average GOP can make a pending
row invalid later (edge case, accepted). Under Lossless, a snap that pulls the intro earlier and the outro later
can make a sub-1 s request valid. Nearest-keyframe snapping is monotonic — exact ties resolve to the earlier
keyframe (`MediaProbe.cs:355`). So when both ends are handles, a requested outro at or before the intro stays at
or before it after any snap. The failure branch's identity snap leaves it there too, and under Exact cut the cut
*is* the request. That case, and only that case, is reported invalid before the scan. It covers a tail longer
than the file — a profile clamps the outro to 0, while ⧉ does not clamp, so its outro goes negative
(`BulkCutViewModel.cs:1512`) — and an intro at or past the outro. Everything else is pending.

**A no-outro row is never certain.** Its upper bound is the raw `Duration` (`upper = EffectiveOutroStart ?? d`,
`BulkItemViewModel.cs:398`), which never snaps, while the intro does. Real keyframes come from packet timestamps
(`MediaProbe.cs:267-277`), so the last one can sit well before `Duration`: a long final GOP after scene-cut
keyframes (credits, a static tail). A profile clamps an overshooting intro to `Duration`
(`CutProfileApplier.cs:51`), and ⧉ copies it unclamped (`BulkCutViewModel.cs:1508`). Either way the intro then
snaps back to that last keyframe. On a 60 s file with keyframes every 2 s up to 40 s, intro 60 snaps to 40, and
`40 < 60 − 2`: the row turns Ready. Such a row is pending.

**One rule in both precisions.** Under Exact cut more scanning rows are certain to fail. The cut is the request
(`BulkItemViewModel.cs:366`, `:369-370`), and `MinKeptSpan` never drops below 1 s. So a positive span under 1 s,
or a no-outro intro at or past `Duration`, can never pass `IsValidCut` (`:398-401`). Those rows are still
classified pending (§ Edge cases). The rule ignores precision on purpose. The line is a snapshot of the click
(OQ3), precision can be flipped after it, and an outro handle at or before its intro is the one verdict no snap
and no flip reverses. So a row the line calls invalid always ends red. `IsValidCut` itself is **not modified**.
`InternalsVisibleTo` already exposes `internal` members to the test assembly (`src/App/AssemblyInternals.cs:6`).

**Refinement over D-005 (R4 classification):** D-005 judged a scanning row by `IsRequestedCutValid`, the
`IsValidCut` bounds applied to the requested times against the 1 s floor, extracted through `CutBoundsHold`.
That reports a 0.6 s request `now invalid` even though a snap can still make it valid — the false alarm G-057
success criterion 3 forbids. T-173 reports as invalid only what no snap and no precision can rescue, and drops
the `IsRequestedCutValid` / `CutBoundsHold` extract.

**4. The record carries the three facts it cannot express today** (`BulkCutViewModel.cs:58`):

```csharp
public sealed record ApplyToAllReport(
    int AppliedCount,
    IReadOnlyList<BulkItemViewModel> InvalidatedRows,
    int InvalidStillScanningCount,                       // of InvalidatedRows: still scanning at the click, so not red yet
    IReadOnlyList<BulkItemViewModel> PendingSnapRows,   // applied; the snap lands when their scan does
    int SkippedNotLoadedCount);                          // in-scope targets with no Duration
```

Two construction sites: `BulkCutViewModel.cs:1535` and `CutProfileApplier.cs:78`. No test deconstructs the record
positionally; the 33 test references read `AppliedCount` / `InvalidatedRows` by name.

**5. The apply line** (`ApplyReportSummary`, `:547-548`, bound at `BulkCutView.xaml:637`). Parts in a fixed order —
applied · invalid (red) · invalid (red when their scan finishes) · waiting · skipped — joined with ` · `, one
trailing period. The red part counts `InvalidatedRows.Count − InvalidStillScanningCount`. A part appears only when
its count is above zero. Today's two strings are unchanged when no applied row was still scanning and nothing was
skipped.

**Refinement over D-005:** the skipped part reads `not loaded, skipped`, not D-005's `not loaded yet, skipped`.
A checked row whose probe *failed* is also counted, and "yet" would be untrue for it. That row already shows its
own `LoadFailed` state.

**Refinement over D-005 — the waiting part** reads `N waiting for their scan`, not `N will snap when their scan
finishes`. Under Exact cut nothing snaps: the cut lands on `Requested` (`EffectiveIntroEnd`,
`BulkItemViewModel.cs:366`), and the row shows no snap note. `HasSnapNote` is false whenever `SuppressSnapNote`
is set (`CutMarkerViewModel.cs:143`), and the view shows the note only while `HasSnapNote` is true
(`BulkCutView.xaml:1046-1049`). So one wording has to be true in both modes. The run waits for the scan in both
(R3), so "waiting for their scan" is. Wording chosen by precision would also need the precision captured on the
record: the line is a snapshot of the click (OQ3), and flipping precision afterwards would make it stale.

**Refinement over D-005 — an invalid row that is still scanning** gets its own part,
`K invalid (red when their scan finishes)` (user decision 2026-09-13, [[G-057]] § Decisions). Only
`RowState.Invalid` is red (`BulkCutView.xaml.cs:642`). A scanning row is `Loading` (`BulkItemViewModel.cs:431-434`):
a muted `loading…` chip (`BulkCutView.xaml.cs:640`), and no `ExclusionReason` either, because `IsAutoDisabled`
needs `KeyframesReady` (`:554`). Until its scan lands, nothing on screen picks the row out. So the part does not
say `(see the red rows)`, which would send the user looking for rows that are not red yet; it says when they turn
red, so the user knows when to look. `(see the red rows)` is said only of rows that were ready at the click. The
split is captured at the click in `InvalidStillScanningCount`, never re-read from the rows later. *Rejected:*
marking the row as invalid right away (more UI change); folding these rows into the waiting count (the line would
under-report a certain failure).

**6. Inherited decisions (D-005, sealed 2026-09-13).** Q1 a row takes a cut once probed · Q2 all three paths,
one rule · OQ1 the line reports pending and skipped rows · OQ3 the line is a snapshot of the click and is not
re-issued when scans land.

## Detail

Per target, at the moment of an apply:

| Target state | `Duration` | `KeyframesReady` | Handles written? | `AppliedCount` | Classified as | Handle reads afterwards |
|---|---|---|---|---|---|---|
| probe not returned yet | null | false | no | — | `SkippedNotLoadedCount` +1 | unchanged — chip `loading…`, note `→ snapping…` (see below) |
| probe failed (`LoadFailed`) | null | false | no | — | `SkippedNotLoadedCount` +1 | unchanged |
| scanning, any other requested cut (incl. a no-outro intro at or past `Duration`) | set | false | yes | +1 | `PendingSnapRows` | `00:12.0 → snapping…`; the scan decides — Ready, no-op or red |
| scanning, outro handle requested at or before the intro | set | false | yes | +1 | `InvalidatedRows`, `InvalidStillScanningCount` +1 | `→ snapping…`, chip `loading…` (muted), no exclusion reason; red `invalid` once the scan lands, in either precision |
| ready, valid | set | true | yes | +1 | — | `00:12.0 → 00:11.6 (−0.4s)` |
| ready, invalid | set | true | yes | +1 | `InvalidatedRows` | red row (as today) |

Under Exact cut the `→ snapping…` notes above are hidden on rows that were in the list when Exact was switched on.
A row added after the toggle, and an outro handle added later, keep their note — and such a row is judged on
`Snapped` — until [[T-176]] lands (§ Exact cut).

**What a skipped, unprobed row looks like.** Its chip reads `loading…` and its IN note reads `→ snapping…`,
because `IntroEnd` is born pending (`BulkItemViewModel.cs:174`). An applied pending row looks the same. Only the
IN value (`IntroEnd.Requested`, `BulkCutView.xaml:1042`) differs, because the apply did not write it; the line's
`N not loaded, skipped` is what tells the two apart. `AddFilesAsync` adds every row to `Items` first, then probes
them one at a time (`foreach (var item in added) await PopulateAsync(item)`, `BulkCutViewModel.cs:1166-1169`).
Right after a large drop, many rows can sit in this state for seconds, and the re-apply trap of § Concept remains
for them (§ Out of scope).

**Who counts as "skipped".** Only targets the path would otherwise have written:
- profile → all checked rows: checked rows without a `Duration`;
- profile → selected: the selected row, if it has no `Duration`;
- ⧉ apply-to-all and the fan-out: checked rows other than the source, without a `Duration`.

An **unticked** row is out of scope by the user's own intent (SPEC-011 I22), never "skipped". A null entry in
the target enumerable is ignored, as today. An unprobed **source** copies nothing and counts nothing: ⧉ and the
set-at-playhead fan-out both reach `ApplyToAll`, which returns null with no report (§ Out of scope).

**Apply line, exhaustively:**

| Situation | Line |
|---|---|
| all ready and valid | `Applied to 5 row(s).` *(unchanged)* |
| some invalid, all ready | `Applied to 5 row(s) · 1 now invalid (see the red rows).` *(unchanged)* |
| some still scanning | `Applied to 5 row(s) · 3 waiting for their scan.` |
| invalid and scanning | `Applied to 5 row(s) · 1 now invalid (see the red rows) · 3 waiting for their scan.` |
| every invalid row still scanning | `Applied to 20 row(s) · 1 invalid (red when their scan finishes) · 19 waiting for their scan.` |
| invalid rows of both kinds | `Applied to 5 row(s) · 1 now invalid (see the red rows) · 1 invalid (red when their scan finishes) · 3 waiting for their scan.` |
| a target not loaded | `Applied to 4 row(s) · 1 not loaded, skipped.` |
| all five parts | `Applied to 5 row(s) · 1 now invalid (see the red rows) · 1 invalid (red when their scan finishes) · 2 waiting for their scan · 1 not loaded, skipped.` |
| select-apply on an unprobed row | `Applied to 0 row(s) · 1 not loaded, skipped.` *(today: `Applied to 0 row(s).`)* |
| any of the above with Exact cut on | the same string — no part depends on precision |

**Exact cut.** The cut lands on `Requested` (`BulkItemViewModel.cs:366`), and `IsValidCut` still waits for
`KeyframesReady`, so the run waits for the scan as before. The note is hidden through `SuppressSnapNote` (T-125),
which makes `HasSnapNote` false (`CutMarkerViewModel.cs:143`). The view binds the note's visibility to
`HasSnapNote`. The `SnapNote` text itself still reads `→ snapping…` while pending (`:137-140`), so tests assert
`HasSnapNote`.

**Until [[T-176]] lands, two older gaps apply.** An outro handle an apply **adds** under Exact still shows its note,
and a row added **after** Exact was switched on is built without precision (`AddFilesAsync`,
`BulkCutViewModel.cs:1139-1151`; the `ExactCut` setter reaches only rows already in `Items`, `:483-489`), so it shows
its notes and is judged on `Snapped`. **Every Exact-cut test in this ticket therefore adds its rows first and switches
`ExactCut` on afterwards** (the I91 path), and asserts `row.IntroEnd.SuppressSnapNote` is true as a precondition — so
the cases hold in either landing order, and a wrong order fails loudly instead of passing vacuously.

## Interfaces / contracts

- **New** `BulkItemViewModel.CanTakeCut` (`public bool`) — the single eligibility rule.
- **New** `BulkItemViewModel.IsCutHopelessBeforeSnap` (`internal bool`) — an outro handle requested at or before
  the intro. It is the only pre-scan invalidity that no snap and no precision can rescue; a no-outro row is never
  hopeless. `IsValidCut` is not modified.
- **New** `CutProfileApplier.Classify(...)` (`internal static`) — the only place scanning rows are sorted into
  invalid vs pending.
- **Changed** `ApplyToAllReport` — three new positional members. Invariants: `PendingSnapRows ⊆ applied`,
  `InvalidatedRows ⊆ applied`, the two are disjoint, `0 ≤ InvalidStillScanningCount ≤ InvalidatedRows.Count`,
  and `SkippedNotLoadedCount` counts in-scope targets without `Duration`.
- **Changed** `ApplyToAll(source)` — returns null iff `source is null || !source.CanTakeCut`.
- **Changed** `ApplyReportSummary` — the wording table above.
- **Consumed by** [[T-175]], which documents the apply line in this ticket's wording.
- **Shared surface with** [[T-174]] and [[T-176]] — all three edit `BulkItemViewModel.cs`. No ordering dependency;
  invariant ids are fixed in advance ([[G-057]] § Plan).

## Acceptance criteria + Case-Coverage Matrix

- [ ] **Repro first.** Before any production change, a test applying a profile to a probed row whose scan is
      held open (the fake probe's `GatedPaths`) is run against the current code and observed **failing**:
      the row is untouched and `AppliedCount` excludes it. It passes afterwards.
- [ ] Profile apply (to all, and to the selected row) reaches a probed scanning row: `Requested` set
      (clamped), `IsSnapPending` true, `Display` ends `→ snapping…`, counted in `AppliedCount` and
      `PendingSnapRows`. *Mutation:* restore `!target.KeyframesReady` at `CutProfileApplier.cs:45` → fails.
- [ ] ⧉ apply-to-all reaches a scanning **target** (*mutation:* restore the guard at `:1503`) and applies from a
      scanning **source** (*mutation:* restore it at `:1490`).
- [ ] Set-at-playhead with apply-to-all-rows on reaches a scanning checked row. *Mutation:* give
      `FanOutToCheckedRows` its own `KeyframesReady` filter over the targets → fails.
- [ ] **Set-at-playhead from a scanning selected row.** The selected source row's scan is held open
      (`GatedPaths`) and the player is made ready (`ScopeTestPlayer.MakeReady`, the private player in
      `SetAtPlayheadScopeTests.cs:32`, `:47`, so the case lives in that class). `CanSetCutAtPlayhead` needs only a
      selection and a ready player (`BulkCutViewModel.cs:985`). Setting the intro with apply-to-all-rows on
      writes the cut to the checked targets; today it fans out to nothing, via the null return at `:1490`.
      *Mutation:* `if (!_selectedItem!.KeyframesReady) return;` at the top of `FanOutToCheckedRows` → fails.
- [ ] A write during the scan keeps `IsSnapPending` true until the scan lands. *Mutation:* `Resnap()` clears
      `IsSnapPending` → fails.
- [ ] When the scan lands, the applied cut snaps to the nearest keyframe; when it fails, the snap is identity.
      Both clear pending. The failure case applies the cut while the scan is held open, then fails the held scan
      with `probe.ScanGate.TrySetException(new IOException())` — the fake awaits `ScanGate.Task`
      (`BulkTestFakes.cs:97`), so the exception reaches `ScanBodyAsync`'s failure branch. No new fake is needed.
      *Mutations:* drop `ResolveSnap` from the success branch (`:728-729`) or from the failure branch (`:711-712`)
      → fails.
- [ ] **Run safety (I156).** After an apply to a scanning, enabled row: `IsValidCut` false and `CanRunBatch` false
      until `ReleaseScans()`. Then `CanRunBatch` is true and the row's `IntroEnd.Snapped` equals the
      keyframe-snapped time. *Mutation:* drop the `KeyframesReady` term from `IsValidCut` → fails. With the scanning row
      **unticked** beside a ready, valid row, `CanRunBatch` is true and the scanning row is not in the run set — I156
      claims only that an enabled row blocks the run (I37).
- [ ] **Classification — scanning rows.**
  - A positive requested span → `PendingSnapRows`, never `InvalidatedRows`. *Mutation:* classify scanning rows
    with `IsValidCut` → fails.
  - A 0.6 s requested span (profile intro 10 s, tail 49.4 s, on a 60 s scanning row) → `PendingSnapRows`, not
    invalid. *Mutation:* judge scanning rows by the `MinKeptSpan` bounds (D-005's `IsRequestedCutValid`) → fails.
    With Exact cut switched on after the row is added (precondition: `IntroEnd.SuppressSnapNote` true), the same
    row is still pending (§ Edge cases). *Mutation:* judge scanning rows by those
    bounds only when `_exactCut` → fails.
  - An empty requested span (tail longer than the file, so the outro clamps to 0) → `InvalidatedRows` and
    `InvalidStillScanningCount` 1. *Mutations:* send every scanning row to pending, or drop
    `invalidStillScanning++` → fails.
  - A no-outro intro at or past `Duration` → `PendingSnapRows`, then Ready when the scan lands. Setup: profile
    intro 80 s, no tail, on a 60 s scanning row whose keyframes are hand-set through `ByPath` to 0, 2, …, 40 s
    (`AverageGop` 2 s). The intro clamps to 60 (`CutProfileApplier.cs:51`) and snaps to 40, and `40 < 60 − 2`.
    `SetUniform` cannot expose this: it always puts a keyframe at `Duration` (`BulkTestFakes.cs:56-62`).
    *Mutation:* restore the `(OutroStart?.Requested ?? Duration) <= IntroEnd.Requested` form → fails.
- [ ] **Classification — ready rows.**
  - A row valid as requested but invalid after the snap → `InvalidatedRows`, `InvalidStillScanningCount` 0,
    `PendingSnapRows` empty. Setup: a 60 s file, `SetUniform` step 6 (`AverageGop` 6 s, so `MinKeptSpan` 6 s),
    profile intro 10 s + tail 40 s. Intro 10 snaps to 12, outro 20 snaps to 18, and `12 < 18 − 6` is false.
    *Mutation A:* classify ready rows with the scanning rule (`IsCutHopelessBeforeSnap`) → the row goes to
    pending → fails.
  - A ready, valid row → `PendingSnapRows` empty. *Mutation B:* send ready valid rows to pending → fails.

  The sets are disjoint.
- [ ] **Classification — the ⧉ path, unclamped.** A ready 60 s source (intro 10, outro 50, so tail 10) is copied
      with ⧉ onto a checked 8 s target whose scan is held open (`GatedPaths`), beside a checked load-failed row
      (`FailProbePaths`, `BulkTestFakes.cs:30`). ⧉ does not clamp: the target gets intro 10, past its end
      (`BulkCutViewModel.cs:1508`), and an added outro at −2 (`:1512`, `:1519`). Assert:
      - the target is in `InvalidatedRows`;
      - `InvalidStillScanningCount` is 1 and `SkippedNotLoadedCount` is 1;
      - `ApplyReportSummary` reads
        `Applied to 1 row(s) · 1 invalid (red when their scan finishes) · 1 not loaded, skipped.`

      *Mutation:* pass `0`, or a counter that never reaches the record, at the construction site
      `BulkCutViewModel.cs:1535` → fails.
- [ ] Targets without a `Duration` are untouched and counted in `SkippedNotLoadedCount`; unticked rows are
      **not** counted. *Mutations:* drop the counter, or count unticked rows → fails.

## Edge cases

- **Removed or cleared mid-scan.** `CancelScan` (`:1218` Remove, `:1246` Clear) → the cancel branch clears the
  flag without `ResolveSnap`. The row is gone, so nothing renders it. **The apply line:** `Remove` (`:1205-1228`)
  never touches `ApplyToAllReport`; only `Clear` (`:1253`) and a run's start (`RunBatchAsync`, `:2139`) null it.
  After removing a pending row, the line keeps its click-time counts (e.g. `3 waiting for their scan` with 2 rows
  left) until the next apply, run or Clear. That is the OQ3 snapshot, and today's line behaves the same way for a
  removed invalid row. The boundary is I157, enforced by the source-assert test: a future caller that cancels a
  *surviving* row's scan must resolve its handles and request their frames (§ Interfaces).
- **Scan superseded.** The flag stays true and the newest scan resolves. The only caller today is
  `PopulateAsync` `:1197`, once per row.
- **Valid on request, invalid after the snap.** A positive requested span that the scan proves too short: a long
  GOP lifts `MinKeptSpan` above the 1 s floor, or the snap narrows the span. The row is reported waiting, then
  turns red on resolve. The apply line is not re-issued (OQ3).
- **Waiting on request, a no-op after the snap.** `ComputeBaseRowState` checks `IsNoOpTrim` before `IsValidCut`
  (`BulkItemViewModel.cs:436-441`). A pending row whose effective intro lands within 0.5 s of 0 — with no outro, or
  with its outro within 0.5 s of EOF — becomes `no-op` when its scan lands: a muted chip and the reason
  `nothing to trim yet — set an intro or outro`. Example: a 60 s row on an 8 s GOP, profile intro 3 s and no tail,
  under Lossless — the line said `1 waiting for their scan`, then the intro snaps to 0. This matches a ready row
  today, where the apply line does not call a no-op invalid.
- **Invalid by the 1 s floor, valid after the snap (Lossless).** Under Lossless, nearest-keyframe snapping can
  move the intro earlier and the outro later. A locally sparse keyframe gap around the cut, while `MinKeptSpan`
  (`max(1 s, average GOP)`) stays low, can turn a 0.6 s request into a valid cut. Such a row is **not** called
  invalid: only an outro handle at or before the intro is (§ Design 3). It reads `waiting for their scan`, and the
  chip decides.
- **A no-outro intro at or past `Duration`.** Pending, not invalid, because `Duration` never snaps (§ Design 3).
  Under Lossless the row turns Ready if its intro snaps back earlier than `Duration − MinKeptSpan`, and red
  otherwise. It is always red on a file with a keyframe at `Duration`.
- **Exact cut: certain to fail, still reported waiting.** Under Exact the cut is the request
  (`BulkItemViewModel.cs:366`, `:369-370`), and `MinKeptSpan` never drops below 1 s (`:379-386`). Two kinds of
  scanning row are therefore certain to fail `IsValidCut` once the scan lands: a positive requested span under
  1 s, and a no-outro intro at or past `Duration`. Each is still classified pending, reads
  `waiting for their scan`, then turns red. Accepted: the classification is one rule in both precisions, because
  precision can be flipped after the click and the line is a snapshot (OQ3). Flipping to Lossless can rescue
  either row; only an outro handle at or before its intro stays invalid through a flip.
- **Saving a profile from a row whose handles are pending.** `BuildProfileFromRow` reads `Requested`
  (`CutProfileApplier.cs:94-99`), so it is unaffected.
- **Run pressed while applied rows still scan.** `CanRunBatch` is false, and the run-scope line already says
  `N still scanning` (`:627-630`).

## Risks

- **Visible change.** Many rows can read `→ snapping…` at once after an apply. Intended, and the apply line
  now says so.
- **Pending rows can turn red after the snap.** Any of these pending rows can turn red:
  - its requested span proves shorter than the scanned `MinKeptSpan`, or the snap narrows it;
  - it has no outro, and its intro does not snap back far enough;
  - under Exact cut it is already certain to fail (§ Edge cases).

  The apply line calls a row invalid only for an outro handle at or before its intro, which no snap and no
  precision flip can rescue. So the surprise always runs waiting → red or waiting → no-op, never invalid → ready. The row chip and
  its `ExclusionReason` cover it.
- **A hidden consumer of the old skip.** Any code that relied on "apply never touches a scanning row" — search
  for `ApplyToAllReport` and `ApplyToAll(` callers at build; today they are the two profile commands and the
  fan-out.
- **Latent `CancelScan` trap.** Unreachable today. It is pinned as I157 and enforced by a source-assert test, so
  a new caller on a surviving row fails the suite instead of arriving silently.

## Out of scope

- Precision inheritance for rows and outro handles added after the Exact toggle — [[T-176]].

- **Deferred apply-on-probe** (D-005 Q1 applies only to rows already probed). A row still unprobed at the click is
  skipped and not revisited when its probe lands, so right after a large drop the re-apply trap remains for those
  rows.
- **A silent ⧉ on an unprobed source.** `ApplyToAll` returns null before assigning a report
  (`BulkCutViewModel.cs:1490-1493`), so the click writes no line and leaves the previous one in place.
- **A silent set-at-playhead fan-out from an unprobed selected row.** `CanSetCutAtPlayhead` needs only a selection
  and a ready player (`BulkCutViewModel.cs:985`). `PlayerViewModel.IsReady` is the decoder's own duration
  (`PlayerViewModel.cs:223`), not the row's probed `Duration`. Rows are selectable as soon as they are listed
  (`:1151`) but probed one at a time (`:1166-1169`). So right after a large drop, the user can set a cut on a row
  that has not loaded. The gesture writes the selected row (`:1376` intro; `:1396` / `:1400` outro), then
  `FanOutToCheckedRows` calls `ApplyToAll`, which returns null before assigning a report. What the user sees:
  - the selected row's IN (or OUT) changes;
  - every checked row stays untouched, and nothing is counted;
  - no new line appears, and the previous apply's line, if any, stays up.

  § Concept's silent-skip trap remains on this path until the selected row loads.
