## Reported
> for profile setting please make sure setting was saved and restore able even after reinstall app again

## What is true today — checked, not assumed

**Uninstall does not delete them.** `packaging/VideoSplitJoiner.iss` has no `[UninstallDelete]` section
and touches nothing under the user profile, so a reinstall keeps whatever was there. Good — but that is an
*accident of the current script*, not a stated guarantee. Nothing asserts it, so a future installer edit
could start wiping user data and no test would notice.

**A profile is split across TWO roots, and that is the real hazard:**

| what | where | API |
|---|---|---|
| the profile (name, intro, outro) | `%APPDATA%\VideoSplitJoiner\settings.json` | `SpecialFolder.ApplicationData` — **Roaming** |
| its picture | `%LOCALAPPDATA%\VideoSplitJoiner\profile-thumbs\` | `SpecialFolder.LocalApplicationData` — **Local** |

So anyone who backs up "their settings", or moves to a new machine via a roaming profile, takes the
profiles and **leaves every picture behind**. The profile survives with a `ThumbnailPath` pointing into a
folder that does not exist there. Nothing today makes that visible, and it is not obviously anyone's bug.

**There is no export/import.** "Restorable" currently means finding two folders and copying them by hand.

## Design
1. **Pin the survival guarantee with a test** so it cannot regress: assert the installer script contains
   no `[UninstallDelete]` targeting user-data paths. Cheap, and it turns today's accident into a stated
   invariant.
2. **Decide the two-root split deliberately** — either move the thumbnails beside the settings so one
   folder is the whole story, or keep them apart and make export the supported path. Record it in an ADR;
   a broken `ThumbnailPath` after a machine move should be a decision, not a surprise.
3. **Export / Import** — the actual ask behind "restorable". One file carrying the profiles *and* their
   images (they are ~96px, so embedding is cheap), with import as an **upsert by name**, never a
   wipe-and-replace.
4. **Import must be defensive**: a corrupt or truncated file leaves existing profiles untouched, and a
   name collision is the user's decision, not a silent overwrite.
5. Confirm the existing missing-thumbnail fallback still holds when the path points at another machine's
   folder — the placeholder should show and the cut should still apply.

## Acceptance criteria
- [x] A test asserts the installer removes no user data on uninstall. (`InstallerLeavesUserDataTests` reads the real `.iss`: no `[UninstallDelete]`, no `{userappdata}`/`{localappdata}`/`{userdocs}`.)
- [x] Profiles and their pictures survive a simulated uninstall/reinstall, asserted over the real paths. (`ProfileSurviveReinstallTests` - neither root is under the install directory, and fresh `AppSettings`/`ProfileThumbnailStore` instances over the same folders find both, byte for byte.)
- [x] Export produces one file containing profiles AND images; import restores both where neither existed. (`ProfileBackup.Export`/`Plan`/`Apply`, images inline as base64.)
- [x] Importing a corrupt or truncated file changes nothing. (Empty / non-JSON / truncated / no-profiles-key / future-version all fail at PLANNING, and a failed plan proposes nothing.)
- [x] A name collision on import is resolved by the user, never silently. (`Plan` separates `New` from `Colliding`; `ConfirmProfileOverwrite` defaults to KEEPING existing, so an unwired host cannot overwrite - and the question is only asked when something would actually be overwritten.)
- [x] A profile whose image is missing shows the placeholder and still applies its cut. (`PathToBitmapConverter` returns null for a stale cross-machine path; `CutProfileApplier` applies intro/outro regardless.)
- [x] SPEC-007 updated (I79-I94, +2 sources, G-051); two-root decision recorded in **ADR-0021**.

## Out of scope
Cloud sync. Sharing profiles between users.

## Outcome — 2026-09-01

**Shipped.** Reinstall survival was already true and is now *asserted*; portability is new.

- **The guarantee, pinned.** `InstallerLeavesUserDataTests` reads `packaging/VideoSplitJoiner.iss` and
  fails if an `[UninstallDelete]` section or any `{userappdata}`/`{localappdata}`/`{userdocs}` path ever
  appears. Today's accident is now a stated invariant (SPEC-007 I79).
- **The two-root split was kept, deliberately** (ADR-0021). Migrating existing installs between Roaming
  and Local meant copy + path-rewrite + partial-failure handling on every user's machine, to buy only
  "a manual folder copy would work" — real data-loss risk for a workflow nobody asked to perform.
- **Backup carries the images instead.** `ProfileBackup` writes ONE file, pictures inline as base64
  (~96px, so the size cost is nothing). One file is the whole story: no relative paths, no sibling
  folder, no unzip step, and no question of which root a picture came from.
- **Import plans before it acts.** `Plan()` reads and reports; `Apply()` acts on the plan. Corrupt,
  truncated, empty, and future-version files all fail at planning — and a failed plan proposes nothing,
  which is what makes a bad file a genuine no-op rather than a half-applied restore.
- **The collision decision is the user's, defaulting to keep.** An unwired or half-wired host cannot
  silently overwrite profiles; the prompt only appears when something would actually be overwritten.

### Mutation-checked, and one honest survivor
M1 (default overwrite hook flipped to yes), M2 (ask when nothing collides), M3 (accept a future format),
M4 (apply collisions regardless) — all died. **M5 survived**: removing the `plan.Failed` guard in `Apply`
broke no test. That is correct rather than a gap — the guard is defence in depth, redundant *because* a
failed `Plan` returns empty lists. The contract the safety actually rests on was unpinned, so it now is:
a failed plan has empty `New`/`Colliding`/`Images`. If `Plan` ever starts returning partial results beside
an error, that guard becomes load-bearing and the test will say so.
