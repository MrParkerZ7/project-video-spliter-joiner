## Why / vision
When the user adds cut points out of chronological order (a cut at 5:00, then one at 2:00), the "Cut markers" list shows them in the order added (5:00, 2:00) — confusing, since the parts they produce are chronological. The list should read top-to-bottom in time order.

## Grounding (2026-07-18)
- **The split output is ALREADY time-ordered** — not a correctness bug:
  - `SplitPlan.BuildPlan` sorts requested cuts ascending, drops out-of-range, dedupes (`SplitPlan.cs:90-91`).
  - The segments/"Parts to export" list derives from `Markers.Select(m => m.Snapped).OrderBy(t => t)` (`SplitViewModel.cs:1008-1011`) — parts are numbered by time.
- **Only the `Markers` collection is append-order** — `AddSnappedMarker`/`AddPendingMarker` call `Markers.Add(marker)` (`:702`, `:758`), appending. The "Cut markers" list (T-059 section) binds to `Markers`, so it shows add-order.
- `CutMarkerViewModel` has `Requested` (the click time) and `Snapped` (the resolved keyframe time); a pending marker (T-041) starts with `Snapped` unresolved and updates when the background keyframe scan finishes (raises `Snapped` PropertyChanged, handled at `:972`).

## Decisions
- **D1 · Order `Markers` by time.** Two clean options — pick the lower-risk during build:
  - **(a) Sorted insert** — insert each new marker at its correct sorted index (by `Requested` while snap is pending, by `Snapped` once resolved) instead of `Add`; when a pending marker's `Snapped` resolves, re-position it (remove + sorted-insert) so it settles into the right slot. Makes marker index == chronological order everywhere.
  - **(b) Live-sorted view** — keep `Markers` append-order but expose a `CollectionViewSource`/`ICollectionView` with a `SortDescription` on the time key + live sorting (`IsLiveSorting`) so it re-sorts when `Snapped` changes; bind the list to the sorted view. Underlying collection untouched.
  - Prefer **(a)** if any code relies on marker index meaning "Nth part"; prefer **(b)** if a pure display sort is enough and re-positioning churn is a concern. Note the choice.
- **D2 · Sort key** — `Snapped` when resolved; `Requested` as the provisional key while pending (so a pending marker still lands roughly right, then settles on resolve). Ties → stable.
- **D3 · No output change** — the plan/segment sorting already handles correctness; verify the produced parts are byte-identical before/after (only the list order changes).

## Plan
```
T-071 order the Markers list by time (sorted-insert or live-sorted view), handle pending→resolved re-order + removal; docs
```

## Risks
- **T-041 pending re-order** — a pending marker added out of order must re-settle when its snap resolves; option (a) needs a careful remove+reinsert guarded against the staleness checks; option (b) needs live sorting to fire on the `Snapped` change.
- Don't disturb the timeline ticks (already drawn by time) or the segments list (already sorted).
- Keep dedupe semantics (dedupe on `Snapped`) intact.

## Out of scope
Re-ordering the Join clip list (that's a user-controlled order — intentional); changing part numbering (already by time); marker grouping/labels.
