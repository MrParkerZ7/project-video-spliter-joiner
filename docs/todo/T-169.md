## Concept

Hovering a profile chip opens a floating card showing that profile's thumbnail much larger than the 28px
chip, with its name and cut values, so you can recognise a profile without selecting it.

## Design

### Use a `Popup`, not a `ToolTip` — the app already decided this twice
The request says *"something like tooltip but bigger"*, and a `ToolTip` is the obvious reach. It is the
wrong one here, for three concrete reasons:

1. **The themed `ToolTip` is built for text.** `Controls.xaml:157-186` sets `MaxWidth="360"`,
   `Padding="10,6"` and a wrapping `TextBlock` style. Usable, but it is a text chrome.
2. **`ShowDuration` auto-hides.** WPF's default dismisses a tooltip after ~5s. For a *"quick review"*
   panel the user may hold on, a control that vanishes mid-look is precisely wrong.
3. **This app already has a hover-thumbnail idiom, and it is a `Popup`** — twice:
   `PlayerView.xaml:79` and `BulkRowScrubView.xaml:37` (whose comment says it *"mirrors PlayerView's"*).
   A third instance should be the same shape, not a new one.

Copy `PlayerView.xaml:79-114` wholesale — it has already solved the hard parts:
`AllowsTransparency="True"` · `StaysOpen="True"` (never steals focus) ·
**`IsHitTestVisible="False"`** (never intercepts the click that selects the chip — load-bearing here,
because SPEC-007 **I97** requires a click to SELECT) · `Placement` + offsets · a fixed-width box with a
letterboxed image so the popup does not jump between frames of different aspect.

### What the card shows
The thumbnail is the point, but a picture alone does not identify a profile. Include the **name** and the
**intro/outro values** — the chip truncates the name (`ProfileItemTemplate`, `TextTrimming`), so the popup
is also where a long name becomes readable. Mirror PlayerView's shape: image box, then a mono caption.

### Placement and edge cases
- A chip near the right edge or the bottom row must not push the card off-screen. `Popup` renders in its
  own window so it is **not clipped by the card**, but it can still leave the monitor — set a `Placement`
  that flips.
- **A profile with no thumbnail is normal**, not a failure (SPEC-007 **I78**). The popup must still be
  useful: show the placeholder plus the name and values, or do not open at all. Pick one deliberately.
- Wire `MouseEnter` / `MouseLeave` on the chip with a short open delay, so sweeping the cursor across a
  wrapped grid of chips does not strobe. This is the one thing `ToolTip` would have given free.

## ⚠ Two findings this planning turned up

**1. SPEC-007 I74 is inaccurate.** It states all three thumbnail sources *"store at
`ProfileThumbnailWidth`, so the stored picture is the same size whichever produced it."* The **upload**
path does not resize: `UploadThumbnail` (`BulkCutViewModel.cs:1760`) hands the user's chosen file
straight to `TryAttachThumbnail` (`:1775`), and `ProfileThumbnailStore.Save` copies **bytes verbatim**
(SPEC-007 I42). So an uploaded picture keeps its original resolution while a captured one is 96px wide.

Consequence for this feature: **preview sharpness silently depends on how the thumbnail was made** — crisp
for uploads, soft for captures — with nothing on screen explaining the difference. Fix the invariant text
either way; it is wrong today independently of this ticket.

**2. `PathToBitmapConverter` decodes at full resolution** (`Converters.cs`, no `DecodePixelWidth`). Good
news for the preview — the pixels are already there. Less good at 40 profiles: every chip holds a
full-resolution decode for a 28px display, and after [[T-168]] all of them may be realised at once.
Measure before assuming it matters; do not "fix" it speculatively.

## Acceptance criteria
- [x] The card shows the picture at 320px against the chip's 28.
- [x] The card never intercepts the selecting click — a `ToolTip` is neither hit-testable nor
      focusable, both asserted rather than assumed (I97 unbroken).
- [x] It does not steal focus, and `ShowDuration` defeats the ~5s auto-hide.
- [x] No picture → the letterbox collapses and the name and values carry the card (I78).
- [x] A 120-char name is fully readable in the card, where the chip trims it.
- [x] Normalization only ever shrinks; a 64px picture is stored untouched, never inflated.
- [x] Six mutations, all dead: width back to 96 · normalization removed · upscaling allowed ·
      the `DataContext` binding broken · `ShowDuration` back to 5s · `InitialShowDelay` to 0.

## Testability — state the limit honestly
The STA harness (`StaViewHarness.cs`) measures laid-out visual trees. A `Popup` renders in a **separate
window** and needs `IsOpen=true` plus a pumped dispatcher, so a hover *gesture* is likely not assertable
there. What **is** assertable: the popup exists in the template, its bindings resolve, its configured
sizes, `IsHitTestVisible`/`StaysOpen`, and — by setting `IsOpen` directly — the content's measured size.

**The vacuity trap to avoid:** a test that asserts "the Popup element exists" passes whether or not hover
ever opens it, and whether or not the image is bigger. Any test claiming to cover this must assert the
rendered image **size** and the click-through behaviour, not the element's presence.

## Decisions (answered)

### How big should the preview be? — answered 2026-09-07 via `todo-options`

**Chosen: normalize EVERY thumbnail source to ~320px on save.** Captures grab at 320, and uploads are
**re-encoded** to 320 rather than copied byte-for-byte as they are today.

**Original fork (archived):**
> How big, given captures are stored 96px wide? (a) preview at native 96 — sharp, modest, zero migration;
> (b) raise `ProfileThumbnailWidth` to ~320 for NEW captures, old profiles stay 96; (c) (b) plus a
> re-capture affordance for existing profiles.

**Why the fork as written was the wrong question.** Grounding it against the real store changed the
answer. The 11 pictures in `%LOCALAPPDATA%/VideoSplitJoiner/profile-thumbs` measure:

| stored width | count |
|---|---|
| 64px | 6 |
| 96px | 4 |
| unreadable (1 byte) | 1 |

The capture path always scales to 96 (`scale=96:-1`, `FfmpegThumbnailService.BuildArgs`) and
`ProfileThumbnailWidth` has been 96 since the single commit that introduced it (`8eeae8c`), so **a 64px
file cannot be a capture.** Those six are uploads, which `ProfileThumbnailStore.Save` copies verbatim
(I42). So the premise behind options (a)-(c) — that "captures are stored 96px wide" describes the
library — is false for the majority of it, and option (b) would have left 6 of 11 pictures untouched.

**Why the chosen option.** It is the only one that makes preview quality **independent of how the picture
was made**. Today sharpness silently depends on provenance, with nothing on screen explaining why one
profile is crisp and another is mush. It also turns SPEC-007 **I74** from a false claim into a true one:
that invariant already asserts all three sources store at one width, and normalizing on save is what
makes it so. Disk cost is nil — the entire store is 10,483 bytes today, so ~10x is still ~100KB.

**Rejected, and why:**
- *Raise the capture width only (the original (b))* — one constant, but 6 of 11 pictures are uploads and
  stay 64px. The inconsistency, which is the actual complaint, survives.
- *Preview at native size, change nothing* — ships fastest, but previews at 64-96px would be **smaller
  than the 160px hover preview this app already shows on the scrub bar**
  (`ThumbnailPreviewViewModel.ThumbnailWidth`), so the new feature would look worse than an existing one.
- *Normalize plus re-picture existing* — deferred, not refused. The re-capture gesture needs designing,
  and for uploads the original file is long gone, so those could only be upscaled. Worth its own ticket
  if the mixed library actually bothers you once normalization is in.

**Scope this adds to T-169:** `TryAttachThumbnail` must re-encode on the upload path instead of copying
verbatim, and `ProfileThumbnailWidth` becomes the one width all three sources honour. SPEC-007 I42
("copies the source file into the store, bytes verbatim") and I74 both change, so `spec` moves to
`amended`.

**⚠ Found while grounding, not part of this decision:** `P_148de9c5a7a44d19.jpg` in the real store is
**1 byte** (`x`) and is not a valid image. SPEC-007 I73 promises copy-then-swap durability — a failed
`Save` should leave the prior thumbnail byte-identical, never a stub. Filed separately as [[T-170]].

## Outcome — 2026-09-07

Built, and two of the three hardest parts were not the ones the plan expected.

### The mechanism changed during the build, deliberately
The plan committed to a `Popup`, on the grounds that this app already uses one for hover thumbnails
twice. Building it showed the precedent does not transfer: `PlayerView`'s and `BulkRowScrubView`'s popups
**track the cursor** along a timeline, which is precisely why they cannot be tooltips. Hovering an item
to see a card needs no tracking, and `ToolTipService` supplies the open delay, the dismissal and the
screen-edge flip — including the open delay the plan itself named as *"the one thing ToolTip would have
given free"*. Both of the plan's objections were settable: `ShowDuration` defeats the ~5s auto-hide, and
the themed 360px cap comfortably holds a 320px picture. Recorded as I102.

### A defect the tests caught that a code read would not have
The first working version rendered a card that was present, correctly sized, and **completely empty**.
Two independent causes, both invisible in review:

1. A `UIElement` in a `Style` setter is a **single shared instance** across every item, so one tooltip
   was serving all chips with no per-item context.
2. A `ToolTip` is a **logical** child, not a visual one, so it does not inherit the template's
   `DataContext` and a plain `{Binding}` resolves to **null**.

The card is now declared in the item `DataTemplate` and takes its `DataContext` from
`PlacementTarget.DataContext`. This is exactly the vacuity the ticket warned about: a test asserting "the
chip has a tooltip" would have passed against the empty card. Every test here opens it and measures what
is inside. Recorded as I103.

### The harness limit, and what it cost
An **open** `ToolTip` is hosted in a `Popup` that owns layout, and with no `PresentationSource` behind it
every child measures 0 — the card renders for a user and is invisible to a test. Measuring the **closed**
control after `ApplyTemplate` gives the same tree under ordinary layout. Four attempts went into finding
that; the diagnostic string left in the first test is deliberate, so the next person spends less.

### The decision, delivered
`ProfileThumbnailWidth` 96 → 320, and **uploads are re-encoded** rather than copied verbatim, so all
three sources finally converge on one width — which SPEC-007 I74 has claimed since it was written. I74
is now annotated with when it became true. Shrink-only and best-effort: a 64px picture is stored
untouched, and any re-encode failure stores the original.

Documented as SPEC-007 **I101-I107**. Suite 1482 → **1494 green**, 0 warnings.
