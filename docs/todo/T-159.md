## Found

`BulkItemThumbnailTests.ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree` failed once during the
[[T-157]] verification run, passed on the retry, and then reproduced twice more in four runs — but
**only** in the configuration that builds first. Thirteen consecutive `--no-build` runs were clean.

That pattern is the whole diagnosis: the test loses when the machine is busy, and a full build is what
makes it busy. It is a load-sensitive test, not an intermittent product bug.

**It is not related to the change that surfaced it.** The test exercises `BulkItemViewModel`, the shared
thumbnail gate and `FakeThumbnailService`; nothing in T-154/T-157 touches any of them.

## Why it fails

Two `SpinUntil` waits, each a wall-clock deadline racing real work:

```csharp
var spun    = SpinUntil(() => thumbs.CurrentConcurrent    >= 3, TimeSpan.FromMilliseconds(500));
var drained = SpinUntil(() => thumbs.GetThumbnailCallCount >= 8, TimeSpan.FromSeconds(2));
```

Neither asserts anything about the gate. They assert that eight queued grabs *arrive quickly enough*,
which is a statement about the host, not the code. On a loaded runner they do not, and the test reports
the concurrency bound as broken when the bound was never reached in the first place.

The failing duration named the culprit: **2 s**, which is the second wait's timeout, not the first.
The first fix pass replaced only the 500 ms spin and the flake survived — the failure had been the drain
wait all along.

## Design

Give the fake a signal instead of asking the test to guess a duration. Both waits complete from **inside
the same lock** that updates the counter, so there is no window between reaching the count and observing
it; the remaining timeout is a deadlock guard, not a timing assumption.

## Acceptance criteria
- [x] `FakeThumbnailService.WhenConcurrentReaches(n)` and `WhenCallCountReaches(n)` — signalled under the
      counter's own lock.
- [x] Both spins in the test replaced; the surviving timeouts are 30 s deadlock guards.
- [x] Six consecutive full solution runs **with a build** (the configuration that reproduced it) are green.
- [x] The concurrency bound itself is unchanged — `PeakConcurrent <= 3` still asserted, and the test
      still fails if the gate stops bounding.

## Out of scope
Auditing every other `SpinUntil` in the suite. This one had a reproducible failure; the rest do not yet,
and rewriting waits speculatively is churn. Worth a sweep if a second one ever flakes.

## Outcome — 2026-09-04

Fixed as designed. The lesson worth keeping is the misdiagnosis: the obvious wait was not the failing
one, and replacing it produced a run that still flaked while *looking* addressed. The failure duration
(2 s, matching the second timeout exactly) was the evidence that settled it — the same "read what the
instrument actually says" discipline as T-137's stale build and T-155's green line from a crashed host.

Related: a flaky test matters more now than it did last week, because [[T-149]] just made the release
gate capable of failing. A gate that fails at random is barely better than one that cannot fail at all.
