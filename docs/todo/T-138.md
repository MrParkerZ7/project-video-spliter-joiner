## Reported
> after click on Save current as.. then save then UI gone broke untill I click X everything back to normal

## Cause found — dangling mouse capture from a programmatically-closed popup

This is recorded honestly rather than guessed at. **I could not reproduce it from code reading**, and the
one detail that would narrow it fastest is missing: what "broke" looked like, and which ✕ was clicked.

Verified:

- `CommitSaveProfile` (`BulkCutView.xaml.cs:314`) **does** close the popup — `SaveProfilePopup.IsOpen = false`
  runs synchronously right after `SaveProfileCommand.Execute(name)`. So the popup should not linger.
- **No crash log was written.** `%LOCALAPPDATA%\VideoSplitJoiner\logs` holds nothing newer than 2026-08-22,
  so no unhandled exception reached the global net. That weakens (does not kill) the theory that
  `SaveProfileCommand.Execute` threw and skipped the close.

Candidate causes, in the order I would test them:

1. **The bar re-lays-out mid-save.** Saving the FIRST profile flips `HasProfiles` false→true, so the
   picker and Delete appear at once. Since T-136 the bar is a `WrapPanel`, so that can now push it onto a
   second line and change the profile bar's HEIGHT. If the containing row does not absorb that, controls
   overlap or clip. **This is the newest change in the area and therefore the first suspect** — T-136
   (`853a8ea`) was minutes before this report.
2. **The async tail keeps mutating the UI after the popup closes.**
   `SaveProfileWithAutoThumbnailAsync` saves, refreshes the profile list, then **shells out to ffmpeg** for
   the intro-end frame, then refreshes the list AGAIN. So the profile bar re-projects twice, seconds apart,
   after the dialog is gone. A second re-projection landing while the user is interacting is a plausible
   "it went weird then came back".
3. **The popup is genuinely still open but not visibly so.** `AllowsTransparency="True"` +
   `StaysOpen="False"`; a transparent popup that keeps mouse capture would make the app look dead until
   dismissed — which fits "until I click X" better than 1 or 2 do.

**The distinguishing question:** the ✕ that fixed it — was it the popup's own **Cancel**, the red ✕
**Delete profile** button in the bar, or the app window's ✕? Cause 3 predicts the first; the others do not
explain why a click was needed at all.


## Attempt 1 — WRONG. Reopened.

The user retested and reported the problem unchanged: *"you fix nothing! my problem still there!"*
The build they were running (22:27) **did** contain the capture fix — the publish preceded the commit —

Releasing capture on close is still correct and stays in. It was not the cause.

## Attempt 2 — remove the mechanisms instead of cleaning up after them

Rather than guess at a third mechanism and patch it, the popup's two known input-hazard settings are gone:

| was | why it could do this | now |
|---|---|---|
| `StaysOpen="False"` | makes WPF TAKE mouse capture to detect click-outside | `StaysOpen="True"` — capture is never taken, so nothing can dangle. Dismissal is fully explicit: Save, Cancel, Escape all call `CloseSaveProfilePopup()` |
| `AllowsTransparency="True"` + `PopupAnimation="Fade"` | together make the popup a LAYERED window with a fade-out; one that does not finish can sit invisibly over the app swallowing clicks | both removed — neither is load-bearing for a small name box |

Trade-off accepted: clicking outside no longer dismisses the popup. For a box you are typing a name into,
that is arguably better.

**STILL NOT REPRODUCED.** I could not drive the app to the failing state — the file dialog would not open
under UIAutomation, and my attempts resized the user's window, so I stopped. This removes the two
mechanisms that are known to produce exactly this symptom; it is not a confirmed fix, and the ticket stays
OPEN until the user says it is gone.


## How to settle this on the next occurrence

`packaging/diagnose-frozen-ui.ps1` captures the evidence that distinguishes the remaining candidates.
Run it **while the UI is dead, before clicking anything to recover it** — the recovery click is what
destroys the evidence:

```
powershell -ExecutionPolicy Bypass -File packaging/diagnose-frozen-ui.ps1
```

Healthy baseline, measured against the running app on 2026-08-31:

```
Responding  True          WM_NULL  answered within 3s
capture     0             no window holds the mouse
windows     1 visible, none visible+layered
```

How the reading picks the cause:

| observation | means |
|---|---|
| `Responding=False` / WM_NULL times out | the UI thread is genuinely stuck — a deadlock or blocking call, NOT a popup |
| `capture != 0` | a window still holds mouse capture; input is being swallowed (attempt 1's theory) |
| an extra window that is visible AND layered | an un-dismissed popup sitting over the app (attempt 2's theory) |
| `foreground != app window` | the app merely lost activation; the first click just re-activates it |

Read-only: it sends `WM_NULL` and reads window state, so it cannot itself clear the condition.

## Superseded first diagnosis (kept for the record)

**Candidate 3 was right.** A `Popup` with `StaysOpen="False"` takes MOUSE CAPTURE so it can notice a
click outside itself and dismiss. Pressing **Save** closes it PROGRAMMATICALLY (`IsOpen = false`) while
keyboard focus is still inside `ProfileNameBox`, and in that path the capture can be left dangling: the
popup is gone, but the window keeps routing mouse input at a target that no longer exists. The app looks
frozen until some other interaction forces the capture loose — which is exactly "until I click X".

It also explains the two things that puzzled me: the popup really *was* closed (so `IsOpen = false` was
not the problem), and nothing threw (so no crash log).

Fix: every close path — Save, Cancel, Escape — now goes through `CloseSaveProfilePopup()`, which closes,
releases capture (`Mouse.Capture(null)`), then returns focus to the button that opened it. That is correct
on every path regardless of this bug: a closed popup should hold neither capture nor focus.

**Honest status:** this is a strongly-supported diagnosis with a fix that is independently correct, but I
could not reproduce the freeze myself — it needs a real click on a real window. If saving a profile still
misbehaves, the remaining candidates (1: the bar re-laying-out mid-save; 2: the async grab re-projecting
the profile list twice) are recorded above and untouched.

## Outcome — 2026-09-01: it was candidate 1 all along

**Cause: the layout.** Not the mouse capture of attempt 1, not the layered popup of attempt 2 — the
candidate listed first and tested last. Saving the first profile flips `HasProfiles` false→true, revealing
the picker, Delete and apply controls at once; the header gets taller; and if the window's middle row does
not defend its space, the header takes it and the screen goes blank. That is precisely what the user's
screenshot showed: *"the profiles bar move to middle of page and all content gone"*.

It was fixed in T-141/T-142, which restructured the header into stacked full-width rows. What holds the
line is `RootGrid`'s middle row — `Height="*" MinHeight="220"`.

### Why this took three attempts, and what actually changed
The first two attempts shipped on hypotheses because *"I could not reproduce it locally"* was accepted as
a reason to guess. That was wrong, and the user paid for it twice — *"you fix nothing! my problem still
there!"*

It was reproducible all along, without a popup, a file dialog, a video, or a single click. Build the real
`BulkCutView`, lay it out at a real window size, make the header taller, and look at the content area.
`BulkCutViewLayoutTests` does exactly that, in about a fifth of a second.

### The evidence
Three mutations of the guard, each reproducing the reported symptom:

| mutation | result |
|---|---|
| middle row `Height="Auto"` (sizes to content) | 1 test fails |
| `MinHeight` removed (`Height="*"` alone) | **2 tests fail — the content genuinely collapses** |
| floor shrunk to `MinHeight="20"` | 2 tests fail |

The middle mutation is the interesting one: with the floor gone the content really does get squeezed out
when the header grows, at the smaller window sizes. That is the user's bug, on demand.

The test also lays the view out with the app's **real** theme dictionaries, so it doubles as a guard for
the other thing that has bitten this screen: a `StaticResource` that does not resolve builds green and only
throws at first render.

### Recorded as SPEC-011 I120
The three-row shape and the middle row's floor are now a stated invariant rather than an implementation
detail someone could reasonably "tidy up".

### What stays from the wrong attempts
Both are independently correct and stay in: a closed popup should hold neither mouse capture nor focus,
and a small name box does not need `AllowsTransparency` + a fade. Neither was the cause.

### Worth carrying forward
"I could not reproduce it locally" is a statement about the harness, not the bug. A WPF layout bug does not
need a human at the keyboard — `Measure`/`Arrange` on the real view is a test, and it would have found this
before the first wrong fix shipped.
