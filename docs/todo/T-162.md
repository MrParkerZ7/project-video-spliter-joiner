## Concept

After a split finishes, the source file is usually the one thing you no longer want — the parts replace
it, and a split *multiplies* disk usage rather than moving it. Bulk Cut can already reclaim that space
(G-050); Split cannot. This adds the same gesture to Split: one button, Recycle Bin only, refused
whenever it cannot prove the parts survived.

This is the deletion **path** the auto layer ([[T-163]]) will route through. Building the auto layer
first would mean a hidden deletion with no visible counterpart — the shape [[T-156]] explicitly refused
("one deletion path, so there is only one place for it to go wrong").

## Design

**Reuse, don't re-implement.** The mechanism already exists and is already hardened:
`ShellRecycleBin.TryRecycle` (`SHFileOperation` with `FOF_ALLOWUNDO | FOF_SILENT | FOF_NOCONFIRMATION |
FOF_NOERRORUI`, verified-gone, bounded retry — ADR-0022 / SPEC-011 I127-I131) behind the
`IOriginalDisposer` seam. `SplitViewModel` takes the same seam Bulk takes, defaulting to a no-op so an
unwired host can never delete.

**The eligibility rule is the ticket.** Bulk asks *"is this row's one output on disk?"*; Split must ask
*"are **all** the parts on disk and non-empty?"* — deleting a 4 GB source when part 4 of 6 failed to
write loses footage that exists nowhere else.

`CanDeleteOriginal` is true only when **all** hold:
1. A split completed successfully this session (`LastResult` non-null, `Operation` not running, not failed).
2. `LastResult.Segments` is non-empty, and **every** produced segment exists on disk with length > 0.
3. The source file still exists and is not itself one of the outputs (guard the degenerate
   output-dir == source-dir + same-name case).

Re-checked **at deletion time**, not only when the button was enabled — that confirm→sweep window is
exactly what [[T-150]] closed on Bulk Cut, and copying the feature without copying that fix would
re-open it here.

**Release the handle first.** The preview player may hold the source open (T-145's lesson, and T-155's:
a locked file is reported, never dialog'd). Unload the player before the sweep and report the holder
via `FileLockOwner` if it still refuses.

### Rejected
- **Delete on run completion with no gesture.** That is [[T-163]], and only behind an explicit opt-in.
- **Permanent delete.** Recoverability is what makes this safe to offer at all (ADR-0022).
- **A second disposer implementation for Split.** Two deletion paths is the defect this avoids.

## Detail
- `SplitViewModel` ctor gains an optional `IOriginalDisposer?` (default no-op), mirroring Bulk's wiring.
- New members: `CanDeleteOriginal`, `DeleteOriginalLabel` (count-and-prize — names the file and the bytes
  reclaimed, as Bulk's does), `DeleteOriginalCommand`, and a result summary line.
- Counted confirmation before deleting, defaulting to **refuse** on an unwired host — Bulk's
  `ConfirmPermanentDeletion` seam pattern (SPEC-011 I126-ish / T-156's `ConfirmReplaceOriginals` shape).
- Placement in the Split footer mirrors T-146: danger vocabulary, its **own** column, at the opposite end
  from Run — never on Run's pixels. Hidden (not greyed) until it can do something.
- Summary states what was binned and what was refused, and why — never implies total success.
- **Shared extraction:** the eligibility-and-sweep logic Split and Bulk both need should land in one
  place. Prefer extracting the shared part over copying it; if extraction turns out to churn Bulk more
  than it saves, say so in the Build log and keep them separate deliberately rather than by accident.

## Interfaces / contracts
- `IOriginalDisposer` (`Core/Io`) — unchanged, reused.
- `ShellRecycleBin.TryRecycle` — unchanged, reused.
- `SplitViewModel.LastResult` (`SplitResult.Segments`) — the eligibility input.
- `IAppSettings` — untouched by this ticket (T-163 adds the flags).

## Acceptance criteria + Case-Coverage Matrix
- [x] A successful split enables a Delete-original control naming the file and the space it reclaims.
- [x] **Refused when any produced part is missing or zero-byte** — the invariant this ticket exists for.
- [x] Refused when no split ran, when the run failed, and while a run is in flight.
- [x] Eligibility is **re-checked at deletion time**, not trusted from when the button was enabled
      ([[T-150]]'s window, not re-opened here).
- [x] Goes to the Recycle Bin, never a permanent delete — asserted directly, and a mutation dropping
      `FOF_ALLOWUNDO` fails it (SPEC-011 I128's lesson: without a direct assertion every "did it vanish"
      check still passes).
- [x] A locked source is **reported with its holder**, not dialog'd, and never crashes the sweep.
- [x] An unwired host (no disposer) deletes nothing.
- [x] The confirmation defaults to refusing.
- [x] Mutations: removing the all-parts-exist check, the deletion-time re-check, and the confirmation
      gate each fail a test.

| case | expected |
|---|---|
| clean split, all parts present | eligible; bins the source |
| part 4 of 6 missing | refused, says which |
| part present but 0 bytes | refused |
| run failed / cancelled | not offered |
| run in flight | not offered |
| source locked by the preview player | player released first, then binned |
| source locked by another process | refused, names the holder |
| no disposer wired | no-op, nothing deleted |
| output written next to source, same name | guarded — never deletes an output |

## Edge cases
Zero segments produced; a segment deleted by the user between run and press; source on a different
volume from the parts; source already in the Recycle Bin; UNC/long paths; split run twice with the
second producing fewer parts.

## Dependencies
None — `IOriginalDisposer` and `ShellRecycleBin` already ship. Blocks [[T-163]] and [[T-164]].

## Risks
- **Data loss is the failure mode.** Every guard here is load-bearing; this is the ticket where a vacuous
  test is most expensive. `APartlyFailedBatchNeverAutoDeletes` was vacuous on first write (T-156) because
  the VM had no disposer — inject a real one and assert on it.
- Split's output dir defaults to the source's folder, so output/source path collisions are plausible.

## Out of scope
Auto-delete and empty-bin ([[T-163]]). Deleting parts. Replace-originals mode on Split.

### On the ticket's "prefer extraction over copying"
Taken in three places, refused in one, and the refusal is the interesting one.

**Extracted:** `FileFacts` (`Exists` / `IsNonEmpty` / `Same`) — Bulk had these three privately and Split
needed exactly them. Each one guards an irreversible action, so two copies is the worst possible place
for a subtle divergence: a slightly different "is this file really there?" on one screen is a deleted
original on the other. Bulk now uses them too, and its 25 delete-originals tests passing unchanged is
the evidence the behaviour is identical.

**Extracted:** the danger-button style, `ProfileDangerButton` → `Themes/Controls.xaml` as `DangerButton`.
Two screens wanting one look is the promote-to-shared rule; two copies of it is how they drift.

**Extracted:** the byte formatter — I had written a third `FormatBytes` before noticing
`MediaFormat.FormatSize` already existed. Split uses that. (Bulk keeps its own: it floors to MB with a
1 MB minimum, and changing a user-visible label is not this ticket's business.)

**NOT extracted — the eligibility-and-sweep logic itself.** The ticket asked for this and it is the right
call to decline. Bulk iterates rows, each with its own `RowState` and one output; Split has one source
and N segments where the question is "are they ALL there?". The control flow, the failure reporting and
the per-item isolation are different shapes — a shared abstraction would need enough parameters to be
harder to read than either copy, and this is the code least improved by cleverness. Recorded here as a
decision rather than an oversight.

### The layout test caught my own wrong assumption
The first version asserted the button sits left of the WINDOW's midpoint, copying T-146's Bulk test
verbatim. It failed at all five sizes — because Split's footer lives inside the right-hand tool panel of
the `OrientedSplitPanel`, so the row itself begins most of the way across the screen. The placement was
right; the assertion was measuring against the wrong container. Now measured against the action row.
