## Concept
During a split into N parts, report and show which part is being written and its local progress — for the fast single-pass muxer path (derived from ffmpeg time) and the per-segment subset path (natural loop index) — without slowing the fast path.

## Design
### Core reporting
- **Per-part channel:** extend reporting to carry `(int PartIndex /*1-based*/, int PartCount, double PartProgress /*0..1*/)`. Either enrich `OperationStatus` with optional part fields OR add a typed `PartProgress` record reported via a new `IProgress<PartProgress>` threaded alongside the existing `IProgress<double>`. Pick the lower-churn option; keep the existing overall `IProgress<double>` intact.
- **`ExtractSelectedPerSegment` (subset path):** already one ffmpeg run per selected part — report `PartIndex` = the part's original 1-based index, `PartProgress` from that run's ffmpeg time/segment-duration, as each run advances.
- **`ExtractAllViaSegmentMuxer` (fast full-set path):** DO NOT change to per-segment. Derive per-part from ffmpeg's reported `time=`: given the keyframe-snapped part boundaries `[start_k, end_k)` from the plan, the current `time` falls in part K; `PartProgress = (time - start_k) / (end_k - start_k)`. Implement the mapping as a **pure function** `(TimeSpan time, IReadOnlyList<TimeSpan> boundaries) → (int partIndex, double partFraction)` — unit-test edges (exactly on a boundary, before first, after last, single part).
- Keep reporting cheap (the muxer path already parses ffmpeg time for overall progress — reuse it; no extra ffmpeg passes).

### UI (App)
- **Parts list ("Parts to export"):** each part row (`SplitSegmentViewModel`) gains a live state — `Pending` / `Writing (x%)` / `Done` — driven by the per-part channel: row K shows a small progress bar while part K writes, a check/"done" when past it. Bind from the VM; update as `PartProgress`/`PartIndex` arrive.
- Optional status line "Splitting part K of N" alongside the existing staged status.
- Keep the overall bar + ETA (T-068) too — per-part is additive.
- **UX/UI reviewer pass** for the per-row progress affordance (fits the sample's mono/dense style; gold accent for the active row).

## Acceptance criteria + Case-Coverage Matrix
- [ ] Splitting into N parts (full set) shows each part's row advancing Pending→Writing→Done, tracking the real write.
- [ ] Subset selection (e.g. parts 1 & 3 of 3) shows per-part progress for the selected parts via the per-segment path.
- [ ] The fast single-pass muxer path is unchanged in speed (no extra ffmpeg runs) — per-part is derived, not re-extracted.
- [ ] The time→part mapping is a pure, unit-tested function (boundary/edge cases covered).
- [ ] Overall progress + ETA (T-068) still work; build 0-warning; suite green + new mapping/VM tests.
- [ ] UX/UI review of the per-row progress done.
- Matrix — Required-Success: N parts → N rows animate in order. Boundary: 1 part; many parts; subset (non-contiguous); part boundary exactly on a keyframe. Required-Fail: none. (Live write behavior = app-run/user-verified.)

## Dependencies
Independent of T-068 (can run in parallel), but T-070 docs wait on both.

## Risks
- **Muxer-path derivation** (time→part) is the crux — off-by-one at boundaries; ffmpeg `time` can jump; guard clamping. Pure-function + tests de-risk it.
- Per-row UI churn — throttle updates so N rows don't thrash the UI on a fast split.
- Don't regress the fast path or the overall/staged reporting.

## Out of scope
Per-part ETA; join per-clip progress; taskbar changes (T-068).
