> ⚠ **Stale on Exact cut — do not build from this revision.** On 2026-09-13 the user chose *show the real cut
> frame* ([[G-057]] § Decisions 1): grab at the time the run will cut — Lossless waits for the snap, Exact grabs at
> the requested time right away, and a precision flip re-grabs. The Design, Detail, Risks and Out-of-scope sections
> below still gate both modes and leave the Exact frame unchanged. § Build log names the revision.

## Concept

While a row's keyframe scan runs, a handle's `Snapped` time is provisional: an identity snap of the requested
time. The per-handle frame thumbnail (T-108) is grabbed at it anyway, then grabbed again when the scan lands.

**The outcome this ticket buys:** the cut-point chip never shows a frame the lossless cut will not use, and the
per-row cut-point grabbers (T-108) do no throwaway ffmpeg grabs while scans run. The profile auto-thumbnail on save
is a separate grab path and is unchanged here (§ Out of scope). Today every settled drag made during a scan costs
one such grab, and the provisional frame stays on the chip until the scan-completion grab replaces it. After
[[T-173]], a single profile apply across 20 scanning rows can fire up to 40 (intro + outro). These grabs do not
block the scans, because grabs have their own gate (SPEC-011 I67). But each one is ffmpeg work whose frame is thrown
away when the scan lands. Wait for the snap; grab once.

## Design

**The choke point is the two request helpers, not the change handler.** D-005 § R5 proposed gating
`OnHandleChanged`. The call sites show that would miss one:

| Call site | Line | Fires while the handle is pending? |
|---|---|---|
| `OnHandleChanged` → `RequestIntroThumbnail` / `RequestOutroThumbnail` on a `Snapped` change | `BulkItemViewModel.cs:890`, `:894` | **yes** — each write during a scan moves the identity `Snapped` |
| `AddOutro` explicit kick | `:273` | **yes** — the kick is unconditional, and mid-scan the new handle stays pending (`snapPending: true`, resolved only `if (KeyframesReady)`, `:263-265`) |
| `ScanBodyAsync` failure branch → `RequestAllThumbnails` | `:714` | no — runs after `ResolveSnap` |
| `ScanBodyAsync` success branch → `RequestAllThumbnails` | `:734` | no — runs after `ResolveSnap` |

Every path to the per-row cut-point chip (`IntroThumbnailPath` / `OutroThumbnailPath`) converges on
`RequestIntroThumbnail` (`:311`) and `RequestOutroThumbnail` (`:314`), so gate there. That covers the chip's grab
paths only. The one other grab at a cut time is the profile auto-thumbnail on save
(`BulkCutViewModel.cs:1602-1604`). It does not go through these helpers and is deliberately left unchanged
(§ Out of scope).

```csharp
private void RequestIntroThumbnail()
{
    if (!IntroEnd.IsSnapPending)                                   // D-005 R5: never grab a provisional cut
    {
        _introGrabber?.Request(Path, IntroEnd.Snapped);
    }
}

private void RequestOutroThumbnail()
{
    if (HasOutro && !OutroStart!.IsSnapPending)
    {
        _outroGrabber?.Request(Path, OutroStart.Snapped);
    }
}
```

**Ordering holds.** `ResolveSnap()` runs `Resnap()` *before* `IsSnapPending = false` (`CutMarkerViewModel.cs:179`).
The `Snapped` change raised *inside* a resolve is therefore gated too. The explicit `RequestAllThumbnails()` that
follows in both completion branches (`:714`, `:734`) then grabs exactly once, at the resolved time. After this change,
that explicit request is the **only** route to a frame at a resolve (the post-resolve kick contract, § Interfaces).
A drag on a ready row is not pending and grabs as today.

**Latest-wins is untouched.** A skipped request never calls `HandleThumbnailGrabber.Request` (`:995`), so it
neither issues nor cancels a grab. There is no earlier grab to preserve: a row's first grab is the scan-completion
kick (T-108).

## Detail

| Situation | Grab requests today | After |
|---|---|---|
| drag the intro during a scan, then the scan lands | one per settled drag + one at the land | one, at the land |
| an apply adds an outro to a scanning row ([[T-173]]) | the outro kick (`:273`) + one at the land | one per handle, at the land |
| scan fails | any mid-scan grabs + one identity grab (`:714`) | one identity grab |
| drag on a ready row | one per settled drag | unchanged |
| `AddOutro` on a ready row | one kick | unchanged — the handle resolves before the kick (`:264-265`) |
| row removed during a scan | cancelled by `CancelScan` | nothing requested |
| unprobed row (probe not returned: `IsIndexingKeyframes` starts true, `BulkItemViewModel.cs:119`; handles born pending, `:174`, `:262`): an IN/OUT field edit (`CommitCutTime`, `BulkCutView.xaml.cs:326`, write at `:346`) or **+ outro** (`OnAddOutroClicked`, `:283-296`, which drops the outro at zero while the duration is unknown). Neither has a `Duration` guard | one grab per settled write, at the provisional time | none until the scan lands, then one per handle; the chip shows the placeholder until then. If the probe fails, the row becomes `LoadFailed` (next row) |
| `LoadFailed` row (`MarkLoadFailed`, never scanned): any write — field edit or + outro | one grab per settled write, at the identity time | none, ever — the chip stays a placeholder for good (intended; see Edge cases) |

While a handle is pending, its thumbnail chip shows the placeholder, as it already does before a row's first scan
lands (the path is null until a grab resolves). On a `LoadFailed` row that lasts for good.

## Interfaces / contracts

- No public surface change. The private helpers `RequestIntroThumbnail` / `RequestOutroThumbnail` gain the gate.
- It relies on `CutMarkerViewModel.IsSnapPending` (public get) and on only `ResolveSnap` clearing it. That holds
  in code today (`CutMarkerViewModel.cs:179`) and [[T-173]] pins it with a test.
- **The post-resolve kick contract (the second half of the gate).** `ResolveSnap` raises its `Snapped` change while
  the handle is still pending (`CutMarkerViewModel.cs:178-179`), so under the gate that change grabs nothing. The
  explicit request after a resolve becomes the only route to a frame. Contract: **every `ResolveSnap` site on a Bulk
  handle is followed by a frame request for that handle.** All three sites comply today, and each is pinned by a
  test that fails if its request is deleted:
  - failure branch `BulkItemViewModel.cs:711-712` → `:714`, pinned by the scan-failure test below;
  - success branch `:728-729` → `:734`, pinned by the repro test below;
  - `AddOutro` `:265` → `:273`, pinned by `AddOutro_GrabsOutroFrame_ThenClearOutro_DropsIt`
    (`BulkItemThumbnailTests.cs:248`). On a ready row the resolve runs before `OnHandleChanged` subscribes, so the
    kick is that row's only grab.

  A future caller that resolves without requesting leaves a permanent placeholder. The comment at `:732-733`
  describes the kick as a gap-filler for "a ResolveSnap that did NOT move Snapped". It is rewritten in the same
  change to say the kick now carries every grab at the land.
- The test seams already exist:
  - the row constructor's `thumbnailDebounce` / `thumbnailDelay` (`BulkItemViewModel.cs:159-160`, used by
    `BulkItemThumbnailTests.cs:160-161`);
  - `FakeThumbnailService.Requests` / `GetThumbnailCallCount` (`BulkTestFakes.cs:239`);
  - `BulkItemViewModel.InFlightGrabs` (`internal`, `BulkItemViewModel.cs:112-114`, T-137). Pump-based tests await it
    through the existing `Settle` helper (`BulkItemThumbnailTests.cs:178`). The held-scan tests run without the pump,
    so they call `row.InFlightGrabs.Wait(...)` directly;
  - the gated probe (`GatedPaths` / `ReleaseScans`, plus `ScanGate`, a public `TaskCompletionSource` at
    `BulkTestFakes.cs:37`, for failing a held scan).

  No held-scan **harness** exists yet. `BuildReadyRowAsync` (`BulkItemThumbnailTests.cs:139-168`) awaits the scan,
  so it cannot hold one open. No existing test combines `GatedPaths` with the `PumpContext`: under the pump,
  `ScanBodyAsync`'s `ConfigureAwait(true)` continuation (`BulkItemViewModel.cs:687`) is posted to a queue nobody
  drains, so awaiting `CurrentScanTask` hangs. That is the T-159 failure recorded at
  `BulkItemThumbnailTests.cs:382-389`. The new tests therefore build their row directly, without the pump, as the
  repro criterion specifies.
- **Living spec, same commit.**
  - **Amend SPEC-011 I62** (`SPEC-011-bulk-cut-screen.md:271-273`): a `Snapped` change on `IntroEnd` re-requests
    that handle's frame only when the handle is **not snap-pending**. A pending handle's `Snapped` change requests
    nothing; its grab waits for the scan-completion kick (I61 and the new invariant below).
  - **Amend SPEC-011 I64** (`:278-280`): `AddOutro` grabs the outro-start frame at its snapped time once the handle
    is **not snap-pending**. On a ready row that is immediately. On a scanning or unprobed row it is the
    scan-completion kick, and on a `LoadFailed` row it never happens. The `ClearOutro` clause is unchanged.
  - **One new SPEC-011 invariant, I158**, under § Per-row cut-point frame thumbnails
    (`SPEC-011-bulk-cut-screen.md:266`). SPEC-011 ends at I155 today. The id follows the one allocation written word
    for word in G-057's Plan, [[T-173]] and this ticket: T-173 = I156 (run safety) + I157 (CancelScan reservation);
    T-174 = I158 (no per-row cut-point grab while snap-pending). Wording: "no per-row cut-point frame request
    (`IntroThumbnailPath` / `OutroThumbnailPath`, the T-108 grabbers) while that handle is snap-pending; every
    `ResolveSnap` on a Bulk handle is followed by a frame request for that handle, so scan completion grabs once, at
    the resolved time". The scope is deliberate. The profile auto-thumbnail on save (SPEC-007 I61) still grabs at a
    pending `IntroEnd.Snapped` (§ Out of scope), so an unscoped "no frame grab while a handle is snap-pending" would
    be false the day it lands. If I158 is already taken on main at land, the land-time id check (§ Acceptance
    criteria) renumbers it.
  - **`CancelScan` boundary.** [[T-173]] adds I157 (the CancelScan reservation): `CancelScan` is reserved for rows
    leaving the list, and a future caller cancelling a *surviving* row's scan must resolve its handles (D-005 edge 5;
    D-005's table numbered it I159). Under this ticket that caller must also request their frames. Whichever of the
    two tickets lands second writes the combined wording into I157: "resolve its handles and request their frames".
  - The amendments change no invariant count, so this ticket raises `docs/specs/_index.md` by exactly one, recounted
    mechanically. The freshness guard counts ids, not wording, so it cannot catch a stale I62 or I64. The land notes
    quote both before and after.
  - **Refinement over D-005:** its invariant table (`docs/design/D-005/README.md:239-252`) lists only I157 for R5. It
    misses that the gate makes I62 and I64 false, and that the post-resolve kick becomes a contract. Its I157 wording
    ("no frame grab while a handle is snap-pending") is also wider than the change, because it takes in the profile
    auto-thumbnail on save. This ticket adds the amendments and the contract, and scopes the invariant to the per-row
    grabbers. Its id also moves: D-005's I157 for R5 becomes I158 under the allocation above.

## Edge cases

- **A resolve raises `Snapped` while still pending.** That change is gated. The explicit request right after the
  resolve covers it, and it is now the only grab at a resolve: the post-resolve kick contract in § Interfaces.
- **Several rows share the grab gate** (at most 3 concurrent, `ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree`,
  `BulkItemThumbnailTests.cs:339`). Fewer requests only reduce queueing.
- **A handle stuck pending forever** never gets a thumbnail. There are two paths:
  - **`LoadFailed` row — reachable today.** Nothing on this path ever resolves a handle:
    - `PopulateAsync` calls `MarkLoadFailed` (`BulkCutViewModel.cs:1190`, `:1201`) and never starts a scan;
    - `MarkLoadFailed` (`BulkItemViewModel.cs:866-871`) never calls `ResolveSnap`;
    - `IntroEnd` is born pending (`:174`);
    - `AddOutro` on such a row stays pending, because `KeyframesReady` requires `Duration` (`:352`).

    The row stays in `Items`, and its intro chip has no visibility gate (`BulkCutView.xaml:1016-1017`). Today a
    field edit or + outro on it grabs at the identity time. After the gate it never grabs, and the chip stays a
    placeholder for good. That is intended: the source failed to probe.
  - **`CancelScan` on a surviving row** is unreachable today. [[T-173]] records it as an invariant: `CancelScan` is
    reserved for rows leaving the list. Under this ticket, a future caller that cancels a surviving row's scan must
    resolve its handles **and request their frames** (§ Interfaces, `CancelScan` boundary).

## Risks

- An existing test that expects a grab at a pending time needs an explicit expectation change. It is named in
  the land notes, not silently rewritten.
- **Visible change, accepted under OQ2.** Today's provisional grab is not a brief flash. It arrives after the debounce
  (`DefaultThumbnailDebounce` 200 ms, `BulkItemViewModel.cs:95`) and stays on the chip until the scan-completion kick
  (`:734`) replaces it. After this ticket, a scanning row's chip shows the placeholder for the whole remaining scan
  and does not follow drags during that time. The scan includes the row's wait behind the 3-scan gate (SPEC-011 I3),
  which can be long for rows queued in a 20-file drop.
- OQ2 was sealed without this trade-off stated: D-005 (`README.md:295`) lists only "keep grabbing twice" as the
  rejected alternative. The change is cheap to reverse and does not reopen the decision.
- `docs/USER_GUIDE.md:349-351` ("They **update as you drag** each handle") becomes untrue for a scanning row. So
  does T-108's accepted "drag the handle → thumb updates" (`docs/todo/T-108.md:59`). [[T-175]] updates the guide
  line under the criterion quoted in § Dependencies.

## Out of scope

- Which time the grab uses under Exact cut (unchanged by this ticket).
- Grab debounce or concurrency tuning.
- Eligibility and the apply line — [[T-173]].
- **The profile auto-thumbnail on save** (`SaveProfileWithAutoThumbnailAsync`, grab at
  `BulkCutViewModel.cs:1602-1604`, SPEC-007 I61) is deliberately unchanged. Its only gate is a selected row
  (`CanSaveProfile`, `:390`). Saving a profile from a scanning, unprobed or `LoadFailed` row therefore still grabs at
  a pending `IntroEnd.Snapped`. The saved thumbnail is the frame at the requested time, and nothing re-grabs it when
  the scan lands.

  That is the right frame, for two reasons:
  - **A pending `Snapped` equals `Requested`.** The handle is born as an identity snap
    (`CutMarkerViewModel.cs:46-52`) and re-snaps as one while `Keyframes` is empty (`:191-196`). `Keyframes` is set
    only at `BulkItemViewModel.cs:726`, just before `ResolveSnap`, and production starts one scan per row
    (`BulkCutViewModel.cs:1197`).
  - **`Requested` is the time the profile stores** (`BuildProfileFromRow`, `CutProfileApplier.cs:94`).
