## Concept

Each Bulk row shows a small frame at each cut point (T-108). Today that frame is always grabbed at the handle's
**snapped** time, whatever the precision, and at any moment:

- **Lossless, during a keyframe scan.** `Snapped` is provisional — an identity copy of the requested time. The chip
  shows a frame the cut will not use, until the scan lands and a second grab replaces it. Every drag during a scan
  costs one throwaway ffmpeg grab. After [[T-173]], one profile apply across 20 scanning rows costs up to 40.
- **Exact cut, after the scan.** The run cuts at the **requested** time (`EffectiveIntroEnd`,
  `BulkItemViewModel.cs:366`), but the chip shows the nearest keyframe. An Exact user sees a frame up to a GOP away
  from where their cut lands, and a drag that stays within one GOP does not update the chip at all.
- **A precision flip.** Nothing re-grabs, so the chip keeps the previous mode's frame.

**The outcome:** the chip shows the frame the run will cut at, in both precisions, to the thumbnail cache's
one-second granularity:
- **Lossless** waits for the snap and grabs once.
- **Under Exact cut**, every change of the requested time grabs right away once the row has a known duration —
  during the scan and after it. A precision flip grabs whenever it moves a handle's grab time to a new known time.
- **A handle whose cut time becomes provisional** gets its chip cleared back to the placeholder.
- **A row's first frame** otherwise arrives when its scan lands, as today (T-108).

This is the user's decision of 2026-09-13 ([[G-057]] § Decisions 1).

## Design

**1. Grab at the effective cut time; skip only while it is provisional.** One rule, shared by both handles:

```csharp
/// <summary>
/// The time the run will cut this handle at, or null while that time is still provisional (D-005 R5, G-057 decision 1):
/// no known duration yet, or Lossless with the snap still pending. Exact cut is never provisional — it cuts where
/// the user set it.
/// </summary>
private TimeSpan? GrabTime(CutMarkerViewModel handle) =>
    Duration is null ? null
    : _exactCut ? handle.Requested
    : handle.IsSnapPending ? null
    : handle.Snapped;

private void RequestIntroThumbnail()
{
    if (GrabTime(IntroEnd) is { } time)
    {
        _introGrabber?.Request(Path, time);
    }
}

private void RequestOutroThumbnail()
{
    if (OutroStart is { } outro && GrabTime(outro) is { } time)
    {
        _outroGrabber?.Request(Path, time);
    }
}
```

The non-null branch agrees with `EffectiveIntroEnd` / `EffectiveOutroStart` (`BulkItemViewModel.cs:366`,
`:369-370`), the cut-time pair the run's eligibility already reads.

**2. The helpers are the choke point.** Every path to `IntroThumbnailPath` / `OutroThumbnailPath` converges on
`RequestIntroThumbnail` (`:311`) and `RequestOutroThumbnail` (`:314-320`):

| Call site | Line | Today | After |
|---|---|---|---|
| `OnHandleChanged` on a handle change | `:886`, `:890`, `:894` | grabs on every `Snapped` change | grabs when the **effective** time's property changes — step 3 |
| `AddOutro` explicit kick | `:273` | unconditional, at `Snapped` | through the helper: skipped while the new handle's time is provisional |
| `ScanBodyAsync` failure branch → `RequestAllThumbnails` | `:714` | after `ResolveSnap`, at `Snapped` | same point, at the effective time |
| `ScanBodyAsync` success branch → `RequestAllThumbnails` | `:734` | after `ResolveSnap`, at `Snapped` | same point, at the effective time |
| `SetExactCut` — **new** | `:448-465` | never grabs | follows each handle's grab time across the flip — step 4 |

The profile auto-thumbnail on save (`BulkCutViewModel.cs:1602-1604`) is a separate grab path that does not go
through these helpers. It is unchanged (§ Out of scope).

**3. Trigger on the property that is the cut.** In `OnHandleChanged`, the grab reacts to `Requested` under Exact and
to `Snapped` in Lossless:

```csharp
var cutProperty = _exactCut ? nameof(CutMarkerViewModel.Requested) : nameof(CutMarkerViewModel.Snapped);
if (e.PropertyName == cutProperty)
{
    if (ReferenceEquals(sender, IntroEnd)) RequestIntroThumbnail();
    else if (ReferenceEquals(sender, OutroStart)) RequestOutroThumbnail();
}
```

- Lossless: a drag that snaps to the same keyframe raises no `Snapped` change and grabs nothing, as today — the cut
  did not move.
- Exact: every drag moves the cut, so every settled drag re-grabs, even within one GOP.

**4. A precision flip follows each handle's grab time.** `Snapped != Requested` is **not** the right test: a
snap-pending handle always has `Snapped == Requested` (an identity snap, `CutMarkerViewModel.cs:46-51`), yet its grab
time does change on a flip. In `SetExactCut`, after the early return (`:450-453`) and **before** `_exactCut = exact`,
capture each handle's `GrabTime`; after `RecomputeAll()` (`:464`), compare:

| Grab time before → after | When | Action |
|---|---|---|
| null → null | a row with no known duration — unprobed or load-failed — in either direction | nothing |
| t → t | a handle whose snap offset is zero | nothing |
| null → t | **Lossless → Exact on a scanning row with a known duration** | request the frame |
| t₁ → t₂ | a scanned row with a snap offset (either direction) | request the frame |
| t → null | **Exact → Lossless on a snap-pending handle** | cancel that handle's grabber and set its thumbnail path to null — exactly what `ClearOutro` does (`:283-284`) — so the chip shows the placeholder |

```csharp
// T-174: the chip shows the cut the run will make — follow each handle's grab time across the flip.
private void FollowGrabTime(CutMarkerViewModel handle, TimeSpan? before, HandleThumbnailGrabber? grabber,
    Action clearPath, Action request)
{
    var after = GrabTime(handle);
    if (after is null)
    {
        if (before is not null)
        {
            grabber?.Cancel();
            clearPath();
        }
    }
    else if (after != before)
    {
        request();
    }
}
```

A fresh row [[T-176]] starts in Exact from `AddFilesAsync` has no `Duration`, so its grab time is null on both
sides: a drop under Exact fires no burst.

**5. `Cancel()` must also drop a result that was already posted.** Today `HandleThumbnailGrabber.Cancel()`
(`BulkItemViewModel.cs:1003-1020`) cancels the request's token but leaves `_requestId` unchanged. `GrabAsync` checks
the token only **before** `_postResult.Report` (`:1049-1054`), and `OnResolved` drops a post only when
`result.Id != _requestId` (`:1076-1084`). A grab that finished just before the cancel therefore still commits its
frame after the chip was cleared. Fix: `Cancel()` advances `_requestId` **first — before** its `if (cts is null) return;`
(`BulkItemViewModel.cs:1005-1010`). A grab that has already finished has nulled `_requestCts` in its `finally`
(`:1066-1069`), so an increment placed after that early return would never run in exactly the case it exists for.
Any post already queued is then dropped.
`Request` calls `Cancel()` then `++_requestId`; the extra increment is harmless. This also closes the same window in
`ClearOutro` and in `CancelScan`, whose "commits no frame path" promise (SPEC-011 I66) now holds even for a grab that
had already finished.

**6. Ordering and the post-resolve kick.** `ResolveSnap()` runs `Resnap()` *before* `IsSnapPending = false`
(`CutMarkerViewModel.cs:179`). In Lossless, the `Snapped` change raised *inside* a resolve is still pending, so the
helper skips it. Under Exact, a resolve changes `Snapped`, not `Requested`, so it raises no grab trigger. Either way,
the explicit `RequestAllThumbnails()` after the resolve (`:714`, `:734`) is the grab at the land. **Contract: every
`ResolveSnap` site on a Bulk handle is followed by a frame request for that handle.** All three sites comply today:
failure `:711-712` → `:714`, success `:728-729` → `:734`, `AddOutro` `:265` → `:273`. The comment at `:732-733`,
which calls the kick a gap-filler for "a ResolveSnap that did NOT move Snapped", is rewritten to say the kick now
carries every Lossless grab at the land.

**7. The one duplicate is free.** Under Exact, a handle written during the scan was already grabbed at its requested
time, and the land kick requests the same time again. `FfmpegThumbnailService` caches by `(inputPath, time floored to
a 1 s bucket)` and returns a cached file **without running ffmpeg** (`src/Core/Thumbnails/FfmpegThumbnailService.cs:16-18`),
so the second request is a cache hit. No dedupe code is added.

## Detail

| Situation | Grab requests today | After |
|---|---|---|
| Lossless — drag during a scan, then the scan lands | one per settled drag (at the provisional time) + one at the land | one, at the land, at the snapped time |
| Lossless — an apply adds an outro to a scanning row ([[T-173]]) | the kick (`:273`) + one at the land | one per handle, at the land |
| Lossless — scan fails | any mid-scan grabs + one identity grab (`:714`) | one identity grab |
| Lossless — drag on a ready row | one per settled drag that moves `Snapped` | unchanged |
| **Exact — drag during a scan** | one per settled drag, at the provisional `Snapped` (= requested) | one per settled drag, at the requested time; the land request is a cache hit |
| **Exact — drag on a ready row within one GOP** | none (`Snapped` unchanged) — the chip stays on the keyframe | one, at the new requested time |
| **Exact — ready row after the scan** | chip shows the nearest keyframe | chip shows the requested (cut) time |
| **Flip on a scanned row with a snap offset** | none — the chip keeps the old mode's frame | one per moved handle |
| **Lossless → Exact on a scanning row with a known duration** | none — placeholder until the land | one per handle, at the requested time |
| **Exact → Lossless on a scanning row whose chip shows an Exact frame** | none — the Exact frame stays until the land, though Lossless will cut elsewhere | that grab cancelled, chip back to the placeholder, no request |
| Flip on an unprobed or load-failed row, or on a resolved zero-offset handle | none | none |
| Exact — a write made before the row's probe returned | one per settled write, at the provisional time | none then (no duration); the first frame arrives on the next write, a flip back into Exact, or the land |
| `AddOutro` on a ready row | one kick | unchanged (effective time, resolved first `:264-265`) |
| Unprobed row (no `Duration`; `IsIndexingKeyframes` starts true, `:119`) — field edit or + outro | one per settled write | none while it has no duration |
| `LoadFailed` row (`MarkLoadFailed`, `:866-871`; `Duration` stays null) | one per settled write | none, ever — the chip keeps its placeholder (intended) |
| Row removed during a scan | cancelled by `CancelScan` | nothing requested, and nothing already posted can commit (step 5) |

While a handle's grab time is provisional, its chip shows the placeholder: it has not been grabbed yet, or the flip
in step 4 cleared it.

**What the user can tell apart.** An unprobed row and a probed row whose scan is still running both read `loading…`
(`RowState.Loading`, `BulkItemViewModel.cs:431-434`; the label at `BulkCutView.xaml.cs:640`). So the chip is not a
function of that label:
- in Lossless, a `loading…` row's chip is the placeholder;
- under Exact, a `loading…` row **with a known duration** shows its cut frame as soon as a cut is written or the
  precision flips; before its probe returns, it shows the placeholder;
- a load-failed row always shows the placeholder.

An outro added before the probe returns (+ outro places it at 0 while the duration is unknown, *Set outro-start here*
needs only a selection and a ready player) gets its frame once the probe sets `Duration` and the scan lands.

**What "the frame the run will cut at" means precisely.** The service floors the time to a one-second bucket, so
the chip shows the frame at the cut time rounded down to the whole second, in both precisions. That granularity is
unchanged (§ Out of scope). The ticket's promise is *the right cut time*, not frame accuracy.

## Interfaces / contracts

- No public surface change. Inside `BulkItemViewModel`:

  - the nested `HandleThumbnailGrabber.Cancel()` advances `_requestId`.
- It relies on `CutMarkerViewModel.IsSnapPending` (public get), and on only `ResolveSnap` clearing it. That is true
  in code today (`CutMarkerViewModel.cs:179`), and [[T-173]] pins it with a test.
- **Test seams — all exist, with two rules the tests must follow:**
  - the row constructor's `thumbnailDebounce` / `thumbnailDelay` (`BulkItemViewModel.cs:159-160`), and the
    `Immediate` seam (`BulkItemThumbnailTests.cs:129-130`);

  - the gated probe (`GatedPaths` / `ReleaseScans`) and its public `ScanGate` (`BulkTestFakes.cs:37`).

  **Rule 1 — without the pump, assert on `Requests` only.** A committed path arrives through `Progress<PathResult>`
  (`:989`, posted at `:1054`), which runs after `InFlightGrabs` completes. `InFlightGrabs.Wait(...)` without a pump
  settles *requests*, not *paths*; a path assertion there is the T-137 / T-159 flake class.

  **Rule 2 — a held scan cannot be awaited under the pump** (the T-159 hang, `BulkItemThumbnailTests.cs:382-389`). A
  test that needs both a held scan and a committed path installs a `PumpContext` **before** constructing the row, so
  both grabbers' `Progress` capture it, then restores the previous context **before** `StartKeyframeScanAsync()`, so
  the scan's continuation does not park in the pump. It never awaits `CurrentScanTask` while the scan is held, and
  reads paths only after `row.InFlightGrabs.Wait(...)` and `pump.PumpSettled()`.

      Exact `loading…` row with a known duration shows its frame. If it does not, fix it before landing.

## Edge cases

- **A resolve raises `Snapped` while still pending (Lossless).** The helper skips it; the land kick covers it.
- **A resolve under Exact.** `Snapped` changes but `Requested` does not, so there is no trigger; the land kick
  re-requests the same requested time, which the service's cache answers without ffmpeg.
- **A flip back and forth mid-scan.** Exact → Lossless clears the chip; Lossless → Exact requests again. The second
  request is a cache hit.
- **`Duration` arriving under Exact after an earlier write.** The `Duration` setter (`:197-206`) raises no grab, so
  the first frame waits for the next write, a flip back into Exact, or the land. That is stated in § Detail rather than adding a grab
  to the setter, which would request a frame for every dropped row under Exact.
- **Several rows share the grab gate** (at most 3 concurrent — I67, `ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree`,
  `BulkItemThumbnailTests.cs:339`). Exact grabs during scans, and a Lossless → Exact flip over many scanning rows,
  add queueing on that gate — never on the scan gate.
- **A handle stuck pending forever** never gets a Lossless thumbnail. Reachable today through a `LoadFailed` row,
  which has no duration either, so it gets no thumbnail in either precision. That is intended: the source failed to
  probe. The `CancelScan`-on-a-surviving-row path is unreachable today and pinned by [[T-173]]'s I157.

## Risks

- **Visible change, both ways.**
  - In Lossless, a scanning row's chip shows the placeholder for the whole remaining scan, including its wait behind
    the 3-scan gate (SPEC-011 I3), and does not follow drags during that time.
  - Under Exact, the chip moves on every settled drag and on every flip, and shows a different frame than before.

  Both follow decision 1.
- **More grabs under Exact.** A Lossless → Exact flip while many rows scan requests up to two frames per scanning row
  with a duration. Each is a frame the user will see; the 3-grab gate bounds them, and later duplicates are cache
  hits.
- **The grabber's cancel changes for every caller.** `ClearOutro` and `CancelScan` also use `Cancel()`. Advancing
  `_requestId` there only drops posts that the cancel already meant to drop; their existing tests (`:286`, `:306`)
  stay green.
- An existing test that expects a grab at a pending time, or no grab on a flip, needs an explicit expectation change,
  named in the land notes.

## Out of scope

- **The thumbnail service's one-second bucket** (`FfmpegThumbnailService.cs:16-18`). The chip shows the frame at the
  cut time rounded down to the whole second, in both modes — unchanged.
- A grab when `Duration` arrives (see § Edge cases).
- Grab debounce or concurrency tuning.
- Eligibility and the apply line — [[T-173]]. Precision inheritance for added rows and outros — [[T-176]].
- **The profile auto-thumbnail on save** (`SaveProfileWithAutoThumbnailAsync`, `BulkCutViewModel.cs:1602-1604`,
  SPEC-007 I61) still grabs at `IntroEnd.Snapped`.
  - For a snap-pending handle, that equals `Requested` — the time the profile stores (`CutProfileApplier.cs:94`).
  - For a ready row under Exact, it is the keyframe frame. That older mismatch is not changed here.
