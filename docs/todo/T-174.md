## Concept

Each Bulk row shows a small frame at each cut point (T-108). Today that frame is always grabbed at the handle's
**snapped** time, whatever the precision, and at any moment:

- **Lossless, during a keyframe scan.** `Snapped` is provisional — an identity copy of the requested time. The chip
  shows a frame the cut will not use, until the scan lands and a second grab replaces it. Every drag during a scan
  costs one throwaway ffmpeg grab. After [[T-173]], one profile apply across 20 scanning rows costs up to 40.
- **Exact cut, after the scan.** The run cuts at the **requested** time (`EffectiveIntroEnd`,
  `BulkItemViewModel.cs:366`), but the chip shows the nearest keyframe. An Exact user sees a frame up to a GOP away
  from where their cut lands, and a drag that stays within one GOP does not update the chip at all.

**The outcome:** the chip shows the frame the run will cut at, in both precisions (to the thumbnail cache's
one-second granularity). In Lossless it waits for the snap and grabs once. Under Exact it follows the requested
time right away, during the scan and after it. This is the user's decision of 2026-09-13 ([[G-057]] § Decisions 1).

## Design

**1. Grab at the effective cut time; skip only while it is provisional.** One rule, shared by both handles:

```csharp
/// <summary>
/// The time the run will cut this handle at, or null while that time is still provisional (D-005 R5, G-057 decision 1):
/// no known duration yet, or Lossless with the snap still pending. Exact cut is never provisional — it cuts where
/// the user set it.
/// </summary>
private TimeSpan? GrabTime(CutMarkerViewModel handle) =>
    Duration is null ? null
    : _exactCut ? handle.Requested
    : handle.IsSnapPending ? null
    : handle.Snapped;

private void RequestIntroThumbnail()
{
    if (GrabTime(IntroEnd) is { } time)
    {
        _introGrabber?.Request(Path, time);
    }
}

private void RequestOutroThumbnail()
{
    if (OutroStart is { } outro && GrabTime(outro) is { } time)
    {
        _outroGrabber?.Request(Path, time);
    }
}
```

The non-null branch agrees with `EffectiveIntroEnd` / `EffectiveOutroStart` (`BulkItemViewModel.cs:366`,
`:369-370`), the cut-time pair the run's eligibility already reads.

**2. The helpers are the choke point.** Every path to `IntroThumbnailPath` / `OutroThumbnailPath` converges on
`RequestIntroThumbnail` (`:311`) and `RequestOutroThumbnail` (`:314-320`):

| Call site | Line | Today | After |
|---|---|---|---|
| `OnHandleChanged` on a handle change | `:886`, `:890`, `:894` | grabs on every `Snapped` change | grabs when the **effective** time's property changes — see step 3 |
| `AddOutro` explicit kick | `:273` | unconditional, at `Snapped` | through the helper: skipped while the new handle's time is provisional |
| `ScanBodyAsync` failure branch → `RequestAllThumbnails` | `:714` | after `ResolveSnap`, at `Snapped` | same point, at the effective time |
| `ScanBodyAsync` success branch → `RequestAllThumbnails` | `:734` | after `ResolveSnap`, at `Snapped` | same point, at the effective time |
| `SetExactCut` — **new** | `:447-464` | never grabs | re-grabs a handle whose effective time moved — see step 4 |

The profile auto-thumbnail on save (`BulkCutViewModel.cs:1602-1604`) is a separate grab path that does not go
through these helpers. It is unchanged (§ Out of scope).

**3. Trigger on the property that is the cut.** In `OnHandleChanged`, the grab reacts to `Requested` under Exact and
to `Snapped` in Lossless:

```csharp
var cutProperty = _exactCut ? nameof(CutMarkerViewModel.Requested) : nameof(CutMarkerViewModel.Snapped);
if (e.PropertyName == cutProperty)
{
    if (ReferenceEquals(sender, IntroEnd)) RequestIntroThumbnail();
    else if (ReferenceEquals(sender, OutroStart)) RequestOutroThumbnail();
}
```

- Lossless: a drag that snaps to the same keyframe raises no `Snapped` change and grabs nothing, as today — the cut
  did not move.
- Exact: every drag moves the cut, so every settled drag re-grabs, even within one GOP.

**4. A precision flip re-grabs only a handle whose cut moved.** At the end of `SetExactCut`, after `RecomputeAll()`
(`:463`):

```csharp
// T-174: the chip shows the cut the run will make — re-grab a handle whose effective time just moved.
if (IntroEnd.Snapped != IntroEnd.Requested) RequestIntroThumbnail();
if (OutroStart is { } outro && outro.Snapped != outro.Requested) RequestOutroThumbnail();
```

- A scanned row with a non-zero snap offset re-grabs: Snapped → Requested going to Exact, Requested → Snapped going
  back.
- A pending, unprobed or zero-offset handle has `Snapped == Requested`, so nothing is requested. That includes every
  fresh row [[T-176]] starts in Exact from `AddFilesAsync`, so a drop under Exact fires no burst of grabs.

**5. Ordering and the post-resolve kick.** `ResolveSnap()` runs `Resnap()` *before* `IsSnapPending = false`
(`CutMarkerViewModel.cs:179`). In Lossless, the `Snapped` change raised *inside* a resolve is still pending, so the
helper skips it. Under Exact, a resolve changes `Snapped`, not `Requested`, so it raises no grab trigger. Either way,
the explicit `RequestAllThumbnails()` after the resolve (`:714`, `:734`) is the grab at the land. **Contract: every
`ResolveSnap` site on a Bulk handle is followed by a frame request for that handle.** All three sites comply today:
failure `:711-712` → `:714`, success `:728-729` → `:734`, `AddOutro` `:265` → `:273`. The comment at `:732-733`,
which calls the kick a gap-filler for "a ResolveSnap that did NOT move Snapped", is rewritten to say the kick now
carries every Lossless grab at the land.

**6. The one duplicate is free.** Under Exact, a handle written during the scan was already grabbed at its requested
time, and the land kick requests the same time again. `FfmpegThumbnailService` caches by `(inputPath, time floored to
a 1 s bucket)` and returns a cached file **without running ffmpeg** (`src/Core/Thumbnails/FfmpegThumbnailService.cs:16-18`),
so the second request is a cache hit. No dedupe code is added.

## Detail

| Situation | Grab requests today | After |
|---|---|---|
| Lossless — drag during a scan, then the scan lands | one per settled drag (at the provisional time) + one at the land | one, at the land, at the snapped time |
| Lossless — an apply adds an outro to a scanning row ([[T-173]]) | the kick (`:273`) + one at the land | one per handle, at the land |
| Lossless — scan fails | any mid-scan grabs + one identity grab (`:714`) | one identity grab |
| Lossless — drag on a ready row | one per settled drag that moves `Snapped` | unchanged |
| **Exact — drag during a scan** | one per settled drag, at the provisional `Snapped` (= requested) | one per settled drag, at the requested time; the land request is a cache hit |
| **Exact — drag on a ready row within one GOP** | none (`Snapped` unchanged) — the chip stays on the keyframe | one, at the new requested time |
| **Exact — ready row after the scan** | chip shows the nearest keyframe | chip shows the requested (cut) time |
| **Precision flip on a scanned row with a snap offset** | none — the chip keeps the old mode's frame | one per moved handle |
| Precision flip on a pending, unprobed or zero-offset row | none | none |
| `AddOutro` on a ready row | one kick | unchanged (effective time, resolved first `:264-265`) |
| Unprobed row (no `Duration`; `IsIndexingKeyframes` starts true, `:119`) — field edit or + outro | one per settled write | none until the row has a duration; then as above |
| `LoadFailed` row (`MarkLoadFailed`, `:866-871`; `Duration` stays null) | one per settled write | none, ever — the chip keeps its placeholder (intended) |
| Row removed during a scan | cancelled by `CancelScan` | nothing requested |

While a handle's grab time is provisional, its chip shows the placeholder, as it does today before a row's first
scan lands (the path is null until a grab resolves).

**What "the frame the run will cut at" means precisely.** The service floors the time to a one-second bucket, so
the chip shows the frame at the cut time rounded down to the whole second, in both precisions. That granularity is
unchanged (§ Out of scope). The ticket's promise is *the right cut time*, not frame accuracy.

## Interfaces / contracts

- No public surface change. Private `RequestIntroThumbnail` / `RequestOutroThumbnail` read the new private
  `GrabTime`. `OnHandleChanged`'s trigger follows the precision, and `SetExactCut` gains the moved-handle re-grab.
- It relies on `CutMarkerViewModel.IsSnapPending` (public get), and on only `ResolveSnap` clearing it. That is true
  in code today (`CutMarkerViewModel.cs:179`), and [[T-173]] pins it with a test.
- **Test seams — all exist:**
  - the row constructor's `thumbnailDebounce` / `thumbnailDelay` (`BulkItemViewModel.cs:159-160`), and the
    `Immediate` seam (`BulkItemThumbnailTests.cs:129-130`);
  - `FakeThumbnailService.Requests` / `GetThumbnailCallCount` (`BulkTestFakes.cs:239`). The fake records the
    **requested** time, with no bucketing, so tests can tell 10.4 s from 10.8 s;
  - `BulkItemViewModel.InFlightGrabs` (`internal`, `:112-114`, T-137), awaited through `Settle`
    (`BulkItemThumbnailTests.cs:178`) under the pump, or `row.InFlightGrabs.Wait(...)` directly without it;
  - `BuildReadyRowAsync` (`:139-168`) for ready rows, the gated probe (`GatedPaths` / `ReleaseScans`) and its public
    `ScanGate` (`BulkTestFakes.cs:37`, `TrySetException` fails a held scan).

  **No held-scan harness exists.** `BuildReadyRowAsync` awaits the scan, and awaiting `CurrentScanTask` under the
  `PumpContext` hangs (the T-159 note at `BulkItemThumbnailTests.cs:382-389`). The held-scan tests therefore build
  the row directly, without the pump (§ Acceptance, repro).
- **Living spec, same commit** (`docs/specs/SPEC-011-bulk-cut-screen.md`):
  - amend **I61** (`:267-270`) — the grab on scan-resolve targets the handle's **effective cut time**: the snapped
    time in Lossless, the requested time under Exact;
  - amend **I62** (`:271-273`) — a change of the intro's effective cut time re-requests its frame: `Snapped` in
    Lossless (once not snap-pending), `Requested` under Exact;
  - amend **I63** (`:274-277`) — "only the final snapped cut reaches the service" becomes the final **effective** cut;
  - amend **I64** (`:278-280`) — `AddOutro` grabs the outro frame at its effective cut time once that time is not
    provisional. On a ready row that is immediate. On a scanning Lossless row it is the land kick. On a row without a
    duration it is never. The `ClearOutro` clause is unchanged;
  - amend **I93** — a precision flip is still pure VM state with **no probe work**. It now re-requests a cut-point
    frame for any handle whose effective time moved (`Snapped ≠ Requested`);
  - **new I158**, under § Per-row cut-point frame thumbnails: "a per-row cut-point frame is requested only at the
    handle's effective cut time, and never while that time is provisional — no known duration, or Lossless and
    snap-pending; every `ResolveSnap` on a Bulk handle is followed by a frame request for that handle". The scope is

  The ids are fixed across the epic ([[G-057]] § Plan): T-173 = I156 + I157, **T-174 = I158**, T-176 adds none.

## Edge cases

- **A resolve raises `Snapped` while still pending (Lossless).** The helper skips it; the land kick covers it.
- **A resolve under Exact.** `Snapped` changes but `Requested` does not, so there is no trigger; the land kick
  re-requests the same requested time, which the service's cache answers without ffmpeg.
- **Several rows share the grab gate** (at most 3 concurrent — I67, `ManyRows_ShareOneGate_BoundsConcurrentGrabsToThree`,
  `BulkItemThumbnailTests.cs:339`). Exact grabs during scans add queueing on that gate, never on the scan gate.
- **A handle stuck pending forever** never gets a Lossless thumbnail. Reachable today through a `LoadFailed` row,
  which has no duration either, so it gets no thumbnail in either precision. That is intended: the source failed to
  probe. The `CancelScan`-on-a-surviving-row path is unreachable today and pinned by [[T-173]]'s I157.

## Risks

- **Visible change, both ways.**
  - In Lossless, a scanning row's chip shows the placeholder for the whole remaining scan, including its wait behind
    the 3-scan gate (SPEC-011 I3), and does not follow drags during that time.
  - Under Exact, the chip now moves on every settled drag and shows a different frame than before.

  Both follow decision 1.
- **More grabs under Exact during scans.** Each is a frame the user will see, bounded by the 3-grab gate, and the
  land duplicates are cache hits.
- An existing test that expects a grab at a pending time needs an explicit expectation change, named in the land
  notes.

## Out of scope

- **The thumbnail service's one-second bucket** (`FfmpegThumbnailService.cs:16-18`). The chip shows the frame at the
  cut time rounded down to the whole second, in both modes — unchanged.
- Grab debounce or concurrency tuning.
- Eligibility and the apply line — [[T-173]]. Precision inheritance for added rows and outros — [[T-176]].
- **The profile auto-thumbnail on save** (`SaveProfileWithAutoThumbnailAsync`, `BulkCutViewModel.cs:1602-1604`,
  SPEC-007 I61) still grabs at `IntroEnd.Snapped`.
  - For a snap-pending handle, that equals `Requested` — the time the profile stores (`CutProfileApplier.cs:94`).
  - For a ready row under Exact, it is the keyframe frame. That older mismatch is not changed here.
