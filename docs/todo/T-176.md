## Concept

Switch the Bulk Cut tab to **Exact cut**, then add videos. The new rows ignore Exact:
- each is judged on its keyframe-**snapped** time and keeps its snap note;
- Run cuts them exactly, at the **requested** time.

So a coarse-GOP row whose request snaps back to 0 is excluded as "nothing to trim yet". Exact would perform that
trim, so the video silently drops out of the batch with a reason that is untrue.

Separately, an outro handle added after the toggle shows a note such as `→ 00:50.0 (−1.0s)`. That covers
**+ outro**, *Set outro-start here*, a profile tail and ⧉. The note advertises a snap Exact will not make.

Both are the same class as T-127 review finding #1: eligibility must be measured against the cut the batch
actually performs (`BulkItemViewModel.cs:360-362`). The G-057 review panel found them. They predate D-005. The
user decided on 2026-09-13 to own them in this ticket, so [[T-173]] stays about applying cuts during scans.

## Design

Two missing propagations of the tab's precision:

| Gap | Today | Fix |
|---|---|---|
| A row added after the toggle | `AddFilesAsync` builds each row without precision (`BulkCutViewModel.cs:1139-1149`). Only the `ExactCut` setter calls `SetExactCut`, and only over the rows in `Items` at that moment (`:483-489`) | call `item.SetExactCut(_exactCut)` right after construction, before `item.PropertyChanged += OnItemChanged` (`:1150`) |
| An outro handle added after the toggle | `SetExactCut` (`BulkItemViewModel.cs:447-464`) sets `SuppressSnapNote` only on the handles that exist at the flip (`:455-459`), and returns early when precision is unchanged (`:449-452`). `AddOutro` (`:260-274`) builds a new handle without it | in `AddOutro`, set `handle.SuppressSnapNote = _exactCut` right after constructing the handle, before `OutroStart = handle` subscribes `OnHandleChanged` |

**Calling `SetExactCut` on a fresh row is safe.** The row is unprobed: `Duration` is null and `KeyframesReady` is
false. `SetExactCut` only sets `_exactCut` and the intro handle's `SuppressSnapNote`, then calls `RecomputeAll()`.
That is no probe work (SPEC-011 I93). Under Lossless it returns at once, because a new row starts with `_exactCut`
false.

**Afterwards, an added row behaves exactly like a row that was in the list when the toggle flipped:**
- eligibility (`IsValidCut`, `IsNoOpTrim`, `KeptDuration`) is measured on `Requested`, through
  `EffectiveIntroEnd` / `EffectiveOutroStart` (`BulkItemViewModel.cs:366-370`);
- the snap note is hidden;
- both match the run, which is sent `CutPrecision.Exact` (`BulkCutViewModel.cs:2161`) with items built from
  `Requested` (`BuildBulkTrimItem`, `BulkItemViewModel.cs:647`).

## Detail

| Situation | Today | After |
|---|---|---|
| Exact on, then add a coarse-GOP video whose intro request snaps back to 0 | excluded as a no-op ("nothing to trim yet"), note `→ 00:00.0 (−3.0s)`, Run skips it | eligible, no note, Run cuts at the requested 3 s |
| Exact on, then drop files onto the tab | same as above | same fix — every add path goes through `AddFilesAsync` |
| Exact on, then + outro / *Set outro-start here* / a profile tail / ⧉ adds an outro | the outro note shows (`HasSnapNote` true) | hidden |
| Exact on, then back to Lossless | — | the existing I91 propagation restores the notes on every row, added rows and outros included |
| Lossless throughout | notes show | unchanged (`SetExactCut(false)` returns at once) |

- **Living spec, same commit.** Amend SPEC-011 **I91** (`SPEC-011-bulk-cut-screen.md:459-463`) in place:
  precision reaches every row in `Items` **and every row added later** (`AddFilesAsync` → `SetExactCut`), and every
  outro handle **added later** inherits `SuppressSnapNote` (`AddOutro`). No new invariant id, so the
  `docs/specs/_index.md` count is unchanged. The freshness guard stays green.
- **Shared surface, no ordering dependency.** [[T-173]] also exercises Exact-cut apply cases, and [[T-174]] makes a

  fresh, unprobed row requests no frame: T-174 re-grabs on a flip only a handle whose effective cut time moved
  (`Snapped ≠ Requested`), and a fresh row's handles are identity snaps with no `Duration`.
- **Consumed by** [[T-175]] (the CHANGELOG line).

## Edge cases

- **`SetExactCut` on an unprobed row.** `RecomputeAll` runs on a row without `Duration`. Every derived property
  already handles a null `Duration`, because they all recompute when the probe lands.
- **A path already in the list.** The dedup `continue` (`BulkCutViewModel.cs:1134`) returns before construction,
  so it is unaffected.

## Dependencies

None (`blocked-by: []`). Independent of [[T-173]] and [[T-174]].

## Risks

- **Rows dropped under Exact change verdict.** A coarse-GOP row that was excluded as "nothing to trim" becomes
  eligible and runs. That is the verdict the toggle already gives rows that were in the list when it flipped
  (T-127), and the run was already cutting at `Requested`.
- `ExactCut` is not persisted — it is referenced only at `BulkCutViewModel.cs:180`, `:478-496` and `:2161`. So
  today the bug bites only after toggling within a session. The fix does not change that.
