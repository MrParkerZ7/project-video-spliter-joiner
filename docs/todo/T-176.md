## Concept

Switch the Bulk Cut tab to **Exact cut**, then add videos. The new rows ignore Exact:
- each is judged on its keyframe-**snapped** time and keeps its snap note;
- Run cuts them exactly, at the **requested** time.

So a coarse-GOP row whose request snaps back to 0 is excluded as "nothing to trim yet". Exact would perform that
trim, so the video silently drops out of the batch with a reason that is untrue. While the new rows scan, every one
of them also reads `→ snapping…`, under a precision that never snaps.

Separately, an outro handle added after the toggle shows a note such as `→ 00:44.0 (−1.0s)`. That covers
**+ outro**, *Set outro-start here*, a profile tail and ⧉, on a ready row or a scanning one. The note advertises
a snap Exact will not make.

Both are the same class as T-127 review finding #1: eligibility must be measured against the cut the batch
actually performs (`BulkItemViewModel.cs:360-362`). The G-057 review panel found them. They predate D-005. The
user decided on 2026-09-13 to own them in this ticket, so [[T-173]] stays about applying cuts during scans.

## Design

Two missing propagations of the tab's precision:

| Gap | Today | Fix |
|---|---|---|
| A row added after the toggle | `AddFilesAsync` builds each row without precision (`BulkCutViewModel.cs:1139-1149`). Only the `ExactCut` setter calls `SetExactCut`, and only over the rows in `Items` at that moment (`:483-489`) | call `item.SetExactCut(_exactCut)` right after construction, before `item.PropertyChanged += OnItemChanged` (`:1150`) — so it holds from the row's first moment, before its probe and scan |
| An outro handle added after the toggle | `SetExactCut` (`BulkItemViewModel.cs:448-465`) sets `SuppressSnapNote` only on the handles that exist at the flip (`:456-460`), and returns early when precision is unchanged (`:450-453`). `AddOutro` (`:260-274`) builds a new handle without it | in `AddOutro`, set `handle.SuppressSnapNote = _exactCut` right after constructing the handle — **before** the `if (KeyframesReady)` resolve and before `OutroStart = handle` subscribes `OnHandleChanged`, so a handle added to a scanning row is covered too |

**Calling `SetExactCut` on a fresh row is safe.** The row is unprobed: `Duration` is null and `KeyframesReady` is
false. `SetExactCut` only sets `_exactCut` and the intro handle's `SuppressSnapNote`, then calls `RecomputeAll()` (with
[[T-174]] landed it also follows each handle's grab time — an unprobed row has none before or after, so nothing is
requested).
That is no probe work (SPEC-011 I93). Under Lossless it returns at once, because a new row starts with `_exactCut`
false.

**Afterwards, an added row behaves exactly like a row that was in the list when the toggle flipped:**
- eligibility (`IsValidCut`, `IsNoOpTrim`, `KeptDuration`) is measured on `Requested`, through
  `EffectiveIntroEnd` / `EffectiveOutroStart` (`BulkItemViewModel.cs:366-370`);
- the snap note is hidden, from the moment the row appears;
- both match the run, which is sent `CutPrecision.Exact` (`BulkCutViewModel.cs:2161`) with items built from
  `Requested` (`BuildBulkTrimItem`, `BulkItemViewModel.cs:647`).

## Detail

| Situation | Today | After |
|---|---|---|
| Exact on, then add a file — **scan still running** | `00:00.0 → snapping…` | note hidden; chip `loading…`; no exclusion reason; Run waits for the scan |
| Exact on, then add a coarse-GOP video whose intro request snaps back to 0 — scan landed | excluded as a no-op ("nothing to trim yet"), note `→ 00:00.0 (−3.0s)`, Run skips it | eligible, no note, Run cuts at the requested 3 s |
| Exact on, then add a file whose **probe fails** | `load failed` plus a permanent `→ snapping…` (`MarkLoadFailed` never resolves the snap, `:866-871`) | note hidden under Exact; it returns if the tab flips to Lossless |
| Exact on, then drop files onto the tab | same as the rows above | same fix — every add path goes through `AddFilesAsync` |
| Exact on, then + outro / *Set outro-start here* / a profile tail / ⧉ adds an outro — **ready row** | the outro note shows (`HasSnapNote` true) | hidden |
| Exact on, then + outro / *Set outro-start here* on a row **still scanning** | the new outro reads `→ snapping…` | hidden, and still hidden when the scan lands |
| Exact on, then back to Lossless | — | the existing I91 propagation restores the notes on every row, added rows and outros included |
| Lossless throughout | notes show | unchanged (`SetExactCut(false)` returns at once; `SuppressSnapNote = false`) |

## Edge cases

- **`SetExactCut` on an unprobed row.** `RecomputeAll` runs on a row without `Duration`. Every derived property
  already handles a null `Duration`, because they all recompute when the probe lands.
- **A path already in the list.** The dedup `continue` (`BulkCutViewModel.cs:1134`) returns before construction,
  so it is unaffected.
- **A load-failed row under Exact** keeps no visible note, which is consistent with Exact everywhere. Flipping to
  Lossless brings the permanent `→ snapping…` back — today's behaviour for that row, unchanged here.

## Dependencies

None (`blocked-by: []`). Independent of [[T-173]] and [[T-174]].

## Risks

- **Rows dropped under Exact change verdict.** A coarse-GOP row that was excluded as "nothing to trim" becomes
  eligible and runs. That is the verdict the toggle already gives rows that were in the list when it flipped
  (T-127), and the run was already cutting at `Requested`.
- `ExactCut` is not persisted — it is referenced only at `BulkCutViewModel.cs:180`, `:478-496` and `:2161`. So
  today the bug bites only after toggling within a session. The fix does not change that.

## Out of scope

- Persisting the precision choice.
- Which frame the cut-point thumbnail shows under Exact — [[T-174]].
- The apply line and eligibility during scans — [[T-173]].
- The `→ snapping…` note a load-failed row keeps forever under Lossless.
