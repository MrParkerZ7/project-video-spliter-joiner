# (note) auto-clear list checkbox feature doesn't work as expected, after bulk cut…

## 1 — As captured (verbatim — never edited)

> auto-clear list checkbox feature doesn't work as expected, after bulk cut finished the video list still there

## 2 — Clarification

**Read as:** *Auto-clear list* is on, a batch finished with no failures, and the list was still full — the user
expected it empty. **Confirmed from their `settings.json`:** `BulkAutoClearAfterRun = true`, `BulkAutoDeleteOriginals =
false`. That is exactly the case T-171 decision (b) keeps every row for: in the default output mode each finished row's
original is still on disk, so auto-clear cleared nothing and only added "Kept in the list: N originals left to delete"
to the summary. Warned rows were a second trap: lossless runs put planner notes on many rows, and exact-cut fallbacks
on every row of a codec that cannot be re-encoded. *Skipped* rows (another way to never clear) are ruled out — nothing
reaches the engine as Skipped from this screen.

**Generated:** [T-185](T-185.md) — auto-clear empties the list after a clean batch in every mode; kept originals and
exact-cut fallbacks are said in the summary instead of held as rows; a row whose original auto-delete could not bin
stays (unticked) so the delete can be retried; a manual *✕ Delete originals* joins the run's report instead of wiping
it. Reverses T-171 decision (b) for auto-delete off.

**Clarified with:** a UX lens, a QA lens and an adversarial check of the revision (three rounds): the first design —
keeping cleared rows in a hidden list so *✕ Delete originals* could still reach them — was dropped after the UX lens
showed it could double-count a re-added file and bin a later Replace-originals result as an "original".
