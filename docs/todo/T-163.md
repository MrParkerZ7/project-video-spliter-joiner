## Concept

The literal request: *"on Split feature also add auto remove original and auto clear bin same as bulk cut
feature"*. Two checkboxes on the Split footer — delete the source automatically after a clean split, and
optionally empty the Recycle Bin so the space is actually freed.

The reason is the one [[T-156]] recorded and it applies harder here: **the disk fills up mid-session**,
and a split multiplies rather than moves. Reclaiming by hand after every run is the chore this removes.

## Design

**Mirror [[T-156]] exactly, including its safety architecture — not just its checkboxes.** Everything
that made it defensible on Bulk Cut is load-bearing here:

1. **Two independent flags**, both default OFF, both persisted in `AppSettings`
   (`AutoDeleteSplitSource`, `AutoEmptySplitRecycleBin` — named apart from Bulk's so a user who armed one
   screen has not silently armed the other).
2. **The second is disabled unless the first is on.** Emptying the bin is meaningless otherwise.
3. **Arming the second asks once**, in plain words, defaulting to No: permanent, unrecoverable, and
   `SHEmptyRecycleBin` empties the **whole** bin — including files this app never touched and other
   programs put there. That sentence is not optional.
4. **Turning auto-delete back off disarms the bin box.** Without this, tick-both → untick-first →
   re-tick-first silently re-arms permanent deletion on consent given for a configuration that no longer
   exists. T-156 found this and it is subtle enough to re-lose.
5. **Fires only on a clean run** — routed through [[T-162]]'s `DeleteOriginal` path unchanged, so the
   all-parts-present check, the deletion-time re-check and the summary are the same code. One deletion
   path.
6. The counted confirmation is **skipped when auto-delete is armed** (the checkbox is the consent, given
   in advance), but the summary still reports exactly what was binned and what was refused.
7. `DestructiveOutputNote` equivalent in **danger colour**, visible **before** Run is pressed. It says
   "Recycle Bin" when only auto-delete is on and "permanent" only when the bin box is armed too —
   overstating it teaches people to ignore it (SPEC-011 I137).

### Rejected
- **One combined "clean up automatically" checkbox.** Collapses a recoverable action and an
  unrecoverable one into a single click. The whole point of the pair is that the second is a separate,
  louder decision.
- **Sharing Bulk's flags.** Arming Bulk Cut must not silently arm Split.
- **Auto-delete on a partly-failed run.** Never. A failed part is exactly when the source is irreplaceable.

## Detail
- Two `IAppSettings` properties + DTO round-trip, defaults false, tolerant load (a settings file written
  before this feature, or a corrupt one, leaves both OFF — an unreadable file is not consent; SPEC-009
  I27/I28's rule).
- Checkboxes land in the Split footer beside [[T-162]]'s button. **Note the ordering dependency with
  [[T-160]]:** Bulk Cut's footer became cramped by exactly this kind of accretion, and Split's footer is
  about to gain a button and two checkboxes. Lay them out so they wrap rather than clip (WrapPanel, not
  horizontal StackPanel) — the T-136/T-141/T-156 class, fourth and fifth instances.
- Bin-emptying reuses whatever T-156 wired for Bulk; if that is Bulk-private, extract it.

## Interfaces / contracts
- `IAppSettings` / `AppSettings` / its DTO — two new persisted booleans.
- [[T-162]]'s `DeleteOriginal` path — called, not duplicated.
- The bin-empty helper T-156 introduced — reused.

## Acceptance criteria + Case-Coverage Matrix
- [x] Both flags default OFF and persist.
- [x] The bin box is disabled unless auto-delete is on, and **disarms** when auto-delete is switched off.
- [x] Arming the bin box asks once, defaults to No, and says the bin is emptied **whole** — including
      files other programs deleted.
- [x] Auto-delete fires **only** on a clean, fully-successful split, through T-162's path unchanged.
- [x] A run with any missing/zero-byte part deletes nothing — asserted with a **real disposer injected**,
      because T-156's equivalent test passed vacuously against a VM that had none and the mutation
      removing the guard survived it.
- [x] The footer note states the armed state before Run, in danger colour, and says "Recycle Bin" rather
      than "permanent" when only auto-delete is armed.
- [x] An unwired confirmation seam refuses (cannot arm).
- [x] Mutations: the clean-run guard, the confirmation gate, and the disarm-on-untick each fail a test.
- [x] Footer verified at 1280px — nothing clipped.

| case | expected |
|---|---|
| both off (default) | nothing deleted, no note |
| auto-delete on, clean run | source binned automatically, summary says so |
| auto-delete on, a part missing | nothing deleted, summary says why |
| auto-delete on, run cancelled | nothing deleted |
| bin box ticked without auto-delete | impossible — disabled |
| both on, confirmed | source binned, bin emptied, note said "permanent" beforehand |
| both on, confirmation declined | bin box stays off |
| auto-delete unticked after both were on | bin box disarms |
| settings file predating the feature | both OFF |
| corrupt settings file | both OFF |

## Edge cases
Split run twice in a session with the flags on; bin already empty; bin-empty refused by the shell;
source on a network path (no Recycle Bin); user cancels mid-run.

## Dependencies
[[T-162]] — the deletion path this routes through. Hard dependency, not a preference.

## Risks
- **Automatic + irreversible.** The combination is permanent deletion with no undo, and it fires without
  a per-run gesture. Every gate above is the reason it is offerable at all.
- T-156's build found that **two of its tests were vacuous on first write**. Assume the same here and
  mutation-check each gate.

## Out of scope
A low-disk-space monitor or warning ("tell me before the run fails" is a different feature). Auto-delete
on Join.

### The design decisions that carried over intact
**One deletion path.** Auto-delete calls [[T-162]]'s `DeleteOriginal` unchanged, so the all-parts rule,
the deletion-time re-check and the handle release are the same code. The confirmation is skipped because
the checkbox IS the consent — but the *safety* decisions live in `DeletableSource`, not in the prompt, so
an incomplete set of parts still deletes nothing. That separation is why skipping the prompt is safe, and
it is asserted with a **real disposer injected**: T-156's equivalent test was vacuous precisely because
its VM had none and the sweep was inert either way.

**Separate settings keys.** `SplitAutoDeleteSource` / `SplitAutoEmptyRecycleBin`, not Bulk's. Arming one
screen must not silently arm the other — different files, a different moment, and the user consented to
one of them. The mutation pointing Split's getter at Bulk's key dies.

**The bin is emptied only after the source actually went in.** Emptying after a *refused* delete would
destroy unrelated files for no gain whatsoever, because `SHEmptyRecycleBin` is not scoped to this app.
Worth stating as its own rule rather than leaving implicit.

**The note does not overstate.** "Recycle Bin" while it is recoverable; "PERMANENT" only once the bin box
is armed. Crying wolf in red is how a warning stops being read.

### Wiring
`SplitView` supplies both real dialogs and the bin action, exactly as `BulkCutView` does. Both view-model
gates default to refusing and the bin action defaults to doing nothing, so a forgotten wiring can only
leave the feature inert — never destroy a file, and never empty a developer's own bin during a test run.
