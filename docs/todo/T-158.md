## Found

While closing [[T-154]]'s Split/Join half, a review pointed out that every screen has **two** doors for
getting files in — drag-and-drop and the file picker — and T-154 only ever fixed one of them. So each
screen now answers the same question two different ways.

## The two halves

**1. The picker's filter is stale.** All three pickers still carry the pre-T-154 list:

```csharp
Filter = "Video files|*.mp4;*.mkv;*.mov;*.avi;*.webm;*.m4v;*.ts|All files|*.*"
```
`SplitView.xaml.cs:52` · `JoinView.xaml.cs:146` · `BulkCutView.xaml.cs:179`

`VideoFileFilter` accepts **26** extensions. So an `.m2ts` — the exact format whose absence produced the
original report — is **invisible** under "Video files", even though *dropping* one now works. The user who
gives up on dragging and reaches for the button gets the old bug back.

**2. Under "All files" the picker applies no filter at all and says nothing.** Split hands
`dialog.FileName` straight to `LoadCommand`; Join and Bulk hand `dialog.FileNames` straight to
`AddFilesCommand`. Neither routes through the counting entry point T-154 added, so picking a `.txt`
adds it as a row (Join/Bulk) or attempts to load it (Split) with **no refusal message** — the same
silence, through the other door.

## Design

1. Widen the three `Filter` strings to the live allowlist. Generate it from
   `VideoFileFilter.VideoExtensions` rather than re-typing it, so the two can never drift again — the
   hand-maintained copy is exactly how this got stale.
2. Route the picker result through the same `AddDroppedFilesAsync` entry point the drop path uses, so both
   doors count refusals identically and there is one place for the rule to live.

## Acceptance criteria
- [x] The picker's "Video files" filter offers every extension the app accepts, derived from
      `VideoFileFilter` rather than duplicated.
- [x] A file chosen under "All files" that the app cannot use is **refused with a reason**, exactly as a
      dropped one is.
- [x] A test that fails today: assert the picker filter string covers every entry in
      `VideoFileFilter.VideoExtensions`.
- [x] Mutation: removing an extension from the allowlist without updating the picker fails that test.

## Out of scope
Replacing the extension allowlist with probe-based acceptance ([[T-154]] § Design 4) — still open on its
own merits, and it would supersede the filter string entirely rather than fix it.

## Outcome — 2026-09-06

Both halves closed, and the fix is derivation rather than a longer hand-typed string.

`VideoFileFilter.DialogFilter` builds the picker's filter **from the same set the drop path accepts**, so
adding an extension to the accept-list now changes what the picker offers with nothing else to remember.
All three screens use it. Reverting it to the hand-typed seven kills a test; so does dropping the
*All files* escape hatch, which has to stay — an allowlist is a guess about a container, and that entry
is how someone opens the one we guessed wrong.

All three pickers now route their result through the same **counting entry point** the drop path uses
(`AddDroppedFilesAsync`), so a file chosen under *All files* that the app cannot use is refused in words
instead of silently added or silently ignored. Both doors into a screen answer the same question the
same way, which is the whole point of the ticket.

### On "a test that fails today"
The criterion asked for one that fails against the stale filter. Written the obvious way — assert the
filter contains all 26 — it would have passed the day the accept-list shrank, so it also asserts each
extension **through `HasAnyVideo` first**: the test's own list is checked against the app's behaviour
before being checked against the filter. Otherwise it is a hand-typed list guarding a hand-typed list.
