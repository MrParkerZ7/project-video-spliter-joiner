## Concept

Found by the T-187 measurement while it checked that faster Exact heads give the same output. **Every HEVC
Exact result is corrupt after the head/tail joint**, on the current engine path and on every variant tried.

- The concat output takes its codec configuration from the first file, the libx265 head: hev1 extradata,
  2497 B. The copied tail's slices refer to parameter sets that exist only in the source's hvc1 extradata
  (130 B), so they decode against the wrong VPS/SPS/PPS.
- Measured: 250-316 decoder errors (`alignment_bit_equal_to_one=0`, `Too many refs`), frame md5s that differ
  from the source, and a tail PSNR of 11-15 dB. Evidence file: `t187-fixtures/work/smart2-final-current-hevc-10.5.mp4`
  (the evidence source was made by `hevc_nvenc`; `docs/design/references/T-187-bench/measure_result.json`).
- H.264 survives only because the concat demuxer's automatic `h264_mp4toannexb` puts SPS/PPS in-band
  before the tail's IDR. There the decoded frames after the joint are md5-identical to the source. The
  demuxer does that conversion for H.264 only.
- Heads from `hevc_nvenc` still decode with 12-14 errors, so a different encoder is not a fix.

This breaks SPEC-001 I46, which promises *"never a guessed encoder and never a silently corrupt concat"*.
HEVC is the usual codec of phone 4K, so this hits the users G-059 is for.

## Design

- **HEVC is no longer something Exact can reproduce.** Remove `hevc` and `h265` from
  `SmartCutArgsBuilder.VideoEncoders` (`SmartCutArgsBuilder.cs:23-24`). `TryResolveEncoders` checks a small
  named set of codecs whose joint is known to break, before the generic "no known encoder" branch, and
  returns false with a reason in words a user can read: *"frame-exact cutting is not supported for HEVC/H.265
  video yet"* (no internal terms such as "joint"; no nested parentheses inside the row warning).
- **Nothing new on the engine's fallback path.** `SmartCutEngine.CutAsync` already returns
  `FellBack = true, FallbackReason = why` with zero ffmpeg runs when `TryResolveEncoders` fails
  (`SmartCutEngine.cs:98-101`). `BulkTrimEngine` then runs the ordinary lossless cut and adds the row warning
  `"exact cut unavailable (<reason>) - cut snapped to the nearest keyframe"` (`BulkTrimEngine.cs:25, 306`).
  That covers Replace originals too: the sibling temp is swept and the lossless pass owns the destination
  (`BulkTrimEngine.cs:289-294`).
- **The row is honest before Run — one predicate shared by the row and the run.** Today an Exact row hides its
  snap readout (`SetExactCut`, `BulkItemViewModel.cs:487-504`, ADR 0018's forced follow-on *"Any surface that
  offers Exact must suppress the snap readout"*), cuts at `Requested` (`EffectiveIntroEnd`, `:405`) and grabs its
  chip at `Requested` (`GrabTime`, `:317-323`: *"Exact cut is never provisional"*). After this ticket every HEVC
  row in Exact really cuts at the snapped keyframe, so all three would show a cut the run will not make. So:
  - when the row's probe succeeds (`BulkCutViewModel.cs:1415`, where today only `Duration` is kept), the row
    stores whether Exact can cut it and why not, from **`SmartCutArgsBuilder.TryResolveEncoders` on the row's
    probed `MediaInfo`** — the same gate the engine falls back on, so the row and the run never disagree;
  - in Exact mode, a row Exact **cannot** cut behaves exactly as in Lossless: its snap note shows
    (`SuppressSnapNote` stays false on its handles), `EffectiveIntroEnd`/`EffectiveOutroStart` and `GrabTime` use
    `Snapped` (provisional while the snap is pending), and eligibility (`IsValidCut`, `IsNoOpTrim`,
    `KeptDuration`) is computed from `Snapped`;
  - so **every** `_exactCut` read in `BulkItemViewModel` becomes the per-row predicate (Exact on **and** Exact can
    cut this row), not only `:266`, `:323`, `:405` and `:409`. Two more reads matter:
    - `:567`, the T-120 *"cut moved Ns"* note, whose worst snap is forced to zero under Exact; a fall-back row must
      show it like a Lossless row;
    - `:977`, the chip re-grab trigger. Keyed on `Requested`, a fall-back row would grab the old `Snapped` and never
      re-grab on a drag, because the `Requested` setter raises before `Resnap()` (`CutMarkerViewModel.cs:60-68`). A
      fall-back row listens to `Snapped`, as in Lossless;
  - its `Warning` states the reason **before Run**, in the run's own words (`exact cut unavailable (<reason>) -
    cut snapped to the nearest keyframe`), and shows it once after the run. **`RunWarnings` stays intact**: the
    engine's ledger warning is kept there, because the auto-clear summary (`BulkCutViewModel.cs:1570-1601`,
    SPEC-011 I161) finds fall-back rows only through `RunWarnings` entries carrying `ExactFallbackPrefix`. Only the
    `Warning` getter de-duplicates the before-Run text against it;
  - a row Exact **can** cut is unchanged. `BuildBulkTrimItem` still hands the engine `Requested`; the engine
    decides and announces the fallback, as today.

  **Choice logged.** Rejected: leaving the row as it is and logging the honesty as a later ticket. Until that
  ticket, every HEVC Exact row would hide a snap offset that is real, draw its chip at a frame the run will not
  cut at, and could be skipped at Run with no word (next bullet). This ticket exists to stop a silent wrong
  result, the predicate already exists, and T-196's chip time and T-190's start-time rule build on it.
- **The mode's own promise is made honest.** `PrecisionNote` (`BulkCutViewModel.cs:571-574`, the toggle tooltip
  and footer; SPEC-011 I90) promises *"Exact — cuts land where you set them (re-encodes ~1s per cut)"*, which
  becomes false for HEVC. It gains the exception: *"Exact — cuts land where you set them (re-encodes ~1s per cut;
  HEVC video still snaps to keyframes)"*. T-190 adds `.ts`/`.m2ts`/`.mts` to it.
- **The fallback that leaves nothing to trim is explained.** An HEVC Exact row whose requested intro lies
  inside the first GOP, with no outro, snaps to 0. Today `KeptMiddleRequestBuilder` throws `NoOpTrimException`
  and `BulkTrimEngine.cs:334-339` records `Skipped` with `NoWarnings`, so the reason is lost. Two guards:
  - the row is excluded before Run with *"nothing to trim yet — set an intro or outro"* (its eligibility now
    comes from `Snapped`), and its `Warning` carries the reason;
  - the engine carries the row's fallback warning onto a `Skipped` result instead of `NoWarnings`, for callers
    that reach it without the view model.
- **A joint-integrity check that later work reuses.** Add a test helper, `SmartCutJointIntegrity`, that takes
  a final, its source, `Start` and `HeadEnd`. It runs the bundled ffmpeg through `FfmpegRunner`:
  1. It decodes the whole final with `-v error … -f null -` and counts **decoder and demuxer** error lines. It
     excludes the `[null @ …]` muxer timestamp lines (`non monotonically increasing dts to muxer`): the shipped
     H.264 finals print them (verified: 4 on `t187-fixtures/work/smart2-final-current-4k-104.5.mp4`, 1 on
     `t187bulk/final.mp4`), they are a timing symptom, and T-190's joint-timing test owns them and takes the
     full zero-line baseline. The helper also returns the full line count, for T-190.
  2. It writes `framemd5` of the final's video from `HeadEnd − Start` and of the source from `HeadEnd`, over
     the same number of frames, and compares the hash sequence (content, not timestamps, which are T-190's
     concern).

  H.264 passes it on shipped code. HEVC is shown to fail it on the shipped code (the repro), then falls back.
  T-190, T-191 and T-192 keep it green, and the later HEVC repair (T-201) must pass it before HEVC goes back in
  the map. The other mapped encoders (VP9, VP8, AV1, MPEG-4, MPEG-2) stay unverified until T-202.
- **Code comment:** where `hevc` used to be, a one-line comment says why it is absent and points to T-201.

## Detail

- The reason is checked before the generic branch, so the row reads a cause the user can act on, not
  *"no known encoder for video codec 'hevc'"*.
- `ReencodedDuration` is zero on the fallback, as today.
- The lossless cut a fallback writes is today's lossless cut, keyframe-snapped. Nothing about it changes.
- Rows added later take the per-row rule at probe time; a precision flip re-evaluates every row with
  `RecomputeAll()`, as `SetExactCut` does today (SPEC-011 I91).

## Edge cases

- **A start already on a keyframe** stays `PureCopy` in the engine. It falls back before `TryResolveEncoders` is
  reached (`SmartCutEngine.cs:90-95`), and `BulkTrimEngine` shows no warning for it (`:300-307`). The row's
  before-Run note still shows, because the row's rule looks at the source, not the cut; `Snapped == Requested`
  there, so the cut it shows is the cut it makes.
- **An HEVC file mislabelled by its container** (for example codec_name reported differently) follows
  ffprobe's `codec_name`, as today.
- **10-bit HEVC** falls back the same way.
- **A row whose probe failed** is already `can't read this file`; the rule never runs.

## Dependencies

None.

## Risks

- **A visible capability loss.** HEVC users who chose Exact get a keyframe-snapped cut with a note, where
  before they got a file that looked fine until the joint. The note says why, before the run. The later repair
  (T-201) can bring HEVC back once it passes the same check.
- **Other mapped codecs** (VP9, VP8, AV1, MPEG-4, MPEG-2) have never been joint-checked. They are out of scope
  here and logged as T-202, and the new invariant says they are unverified, so that this ticket stays a fix for
  the measured bug.

## Out of scope

- Repairing the HEVC joint (T-201).
- Joint checks for VP9/VP8/AV1/MPEG-4/MPEG-2 (T-202).
- The H.264 joint timing and the `[null @` lines (T-190).
- Any speed change.
