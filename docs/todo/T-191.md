## Concept

Bulk Cut's Exact precision was the measured #1 4K hotspot.

- **The head decodes from the start of the file.** `SmartCutArgsBuilder.HeadReencode` puts `-ss` *after* `-i`
  (`SmartCutArgsBuilder.cs:116-118`). That is an output seek: ffmpeg decodes every frame from 0 up to the
  cut. The doc comment at `:92-93`, the inline comment at `:117`, ADR 0018 § (c) and SPEC-001 I44 all say
  the decode is *"bounded by one GOP"*. It is not.
- **Measured cost, growing with the cut position** (about 0.19 s per second of start): a 1.5 s head takes
  4.8 s at an intro of 10.5 s, 22.83 s at 104.5 s (772 MB read, 89% of the 907 MB file), and 130.7 s at
  540.5 s of the 10-min 4K file.
- **An input seek (`-ss` before `-i`) gives the same frames.** ffmpeg's default `accurate_seek` starts at the
  keyframe before the cut and drops decoded frames until `start`, which is the same frame set. Measured:
  - at 104.5 s, 45 packets and 1.500 s for both heads, the same PSNR against the source (41.9 dB) and the same
    8.5 MB, in **4.94 s against 30.21 s in the same run**;
  - at 540.5 s, **4.65 s against 130.7 s** (28x), with the joint decoding clean;
  - at 10.5 s, the two heads compare at PSNR 99 (identical).
- **The row bar shows nothing during the work.** Every run is started with null progress
  (`SmartCutEngine.cs:124, 145, 160` before T-190), and the row fraction jumps at stage boundaries (0 → 0.5 →
  0.8 → 1.0 today; 0 → 0.5 → 1.0 after T-190). A 4K Exact batch looks frozen. After T-190 the concat copies the
  whole kept range in one run, so on a long file the bar would sit at 0.5 for the whole copy.
- **The batch bar under-counts an Exact row.** The row fraction feeds the batch bar, the taskbar and the
  window-title ETA through `BulkCutViewModel.WeightedOverall`, which weights each row by its kept duration
  (`RowWeight`, `BulkCutViewModel.cs:2868`). An Exact row's head encode costs far more per second than its copy,
  so on a row with a short kept range the batch bar barely moves during the head, and *"~Ns left"* (from the
  overall fraction, `OperationViewModel.cs:541-547`) is wrong for it.

## Design

- **Head args (`HeadReencode`):** `-y -ss <start> -i <input> -t <duration> -map 0 -c:v <enc> -pix_fmt … -s …
  -c:a … -ar … -ac … <out>`. `-ss` moves before `-i`. `-t` stays an output duration. No `-noaccurate_seek`.
  Every other token is unchanged.
- **Comments made true:** the doc comment says the input seek starts decoding at the keyframe before `start`
  and drops frames until it, so the decode is bounded by one GOP. The inline comment at `:117` is replaced.
- **Real row progress (`SmartCutEngine`):** each run gets a `totalDuration` and a scaled sub-progress.
  - The head run: `totalDuration = HeadEnd − Start`, reported into `[0, w)`.
  - The concat run: `totalDuration` = the kept duration (`End − Start`, or `Duration − Start`), reported into
    `[w, 1)`.
  - A `FullReencode`: its one run across `[0, 1)`.
  - **1.0 is reported once, after the final file is moved into place**, never during a run. A run that fails or
    is cancelled never reports 1.0.
  - The weight `w = h·k / (h·k + c)`, with `h` the re-encoded seconds, `c` the copied seconds, and `k` a named
    public constant `SmartCutEngine.EncodeCostFactor`: copy-equivalent seconds per second of re-encoded video,
    chosen from this ticket's bench run and recorded in the Build log.
  - **One pure Core cost function** (for example `SmartCutCost.Of(SmartCutPlan plan, TimeSpan duration)`; the name
    is the builder's) turns a `SmartCutPlan` into `h` (the plan's `ReencodedDuration`), `c` (the copied range
    `[HeadEnd, End ?? duration)`, zero for a `FullReencode`, the whole range for a `PureCopy`) and the cost
    `h·k + c`. The engine's `w` and the batch weight below both use it, so the row bar and the batch bar can never
    weigh the same cut differently.
  - A small monotonic adapter wraps the caller's `IProgress<double>`, so the fraction never goes backwards.
- **Batch weight (`BulkCutViewModel.RowWeight`):** a row that will really be cut exactly (Exact on, and T-189's
  per-row rule says Exact can cut it) weighs the cost function's `h·k + c` for
  **`SmartCutPlanner.Plan(Requested, end, keyframes)`** on the row's own keyframes, where `end` is the kept range's
  end the row hands the engine. So `h` and `c` come from the planner itself, including its 10 ms
  `OnKeyframeTolerance`: a request within 10 ms of a keyframe is a `PureCopy` with `h = 0`, and a range with no
  keyframe inside it is a `FullReencode`. A second *"first keyframe at or after"* search in `BulkCutViewModel` is
  ruled out, the same one-path rule as T-189's predicate. Every other row keeps its kept-duration weight. So the
  batch bar, the taskbar and *"~Ns left"* move during a head in proportion to its real cost.

  **Choice logged.** Rejected: keeping the kept-duration weight and accepting the skew. The row bar would move
  while the batch bar and the ETA sat still during every head, which is the frozen look this ticket removes. The
  change reuses the planner and one pure Core function shared with the engine, and `WeightedOverall` (SPEC-011
  I41) is unchanged.
- **No interface change.** `ISmartCutEngine.CutAsync` already takes `IProgress<double>`, and `BulkTrimEngine`
  already passes the row's progress in (`BulkTrimEngine.cs:265`). The G-025 channels stay distinct; this only
  fills the numeric one.

## Detail

- `FfmpegRunner.RunAsync(args, totalDuration, progress, ct)` already turns `time=` into 0..1 when it is given
  a total. For the head run `time=` counts output time (0..head length). For the concat it counts 0..kept
  length.
- A run that emits no `time=` (very short) leaves its slice unreported. The adapter then jumps to the slice's
  end when the run returns (still below 1.0 for the last run), and 1.0 follows the move into place.
- The planner (`SmartCutPlanner`) and `Start` are untouched. I43 (start honoured exactly) holds, because the
  input seek with `accurate_seek` drops frames before `start` exactly as the output seek did.

**Repro first — confirmed FAILING on shipped code before the fix:**

- [ ] **Head progress (fake runner that reports `time=` fractions when given a total):** the row's

## Edge cases

- **`start` within the first GOP:** the input seek starts at keyframe 0. Same frames, same cost as today.
- **A source whose first keyframe is not at 0** (a leading empty edit): the seek honours container time. The
  frame-identity test runs on such a fixture, made in the test.
- **Near the start of the file the gain is small**, because the encode dominates there. At an intro of 12.5 s on
  the 10 s GOP fixture the input seek gained nothing (18.25 s against 18.98 s). T-192 addresses that constant
  cost.
- **A row that falls back at Run for a reason the row could not know** (Replace originals without a disposer) is
  weighted as Exact and finishes as Lossless; the batch bar then moves faster than its weight. Rare and harmless.

## Risks

- **A deliberate contract change** (SPEC-001 I44, ADR 0018, one test). Frame identity is proven against the
  old args, not assumed.
- **`EncodeCostFactor` is approximate.** It shapes only how the bars move, never correctness, and the adapter
  and I42 keep the bars monotonic whatever the factor.

## Out of scope

- The encoder preset (T-192).
- A status text such as *"re-encoding the first 1.5 s"*. `ISmartCutEngine` has no status channel, and adding
  one runs through `BulkTrimProgress` to the view model. The moving bar answers the measured problem (a bar
  that does not move), so the text is not built or logged.
- Pipelining rows (T-204).
