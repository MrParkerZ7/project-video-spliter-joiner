## Concept

The keyframe scan is the largest wait a user feels on a big 4K file. It is the first thing a split runs into,
before any copy starts. T-187, verbatim: *"Need improve perfomance for 4K video, because when try to split 4K
video it's super slowly. please check all join/spilt/bulk cut"*.

- `ScanKeyframesFromPacketsAsync` runs `ffprobe -select_streams v:0 -show_packets` (`MediaProbe.cs:253-259`)
  and reads **100% of the file**: 865 of 907 MB on the 2-min 4K fixture (0.73 s warm, 0.81 s cold), 2283 of 2283 MB
  on a 5-min one. The 4.5 GB 10-min file takes 2.93 s (cold 3.66 s).
- On this box's 5400-rpm HDDs a cold 4.5 GB read would take about **24-30 s**, and a 20 GB file 2-3.5 min
  (inferred: bytes ÷ 150-190 MB/s).
- Three things wait on it:
  - **Split:** cut snapping (`IsSnapPending` until the scan lands), and Preparing, which awaits the same scan
    (`SplitEngine.cs:135`). *Split enabled* comes 0.99 s after load on the 2-min file and 5.16 s on the
    10-min file, against a 0.27 s and 0.69-0.80 s probe gate.
  - **Bulk Cut:** `CanRunBatch` needs every enabled row's `KeyframesReady` (`BulkCutViewModel.cs:729-732`).
    3 x 4K rows become runnable at 1.93 s (cold 2.51 s), with 3 whole-file reads at once (SPEC-011 I3).
  - **Exact cut:** the planner needs the list (`SmartCutEngine.cs:85`).

An MP4/MOV file already holds this list. Its sample table (`moov → trak → stbl`) records which samples are
sync samples (`stss`) and every sample's timing (`stts`, `ctts`, plus `mdhd` and `elst`). That table is the data
ffmpeg's mov demuxer derives its `K` packet flags from. The T-187 prototype read it in managed code and returned
**identical** lists on all four fixtures, in 0.003 s (cold 0.006 s), reading **0.1 MB**. Its source is kept in
`docs/design/references/T-187-bench/Mp4Index.cs` (the reference copy committed with this plan; the session
scratchpad it was written in will be gone).
Phone and camera 4K is overwhelmingly MP4/MOV.

## Design

**One new Core reader, then a three-path chain inside the one shared scan.**

- **`src/Core/Media/IsoBmffKeyframeIndex.cs`** (internal, UI-free, no process): `TryRead(Func<Stream> open)`
  returns the keyframe list plus the bytes it read, or `null` meaning *decline*.
  - **It never gets in the way of the file.** `MediaProbe` opens it read-only with
    `FileShare.ReadWrite | FileShare.Delete`, so the reader never blocks a Replace-originals swap, a rename, a
    delete or a file still being written.
  - **Any `IOException` or `UnauthorizedAccessException`** (from the open or a read) is a *decline* to the packet
    scan, not a scan failure.
  - It walks the top-level boxes: 32-bit and 64-bit sizes, a size-0 box running to the end. `ftyp` is required.
    `mdat` is **skipped by seeking, never read**. `moov` may be at the front or the end, and only `moov` is
    read. A `moov` over 256 MB declines.
  - It takes the **first** `trak` whose handler is `vide`. That is the stream ffprobe's `v:0` selects, because
    the mov demuxer creates streams in `trak` order. If that track is outside the subset below, the reader
    declines. It never skips ahead to another track.
- **Times are computed exactly as ffprobe prints them**, so the lists are TimeSpan-equal, not just close:
  - in integer track ticks, `pts = dts(stts) + cto(ctts) − media_time(elst)`;
  - a leading empty edit's duration is added after rescaling from the movie timescale to the track timescale
    with round-to-nearest, as the demuxer does;
  - then `seconds = pts / timescale` as a double, formatted with 6 decimals as ffprobe's `pts_time`, and parsed
    by the existing `TryParseSeconds`;
  - sorted and distinct (SPEC-004 I11).
- **The supported subset:**
  - sample entry `avc1`, `avc3`, `hvc1` or `hev1`, and exactly one `stsd` entry;
  - `stss` present, or absent, which means every sample is a sync sample, as in the demuxer;
  - `ctts` version 0, or version 1 with no negative offset;
  - at most one leading empty edit plus one media edit at rate 1, or no `elst`.
- **Anything else declines:**
  - a fragmented file (`mvex` in `moov`, or a top-level `moof`);
  - `stps`;
  - an `sbgp`/`sgpd` of grouping type `rap ` or `sync` on the video track (ffmpeg flags open-GOP random-access
    samples `K`, and `stss` does not list them);
  - more than one media edit, or a media rate other than 1;
  - a negative composition offset;
  - any other codec;
  - a `covr` box (an attached picture can become `v:0`);
  - a keyframe list of fewer than 2 entries;
  - any truncated or malformed box.
- **The anchor (runtime check by ffprobe).** When the reader returns a list `L`, two short packet windows run
  through `FfprobeRunner`, using the existing packet-scan args plus `-read_intervals` and `-nofind_stream_info`:
  - window A, `-read_intervals %<L[1] + 1 ms>` (from the start to just past the second keyframe);
  - window B, `-read_intervals <L[^1] + 1 ms>%` (from just past the last keyframe to the end).

  **ffprobe seeks back.** A `-read_intervals` start makes ffprobe seek to the keyframe at or before it and print
  every packet from there; it drops nothing before the interval start (verified on the synthetic 1080 fixture:
  `-read_intervals 118.001%` returns `118.000000 K`). So the comparison rule is: **the `K` list a window returns
  must equal, TimeSpan-exactly, `L` restricted to [the window's first returned packet pts, the window end], and
  each window must return at least one `K`.** For a correct `L` that means window A returns exactly
  `[L[0], L[1]]` and window B exactly `[L[^1]]`. Then `L` is used. Any difference, an empty window, or an ffprobe
  error sends the scan to the full packet scan. The two windows cost about one GOP each, bounded by GOP length, not
  file length. They catch a systematic offset (an edit-list or timebase misreading) at both ends of a real file
  this project can never sample, and a last "keyframe" that is not one (window B then lands on an earlier
  keyframe, so the restricted `L` holds an entry ffprobe did not flag).
- **`MediaProbe.RunSharedScanAsync` becomes index (+ anchor) → packet scan → frame scan**:
  - the packet scan runs when the index declines or the anchor disagrees;
  - the frame scan runs when the packet scan returns zero or throws, as today (I14/I15);
  - `KeyframeScanPath` gains `Index`;
  - the cache key, success-only caching, T-093 dedup and cancel-safety are untouched, because all of it lives
    inside the one shared scan task.

## Detail

- **Not a second scan pass.** The windows are part of the single shared, deduplicated scan for that file. There
  is still exactly one scan per file per key. ADR 0025 records why this keeps the CLAUDE.md rule *"don't … add
  a second keyframe scan pass"* true.
- The reader runs synchronously inside the already-background shared task (after its `Task.Yield()`). Even a
  long recording's `moov` is a few MB.
- **MKV, TS, AVI** have no `ftyp`, so they decline at the first box and behave exactly as today.

**Declines:**
- [ ] A fragmented MP4 (`frag_keyframe+empty_moov`), an MKV and a TS each give `LastScanPath == Packets` and
      today's list. A truncated copy of an MP4 fixture declines without throwing.
- [ ] Unit tests on **crafted box trees** (no ffmpeg needed) decline for each of these:
      - `mvex`, `moof`, `stps`;
      - `sgpd` `rap `, `sgpd` `sync`;
      - two media edits, a media rate of 0.5;
      - a negative `ctts` offset;
      - two `stsd` entries, an `mp4v` sample entry;

      - `covr`;
      - a `moov` declared larger than 256 MB;
      - a single-entry `stss` (fewer than 2 keyframes);
      - a file with no `ftyp`;
      - a size that overruns its parent.

      They accept 64-bit box sizes and a size-0 final box.
- [ ] **The file is never held against others:** with the stream `MediaProbe` opens for the reader still open, the
      file can be renamed and deleted (`FileShare.ReadWrite | Delete`). An `open` func that throws `IOException`,
      and one that throws `UnauthorizedAccessException`, each give a decline: the packet scan runs (fake runner),
      `LastScanPath == Packets`, nothing throws.
- [ ] The frame fallback is still reached when the packet scan returns zero (I14) or throws (I15). The existing
      fake-runner tests use placeholder `.mp4` files with no `ftyp`, so they decline and pass unmodified.

**Anchor:**
- [ ] **Comparison rule (unit, fake runner returning canned packet lists):**
      - window A returns `[L[0], L[1]]` and window B returns `[L[^1]]` → agree;
      - **seek-back:** window B's output starts at `L[^1]` although the interval starts at `L[^1] + 1 ms` → agree (the
        rule restricts `L` to the first returned pts, not to the interval start);
      - window B lands on `L[^2]` and flags only it (so `L[^1]` is not a real keyframe) → disagree;
      - a window that returns no `K` → disagree;
      - every value one frame later than `L` → disagree.
- [ ] With a test seam making the reader return a list shifted by one frame, the anchor disagrees, the result is
      the packet-scan list, and that list is what gets cached.
- [ ] **Anchor failure paths (fake runner, on a real `ftyp` file so the index is reached):**
      - an anchor window run fails (non-zero exit) → the packet-scan list is returned and cached, with
        `LastScanPath == Packets`;
      - **a caller cancels while an anchor window runs** (a gated fake runner blocks window A): that caller gets
        `OperationCanceledException` for itself only. Once the gate is released the shared scan completes, caches
        the index list with `LastScanPath == Index`, and a concurrent second caller receives that list. This is the
        shipped T-093 contract, unchanged: `RunSharedScanAsync` runs on `CancellationToken.None`
        (`MediaProbe.cs:187-224`), and `MediaProbeInFlightDedupTests.cs:97-117` and `:247` say a caller's
        cancellation never reaches the runner. Cancelling the scan itself is T-198;
      - **the anchor runner itself throws `OperationCanceledException`** → nothing cached, and the next call scans
        again (its first run is a window again, on the fake's record).

        (The existing cancel and dedup tests use placeholder `.mp4` files with no `ftyp`, so they decline before the
        anchor and never reach it.)
- [ ] The anchor's ffprobe args carry `-read_intervals` and `-nofind_stream_info`, use `FfmpegArgs`, and there are
      exactly two runs.

## Edge cases

- **A keyframe before the first media edit** (a negative pts after `media_time` is subtracted): the parity matrix's
  edit-list fixtures show whether ffprobe lists it. If the two disagree, the anchor's window A catches it and the
  scan falls back. The reader never guesses.
- **A disabled video track or a second video track:** `v:0` is the first `vide` track in both readers.
- **iPhone-style MOV with metadata tracks** (`mebx`, `tmcd`): not `vide`, so ignored. They cannot be sampled here,
  so the anchor is the guard.

## Dependencies

- **T-193:** the same file (`MediaProbe.cs`) and spec (SPEC-004 numbering). Built one after the other to avoid merge

- **T-188:** the bench and its fixture matrix.

## Risks

- **Parity on real camera files is unverifiable here** (hard rule). The mitigations, in depth: a narrow subset,
  crafted-box decline tests, a TimeSpan-exact synthetic parity matrix, the runtime anchor at both ends, and the
  packet and frame fallbacks. What the anchor cannot catch is an `stss` error in the middle of the file that
  leaves both ends right. `stss` is a plain list, so that risk is low.
- **No help for MKV/TS.** If the user's 4K is MKV (OBS) or TS, this ticket changes nothing for them. T-199 is
  then the next step, and T-198 matters more.

## Out of scope

- MKV Cues or windowed lookups (T-199).
- A persistent on-disk index (T-200).
- All-intra codecs such as ProRes (T-216).
- Cancelling abandoned scans (T-198).
