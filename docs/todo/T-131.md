## Reported
> I can't do multi bulk cut, Invalid URI: The hostname could not be parsed.

## Root cause — REPRODUCED, not inferred

`FfmeMediaPlayer.OpenCoreAsync` (`src/App/Media/FfmeMediaPlayer.cs:224`) opens the preview with:

```csharp
Run(() => _element!.Open(new Uri(path, UriKind.RelativeOrAbsolute)));
...
catch (Exception ex) { RaiseFailed(ex.Message); }   // the raw .NET message reaches the user
```

`new Uri` throws `UriFormatException` when a UNC path's **server name is not a legal URI hostname**.
Probed on this machine against .NET 8 — the exact user-facing string is reproduced:

| path | result |
|---|---|
| `C:\videos\a.mp4` | OK |
| `Z:\Videos\ep 1.mp4` (mapped drive) | OK |
| `\\NAS\share\a.mp4` | OK |
| `\\192.168.1.5\media\a.mp4` | OK |
| `\\my-nas\share\a.mp4` | OK |
| `\\my.nas.local\share\a.mp4` | OK |
| `\\my nas\share\a.mp4` | **THROW — Invalid URI: The hostname could not be parsed.** |
| `\\Seagate NAS\Videos\ep1.mp4` | **THROW** (same) |
| `\\host:port\share\a.mp4` | **THROW** (same) |
| `\\host[1]\share\a.mp4` | **THROW** (same) |

A **space in the server name** is the realistic trigger — common on consumer NAS boxes ("Seagate NAS",
"My Cloud"). Nothing to do with the file name or the folders; only the `\\server` part.

## What actually breaks — narrower than "can't bulk cut", but it does block the normal workflow

- The **cutting engine is unaffected.** `FfmpegRunner` passes raw paths via `psi.ArgumentList.Add(a)` —
  no `Uri` anywhere — and ffmpeg/ffprobe handle UNC natively. `CanRunBatch` never touches the player.
- The **preview player fails**, and with it `CanSetCutAtPlayhead`
  (`_selectedItem is not null && Player.IsReady`, `BulkCutViewModel.cs:512`) — so **"Set intro-end here"
  and "Set outro-start here" are disabled**, which is the primary way to place cuts. Hence the report.
- **Not bulk-specific.** `FfmeMediaPlayer` is the one production `IMediaPlayer`; the Split screen loads
  through the same call and fails identically. The title says Bulk because that is where it was hit.

## Why the obvious fixes do not work

A UNC host containing a space cannot be expressed as a URI authority at all. Every construction was
probed; every one throws the same error:

```
new Uri(path, RelativeOrAbsolute)                 THROW
new Uri(path, Absolute)                           THROW
new UriBuilder("file", "my nas"){ Path = ... }    THROW
"file:" + "////" + path with / separators         THROW
"file://" + Uri.EscapeDataString(host) + ...      THROW   (%20 is not legal in a host either)
```

So there is no smarter `Uri` to build. FFME's only other entry point is
`MediaElement.Open(IMediaInputStream)`, whose `Read(void*, byte*, int)` / `Seek` require
`AllowUnsafeBlocks`, which this project does not enable. That is T-132.

## Design — the immediate, proportionate fix

1. Decide the path **before** calling `new Uri` (try-parse on a pure, WPF-free seam — do not catch blind).
2. Replace the cryptic .NET string with an actionable message naming the real constraint and the two
   workarounds that genuinely work: **type the times into the IN/OUT boxes** (cutting is unaffected), or
   **map the share to a drive letter** (`Z:\...` parses — verified above).
3. Log the offending path through `ErrorLogWriter`, so the next report is diagnosable without a
   from-scratch reproduction. The current failure writes nothing, which is why this one needed one.
4. Do NOT widen `CanSetCutAtPlayhead`. With no video loaded there is no playhead; those buttons are
   correctly disabled. The fix is to explain, not to pretend.

## Acceptance criteria
- [x] A UNC path with a space in the server name produces the actionable message, not the .NET string.
- [x] The message names both workarounds and states that cutting itself still works.
- [x] The offending path reaches the log file.
- [x] Every path shape that already worked (local, mapped drive, plain/dotted/dashed/IP UNC) still takes
      the ordinary `Open(Uri)` route — asserted, not assumed.
- [x] The decision is unit-testable without WPF (a pure function over the path).
- [x] SPEC-013 gains the invariant. (I49-I52)
