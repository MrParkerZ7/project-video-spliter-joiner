## Concept

Found while finishing T-219.

- **The bug.** On a source whose video does not start at 0, the first keyframe is a source pts above 0. Every `.ts`/`.m2ts`/`.mts` is such a source: about 1.47 s, and 1.466667 s on the test suite's synthetic TS. `SplitPlanner.Plan` drops a snapped cut only when it is `<= 0` or `>= duration` (`src/Core/Split/SplitPlan.cs:148`, SPEC-001 I7). So a cut that snaps to the first keyframe is kept as an interior boundary, although it is the file's start.
- **Who is hit.** Nearest-keyframe snapping sends every request in `[0, first + GOP/2)` there, which is the first ~2.47 s of a TS with a 2 s GOP. A user who places a cut early in a TS gets a plan whose part 1 holds no video frame.
- **Full split.** Since T-219 the segment muxer gets that boundary as `keyframe − video start = 0`. The muxer never cuts before its first packet, so it ignores the boundary and every later part shifts by one. Measured with the bundled ffmpeg n7.1.5 on the synthetic TS: `-segment_times 0,4 -segment_time_delta 0.016667` gave parts of 60/60/180 frames, against the plan's empty/120/180. That is three files whose contents do not match the plan's rows. The evidence is in the T-219 worker's scratchpad `t219/edge/`.
- **Before T-219.** Shipped code gave the same kind of mismatch: it was one GOP late anyway.
- **Subset path.** Part 1 is `[0, 1.466667)`, so `-ss 0 -to 0.023223`, a near-empty file.

## Design

- **Recommended (star):** treat a snapped cut at or before the first keyframe as the file's start. In `SplitPlanner.Plan`'s post-snap guard, drop a cut whose snapped time is `<= keyframes[0]` (when the keyframe list is not empty) with the existing "outside the file bounds — dropped" warning, or a clearer "snapped to the start of the file — dropped". On an ordinary MP4 the first keyframe is 0, so nothing changes there.
- **Rejected:** offsetting the planner's timeline by `start_time`. That is T-219's rejected option, and its out-of-scope item is the timeline offset.
- **Rejected:** special-casing the muxer. The fault is the plan's empty part, not the muxer.

## Out of scope

- Offsetting the timeline the UI shows. This also covers the last ~1.4 s of a TS, whose keyframes lie past `duration` in source pts and are dropped as out of bounds.
- The end overrun of a part that has an end (T-220).
