## Concept
A consistent progress + cancel + error experience for every long operation (split, join, detect), turning raw ffmpeg stderr into human messages so failures are understandable and recoverable.

## Design
- A shared `OperationRunner`/progress-reporting pattern the ViewModels use: `IProgress<double>` + status text + a cancel token wired to a single Cancel button.
- An `FfmpegErrorMapper` in `Core` that classifies a `FfmpegResult` stderr tail into friendly categories (not-found, unsupported-codec, disk-full, permission-denied, incompatible-join, corrupt-input, unknown+raw-tail).

## Detail
- Progress: determinate where total duration is known (split/join/detect); indeterminate spinner otherwise.
- Cancel: cooperative — cancels the token, T-002 kills the process, UI returns to idle; partial outputs cleaned (temp-then-rename in engines).
- Error dialog/banner: friendly headline + "details" expander with the raw stderr tail for power users. Never a bare exception stack.

## Interfaces / contracts
- Consumes: `FfmpegResult` (T-002) from engines (T-004/005/006).
- Produces: mapped `UserFacingError { Category, Message, RawTail }` + the shared progress pattern used by T-007/T-008.

## Acceptance criteria + Case-Coverage Matrix
- [ ] Each op shows progress and can be cancelled to a clean idle state.
- [ ] Known failure classes map to friendly messages (unit-tested against stderr fixtures).
- [ ] Cancel leaves no half-written final output.
- Matrix — Required-Success: op completes → progress 100% + success. Required-Fail: each error class → correct friendly category + raw tail available. Optional: cancel mid-op → idle + cleanup. Boundary: instant op (progress jumps to done); unknown error → generic message + full tail.

## Dependencies
T-004, T-005, T-006 (the operations it wraps).

## Risks
stderr classification brittle across ffmpeg builds. Mitigation: fixture-tested mapping + always fall back to raw tail.

## Out of scope
The operations themselves; screen layout (owned by T-007/T-008, which consume this).
